## 0. Что это за проект

Защищённый VPN-клиент для Windows (приоритет) и Android, который:

```text
Connect
→ валидирует конфиг (strict, fail-closed)
→ поднимает embedded sing-box (TUN/SOCKS)
→ запускает protected probe: DNS через туннель + 2 HTTPS + egress + no-direct-leak
→ running ТОЛЬКО после полного probe pass
→ при отказе канала — переключение только на другой validated канал
→ нет каналов — BLOCKED/ERROR, никогда direct fallback
```

Продукт НЕ обещает работу при полном shutdown/allowlist. Границы — в
docs/CENSORSHIP-THEORY.md.

## 1. Принципы (необъемлемые)

1. **Fail-closed**: защищённый трафик только через validated каналы; `direct`
   запрещён в protected selector, fallback и recovery.
2. **Evidence over claims**: статусы `planned / configured / locally-tested /
   live-verified / degraded / blocked / retired`. `running`, handshake,
   HTTP-ответ или открытый порт не равны `live-verified`.
3. **Один источник правды** — этот файл. Журнал append-only в §6.
4. **Секреты по ссылке**: значения живут в игнорируемых файлах; в git/чат/логи —
   никогда. Сверка конфигураций — по SHA256 хешам значений, не по значениям.
5. **Живая диагностика перед гипотезами**: любой «серверный блокер» сначала
   проверяется SSH-сессией с чтением реальных логов. Ни один длинный блокер
   прошлого плана не пережил эту проверку (см. THEORY §4).
6. **Контекст движка ≠ контекст операции**: движок живёт на собственном
   долгоживущем контексте (владелец — Manager); операции Start/Reload/Stop
   ограничены своими таймаутами.

### 2.3. Найденные и исправленные 2026-09-08 дефекты (все — P0)

1. **Сервер: `route.final: "block"`** — сервер принимал VLESS-сессии и резал
   весь проксируемый трафик. Исправлено на `"direct"` (backup:

   operation not permitted» → после фикса egress клиента = IP VPS.
2. **Manager: engine context отменялся после Start** — operationCtx (30s

   контекст маршрутизатора → все соединения «context canceled» при живом
   процессе. Исправлено: отдельный `engineCtx/engineCancel`, отменяется только в
   Stop. Evidence: до фикса — пустые ответы через туннель; после — egress.
3. **main.go: probe без обязательных полей** — не были заданы ExpectedEgress,
   DNSURL, DNSName, DirectLeakCheck → probe не мог пройти принципиально.
   Исправлено: полный wiring + TUN-aware direct-leak check (SOCKS-режим:
   direct egress ≠ tunnel egress; TUN-режим: равен).
4. **Probe-цели возвращали HTML для Go-клиента** — ifconfig.me без curl-UA
   отдаёт HTML без IP → «no egress evidence». Заменено на JSON-эндпоинты
   (`api.ipify.org?format=json`, `ifconfig.me/all.json`).
5. **HY2: self-signed сертификат** — клиент отклонял «unknown authority».
   Решение: пиннинг публичного PEM сервера в конфиге клиента (не insecure).

## 3. Контракты (перенесены из старого плана без изменений семантики)

### FR-001 Routing
Protected traffic → selector `proxy` (только validated protected tags).
`direct` запрещён в protected selector/fallback/recovery. Нет каналов → BLOCKED.
Private/RU exceptions — отдельный версионированный address-set (сейчас: RFC1918
+ `.local` в клиентском конфиге; расширение — только через validated set).

### FR-002 Channel descriptor
id, transport/core, server reference, port, SNI reference, profile revision,
credential reference (не значение), enabled, validation status, last evidence
tuple. Runtime selector включает только существующие tags, прошедшие validation.
Страны/серверы/endpoints не хардкодятся в Go/UI.

### FR-003 Protected probe (проверено live)
Обязательный набор evidence, иначе fail:
```text
DNS результат через туннель (DoH JSON-эндпоинт, protected resolver path)
HTTPS target 1 + target 2 (разные хосты, JSON-ответы с egress-маркером)
expected egress (конфигурируемый) == observed egress
direct-leak check (TUN-aware: SOCKS → must differ; TUN → must equal)
failure category: DNSFailure | TLSFailure | AuthFailure | ServerUnreachable |
ProtocolFailure | ProtectedChannelUnavailable | Degraded | Unknown
```
Probe report валидируется структурно (не только AllPassed): нельзя подсунуть
частичный отчёт.

### FR-004 Lifecycle (проверено live)
```text
Start:  serialize → snapshot proxy → engine.Start(engineCtx) → set proxy
        → probe (operationCtx, bounded) → running | fail: stop engine + restore proxy
Stop:   serialize → cancel engineCtx → engine.Stop → restore proxy → stopped
Reload: serialize → engine.Reload(engineCtx, newJSON) → на ошибке rollback старого JSON
```
Состояния: stopped/starting/running/stopping/error (+blocked/degraded в UI).

### FR-005 Config validation (проверено локально)
Strict JSON (trailing data, unknown fields — reject); placeholder rejection
(YOUR_*, CHANGE_ME, REPLACE_WITH, PEM в полях); reference graph (DNS detour,
DNS rules, route rules, selector candidates); `route.final` существует и не
`direct`; protected selector: только vless/hysteria, default ∈ candidates, без
`direct`; normalization idempotent (urltest→selector); secrets — только ссылки.

### FR-006 Server baseline (проверено live)
```text
TCP  : CF edge (443) → nginx (TLS, WS /ws) → 127.0.0.1:8443 sing-box vless-in
UDP  : 8444/udp → sing-box hy2-in (salamander obfs, self-signed pinned cert)
route.final = direct; log level = info
```
Серверные изменения: только с backup + `sing-box check` + systemctl restart +
post-verify (listeners + journal). Скрипт «фикса nginx WS» удалён как решающий
несуществующую проблему.

### FR-007 Channel C (HY2) — особые правила
- cert pinning обязателен (PEM сервера в клиентском конфиге), `insecure=false`;
- secrets: password/obfs — файлы в secrets/channels/; сверка с сервером — по
  SHA256, не по значению;
- UDP availability — отдельная probe-проверка перед выбором канала;
- тест на устройстве owner'а: домашний Wi-Fi (UDP доступен) → ожидается pass.

### FR-008 Metadata envelope (B2, подписанный канал доставки профилей)

```text
Envelope: schema=1, version (монотонный), issued_at/expires_at, key_id,
          signature (Ed25519 над canonical-JSON, без signature-поля).
Каналы:   embedded-формат дескрипторов (schema 1/2 render), только ссылки на
          секреты; status override: «live-verified» из envelope допустим ТОЛЬКО
          вместе с evidence_tuple (validated_at) — иначе статус понижается до
          configured (fail-closed против фейковых live-verified).
Валидация: DecodeStrict (unknown fields/trailing data — reject), схема,
          интервал времени ±5min clock skew, expiry, антидаунгрейд
          (version >= последнего принятого; хранится в version.txt рядом),
          unknown key_id → reject, secret-shaped значения ссылок — reject.
          Ревокации НЕ фатальны при валидации: их применяет render (revoked
          канал удаляется из набора; все revoked → рендер откажется).
Доверие:  публичные ключи в %AppData%\snowden-system\metadata\trusted_keys.json
          (0600, dir 0700, hex-ключи Ed25519, key_id = первые 16 hex SHA256
          ключа; key_id в файле обязан совпадать с вычисленным). Нет файла/
          ключей/каталога = override отсутствует, работают встроенные
          дескрипторы (не ошибка). Приватные ключи в AppData запрещены —
          только офлайн (metadatatool).
Хранение: %AppData%\snowden-system\metadata\channels.json — подписанный
          envelope (не в git). Файлы пишутся атомарно (temp+rename).
Semantика override: валидный envelope ЗАМЕНЯЕТ встроенный набор целиком;
          итог повторно проходит общий строгий гейт дескрипторов.
          Повреждённый/неподписанный/просроченный/даунгрейд- envelope —
          ОШИБКА LoadDescriptors, а не тихий откат к встроенным.
Инструмент: windows/tools/metadatatool keygen|sign|verify (секреты не читает
          и не печатает — envelope несёт только ссылки).
Состояние: implemented + locally-tested (V2-033); live-ввод канала B через
          подписанный envelope — после B1 procurement (B1-VPS-1).
```

## 4. Архитектура (целевая)

```text
Vue/Wails UI (позже) → typed facade
  → main.App
  → core.Manager (lifecycle owner, serialization, engine ctx)
    → core.Engine (embedded sing-box, Box on engineCtx)
    → core.ProtectedProbe (evidence-gate)
    → core.ProxyManager (system proxy snapshot/restore)
configs: configs/singbox/* (templates, no secrets)
runtime config: client.local.json (ignored) — рендер из templates+secrets
```

Направление зависимостей и запреты: UI не знает о Engine; probe не меняет
policy; controller (будущий) применяет решения только через Manager.

### 4.1. Контракт UI↔backend (Wails, v1)

UI: Vue 3 + TS (windows/frontend). Единственный источник типов —
`windows/frontend/src/api/contract.ts`; сгенерированные bindings (wailsjs)
ручными правками запрещены. Обязательные правила:

1. UI показывает ТОЛЬКО фактические lifecycle-состояния (stopped/starting/
   running/stopping/error) и статусы валидации каналов (FR-002). Запрещены:
   fake-серверы/страны/трафик, «connected»-синонимы, нули вместо unavailable.
2. Отсутствие данных = явный «нет данных/unavailable» (в т.ч. build phase до
   появления app.go). Ноль не является заменой отсутствия измерения.
3. Секреты в UI: только метаданные (SHA256-fingerprint, статус проверки,
   счётчик раскрытий). Показ/копирование значения — по явному действию;
   значения не логируются и не попадают в diagnostics (§7).
4. Пояснения пользователю — на русском, описывают факт/правило, а не гипотезу
   («probe не пройден», а не «DPI тебя заблокировал»). Хинты объясняют
   fail-closed, смысл статусов и ограничения среды (UDP, TUN admin).
5. Backend-методы фасада (минимум): GetState, Start, Stop, RunProbe,   ListChannels, SelectChannel, ListTests/RunTest, ListSecrets/SaveSecret/
   DeleteSecret/VerifySecret/RevealSecret/TestSecret, OpenLogsDir,
   EnableTUN/DisableTUN/IsTUNMode, NetGuardStatus, RunProxyHeal, OnBeforeClose
   + события EventsEmit(state/log). Единственность экземпляра — Wails
   SingleInstanceLock (второй запуск фокусирует существующее окно и выходит).
   Стабильность (V2-025): закрытие окна = контролируемый Stop (restore прокси);
   failCore останавливает живой runtime (без процессов-зомби на SOCKS:1080);
   сторож (30с) повторяет protected probe по живому туннелю — деградация
   защищённого пути = fail-closed Stop + error (без автоматического
   переключения каналов: это A4, не зачатки самодеятельности); probe-шаги
   идут параллельно (задержка ≈ самому медленному шагу); --auto-connect при
   переключении режима ставится только если VPN был запущен;   карточка активного канала — из дескрипторов, не из хардкода (FR-002). TUN-режим (WIN-TUN-1): Wintun требует администратора,
   минимальные привилегии запрещают requireAdministrator в манифесте ⇒
   переключение = Stop → перезапуск exe с/без --tun (UAC через ShellExecuteW
   runas) → Quit; флаг --tun включает render WithTUN (snowden0,
   auto_route+strict_route, gvisor, тег with_gvisor) и отключает системный
   прокси (маршрутизацию делает адаптер). TestSecret — живой тест значения по виду секрета:
   канальные секреты сверяются хешами с deployed-конфигом сервера по SSH
   (значение не передаётся), vps-ssh-key — реальный вход ключом из хранилища,
   cf-api-token — живой /user/tokens/verify, custom — честный skip. Отчёт —
   пошаговые факты; значения секретов не возвращаются и не логируются.
   Failover (A4, V2-027): сторож (см. п.6 выше) при деградации защищённого
   пути не только останавливает туннель — решение принимает failoverPolicy
   (windows/failover.go): 2 подряд провала → попытка переключения на другой
   validated канал строго через switchChannelCore (= путь SelectChannel:
   render → двойная валидация → Manager.Reload → обязательный probe); лимит —
   2 автоматические попытки за инцидент, между попытками обратный
   экспоненциальный cooldown 30/60с; успех (probe нового канала пройден) =
   счётчики в ноль; кандидаты исчерпаны или их нет → fail-closed Stop +
   BLOCKED (blockedReason = all_channels_failed), никогда direct (FR-001).
   Один краткий провал не переключает канал; успешный тик сторожа сбрасывает
   серию (CGNAT-мерцание без переключения). Кандидаты — только enabled
   live-verified из дескрипторов (HY2-configured не автопереключается —
   FR-007). Контракт: LifecycleState расширен значением `reloading`
   (переключение канала идёт); BlockedReason — значением
   `   all_channels_failed`. Расширение контракта — сначала правка contract.ts + этого раздела, затем
   app.go, затем UI.

6. Правило конкурентного слоя (V2-028, обязательное): `sync.Mutex` в Go
   нерекурсивен — вызов метода, берущего тот же мьютекс, из-под уже
   удержанного = само-дедлок навсегда. В App: `appendLog`/`pushState` берут
   a.mu; коду, который уже держит a.mu, запрещено их вызывать — только
   `appendLogLocked`/`pushStateLocked`. Обязательный критерий приёмки:
   TestAppBindingMethodsDoNotSelfDeadlock (детектор-таймаут) зелёный при
   любом добавлении/изменении UI-биндингов. Аналогично: любой ресурс с
   файлом или общим состоянием (сейчас secretvault.Manager) обязан быть
   внутренне потокобезопасным, а не полагаться на внешний мьютекс вызывающего.
   stopCore обязан дожидаться in-flight Start (startBusy), сторож запускается
   только через ensureWatchdog (один на процесс), а все обращения к
   runtime_.cc — только под runtime_.mu.
