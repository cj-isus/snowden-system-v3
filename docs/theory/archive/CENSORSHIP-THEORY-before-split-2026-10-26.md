## 0. Инженерная поправка 2026-10-19

Нормативные требования перенесены в PLAN FR-009…012. Ниже сохраняется
исследовательская история; прежние формулировки «неотличим», «гарантирует»,
«не блокируется» нельзя читать как универсальное доказательство. В этой
сессии измерений текущих блокировок на сетях владельца не проводилось.

- [исследование] Шифрование/случайный payload не обеспечивают нераспознаваемость:
  USENIX Security 2023 описывает пассивные эвристики для fully encrypted traffic.
  Это измерения конкретной системы и периода, а не доказательство одинакового
  поведения нынешних российских сетей. [Исследование и открытые данные](https://gfw.report/publications/usenixsecurity23/en/).
- [документировано] OONI отделяет аномалию от подтверждённой блокировки:
  нестабильная сеть и отказ сайта могут давать ложные срабатывания. Поэтому
  единичный timeout/reset у нас означает наблюдение, не установленный диагноз.
  [Методика интерпретации OONI](https://ooni.org/support/interpreting-ooni-data/).
- [инженерный вывод] WS/CDN, REALITY, ShadowTLS и HY2 — кандидаты для разных
  условий. TLS/QUIC, порт и fingerprint не дают универсального выигрыша.
  Один origin/ASN/egress или общий DNS остаётся общей точкой отказа.
- [граница измерения] Малый HTTPS echo подтверждает только проверенный запрос;
  freeze, долгие потоки, IPv6/UDP/OS DNS требуют других проверок. Различие
  direct/protected IP не является полным доказательством OS fail-closed.
- [решение проекта] Strict WFP не должен сам открывать direct после crash,
  истечения таймера, автоматической ошибки или повторного запуска GUI.
  Снять барьер может явный Disconnect после остановки engine. Persistent
  filters и транзакции — разные свойства: при переустановке политики нельзя
  удалять старые блоки до готовности новых. [WFP transaction API](https://learn.microsoft.com/en-us/windows/win32/api/fwpmu/nf-fwpmu-fwpmtransactionbegin0).

До оплаты VPS можно доказать локальные lifecycle/data contracts и проверить
синтетические сбои. Реальную скорость и устойчивость к текущей фильтрации
без живого пути измерить нельзя. Критерии сравнения — PLAN FR-012.

**Поправка V2-109, 2026-10-21.** Авторские разделы и история сохранены, но
исправлены причинные и абсолютные выводы: AND-классификатор ТСПУ не установлен;
CDN entry ≠ egress; chunked/Range ≠ новые TCP-соединения; 400 ≠ доказательство
VPN; QUIC CID ≠ обход IP-блока; allowlist ≠ физический shutdown. Сопоставление
с кодом — §7.4, новые основания — §11. Внешние исследования просмотрены;
сеть владельца, серверы и транспортная работоспособность сейчас не измерялись.

## 1. Модель цензуры: слои атаки

Это наша классификация воздействия, **не уровни OSI**. Механизмы могут
сочетаться; одна контрмера иногда затрагивает несколько классов:

```text
L0  закон/платформа     — удаление контента, давление на магазины/CDN/платежи
L1  DNS                 — подмена, NXDOMAIN, block page, фильтр DoH/DoT
L2  IP/маршрутизация    — чёрные списки IP, подсети, ASN, датацентров
L3  HTTP/TLS/SNI        — фильтр Host/SNI, forged RST, ECH-блокировки
L4  DPI/поведение       — fingerprint протоколов, тайминги, размеры пакетов
L5  throttling          — намеренное замедление вместо ошибки
L6  allowlist/интранет  — разрешён только национальный набор сервисов
L7  физический shutdown — BGP withdrawal, глушилки, отключение энергий
```

Ключевые следствия:

- смена DNS не помогает при блокировке на L2/L3/L4;
- обычный VPN (известный IP, известный протокол) уязвим на L2/L4;
- ECH скрывает SNI, но не IP назначения и не факт подключения к провайдеру [документировано, RFC 9849];
- при L6 важны реальные разрешённые пути и возможность использовать их как
  транспорт; при L7 без какого-либо внешнего пути передавать новые данные нельзя (§2.7);
- «подключено» ≠ «защищённый трафик реально прошёл через туннель» [доказано нами — см. случай route.final=block];

## 2. Слой за слоем: механизмы и контрмеры

### 2.1. DNS (L1)

Механизмы: подмена A-записи, NXDOMAIN, redirect на block page, фильтрация DoH/DoT-endpoint'ов.

Варианты (универсального порядка надёжности нет):
1. DoH/DoT к независимому резолверу — скрывает запрос, но endpoint виден и может быть заблокирован.
2. DNS внутри туннеля (dns.detour: proxy) — доминирующая практика; запрос уходит резолверу через защищённый канал.
3. Встроенный резолвер клиента, bootstrap по IP.

Подводные камни:
- direct DoH к IP-литералу шифрует DNS-содержимое до резолвера, но выдаёт
  его адрес и зависит от внешнего пути. Это не plaintext DNS-утечка само по себе;
  для пользовательских имён может нарушать protected-route policy. Bootstrap
  имени самого туннеля — отдельное минимальное исключение, без общего direct fallback;
- правило `{"outbound": "any"}` в dns.rules перенаправляет ВСЕ DNS-запросы (включая резолвинг адреса самого VPN-сервера) на указанный сервер; если этот сервер доступен только через туннель — рекурсивная зависимость и вечный цикл/таймаут [доказано нами];

### 2.2. IP/ASN/CDN (L2)

Механизмы: блок IP, подсети, ASN, хостеров; collateral damage от блокировки CDN.

Контрмеры-кандидаты: другой origin/ASN, доступный CDN reverse proxy. Доли
«большинство сетей» у проекта не измерены; достижимость edge не доказывает
прохождение больших потоков. [Cloudflare описал ограничения в РФ в июне 2025](https://blog.cloudflare.com/russian-internet-users-are-unable-to-access-the-open-internet).

Важно: у прямого HY2 клиент соединяется с IP VPS. При CDN-входе наблюдатель
на участке клиент→edge видит edge-IP; origin может раскрываться через другие
каналы, DNS-историю или ошибки конфигурации. Обычный reverse proxy своего
домена и domain fronting с различными SNI/Host — разные конструкции.

### 2.3. HTTP/TLS/SNI (L3)

Механизмы: фильтр по SNI в ClientHello, по Host в HTTP; forged RST; timeout после ClientHello; поддельные сертификаты (MITM).

Контрмеры:
- TLS 1.3 + ECH (RFC 9849) — скрывает SNI; поддержка CDN/сервера обязательна;
- домен-фронтинг: Google/AWS отключили в апреле 2018, Azure (meek-azure)
  продолжал работать; в 2021–2022 Azure анонсировал запрет, но 2023-09-25
  уточнил исключение Azure Front Door: несовпадение разрешается для доменов
  **одной Azure subscription**, а не произвольного чужого front domain.
  Это не готовый публичный meek-резерв. [Microsoft, политика 2023–2024](https://learn.microsoft.com/en-gb/answers/questions/1461527/take-action-to-stop-domain-fronting-on-your-applic);
- WebSocket-туннель через легитимный домен за CDN — traffic выглядит как обычный HTTPS+WSS к сайту [используется нами];
- REALITY — аутентифицированный транспорт с TLS-маскировкой и обработкой
  неавторизованного трафика через handshake target. Это не «кража сертификата»
  и не гарантия нераспознаваемости; реализация, донор и конфигурация обоих концов
  существенны. [Upstream REALITY](https://github.com/XTLS/REALITY).

Анти-паттерн: отключение проверки сертификата. Наше правило: `insecure` запрещён; для self-signed HY2 — пиннинг сертификата в конфиг клиента [реализовано].

### 2.4. DPI/протокольный fingerprint (L4)

Механизмы: классификация по handshake/таймингам/размерам; active probing (цензор сам подключается к подозрительному серверу).

Контрмеры:
- uTLS (имитация ClientHello браузера) — усложняет пассивный fingerprint; upstream сам помечает как не-undetectable [документировано];
- обфускация транспортного слоя: salamander (HY2), obfs4, WebTunnel;
- WebSocket через CDN скрывает содержимое от внешнего пассивного наблюдателя
  при корректном TLS, но оставляет размеры/время/длительность. CDN завершает
  TLS и видит HTTP/WS; знание WS-пути само по себе не даёт VLESS-credentials;
- анти-active-probing: сервер должен отвечать на неавторизованные подключения как обычный веб-сервер (404/редирект), а не как VPN [направление развития];
- TLS-in-TLS-фингерпринт вложенных рукопожатий — протокол-агностичный детект
  прокси-трафика (USENIX Security 2024, Xue/Kallitsis/Houmansadr/Ensafi):
  padding и mux не устраняют все признаки; split-streams — отдельная
  проверяемая гипотеза, не доказанная этой работой защита (§2.11);

Важно про WS early-data: в нашем рендере выбран `Sec-WebSocket-Protocol`,
данные кодируются base64url, это не литерал «VLESS». Заголовок виден TLS-endpoint,
но не читается пассивно сквозь TLS. Это режим конфигурации, а не обязательное
поведение всякого sing-box WS-клиента (render.go / pinned transport/v2raywebsocket).

#### 2.4a. Поведенческая заморозка: гипотеза AND-сигналов и полевые данные

Обсуждения 2026 года (Habr 1047442/990236) предлагают модель совокупности
сигналов. Это реконструкция чёрного ящика, **не установленное правило AND и
не доказательство замены сигнатур поведенческим анализом во всех ТСПУ**.
Сигналы-кандидаты для контролируемого эксперимента:

1. **AS/подсеть назначения**: зарубежные DC (Hetzner/DO/OVH) и ряд RU-облаков
   проходят «поведенческую проверку» чаще; крупные CDN (Cloudflare/Akamai/Google)
   могут иметь другую политику. Высокая цена collateral damage не запрещает
   цензору деградировать CDN целиком. В нашей хронике CDN-ветка A деградировала
   волнами (V2-026/039/040), а HY2/QUIC — в другие окна.
2. **TLS-fingerprint клиента (JA3/JA4)**: один из возможных признаков.
   uTLS не необходим для всех транспортов и не достаточен для маскировки.
   Сообщения о продлении «штраф-окна» после смены fingerprint — гипотеза;
   нельзя запрещать альтернативы без A/B или менять их бесконечно автоматически.
3. **Тайминги/объём**: известны наблюдения «заморозка после первых ~15–20 КБ»
   (net4people #490) и «долгоживущее TCP-соединение = подозрительное» — ровно
   наш класс V2-026 (freeze после 16 КБ) и подтверждённая живучесть
   коротких запросов.

Практические следствия для нас:
- **Порт имеет значение**: в февральской волне VLESS+REALITY на 443 рубился,
  тот же конфиг на высоком порту (47000+) продолжал работать в заметной доле
  случаев [историческое полевое сообщение, не текущая доля]. Порт 8443 также
  может блокироваться; новый порт требует согласованного descriptor/client/server.
  Один серверный redirect не меняет адрес назначения пакетов клиента у цензора.
- **Multiplex на REALITY — opt-in**, согласованный с сервером. Общая длинная
  TCP-сессия может ухудшать объёмный лимит, но уменьшать число новых TLS-сессий.
  Направление эффекта определяет эксперимент (§2.10 п.8), не имя транспорта.
- **Разнородность как кандидат резерва**: TCP+REALITY, QUIC+obfs, WS+CDN
  имеют разные wire profiles; общая инфраструктура всё ещё может отказать
  одновременно. Выигрыш устойчивости проверяется, не следует из трёх названий.
- **Мобильные сети**: в отдельных сообщениях LTE-операторы работали, когда
  проводные деградировали [полевое наблюдение] — при диагностике фиксировать
  оператора/тип сети (у нас это есть: NetworkFacts.connectionType/ISP).
- **Выборочный SYN-блэкхол не-443 портов (своя дата-точка, 2026-09-14,
  V2-051)**: в сети владельца описан эпизод недостижимости трёх проверенных
  портов VPS (8443/8445/закрытый 12345). Локальное "CONNECTED" не подтверждало
  серверный handshake; на сервере 0 пакетов в capture (методология
  подтверждена тем же фильтром на живом 443-хендшейке); 443 и SSH при этом
  живы, nft-счётчик правила 8445 = 0 с момента создания. Важно: канал
  «порт выше 443 живёт» НЕ абсолютен — фильтр может включаться на дни
  (8443/REALITY был достижим 2026-09-12 из той же сети и чёрный 2026-09-14)
  и затронул проверенный закрытый 12345. Это не скан всего диапазона и не
  доказательство источника drop или поддельного SYN-ACK. Текущий rank портов
  нельзя вывести из одной сентябрьской точки; 443/UDP/high-port — кандидаты,
  каждый требует свежей проверки, без универсального «третьего эшелона».

### 2.5. QUIC/UDP (L1.5)

Механизмы: запрет UDP целиком/по порту, разбор QUIC Initial с извлечением SNI
при отсутствии ECH. Initial secrets выводятся из публичных параметров — это
не расшифровка последующих application data. [RFC 9001 §5.2](https://www.rfc-editor.org/rfc/rfc9001.html#section-5.2).
[Zohaib et al., USENIX 2025](https://gfw.report/publications/usenixsecurity25/en/)
измерили такой механизм в Китае; перенос на нынешнюю РФ требует измерения.

При реальном запрете UDP QUIC не подключится. Но одиночный QUIC timeout не
доказывает такой запрет: в нашей истории диагноз 2026-09-08 был пересмотрен
после live-прохождения HY2 2026-09-09 (PLAN §2.1). TCP и UDP — взаимные
кандидаты резерва; их текущий приоритет зависит от проверенного пути.

### 2.6. Throttling (L5)

Труднее доказать и труднее обойти. Признаки: работает, но медленно; различия между протоколами на одном маршруте. Контрмера: другой транспорт/маршрут; измерение через baseline (OONI-подход), не «на глаз».

### 2.7. Allowlist и shutdown (L6/L7)

Нужно различать три случая [инженерный вывод]:

1. **Исключения из throttling по SNI/Host**: часть имён получает другой режим;
   это ещё не строгий IP allowlist. Ошибка классификации middlebox может
   оставлять путь; проверять в стенде, не обещать программную невозможность.
2. **Строгий allowlist**: наш внешний endpoint недостижим. Путь возможен лишь
   если среди разрешённых сервисов есть реально доступный и пригодный relay
   с контролируемой нами/согласованной серверной стороной. Нельзя произвольно
   превратить чужой разрешённый сайт в VPN простым SNI/Host.
3. **Нет внешнего канала вообще**: программой отсутствующую связь не создать;
   требуется другой оператор/роуминг/физическая среда с рабочей связностью.

Нет проверенного разрешённого пути → BLOCKED при сохранённой защите.
Надпись «подозрение на allowlist» не заменяет диагноз всей сети.

### 2.8. ТСПУ: что известно о самой машине

ТСПУ — распределённая инфраструктура сетевого вмешательства. Ниже разделены
академические измерения, исторические заявления и неподтверждённые сведения;
состав устройств и охват каждого нынешнего оператора этим документом не установлены.

**Правовая хроника [сохранённые ссылки редакции 2026-09-16]:**
Следующие правовые номера, санкции и утверждения об обязанностях не прошли
повторную сверку с действующей редакцией официальных актов в V2-109. Это
исследовательские заметки, не основание юридических/UI-решений; вторичные
публикации не становятся первичными из-за метки «документировано».
- Федеральный закон 90-ФЗ от 01.05.2019 («суверенный Рунет») ввёл в 126-ФЗ «О связи»
  ст. 65.1–65.2, а в 149-ФЗ «Об информации» — ст. 15.9. Практическое заблуждение:
  «ТСПУ прописаны в 149-ФЗ» — на самом деле обязанность оператора пропускать трафик
  через ТСПУ — это п. 5.2 ст. 46 закона «О связи» (126-ФЗ), а ст. 15.9 149-ФЗ — про
  централизованное управление сетями через НЦУС/ЦМУ ССОП. Указывать нужно оба закона.
- Оператор обязан разместить ТСПУ у себя, обеспечить электропитание и доступ ГРЧЦ
  (оператор системы), но НЕ имеет доступа к софту/правилам «чёрного ящика»
  [документировано: Роскомсвобода, Ъ]. Оператор юридически отвечает за непропуск
  трафика через ТСПУ (штрафы 500 тыс — 5 млн руб с 2023 г. [документировано, КоАП]).
- С 1 января 2023 — ужесточение ответственности операторов; с 30 ноября 2024
  операторы обязаны согласовывать с РКН запуск/вывод из эксплуатации сетей
  и не препятствовать ТСПУ [документировано].
- Август 2024: поправки о сборе операторами данных об оборудовании
  абонентов (IP, MAC, регион, номер ТСПУ); декабрь 2024 — проект приказа РКН о
  формате передачи. Цель — корреляция «пользователь ↔ ТСПУ ↔ класс трафика»
  [документировано, Meduza 2024-12-21].
- Октябрь 2024: проект приказа РКН — порядок применения ТСПУ по решениям
  генпрокуратуры и её заместителей без суда [документировано: anti-malware.ru,
  secuteck; порядок действий цензора остаётся засекреченным].

**Deployment [исторические заявления ведомств/публикаций, не наш аудит]:**
- К августу 2023 РКН отчитался: 100% узлов связи оборудованы ТСПУ (мобильные,
  ШПД, трансграничные) [Интерфакс 2023-10-24].
- Заявление об импортозамещении (РГ 2024-06-03) не доказывает состав всего парка.
  ГРЧЦ как участник эксплуатации/управления нельзя автоматически называть
  производителем всех аппаратных и программных компонентов.
- ТСПУ ставятся на границе сети оператора: inline либо mirror/SPAN [исследование,
  Habr 992232]. Inline-инстанс может дропать, помечать и инжектить пакеты; mirror —
  наблюдает; отдельный инжектор на том же комплексе всё ещё способен отправлять
  пакеты. Схему конкретного оператора из этих вариантов не выводим.

**Архитектура из академического исследования [исследование: Xue, Mixon-Baca,
ValdikSS, Ablove, Kujath, Crandall, Ensafi — "TSPU: Russia's Decentralized
Censorship System", IMC 2022, dl.acm.org/doi/10.1145/3517745.3561461]:**
- ТСПУ — это ДЕЦЕНТРАЛИЗОВАННАЯ система: тысячи инстансов близко к абоненту,
  с централизованным управлением правилами (не «один большой фаервол» в центре).
- Инстансы in-path (в разрыв) и stateful (помнят соединение) с уникальным для
  каждого инстанса состоянием — отсюда «разные сети режут по-разному».
- Авторы выделяют SNI/IP/QUIC-триггеры и шесть поведений, включая drop и
  модификацию пакетов. Ранее здесь ошибочно смешивались триггеры, fingerprint
  и способы вмешательства; точная таксономия — §5.2 статьи, не наша новая шестёрка.
- Активное пробирование в РФ — отдельная гипотеза из dev.to/shinomontaz 2026-02;
  IMC'22 не доказывает её и не атрибутирует случайные сканы цензору.
- В выборке исследования 70% обнаруженных endpoints были не далее двух хопов
  от middlebox. Это не «все ТСПУ всегда в 1–2 хопах» и не замер задержки вмешательства.

**Что это означает практически [вывод]:**
- Один и тот же сервер может быть жив в МТС и мёртв в Мегафоне одновременно.
  Диагностика обязана фиксировать оператора/регион (NetworkFacts), иначе
  «работает/не работает» не интерпретируемо.
- Блокировка может проявиться только на части соединений (stateful
  per-соединение) — важна серия повторов, не один probe.
- Централизованное управление совместимо с несинхронным применением и
  локальным состоянием; нельзя предполагать единую текущую политику всех сетей.

### 2.9. Как операторы мешают VPN: каталог методов с фактчекингом

Уровни воздействия ТСПУ на VPN-трафик — от грубого к тонкому. Для каждого —
источник и уровень достоверности.

**A. Блокировка по IP/подсети [документировано]:** чёрные списки IP известных
VPN-провайдеров. Смена IP может помочь, пока не повторена блокировка и не
затронута новая подсеть; реестр не обязан исчерпывать фактические фильтры.

**B. Протокольная блокировка [документировано — хронология волн, Amnezia
(habr.com/ru/companies/amnezia/articles/861198)]:**
- 2021-09 — первые блокировки VPN-сервисов (VyprVPN, Opera VPN).
- 2023 — протокольные волны: OpenVPN, IKEv2/IPsec; 2023-08 — массовая волна
  OpenVPN+WireGuard; 2023-09 — WireGuard у ~20% пользователей не восстановился.
- 2024-08 (волна вокруг 1 августа) — широкая блокировка WireGuard во многих
  регионах; прошла почти незаметно на фоне замедления YouTube.
- 2024-10-15 — блокировка Shadowsocks на мобильном интернете.
- 2025-12-04 (РБК) — донастройка ТСПУ: целевая блокировка SOCKS5, VLESS, L2TP.
  РКН подтвердил только «развитие систем безопасности» [РБК]. Эксперты: VLESS
  стали выявлять по косвенным признакам, т.к. раньше он оставлял «минимум
  технических следов» [The Moscow Times, 2026-02-17].
- 2026 — продолжение: выборочные деградации по регионам и операторам.

**C. Функциональное подавление [наблюдаемый класс]:** соединение может
установиться, а передача данных — остановиться. Cloudflare описывает resets
и timeouts своих путей в июне 2025; этот источник не доказывает DNS-подмену
во всяком таком случае. Поэтому «подключено» ≠ «работает».

**D. Объёмная остановка [измерения поставщика + полевое сообщение]:**
- [Cloudflare, 2025-06-26](https://blog.cloudflare.com/russian-internet-users-are-unable-to-access-the-open-internet)
  описал ограничения с 9 июня на пути из РФ к своим сервисам: около первых
  16 КБ, разные TCP/TLS и QUIC варианты, resets и timeouts. Это данные о его
  сети в тот период, не универсальный порог российского интернета.
- [net4people #490, 2025-06-27](https://github.com/net4people/bbs/issues/490)
  описывает остановку после примерно 15–20 КБ server→client **на TCP-соединение**
  для некоторых зарубежных сетей. Новые соединения помогали в сообщённых
  опытах; HTTP-запросы внутри прежнего соединения — нет. Пакетные лимиты,
  исключения SSH/RDP и отдельные ASN — варианты сообщений, не один доказанный
  общий алгоритм. Нельзя объединять их с Cloudflare в закон «25 пакетов = 16КБ».

**E. TLS connection-based policing (TCP+TLS на 443) [полевое наблюдение]:**
net4people/bbs#546 (2025-11-14+): MTS/MGTS, JustLan, LanInterCom, Ростелеком
(Ижевск). Симптоматика: соединение рвётся как только идёт реальный трафик через
туннель (VLESS+Reality+vision); чем больше трафика, тем быстрее разрыв;
curl/браузер на тот же endpoint работает; через ~60 секунд можно переподключиться.
Гипотеза автора — влияние числа активных TLS-соединений; причина не установлена.
Mitigation по данным #546: убрать flow (vision), включить mux; смена порта с 443.
Позже (22.11) mux/XHTTP перестали помогать у части пользователей.

**F. Белые списки (L6 в нашей модели) [документировано]:**
- Эксперименты с «белым списком» мобильного интернета (2025, несколько регионов).
- 2026-03: Москва, 10 дней теста — доступ только к списку Минцифры; часть
  районов осталась без связи [Новая газета 2026-03-14].
- Эти публикации описывают разные режимы ограничений; техническая граница
  определяется доступными relay и реальным enforcement, см. §2.7.

**G. Полное отключение интернета (L7) [документировано]:**
- 2025-07 — 2099 шатдаунов мобильного интернета за месяц (проект «На связи»);
  с мая 2025 хотя бы раз отключали в каждом из 83 регионов [Novaya Europe 2026-03-26].
  Причина — БПЛА; механика — по регионам и по операторам, на часы.
- 2025-08: сообщения об ограничениях звонков WhatsApp/Telegram [Хабр/РБК].
  SIP-сигнатуры этих приложений первичным измерением здесь не подтверждены;
  общий факт ограничения звонков не раскрывает их протокол или механизм фильтра.
- В шатдауне программного обхода нет — только альтернативный физический путь.

**H. Активное пробирование [класс атак; атрибуция РФ не доказана здесь]:**
проверяются ответы, тайминги, replay и некорректные входы сервера. В GFW
такой класс измерен [Wu et al.](https://gfw.report/publications/usenixsecurity23/en/).
REALITY и web fallback — меры против части проб; ответ 404/400 сам по себе
не удостоверяет ни маскировку, ни VPN. Проверять отличимость от контрольного сайта.

**I. Сигнатурное вмешательство (IMC'22):** SNI/IP/QUIC-триггеры;
не подменять их универсальной гипотезой фильтра по QUIC CID (§2.8).
Механика помех смешанная: инстансы ТСПУ stateful, решения по соединениям
асинхронны.

**J. Сбор и корреляция данных [документировано]:** РКН собирает с операторов
IP/MAC/регион абонента + номер ТСПУ, через который идёт трафик (август–декабрь
2024). Плюс отчёт ГРЧЦ за 2023: «более 100 сигнатур для ограничения доступа...
в т.ч. VPN-сервисам, с эффективностью >95%» [документировано, отчёт ГРЧЦ].
Плюс ML-классификация зашифрованного трафика (VAS Experts, ResNet, 2023).

**Что из этого НЕ работает (фактчекинг анти-знания):**
- Правовые тезисы предыдущей редакции смешивали использование инструмента,
  рекламу и поиск материалов, административную и уголовную ответственность.
  Старые суммы/номера отозваны как непроверенная правовая справка. Техническая
  модель не устанавливает законность конкретного действия; юридические тексты
  продукта требуют отдельной актуализации по официальным актам.
- «Смена порта решает» — НЕ абсолют: эпизоды V2-051 (2026-09-14) показывают,
  что фильтр может закрывать и не-443 порты; выборочно и временно.
- «ECH гарантирует доступность» — неверно: ECH под Cloudflare (public_name
  cloudflare-ech.com) заблокирован с 2024-11-05 по сигнатуре «SNI cloudflare-ech.com
  + ECH extension» [net4people/bbs#417, ЦМУ ССОП официально рекомендовал
  отказаться от Cloudflare 2024-11-07]. Cloudflare при этом временно отключил ECH
  (community.cloudflare.com). ECH с другим public_name (defo.ie, tls-ech.dev)
  работал в описанном опыте. Это историческая сигнатура, не текущий тест всех
  CDN. ECH решает задачу приватности части ClientHello, не гарантирует путь.
- «Фрагментация всегда спасает» и «фрагментация всегда бесполезна» — оба
  утверждения чрезмерны. TLS records, TCP segmentation, IP fragmentation и
  рассинхронизация парсеров — разные методы. Их эффект зависит от middlebox;
  обычная нарезка payload не обходит счётчик суммарных байтов соединения.

**Контрмеры, которые подтверждаются данными [направление для нас]:**
1. Многоканальность с РАЗНЫМИ классами отказа (TCP+CDN / UDP+QUIC / high-port) —
   предохранитель от точечных донастроек ТСПУ (2025-12 показала: за один день
   легли SOCKS5+VLESS+L2TP у части операторов).
2. Проверять срок жизни/объём carrier-соединения как параметр (§2.4a),
   учитывая стоимость handshake и невозможность просто переоткрыть произвольный
   пользовательский TCP-поток с середины без поддерживающего это транспорта.
3. Различать **entry ASN**, видимый провайдеру клиента, и **egress ASN**, видимый
   целевому сайту. CDN reverse proxy меняет первый, дополнительный exit — второй.
4. Fail-closed + честная диагностика: различать "заморозку" (таймаут без RST),
   "RST", "DNS-саботаж" и "белый список" — разные реакции клиента (таймаут-логика
   vs мгновенный fail vs отсутствие пути). Словарь причин — в диагностике.
5. Регион/оператор как первоклассный факт телеметрии — ТСПУ распределённые,
   поведение зависит от них; без этого тега любая статистика блокировок шум.

### 2.10. Контрмеры: как противостоять каждой механике ТСПУ

Свод кандидатов по документации и полевым данным: для каждой механики из §2.9 —
возможные меры, не гарантии. Сверено с нашими правилами (PLAN V2-031 —
ядро не меняем; V2-037 — mux не глобальный дефолт; §2.3 этого файла —
insecure запрещён; серверные правки — только по явному разрешению владельца).

**Матрица «механика → контрмера»:**

| Механика (§2.9) | Контрмера | Статус/источник |
|---|---|---|
| A. IP/подсеть блок | CDN-фронт (edge IP не наш); смена ASN | [документировано] практика |
| B. Протокольная блокировка | иной wire profile: HTTPS/REALITY/QUIC-obfs; число профилей не равно независимости | дизайн upstream, проверка §10 |
| C. «Портит, не рвёт» | fail-closed + классификация отказа (см. ниже) | [доказано нами] |
| D. Объёмная остановка | проверять новые carrier-соединения/иной путь; HTTP chunks не сбрасывают TCP-счётчик, QUIC также может ограничиваться | исторические §2.9-D, эксперимент E-02 |
| E. TLS-policing на 443 (#546) | mux/XHTTP (меньше одновременных TLS), перенос порта, другой класс транспорта | [полевое] #546 |
| F. Белые списки | определить enforcement/доступный relay; нет validated пути → BLOCKED | §2.7; Cheburcheck описывает иной режим исключений |
| G. Шатдаун | fail-closed, честный BLOCKED, авто-reprobe по факту возвращения сети (V2-053/054 уже сделано) | [доказано нами] |
| H. Активное пробирование | аутентификация до отличимого поведения, web fallback, replay/error/timing matrix | дизайн, эксперимент E-04 |
| I. SNI/IP/QUIC-сигнатуры | согласованный TLS/obfs-профиль; CID migration не меняет заблокированный destination IP | §2.3/2.5, pinned compatibility |
| J. Сбор/корреляция | минимизация метаданных и доверительных сторон; VPN не предоставляет анонимность сам по себе | threat model §7 |

**Транспортный уровень — конкретика по документации sing-box (pinned ядро):**

1. **TLS-пиннинг лучше, чем мы думали**: sing-box 1.13+ умеет
   `tls.certificate_public_key_sha256` — пиннинг ПО ПУБЛИЧНОМУ КЛЮЧУ
   (список base64 SHA-256). Продление сертификата с тем же SPKI может сохранить
   пин; **ротация ключа меняет пин**. Нужны signed current/next, overlap,
   revocation, rollback policy и привязка к ChannelID; `insecure` запрещён.
   [документировано: sing-box.sagernet.org/configuration/shared/tls]
2. **REALITY**: сервер должен иметь `handshake.server` на реальный TLS 1.3 + h2
   донора и заполненный `server_name` (наш дефект 2026-09-12, §3.11: пустой список
   принятых SNI отвергал всех клиентов). «Steal oneself» (донор = свой сайт на той же
   машине) — вариант сократить зависимость от чужого донора, но не доказательство
   неотличимости. Нужна проверка клиента и неавторизованных входов.
   [документировано: XTLS/Xray-core docs; sing-box reality fields]
3. **uTLS — ограниченная имитация**: текущая upstream-документация помечает uTLS
   «Not Recommended» — uTLS копирует структуру ClientHello, но браузеры
   (BoringSSL/NSS) поведенчески другие, детект возможен; рекомендуемая альтернатива
   — NaiveProxy/браузерный dialer [документировано: sing-box TLS docs]. Для нас:
   существующий pinned путь сохраняется, NaiveProxy рассматривается отдельно.
   Рекомендация upstream не заменяет сравнительный замер (§9.3).
4. **TLS-фрагментация (`fragment`/`record_fragment`, 1.12+)**: upstream
   предупреждает об ограниченности простой нарезки и цене задержки. Это не
   эксперимент, исключающий все методы рассинхронизации на всех ТСПУ. Низкий
   приоритет до доказанного дефекта parser enforcement, не глобальный default.
5. **TLS `spoof` (sing-box 1.14)**: инжект фейкового ClientHello с белым SNI
   перед настоящим (wrong-sequence/checksum/ack/md5/timestamp — сервер отбрасывает,
   middlebox видит легитимный SNI). Требует CAP_NET_RAW/Windows-администратора
   (WinDivert). Кандидат на «режим проверки белых списков», но режим ТСПУ
   «всё, кроме списка» не обходит [документировано: sing-box TLS docs, 1.14].
6. **HY2/QUIC**: пример **нативного Hysteria2**, не JSON нашего sing-box:
   port hopping через диапазон — сервер: `listen: :20000-50000`
   (сам настраивает nftables-redirect); клиент sing-box (since 1.12.0):
   `server_ports: ["2080:3000"]` + `hop_interval` [документировано:
   sing-box hysteria2 outbound docs, v2.hysteria.network Full Server Config].
   Контрмера к точечному портовому дропу; `obfs.salamander` — когда режут
   QUIC-сигнатуры (превращает пакеты в случайные байты, НО несовместим с
   «валидным HTTP/3» — включать осознанно, per-канал); `sniGuard: strict` —
   сервер принимает только свой SNI. Поддержку аналогичной политики в конкретной
   server implementation проверять отдельно, названия YAML/JSON не взаимозаменяемы.
7. **TCP Brutal**: конгест-контроль «шлём с заданной скоростью, игнорируя потери»
   — v2 не требует поддержки протоколом (правило `brutalctl add <dst> <rate>`);
   критично НЕ делать его дефолтным конгест-контролем (без правила = 1 Mbps);
   проверяется отдельно при loss, с лимитом скорости и измерением задержки
   соседнего трафика; не создаёт пропускную способность [документировано:
   github.com/apernet/tcp-brutal README].
8. **Multiplex — per-канальная политика, НЕ дефолт** (наш принцип §3.12):
   - при лимите байтов на carrier mux может ухудшить ситуацию;
   - при ограничении количества TLS-сессий может помочь. Сообщения #546
     неоднородны. Гипотеза механизма определяет эксперимент, не автоприменение
     mux по одному timeout. Параметры должны поддерживаться обоими концами.
9. **XHTTP-идея (референс, у нас в ядре — splithttp-кандидат, V2-047)**: split
   up/down в разные соединения (можно разного транспорта/адреса/даже провайдера),
   TLS 1.2 + настоящий nginx на 443 перед ядром — серверный fingerprint
   подлинный, и Vision не нужен [документировано: Habr 990208, xray-examples].
   **В pinned sing-box 1.13.19 нет ни splithttp, ни xhttp**: проверен switch
   option/v2ray_transport.go. Предыдущая строка об upstream splithttp была
   ошибочна. [Xray design discussion #4113](https://github.com/XTLS/Xray-core/discussions/4113)
   — источник идеи, не готовая совместимость с нашим движком.

**Поведенческий уровень:**

10. **Idle, keep-alive и ротация — разные свойства**: TCP keep-alive проверяет
    простой и может поддерживать NAT-state, но не ограничивает срок жизни или
    накопленные байты. Значения 60/20с — наш исторический профиль, не универсальный
    оптимум. TFO — эксперимент с middlebox/fingerprint/replay-ограничениями,
    а не обязательное ускорение. Не обрывать действующие потоки ради ротации.
11. **Серверная разбивка контента**: chunked transfer и HTTP Range полезны
    для собственной HTTP-диагностики/докачки, но при reuse одного TCP-соединения
    счётчик байтов не обнуляют. VPN не может произвольно переписать Range внутри
    end-to-end HTTPS; миграция байтового потока требует поддержки обоих концов.
12. **Мультистратегичный DNS bootstrap** (V2-037 реализовано): plain UDP флот +
    DoH по IP-литералу + кэш последнего хорошего. Никогда не 853-only
    [§2.1, документировано].

**Маршрут/egress:**

13. **Egress-репутация — отдельное измерение** (V2-041): CDN-fronted вход
    обычно оставляет выходом VPS. Дополнительный WARP/server outbound может
    менять exit, но добавляет зависимость/доверие и не гарантирует снятие challenge.
14. **Первый хоп внутри РФ** [гипотеза]: меняет маршрут клиент→entry и точку
    международного выхода, но добавляет наблюдателя/стоимость/общий отказ.
    IMC'22 не устанавливает, что весь внутристрановой трафик не фильтруется.
    Нужны отдельные измерения обеих частей; в MVP не входит.
15. **Разные сети = разные failure domains** (LTE vs wired, §2.4a): при
    деградации одного класса сетей — переключение канала, а не ожидание.

**Диагностика и реакция (совместимо с fail-closed):**

16. **Классификация отказа по наблюдаемому поведению** — словарь причин для
    controller — **исторические имена, не доказанные причины**:
    - `ResetInjected`: наблюдается reset; без wire/capture нельзя отличить
      серверный сброс от инжекции, тем более доказать SNI-блок;
    - `SilentFreeze`: EOF/timeout в малом probe не доказывает объёмный freeze;
      нужны bytes/time/completion на ограниченной объёмной проверке;
    - `TlsPolicing443`: сравнение браузера и туннеля даёт гипотезу, не диагноз;
    - `PortBlackholed`: отсутствие ответа — также routing/firewall/server fault;
    - `DnsSubverted`: отличать ошибку DNS-пути от подтверждённой подмены;
    - `WhitelistMode`: гипотеза политики требует набора контрольных направлений;
      нельзя отнимать рабочий validated путь по одной TLS-ошибке;
    - `DirectLeakConfirmed`: отдельный структурный safety outcome, а не regex
      или просто совпавший публичный IP; реакция немедленная, без debounce.
    Реальный словарь failclass.go включает другие коды (`dns_path_failure`,
    `protected_channel_unavailable`, `unknown`); первая версия списка не API.
    Target, route, network epoch и форма ошибки обязательны для интерпретации.
17. **Методика Cheburcheck как референс, не production security probe**:
    [страница whitelist](https://cheburcheck.ru/kb/whitelist) прямо отделяет
    доменные исключения из замедления от мобильного allowlist. Её SNI-тест
    использует отключённую проверку сертификата; переносить его в protected
    probe запрещено. `--resolve` меняет DNS→IP, не отдельно SNI; URL задаёт
    имя, а смена URL одновременно меняет другие HTTP/TLS-параметры. Для
    причинного A/B нужен собственный endpoint с известными виртуальными
    хостами и валидным доверием, контроль Host/ALPN/reuse. Один Range-ответ
    доказывает лишь завершение этого запроса. Программная/правовая безопасность
    внешнего измерения из наличия команды не следует.

**Анти-знание (не повторять):**

- «любая TLS-фрагментация спасёт от ТСПУ» — нет универсального результата;
- «uTLS = невидимость» — upstream Not Recommended; поведенческий детект жив;
- «ECH решит SNI» — сигнатурно заблокирован на CF с 2024-11 (§2.9 анти-знание);
- «RFC-стандарт = доступен» — ECH стандартизован лишь в марте 2026 (RFC 9849),
  а deployment упирается в политику каждого CDN — стандарт ≠ поддержка ≠ доступность;
- «Brutal-дефолт ускорит» — без правила = 1 Mbps, дефолтом быть не должен;
- «смена порта — абсолют» — V2-051: фильтр может закрыть весь не-443 диапазон.

**Правовые тексты продукта — отдельная проверка:** прежний вывод о запрете
конкретных слов в UI и смешение видов ответственности не обоснованы этой
технической теорией. Не вводить такое продуктовое правило без сверки
действующих официальных норм; юридическая актуализация здесь не выполнена.

### 2.11. Дополнение из стороннего AI-обзора (GPT-5): что принято, что опровергнуто

Нам прислан большой обзор «методов обхода для РФ» (автор — LLM). По правилу §6
каждое значимое утверждение пропущено через фактчекинг; здесь — итог интеграции.

**Принято (подтверждено первоисточниками):**

1. **TLS-in-TLS-детект вложенных рукопожатий** — реальное исследование:
   «Fingerprinting Obfuscated Proxy Traffic with Encapsulated TLS Handshakes»
   (Xue, Kallitsis, Houmansadr, Ensafi, USENIX Security 2024). Протокол-
   агностичное обнаружение прокси по паттернам вложенных TLS-хендшейков.
   Следствие для нас: канал A (VLESS+WS+TLS: внешний TLS к CF + внутренние
   TLS-сессии абонентов) в принципе ложится под такой детект. Контрмеры:
   работа показывает ограничения random padding и mux: признаки burst/roundtrips
   могут оставаться. Split-streams/XHTTP надо испытывать отдельно; статья не
   доказывает их нераспознаваемость. [USENIX, paper](https://www.usenix.org/conference/usenixsecurity24/presentation/xue-fingerprinting).
2. **Эвристики против полностью зашифрованного трафика** — «How the GFW Detects
   and Blocks Fully Encrypted Traffic» (Wu et al., USENIX Security 2023):
   цензор не определяет «зашифрованность» точно, а применяет грубые эвристики
   с исключениями для «похожего на известные сервисы» трафика. Прямо перекликается
   с общей идеей сочетания признаков, но не подтверждает российскую AND-модель.
3. **Бюджет донастройки**: РКН обновлял систему замедления/блокировок
   на ~60 млрд руб. (2025–2027) [документировано: Forbes 2024-09-10] —
   ожидать продолжения волн донастройки ТСПУ (уже видим: 2024-12, 2025-12).
4. **Домен-фронтинг** — история уточнена (см. §2.3): «мёртв с 2018» — неточно;
   Azure Front Door изменил исключение в 2023 (§2.3). Собственный Azure
   reverse proxy — кандидат после проверки договора/WS/стоимости; произвольный
   domain fronting не следует из этого исключения.
5. **Класс стегано/медиа-транспортов** (Stegozoa, CovertCast, DeltaShaper —
   разные cover media, не одна скорость) и **traffic morphing/padding/FEC** —
   исследовательские направления. FEC исправляет часть потерь за лишние байты,
   сам по себе не маскирует протокол и не исправляет shutdown. Для MVP не берём.
6. **Рейтинг Tor-мостов в РФ не установлен**: исходное Snowflake > meek >
   obfs4 не имеет сопоставимой выборки. [Tor в январе 2026](https://forum.torproject.org/t/tor-project-user-support-report-for-january-2026/21221)
   описывает неоднородные блокировки и проблемы доставки мостов. Публичный
   список и доступность distribution plane столь же важны, как транспорт.

**Опровергнуто/скорректировано (анти-знание):**

1. **«VLESS не отвечает неавторизованному подключению»** — слишком широко:
   400 на некорректный WS наблюдался в нашей истории, но ошибочный HTTP-запрос
   может получить 400 и у обычного сайта. Вопрос — воспроизводимая отличимость
   серии ответов/таймингов от cover, а не сам код; REALITY также требует проверки.
2. **«Trojan выдаёт себя ответом на неверный запрос»** — по дизайну наоборот:
   Trojan при неуспешной аутентификации отдаёт настроенную веб-страницу
   (анти-probing by design) [документировано Trojan-GFW]. Риск пробирования
   существует при неправильной настройке, но это не свойство протокола.
3. **«Проценты детекции» (OpenVPN 100%, SS ~95%, Trojan ~90%, VMess ~80%,
   VLESS <5%)** — источник в обзоре не верифицируется ([42] без выходных
   данных). Ни порядок рейтинга, ни эти ЧИСЛА
   считать фактами или рабочими вероятностями нельзя: [неверифицируемо, не использовать].
4. **«SSH-туннель как постоянный резерв»** — под 16КБ-механикой SSH — исключение
   (#490 upd2), но считать его постоянным резервом нельзя: исключение может закрыть
   в любой день (см. судьбу не-443 портов, V2-051) [вывод].
5. **«ML/RL-агент выбирает транспорт»** — направление осмысленное, но у нас
   уже есть детерминированный AdaptiveController с классификатором причин
   (§2.10 п.16); по AGENTS §2.3 сначала зрелые аналоги, RL — не MVP. ML
   можно рассматривать только после валидации телеметрии/ground truth и
   выигрыша на отложенных сетях; не автономный агент без safety shield (§8).
6. **«TLS 1.3+ECH скрывает SNI»** — верно для внутреннего ClientHello в модели
   RFC 9849, но из этого не следует доступность или сокрытие IP. Исторический
   CF ECH-блок — пример ограничения deployment, не опровержение криптографии.

**Итог интеграции:** ценность обзора — в систематике классов (стегано, morphing,
мультихоп, RL) и двух свежих исследованиях (USENIX 2023/2024); слабость —
непроверяемые проценты и игнорирование наших live-фактов (sing-box 400,
ECH-блокировка, 16КБ-механика не упомянута вовсе). Правило сохраняем: теории
в этот файл попадают только после сверки с первоисточником или живым тестом.

## 3. Архитектурные принципы защищённого клиента (выводы из практики)

1. **Fail-closed** — при отсутствии подтверждённого защищённого пути трафик не выпускается. Никакого «а вдруг напрямую получится».
2. **Доказательство, а не индикация**: protected probe = DNS через туннель + 2 HTTPS-цели + ожидаемый egress + negative direct-leak test. HTTP 101/открытый порт/успешный handshake — НЕ доказательство [доказано нами: сервер с route.final=block принимал VLESS-сессии и блокировал весь трафик, при этом клиент выглядел «подключённым»].
3. **Один владелец lifecycle**: обёртка владеет контекстом движка. Операционный таймаут операции (Start/Reload) не должен быть контекстом движка — иначе движок умирает сразу после старта [доказано нами: P0-дефект Manager].
4. **Секреты только по ссылке**: конфиги в git — с плейсхолдерами; рендер в runtime — локально; секреты никогда не в чат/лог/diff.
5. **Сертификат pinned, не disabled**: self-signed сервер = пиннинг PEM в клиенте, `insecure` запрещён.
6. **Два протокола не означают два независимых пути**: TCP/CDN и UDP/direct
   различаются частью причин отказа, но один VPS/аккаунт/exit/publisher может
   отключить оба. Нужна карта общих зависимостей (§7.3).
7. **Валидация конфига до запуска**: references, selector без direct, отсутствие плейсхолдеров, strict JSON.
8. **Клиентская фича транспорта = контракт ОБОИХ концов**: при включении транспортной оптимизации на клиенте (mux, padding, новые поля) серверный inbound обязан уметь её терминировать ТЕМ ЖЕ изменением — иначе получаем невидимую снаружи деградацию: CDN жив, TLS жив, auth проходит, а данные рвутся (EOF) [доказано нами 2026-09-12: клиентский h2mux+padding по умолчанию против сервера без multiplex → probe «3 of 4 failed: EOF» при полностью рабочем пути]. Отсюда же: default-on транспортных фич небезопасен при гетерогенной серверной ферме — включать фичу стоит вместе с сервером или через дескриптор (per-канал), а не глобальным дефолтом.
9. **Провал probe ≠ утечка ≠ недоступность канала**: одиночный liveness failure
   допускает bounded reprobe при сохранённом барьере. Наличие барьера подтверждать
   отдельно, из timeout его не вывести. Совпавший direct/tunnel IP бывает при
   общем NAT/exit; различный IP тоже не доказывает отсутствие всех OS-утечек.
   Подтверждённый safety outcome — немедленный fail-closed; неопределённость
   нельзя превращать в security PASS. Исторический V2-026 показывает цену
   ложных остановок, но его атрибуция именно CGNAT не установлена здесь.
10. **Bootstrap не должен быть единственным и экзотичным**: резолв имени туннельного сервера ДО старта движка — мультистратегичный (plain UDP флот + DoH по IP-литералу + кэш последнего хорошего), в коде приложения, а не в конфиге ядра: политика владеет кодом, а не hopes. DoT/853 — популярная тихая точка отказа в фильтрующих сетях [вывод из THEORY §2.1; реализация preflight в V2-037].
11. **Idle требует проверки и восстановления**: keep-alive, app heartbeat,
   срок жизни carrier и NAT — разные параметры (§2.10 п.10). Исторические
   60/20с/TFO не универсальный default. Parser/check не доказывает семантику:
   в инциденте 2026-09-12 REALITY без принятого server_name отвергал аутентичных
   клиентов, хотя TCP/донор отвечали. Это evidence конкретной конфигурации.
12. **Multiplex имеет разнонаправленные эффекты**: меньше хендшейков, общие
   очереди/потери и больший объём carrier. Не «маскирует объём» автоматически.
   Выбирать согласованный профиль по E-02/E-03 и workload, не по догадке о DPI.

## 4. Реестр ложных блокеров (анти-знание)

Эти «блокеры» были найдены в старом плане/аудите и опровергнуты live-проверкой. Фиксируем, чтобы не повторить:

| Ложный блокер | Откуда | Правда |
|---|---|---|
| «nginx возвращает 400 на Sec-WebSocket-Protocol: VLESS» | SERVER-2026-09-01-1 | nginx отдаёт 101; 400 отдаёт сам sing-box на невалидный base64 subprotocol. Литерал «VLESS» не используется реальным клиентом [доказано] |
| «нужен скрипт vps-diagnose-and-fix-nginx-ws.sh» | тот же | Скрипт решал несуществующую проблему; сервер ни разу не был причиной 400 [доказано] |
| «CF token IP-restricted = мягкий блокир» | phase-0 evidence | Реального чтения через API не требовалось: всё проверяется DNS/TLS/SSH. Токен вообще не нужен для текущего MVP [доказано] |
| «нужен второй домен для независимого failure domain» | PLAN §5 Phase B (B1) | Верно, но это не блокер разработки клиента; каналы живут на одном VPS и это документированный компромисс |
| «WS 400 — ожидаемо, реальный клиент пройдёт» | PHASE-8A journal | Дважды неверно: и 400 не от nginx, и «пройдёт» оказалось ложью, пока не починили серверный route.final [доказано] |
| «сертификат snowdensys не соответствует → Full (Strict) недоступен» | RELEASE-2026-08-28-1 | Починено и не имеет отношения к клиентскому пути |

| «клиентский mux можно включить глобальным дефолтом, сервер не трогая» | V2-037 live | EOF на всех соединениях при живом CDN+TLS+auth: sing-box-сервер без multiplex-блока рвёт mux-стримы; чинится сервером (multiplex enabled+padding) или per-канальным дескриптором [доказано] |
| «probe EOF однозначно означает дефект клиента/сервера (V2-039)» | сессия 2026-09-12 | Mux on/off дали одинаковое зависание, сервер видел dial/open stream. Это не локализует неисправность только в клиент↔CF и не исключает серверный egress/CDN/цель. Старое «сервер ни при чём» и контрфактическое «curl прошёл бы» отозваны. Нужны независимые контрольные запросы и captures обоих концов. |

Мета-вывод: история содержит реальные серверные ошибки, но доля «почти все»
не посчитана. Проверка обоих концов ускоряет локализацию; clean logs и живой
/ip не исключают остальные причины. Текущий офлайн-режим сохраняется.

## 5. Открытые вопросы и направления (исследовательские заметки)

Статусы исполнения принадлежат PLAN §5.1/§5.3. Ниже — история вопросов и
уточнения, не параллельная очередь разработки.

- REALITY/XHTTP как канал B: **исследовано 2026-09-11** (docs/B1-REALITY-RESEARCH.md, PLAN V2-031): ядро умеет REALITY (клиент под with_utls), XHTTP — нет (форки client-only); выбран VLESS+TCP+REALITY без Vision. Осталось открытым: live-поведение REALITY в целевых РФ-сетях после деплоя VPS-B [требует полевой проверки];
- ECH через Cloudflare для VLESS+WS: **частично закрыто 2026-09-16**: ECH на CF
  (public_name cloudflare-ech.com) блокировался в описанных сетях с 2024-11-05
  (§2.9, #417) — рассчитывать только на ECH через CF
  как на защиту нельзя; ECH с собственным public_name на своём домене — открытый
  вариант [гипотеза, требует серверного эксперимента];
- XHTTP вместо WS: **изучено 2026-09-11**: в pinned upstream-ядре отсутствует (SagerNet/sing-box#3076 открыт), есть только в форках (sing-box-lx — client transport, сервер = Xray). Смена ядра отклонена (V2-031); переоценить, если XHTTP попадёт в upstream;
- anti-probing: сравнить всю матрицу WS/REALITY ответов с cover-сайтом;
  исторический 400 не доказательство VPN, дизайн REALITY не закрывает E-04;
- национальный DNS: поведение клиента в сети, где домены удаляются из резолверов [исследование];
- классификатор причин срыва (§2.10 п.16): словарь ResetInjected / SilentFreeze /
  TlsPolicing443 / PortBlackholed / DnsSubverted / WhitelistMode /
  DirectLeakConfirmed — **v2 интегрирован 2026-09-23** (windows/failclass.go,
  PLAN V2-087): детерминированный, поверх probe-отчёта; leak и allowlist дают

- failure domains / независимость каналов (§2.10 п.18): **модель v1 реализована
  2026-09-16** (windows/backend/render/fdmodel.go, PLAN V2-059; PLAN §5 Phase B):

- первый хоп внутри РФ (§2.10 п.14): RU-VPS как транзит — серверный эксперимент
  (нужен второй VPS в РФ-датацентре) [гипотеза, вне MVP];
- альтернативный CDN-фронт (Azure Front Door, §2.11): аварийный путь, если
  CF-ветка канала A деградирует целиком; проверить WS-проксирование и стоимость

- семантика `dns.rules.outbound: any` vs `"outbound": ["proxy"]` в sing-box 1.13 [документировано частично, протестировать];

  реализация, rate и политика сайта также существенны. Дополнительный exit
  проверять по целевой задаче; вход через CDN не подменяет выход VPS.

## 6. Как проверять новые факты (метод)

1. **Паспорт утверждения:** формулировка, источник/версия/дата, страна/ASN,
   измерение или дизайн, альтернативное объяснение, что его опровергнет.
   Документация доказывает контракт, source — конкретную реализацию,
   unit — конечный набор случаев, live — только проверенный путь/период.
2. **Сначала вопрос, затем проверка:** не запускать live из наличия команды
   в документе. Офлайн — fixtures/анализ; стенд — отдельная изоляция;
   сеть владельца/сервер — после соответствующего запроса и доступной инфраструктуры.
3. **Локализация:** client→edge→origin→exit→target и обратное направление.
   cf-ray/Server — подсказки, не криптографическое доказательство origin;
   нужны nonce/идентификатор запроса и сопоставимые серверные данные.
4. **Причинность:** paired A/B, один фактор, чередование порядка, одинаковая
   полезная нагрузка; отмечать IP-family, DNS/reuse/cache, server load, время.
   Действие может менять и сеть: блокировка/TTL/остаточное состояние создают carryover.
5. **Приватность:** синтетические payload; публичные key fingerprints/config
   identity, не значения секретов и не хеши слабых паролей. Raw captures могут
   содержать адреса/имена/credentials — локальное ограниченное хранение и redaction.
6. **Вывод:** observation отдельно от inferred mechanism; явные unknown,
   failed/skipped runs, sample size и границы применимости. Возраст evidence
   снижает его пригодность, но не превращает наблюдение в ложь. План экспериментов — §10.

## 7. Строгая модель: что именно мы оптимизируем

### 7.1. Противник, доверие и предел обещаний

[Инженерная модель, не описание секретной реализации ТСПУ.]

| Участник | Что видит/может менять | Чего выбранная защита не обещает |
|---|---|---|
| Локальный ISP / middlebox | IP, порты, размеры/время/направления, открытый ClientHello, drop/reset/rate/reorder, DNS | TLS скрывает содержимое, но не скрывает существование соединения |
| Активный пробер | Создаёт свои сессии, повторяет записи, исследует ошибки/время ответа | Не знает ключ по умолчанию, но может получить публично распространяемый профиль |
| CDN / TLS frontend | Клиентский IP, HTTP/WS после терминации внешнего TLS | Внешний TLS не скрывает эти данные от CDN; внутренний HTTPS защищает свой payload |
| VPN entry/exit и хостер | Метаданные потоков; exit видит target IP/DNS и plaintext протоколы | VPN не заменяет end-to-end TLS и не устраняет корреляцию времени/объёма |
| Publisher / update mirror | Профили, endpoints, распространение версий; mirror может задержать/подменить bytes | Подпись не делает endpoint доступным; компрометация signing key — отдельная угроза |
| Локальный процесс / администратор | Файлы, IPC, права, ОС; возможности зависят от привилегий | Защита сети не доказывает безопасность скомпрометированного хоста |

Не складывать эти роли в одного всеведущего противника без явного сценария.
Модель пассивного ISP и модель CDN с TLS-ключом дают разные наблюдения.
Не применять скрытые настройки downgrade, `insecure` или direct fallback
ради «доступности»: они меняют задачу безопасности, а не решают её.

«Теоретический максимум» — условная граница для заданной сети, противника,
бюджета и допустимого доверия. Нельзя одновременно гарантировать неотличимость,
нулевой overhead, нулевое время восстановления и работу при отсутствии пути.
Цензор может принять высокую цену collateral damage; популярность CDN не veto.

### 7.2. Поверхность наблюдения и экономическая модель

Полезна последовательная модель: дешёвый IP/ASN/порт-фильтр → разбор
handshake → агрегаты потока → дорогая проверка/проба. Это **возможный pipeline**,
а не установленный порядок в РФ. Цель транспорта — уменьшить различимость
в выбранной модели и повысить цену блокировки; цель клиента — сохранить
доступный проверенный путь с ограниченной ценой адаптации.

Четыре независимых вопроса:

1. **Обнаружение:** отличим ли wire image от контрольных легитимных потоков?
2. **Перечисление:** можно ли получить наши endpoints/профили через distribution?
3. **Подавление:** готов ли цензор блокировать эти endpoints/класс целиком?
4. **Восстановление:** можно ли безопасно доставить новый профиль после блокировки?

Хорошая маскировка не исправляет публично перечисляемую единственную IP-точку;
новые IP не исправляют сломанный control plane. Размер/тайминг/серии burst
остаются даже у криптографически корректного протокола [S02][S03].

**Базовая частота важнее красивого accuracy.** Для доли VPN `π`, true-positive
rate `t` и false-positive rate `f` точность положительного решения:

```text
PPV = t·π / (t·π + f·(1−π))
```

Синтетический пример: π=0.001, t=0.99, f=0.01 → PPV≈9%, а не 99%.
Это арифметика условной модели, не замер цензора. Для оценки детектора нужны
base rate, benign corpus, PR/ROC и цена ошибок; «18/18 lab cases» не калибрует
вероятность в живой сети. Проверять на других днях/ASN/нагрузках, не только
на примерах, по которым написаны правила.

### 7.3. Независимость — граф, а не число протоколов

```text
клиент → access ISP → bootstrap/resolver → entry/CDN → origin → exit → target
                                   ↘ profile publisher / trust / time / payment
```

Каждый путь имеет зависимости: физическая сеть, IP-family, prefix/ASN,
carrier, origin/process/host, exit, TLS donor, DNS, publisher/key, учётная запись
и оплата. Отдельные домены на том же аккаунте CDN не устраняют блок аккаунта;
разные VPS в одной подсети не защищают от prefix-block. Один и тот же target
для всех probes создаёт ложный общий отказ даже у здоровых каналов.

Точные соотношения для двух отказов A/B:

```text
P(оба недоступны) = P(A) · P(B | A)
P(хотя бы один работает) = 1 − P(A ∩ B)
```

Подстановка `P(B|A)=P(B)` разрешена только при обоснованной независимости.
Например, два транспорта с одним выключенным origin не дают резерв, сколько
бы строк ни было в selector. Для исследования строить fault tree и минимальные
наборы общих отказов; не выдавать penalty score за вероятность.

Для неизвестных полей хранить **coverage/provenance**, а не только score:
подписанное утверждение владельца, статическая деривация, датированное измерение.
Unknown не означает ни «совпадает», ни «различается». Выбор кандидата при unknown
возможен, заявление о доказанной независимости — нет. Подмена CDN entry на другой
не обязательно меняет origin/exit/publisher; это проверяется отдельно.

### 7.5. Control plane, ключи и автономность

Нужны отдельно доступность профилей, подлинность, свежесть, совместимость и
восстановление доверия. Два mirror с одним key/аккаунтом не дают две независимые
границы доверия. Подписанный вредоносный профиль после кражи publisher key остаётся
подписанным; простая Ed25519-проверка не решает компрометацию издателя.

[TUF 1.0.37, 2026-10-08][S20] — зрелый референс разделения ролей/thresholds,
rollback/freeze/mix-and-match защиты и ротации root. Это не утверждение, что
наш envelope уже реализует TUF. Адаптировать требования и regression scenarios,
решение о библиотеке/миграции принимать отдельно в OFF-06.

До выдачи профиля: ChannelID→SecretID→pin/capabilities, min/max client/core
version, auth и signed validity. Rotation: current+next, overlap, отзыв, crash
между stage/commit, clock jump и восстановление из backup. Пин должен приходить
по доверенному пути; TOFU в атакуемой bootstrap-сети не равен установленному доверию.

Автономность не означает бесконечно принимать expired/revoked профиль. Нужны
явная политика last-known-good **в пределах доверия/сроков**, отдельное поведение
ошибочных часов и восстановление из заранее доверенного offline package.
Expiry при недоступном publisher может снизить availability — trade-off
документировать, не скрывать автоматическим отключением проверки.

## 8. Адаптация при неполных и меняющихся данных

### 8.1. Состояние и наблюдения

Скрытое состояние включает перегрузку, отказ сервера, политику сети, остаточный
блок, неисправность target и клиента. Наблюдение одно и то же (timeout) может
порождаться каждым из них. Следовательно, controller решает задачу частичной
наблюдаемости; на первом этапе достаточно детерминированных правил с `unknown`.
POMDP/bandit/RL — возможные модели исследования, не необходимость внедрения ML.

Минимальное observation: mono time + wall time, network epoch, channel/config
identity, attempt/generation, target и фактический route/IP-family, stage
DNS/dial/TLS/auth/data, bytes up/down, deadline/completion/error form,
provenance и ограничения. Не писать browsing history, payload или credentials.
Структурное событие сильнее regex; отсутствие capture не заполнять «SNI-block».

Раздельные оси: **Safety**, TransportHealth, EgressHealth, EndpointHealth и
InfrastructureHealth. HTTP challenge обычно даёт сведения о site policy,
certificate error — о trust/config/time; ни одно не следует автоматически
лечить перебором портов. Пример альтернативных причин — OONI [S05].

### 8.2. Правило решения и защитные инварианты

```text
validated candidates + свежие наблюдения + budget + protection intent
→ stay / bounded reprobe / diagnose / switch / recover / blocked
→ один Manager, generation/epoch check → apply → fresh protected gate → publish
```

Safety — жёсткое ограничение, а не штраф в utility. После него сравнивать
доступность, p95 recovery/TTFB, goodput и цену. Профиль с меньшим RTT, но без
удостоверенного protected пути не выигрывает score.

- Подтверждённая утечка или недостоверный барьер → safe error немедленно.
- Один liveness timeout → ограниченное подтверждение, не новый «диагноз DPI».
- Только endpoint outage → другой независимый измеритель; не гонять все транспорты.
- Общий origin недоступен → приоритет другого origin, а не всех его протоколов.
- Все пути непроверены/недоступны → BLOCKED и bounded retry без снятия защиты.
- Пользовательский Disconnect отличается от ошибки, crash и закрытия GUI.

Смена транспорта обычно не мигрирует существующий пользовательский TCP-поток.
«Seamless» разрешено писать только для фактически сохранённых потоков;
reconnect новых потоков и verified rollback — отдельные результаты.

### 8.3. Колебания, бюджет и обучение

Cooldown, hysteresis, min dwell и backoff с jitter ограничивают колебания,
но их величины должны измеряться. Reset на новом epoch не должен стирать
protection intent. Старые observations не могут commit после смены сети/сессии.
Репутацию канала ослаблять с возрастом, различать срок действия профиля и TTL
наблюдения; не сбрасывать безопасность из-за устаревшей статистики.

Один общий budget: максимальные concurrent probes, bytes/окно, attempts,
CPU/time, server rate, батарея/стоимость сети; maintenance probes проходят тот
же limiter. Отмена UI не означает, что запущенная работа перестала потреблять
ресурсы. Неподчиняющийся engine Start/Close требует process boundary, не ещё
одного goroutine timeout. Стенд должен проверять boundedness и накопление работы.

Исследование нового кандидата — только из валидного доверенного набора, без
protected user payload до gate. Не сканировать порты/домены массово и не
переобучаться на собственных probes. Сначала replay фиксированного fault schedule,
затем shadow recommendations, canary и rollback. ML допускается при выигрыше
на отложенных сетях/днях и стоимости ошибок, с fallback к объяснимой политике.

## 9. Скорость: физические ограничения и полезные оптимизации

### 9.1. Модель затрат

[Инженерные приближения, не предсказание конкретного результата.]

```text
goodput = полезные завершённые bytes / wall time
goodput ≤ min(access, entry path, relay CPU, relay↔exit, exit↔target, target)
BDP = bottleneck bytes/s × RTT seconds
carrier throughput ≲ in-flight window / RTT  (если именно окно ограничивает)
recovery = обнаружение + очередь/cooldown + prepare/apply + fresh gate
```

Не складывать latency всех стадий вслепую: соединения/резолв могут переиспользоваться,
часть работы параллельна. Отдельно cold start, warm reuse, time-to-first-byte,
полное завершение и latency под нагрузкой. Speedtest с одним длинным скачиванием
не описывает интерактивный browsing и не включает цену отказавших попыток.

Короткие carriers уменьшают накопление байтов, но добавляют RTT, crypto/CPU,
NAT/port state и риск rate limit. При условном лимите `B` байт/carrier и полном
времени цикла `T` последовательный поток ограничен `B/T`; параллелизм может
помочь лишь до общей ёмкости, лимитов и новой сигнатуры. Не предлагать
«новый TCP каждые 16 КБ» без transport reassembly и проверки end-to-end семантики.

### 9.2. Где искать выигрыш

| Мера | Возможный эффект | Цена / обязательный контроль |
|---|---|---|
| Меньше лишних reload/probe/повторов | recovery и CPU без смены протокола | не пропускать fresh gate, cancellation/epoch atomicity |
| Mux / bounded pool | меньше handshakes | TCP-level head-of-line, общий failure blast radius, очереди и bytes/carrier |
| QUIC streams | потери одного stream не требуют упорядоченной доставки другого | общий congestion controller/path; UDP block/MTU/NAT; не обещает отсутствие задержек [S12] |
| Надёжный внешний byte stream для TUN | совместимость TCP-пути | outer loss задерживает внутренние потоки и может вызывать повторные retransmission; отличать packet-over-TCP от split proxy |
| MTU/PMTUD и размеры буферов | устранение blackhole/оконного bottleneck | family/encapsulation overhead, oversized buffers → latency/RAM; E-05 |
| Congestion control / bandwidth caps | лучшее использование loss-path | rate выше доступного вызывает очереди/потери, измерять соседний поток; Brutal не default [S13] |
| Padding / timing shaping | меньше выбранных статистических признаков | bytes/CPU/latency и новые fingerprints, абляция и benign corpus [S03] |
| FEC / дублирование | latency при части случайных потерь | больше wire bytes, не лечит полный drop; не дублировать неидемпотентные запросы |
| Keep-alive / resumption / TFO / 0-RTT | idle recovery/handshake в некоторых условиях | расход сети, replay/idempotency, несовместимость middlebox; не replay control-plane Apply [S06] |

QUIC connection migration [S23] может сохранять сессию при смене адреса/пути, если
это поддерживают оба конца; не означает миграцию в другой независимый VPN exit
и не преодолевает заблокированный destination IP. Для SOCKS отдельно выяснять
поддержку UDP у приложения и прокси; для TUN — ОС-маршрут/DNS/IPv6, не браузерный mock.

### 9.3. Что разумно заимствовать и когда

Это shortlist для оценки, **ничего автоматически не устанавливается**.
Latest docs содержат возможности вне нашего pin; фиксировать tag/commit,
лицензию зависимостей, wire compatibility и rollback до любой интеграции.

Принципы → отдельный compatibility spike: pin, packaging, child process/kill-switch, server capability. Root BSD-style license не отменяет third-party notices |

## 10. Программа экспериментов и критерии знания

Это спецификация будущих проверок. **В V2-109 они не запускались.**
Реализация и статус — PLAN §5.3; живые измерения требуют доступной
инфраструктуры и соответствующего запроса, публикация OONI не включается автоматически.

### 10.1. Минимальный паспорт опыта

- Гипотеза и конкурирующие объяснения, контролируемый фактор и прогноз.
- Client/core/server/tool versions, config identity, capability set, topology,

- Метрики до запуска, точность/размер выборки по значимому эффекту и вариативности;

- Raw synthetic observations, failures/cancellations/timeouts, способ агрегации,

в изолированном стенде. Сначала проверить, что инъекция действительно сработала;
успешный тест с неработавшим fault injector не считается прохождением сценария.

### 10.3. Статистика и stop criteria

Сравнивать внутри блоков ISP×epoch×day×family×workload, чередовать A/B и
сохранять неуспешные серии. Повторения на одном middlebox могут зависеть от
общего состояния: считать их независимыми Bernoulli trials без основания нельзя.
Timeout — цензурированное наблюдение длительности, а не нулевая скорость;
throughput только завершённых быстрых сессий создаёт survivorship bias.

Для uptime/failover учитывать длительность outages и полезные завершённые
операции. Percentile по маленькому n неустойчив; показывать n/распределение,
paired differences и интервалы (например block bootstrap по независимым сессиям/
сетевым окнам). Для нуля failures в n **независимых одинаково распределённых**
испытаниях приближённая верхняя 95% граница failure rate — 3/n; без предпосылок
это правило неприменимо и в любом случае не доказательство абсолютной безопасности.

Перед опытом выбрать primary metric, практически значимый effect и допуски
остальных метрик на baseline. Принять кандидат, если эффект устойчив в
отложенных блоках, safety не нарушена, resource/latency budgets выдержаны.
Остановить опыт при leak, trust failure, потере контроля нагрузки или saturation
стенда; такой run сохраняется как failure/invalid с причиной. Если эффекта нет,
не подбирать ещё десятки fingerprint до случайного PASS — пересмотреть гипотезу.

<a id="android-platform"></a>
### 12.1. Модель защиты и ограничения платформы

`VpnService` получает IP-пакеты через TUN в пределах Android user/profile.
Один профиль допускает один активный VPN; запуск другого может отозвать наш.
Рабочий профиль, личный профиль, tethering и трафик системных компонентов — разные
области. Их нельзя объединять подписью «весь телефон защищён». Always-on запускает
выбранный VPN, но установление туннеля остаётся ответственностью приложения. [A01]

Разделять три факта: **намерение пользователя**, **состояние приложения** и
**системную блокировку без VPN**. Собственный reject внутри работающего TUN не
является барьером после смерти приложения. Для строгого режима требуется проверяемая
конфигурация Android «Постоянная VPN» + «Блокировать соединения без VPN»; где она
недоступна или не включена, честно показывать ограниченную защиту. Ручное отключение,
системный revoke, crash, force-stop и исчезновение сети — разные переходы. ОС может
не разрешить приложению самопроизвольно восстановиться после force-stop. [A01][A03]

Нельзя обещать, что исключённый банковский клиент одновременно работает напрямую
и сохраняет строгий lockdown: системная блокировка может перекрыть исключённые
приложения. Сначала объяснить конфликт и фактическую область политики. Не предлагать
`allowBypass()` как исправление; оно разрешает обход VPN. [A02][A31]

**Остаточный риск ОС.** Mullvad публиковал отчёты о connectivity-check трафике
(2022), DNS (2024) и определённом QUIC-трафике Android 16 (2026), выходящем вне VPN,
в том числе при системной блокировке. Это сообщения конкретных исследований,
не доказательство уязвимости каждого актуального телефона. Версия ОС, security patch,
OEM и внешнее наблюдение обязательны; состояние исправлений на нашем устройстве
не проверено. Приложение не может обещать устранение дефекта ядра/системы. [A34][A35][A36]

### 12.2. Владение VpnService, native-ядром и доказательством готовности

Рекомендуемый раздел ответственности: native Kotlin service владеет жизненным
циклом, libbox — сетевым ядром, UI читает неизменяемые снимки. Activity/Compose,
плитка и уведомление отправляют команды одному владельцу; их пересоздание не
должно перезапускать VPN. На Android нет Windows Job/WFP/DPAPI/Wails lifecycle.
Приватный процесс `:vpn` может изолировать падение UI, но сам по себе не добавляет
системный fail-closed и не защищает от native-зависания.

Контракт операции: `(intentRevision, serviceInstance, networkEpoch, configDigest,
attemptId)` + монотонное время. Запоздалый JNI/callback/probe результат не меняет
новую сессию. Отмена coroutine не доказывает прерывание блокирующего native-вызова:
нужны реальный cancel/close, ограниченная очередь и проверяемое завершение ресурсов.
Если исход завершения неизвестен — `blocked/unknown`, без параллельного нового ядра.

Foreground service должен вовремя перейти в foreground и корректно обрабатывать
revoke/destroy/restart. Для VPN Android документирует категорию `systemExempted`
при выполнении условий; тип, permission и eligibility проверяются для выбранного SDK.
`specialUse` из чужого proxy-service нельзя автоматически переносить. Отказ в
`POST_NOTIFICATIONS` не равен запрету запуска FGS: статус разрешения и работа VPN
должны отображаться отдельно. [A05][A19]

Каждый fd имеет единственного владельца: определить `ParcelFileDescriptor`,
borrow/dup/detach и порядок закрытия TUN/transport sockets/monitor callbacks.
`protect(fd)` выводит **конкретный сокет** из VPN для связи с gateway; требуется
проверить boolean и отказать при неуспехе. Это не проверка шифрования. Не исключать
целиком наш package: внутренний protected probe тогда тоже может выйти напрямую.
Разрешение на bootstrap/protected socket ограничено назначением и сроком. [A03]

«Ядро запущено», иконка ключа, `NET_CAPABILITY_VALIDATED`, успешный handshake и
свежий protected egress — разные факты. Снимок готовности включает версию профиля,
реальную область перехвата, свежесть/возможности проверки и причину ограничения.
Сбой measurement-сервиса не превращается автоматически в отказ канала.

### 12.3. Смена Wi-Fi/LTE, DNS и область правил

Отслеживать физические `Network`/capabilities/LinkProperties, исключая сам VPN;
отдельно учитывать default network, validated/captive/metered/roaming и смену DNS.
Смена default не означает уничтожение прежней сети. Callback не выполняет тяжёлую
работу; изменения сводятся в новую epoch с bounded debounce. Подписки освобождаются.
`setUnderlyingNetworks` информирует ОС о выбранной основе, но не переносит любой
TCP-сеанс. Глобальный `bindProcessToNetwork` опасен для внутренних проверок. [A03][A04]

QUIC migration (§9, [S23]) может сохранить подходящее соединение после смены пути
к тому же серверу; она не переносит произвольный TCP/UDP поток на другой exit.
Разные SIM/ASN/страны/протоколы могут иметь общие origin/CDN/DNS и не давать
независимости. Полезность второго gateway измеряется по failure domains и реальному
восстановлению; смартфон не создаёт разрешённого пути туда, куда оператор не пускает.

Два уровня split: системный `VpnService.Builder` выбирает приложения, libbox
маршрутизирует уже захваченный трафик. Allowed/disallowed package lists взаимоисключены;
изменение может потребовать нового TUN. Удалённый пакет, shared UID, isolated process,
переустановка и рабочий профиль требуют явной семантики. Owner query API29+ помогает
атрибуции TCP/UDP, но не даёт права выдумать owner для любого пакета. Unknown identity
не получает direct. Windows `process_name` нельзя считать Android package policy. [A02][A03]

DNS — часть политики: resolver внутри VPN, bootstrap resolver и DNS исключений
имеют разные scopes. Private DNS, встроенные DoH/DoQ приложений, ECH и общий CDN IP
ограничивают доменную атрибуцию; «домен в списке» не доказывает перехват всех потоков.
Проверять IPv4/IPv6/AAAA, IPv6-only + NAT64/464XLAT и фактическую MTU. Нельзя
лечить IPv6 отсутствием маршрута, которое незаметно открывает обход. `allowFamily`,
route exclusions и отсутствие явного DNS требуют отдельной проверки. [A02][S07]

LAN/печать/casting — ограниченное правило для выбранной сети, без автоматического
доверия всему RFC1918 и без обхода корпоративных overlapping routes. Для target37+
Android документирует `ACCESS_LOCAL_NETWORK`; target≤36 не следует запрашивать
его только из-за наличия в upstream manifest. Отказ и отзыв разрешения — отдельные
состояния. Границы фактического relayed LAN-трафика через VPN уточняются native spike,
а не выводятся из одного INTERNET permission. [A15]

OONI-аномалии могут иметь иные причины; coverage неоднороден [S05]. Ссылки на

опыта фиксировать оператор/AS/регион/день/тип сети, transport и endpoint, а не IMSI,
номер телефона, точные координаты или содержимое пользовательского трафика.

Решение адаптации — `stay → scoped recheck → validated candidate → commit` либо
`blocked`; без direct fallback защищённого трафика. Выбор минимизирует ожидаемый
перерыв/энергию/байты при safety constraints (§8), а не максимизирует абстрактный score.
Ни ECH, ни domain fronting чужого CDN, ни Cloudflare build shell не дают собственного
надёжного gateway по определению. Новый transport допускается только после проверки
обоих концов, лицензии, fingerprint, бюджета и независимого полевого результата.

### 12.5. Доверие, офлайн-перенос и обновления

Android должен принимать тот же публичный профильный контракт и **те же подписанные
байты**, а не Kotlin-пересериализацию JSON перед проверкой. В проекте уже выбран
go-tuf2.4.2 и есть непроверенная Windows source integration: [ADR-001](decisions/001-tuf-delivery.md).
Profile epoch recovery пока только контракт [ADR-002](decisions/002-profile-epochs.md).
Они не являются готовым Android SDK. Переносить portable schema/signature/antirollback
и штатный TUF workflow через узкий seam; UI, filesystem transaction и vault — платформенные.
Не импортировать целиком модуль `windows` ради нескольких полезных packages.

APK signing, TUF update role, profile authority и device enrollment — разные
полномочия. Подписанный профиль не разрешает произвольный APK, а подпись APK не
делает свежим старый профиль. Учесть freeze/expiry/clock uncertainty, revocation,
rollback floor, exact source digest, offline valid cache и управляемое восстановление.
Недоступность доставки не обнуляет сохранённую доверенную историю. [S20][A24]

Android Keystore хранит ключ обёртки vault; hardware backing проверяется, а не
предполагается. Требование биометрии при каждом decrypt несовместимо с unattended
always-on. Credential-encrypted storage до первого unlock недоступно: безопасный
вариант pre-unlock — честно blocked, если секреты не готовы; не складывать credentials
в device-encrypted storage ради красивого autoconnect. [A07][A08]

Auto Backup/перенос телефона не должны восстанавливать ciphertext без рабочего
Keystore или старый trust checkpoint как новую чистую установку. Отделять разрешённые
несекретные настройки от vault и trust history, давать повторное enrollment без
неявного сброса antirollback. Экспорт — явный encrypted bundle; raw credential export
имеет отдельно объяснённую потерю device revocation/policy гарантий. [A09]

Импорт начинается без учётной записи/GMS: файл через системный picker, QR с камеры
или выбранного изображения, ограниченный deep link. ZXing — готовый offline decoder,
не новый QR-алгоритм. Ограничить входные байты/размер картинки/схемы URI/редиректы;
preview и подпись перед применением, никаких auto-connect/авторизации из внешнего Intent.
Token URL, clipboard и QR не попадают в логи/recents/support export. [A20][A21][A25]

### 12.6. Батарея и скорость: мобильные бюджеты

Событийная адаптация предпочтительнее бесконечного таймера/foreground polling.
Doze, sleep и OEM power policy меняют доступное время исполнения; foreground service
не гарантирует вечную работу. Не просить всем отключить энергосбережение и не держать
wakelock постоянно. Периодическая задача обновлений не должна быть VPN keepalive. [A06]

Отдельные бюджеты: dial/handshake/probe bytes, candidate fanout, retries/backoff,
CPU/RSS/native heap/Go goroutines, fd/buffers, wakeups и metered/roaming traffic.
Не копировать безусловный SFA `setMetered(false)`: ОС должна знать реальные ограничения.
Режим «Не мешать сеансу» уменьшает необязательные проверки/переключения; обрыв пути
и потеря доказанной защиты остаются причиной безопасного действия. Слушать микрофон
или читать экран для обнаружения звонка не требуется.

Временные разрешения/TTL используют elapsedRealtime, учитывающий sleep; после
reboot временный grant не продлевается из-за сброса счётчика/смены wall clock. [A23]
Метрики сравнивать на одном устройстве/радиоканале/нагрузке: idle, screen-off,
handover, video/call, mobile data, throughput/latency/loss и стоимость проверок.
Чужие Mbps и RAM без workload не становятся требованиями нашей реализации.

### 12.9. Публикация и пределы текущих выводов

Native AAR означает проверку ABI, ELF/ZIP alignment, JNI/R8 и устройств с 4/16KiB
pages. Текущая Android страница указывает enforcement обновлений Google Play с
2027-02-01 для 64-bit apps target35+; это датированный policy snapshot, не причина
отложить совместимость. При релизе перепроверить. [A12]

API37 соответствует Android17 [A13]; прочитанный SFA HEAD использует compile/target37,
но это не доказывает выбранную нами stable SDK/toolchain. Release notes в выборке
недостаточны для актуального GA утверждения; AND-01 фиксирует поддерживаемый release,
NDK/AGP/Go/gomobile и Play target requirement до создания проекта. [A14]

Google Play требует обоснования VpnService/видимости пакетов и работы с чувствительными
данными; список установленных приложений остаётся локальным. Отдельный APK-канал
тоже требует signing/update/registration решения. На 2026-10-22 developer verification
страница описывает запуск 2026-09-30 в четырёх регионах и расширение в 2027; из этого
не следует, что sideload в России сейчас запрещён. [A10][A11][A26]

Статические документы не доказывают мобильную безотказность. Нужны будущие device/OEM,
screen-off/boot, external-capture и операторские сравнительные опыты, отдельно от
unit/contract/UI checks; планирование их не является разрешением запуска.

## 13. Надёжность и полезная скорость: детали обеих платформ

Исследование 2026-10-23 по запросу владельца. Этот раздел углубляет §§7–12;
требования Windows/общего контура — [PLAN §5.6](PLAN.md#reliability-research),
Android — [ANDROID-PLAN §8.1](ANDROID-PLAN.md#android-reliability-depth).
[Evidence и расчёты](evidence/2026-10-23-deep-reliability.md) отделяют прочитанный
исходник, математический контрпример и будущую native/сетевую приёмку.
Запрос разрешил чтение профильных чатов и необходимые проверки теории;
он не превращает старые результаты или модели ниже в работоспособный VPN.

### 13.1. Что означает «быстрее и стабильнее»

Оптимизируем защищённую **полезную** доставку: время первого успешного действия,
p50/p95/p99 задержки под нагрузкой, goodput, число оборванных рабочих сеансов,
время восстановления и количество ложных переключений. Mbps без idle/loaded latency,
CPU/энергии/байтов и отказов не описывают комфорт. Безопасность — ограничение,
не слагаемое score, которое можно компенсировать скоростью. Tail latency особенно
важна при последовательных зависимостях и высокой загрузке [D16].

Сначала определить bottleneck: радио/оператор, RTT/потери/PMTU, VPS CPU steal/лимит,
криптография, копирование/GC, flow-control window, очередь или удалённый сервис.
Переносить нагрузку на более мощный CPU полезно лишь при подтверждённом CPU bottleneck.
Для телефона добавить screen-off/roaming/OEM; для Windows — startup/resume/worker/
TUN/WFP и native WebView. У каждой метрики есть denominator и наблюдаемая область.

### 13.2. Закреплённый код важнее названия оптимизации

Прочитаны project pins: sing-box1.13.19; SagerNet/quic-go0.59.0-sing-box-mod.4;
sing-quic `d83826c306d7`; sing-tun `7c73233bd0fb`; x/sync0.20.0.
Полные commit/file/blob/SHA256 и лицензии — evidence. Android пока закрепляет
libbox source; бинарный dependency graph/AAR ещё не подтверждён. Выводы из Windows
go.mod не распространяются на ещё не собранный Android artifact автоматически.

Проверить отдельно security/path/resolver/billing/presentation changes; не выкидывать поля из admission fence ради скорости |

**Конкретный source finding, RQ-01.** В `hysteria2/salamander.go` закреплённого
sing-quic vectorised method вычисляет индекс локального буфера с накопленным
смещением и индекс 32-byte key без скобок вокруг общего смещения.
Модель M10 даёт выход за границы для двух buffers `[8,3]` и `[8,64]`;
Git blob сверён. Это подтверждённый контрпример арифметики **если вызывается этот
method**. Достижимость через актуальные QUIC/obfs/writer wrappers и влияние на
наше приложение не установлены; upstream/native код не исполнялся. Не объявлять
воспроизведённый crash, не делать массовый upgrade. До включения новых vectorized
paths — call graph → узкая разрешённая регрессия → upstream fix/backport/rollback gate.
В стандартной ветке прочитанных `quic.go`/basicConn/Salamander вызывается `WriteTo`,
который использует нижележащий writer; это не вызов проблемного vectorised method.
Отдельная TLS Config branch и другие writers не прослежены полностью. Поэтому
этот finding не обосновывает объявление текущего HY2 нерабочим.

### 13.3. PMTU, IPv6, фрагментация и offload

Различать TUN MTU, outer path MTU, UDP payload, QUIC packet и HY2 application
message. QUIC требует доступности UDP payload≥1200; на outer IPv6 path MTU1280
после40-byte IP и8-byte UDP остаётся1232. Протокольный overhead уменьшает payload
дальше. В модели с условными64 bytes остаётся1168, но это **не** основание назначить
inner IPv6 MTU1168. Нужны подходящая application fragmentation/reassembly,
stream representation или другой путь. Число64 иллюстративное, не HY2 спецификация. [D01][D02]

У закреплённого Salamander overhead известен точнее: `salamanderSaltLen=8`,
по8 bytes на внешнюю датаграмму. При outer IPv6 PMTU1280 без extension headers
после IP/UDP/salt остаётся **1224 bytes для QUIC packet**, ещё до QUIC/HY2 headers
(M05). Проверять, что probe size/max packet size и wrapper overhead согласованы;
сырой UDP budget1232 нельзя автоматически использовать как QUIC packet budget.
Это расчёт по прочитанному исходнику, не воспроизведённый PMTU defect или настройка TUN.

DPLPMTUD использует подтверждённые пробы и recovery от blackhole вместо доверия
одному ICMP/PTB. Оно не исправляет UDP block/allowlist. Проверять уменьшение MTU
после handover, асимметрию, отсутствие/подделку PTB, size-dependent loss отдельно
от volume-dependent throttling. Кэш PMTU привязан к конкретному path/endpoint,
а не стране или всему профилю. В pinned HY2 есть application fragment fields;
проверить bounds/count/TTL/duplicate/out-of-order/reassembly memory, не писать новый
fragmenter рядом. У QUIC DATAGRAM нет обязательной повторной передачи payload. [D01][D04]

GSO/GRO уменьшают syscall/packet overhead, но не разрешают больший MTU на проводе.
Batch должен иметь допустимые адрес/размер/segment boundaries; fallback не теряет
и не дублирует packet. Возможность Linux TUN offload из sing-tun не доказывает
доступность для Android fd, выданного VpnService. На Windows Wintun и QUIC UDP
обрабатываются разными слоями. Оценивать CPU/packet и tail latency при том же goodput,
не объявлять «zero-copy» по наличию pooling или vectored API. [D05]

### 13.4. Окна, congestion control, очереди и мультиплексирование

Приближение bandwidth-delay product: `bytes = bits_per_second × RTT / 8`.
100Mbps×80ms≈1MB in-flight (M04). Receive windows меньше BDP могут ограничивать
поток; слишком большие caps при множестве соединений расширяют memory exposure.
Socket buffer, receive credit, congestion window и очередь приложения — четыре
разные величины. 16MiB заполненной FIFO при10Mbps требует≈13.42s дренирования;
это условный расчёт, не прогноз любой UDP queue. [D03][D05][D06]

Brutal требует реалистичной доступной rate, которая на LTE меняется и отличается
от скорости порта VPS. Завышение может увеличить потери, расход и задержку соседних
потоков. BBR/CUBIC/NewReno — не маскировка от DPI; поддерживаемый sender и его
реализацию определяет точная версия ядра. Проверять video+call+bulk, оба направления,
RTT/loss/jitter, metered bytes, CPU и соседний обычный TCP; один speedtest недостаточен.
Upstream Hysteria performance page предлагает большие buffers/priority/chrt —
это материалы для опыта, не готовый системный preset. Real-time priority может
ухудшить работу watchdog/DNS/SSH и других приложений. [D06][D07]

Mux уменьшает handshakes, но собирает failure domain, flow-control credit и CC
нескольких потоков в одном transport. QUIC устраняет stream-level delivery HOL
между независимыми reliable streams, но сохраняет общие congestion/CPU/path ресурсы;
UDP payload в DATAGRAM не становится reliable stream. Вложенный TCP поверх reliable
TCP может усиливать задержки при потере; это не утверждение, что любой TCP tunnel
всегда хуже UDP на сети с UDP block. Разделять bulk/interactive pools, caps потоков
и idle eviction только после server compatibility и scoped измерения. [D03][D04]

FQ-CoDel — готовый алгоритм для очереди в контролируемом bottleneck, не обещание,
что qdisc внутри гостевого VPS устранит очередь у гипервизора/оператора. ECN требует
поддержки и валидации на фактическом transport path. Не переносить DSCP/ECN metadata
в туннель без определённой семантики; L4S/FEC/custom scheduler — отдельный R&D gate,
а не новый обязательный transport первого релиза. [D08]

### 13.5. DNS, адреса и кэши — ускорение с контекстом

Happy Eyeballs полезен для частично сломанного IPv6/IPv4: ограниченные пересекающиеся
попытки к **разрешённым** адресам с освобождением проигравших sockets. Он не означает
соревнование «VPN против direct» и не подтверждает работоспособность приложения.
Resolver/transport race должны учитывать физическую сеть, NAT64/DNS64, policy,
credential/trust generation и единый dial budget. Успешный TCP до gateway не
авторизует новый profile и не заменяет authenticated/protected probe. [D09]

Ключ cache/coalescing — не один hostname: нужны query type, resolver/realm,
путь/назначение bootstrap-vs-protected, policy generation и необходимые privacy
options. В M09 одинаковое имя из work/travel realms даёт разные ответы.
Отдельные кэши transport в sing-box помогают разделять DNS servers, но не доказывают
изоляцию всех наших scopes. Смена namespace инвалидирует прежние ответы; DNS server
order может быть значимым, route/address set order — обычно нет.

Negative caching NXDOMAIN/NODATA отличается от SERVFAIL/timeout. TTL/refresh/backoff
не должны закреплять transient failure на весь день и вызывать query storm после
истечения. Более новый RFC9520 обновляет RFC2308: resolution failures, включая
DNSSEC validation failures, тоже требуют bounded failure caching; рекомендация
«никогда не кэшировать SERVFAIL» была бы ошибкой. Это не право выдавать timeout
за NXDOMAIN или переносить failure cache между resolver realms. [D29]
Область RFC — кэширующий/валидирующий DNS resolver; retry-cache внешнего probe или
клиент без DNSSEC validation не становится таким resolver по одному таймеру.
Применять требования через фактический DNS transport/cache API и его semantics.
Serve-stale из RFC8767 повышает доступность recursive DNS при отказе
authoritative, но не разрешает бессрочное `disable_expire`, reuse чужого network realm,
отключение проверки сертификата или принятие отозванного ключа. DNS TTL и trust expiry
имеют разные полномочия. Новый gateway IP получает проверку обычного имени/пина. [D10][D11]

`x/sync/singleflight` уже в module graph: готовое подавление одинаковых in-flight
вычислений, BSD-3-Clause. Оно не ограничивает количество **разных** ключей, не имеет
автоматической отмены leader по timeout waiter; `Forget` допускает новую работу до
завершения старой. Нужны существующие admission/owned result/context fences и
bounded keys; использовать один экземпляр на правильный namespace.

TLS resumption может сократить startup; caches ticket/token привязаны к authority/
policy и ограничены по жизни/памяти. 0-RTT допускает replay: trust mutation, выдача
credential, платёж/отзыв/одноразовый Apply не отправляются как replay-safe early data.
WS `max_early_data` в renderer — другой механизм, его нельзя называть TLS0-RTT.
Pool reuse не продлевает срок сертификата/профиля и не переживает urgent revoke. [D12]

### 13.6. Управление восстановлением без самоперегрузки

Три уровня по3 попытки дают до27 нижних работ вместо3 у единственного retry owner
(M02). У QUIC уже есть PTO/loss recovery; внешний controller, HTTP client и UI
не должны независимо повторять одно действие. Передавать remaining end-to-end
deadline, retry classification и spent budget; auth/revocation/permission/permanent
schema errors не лечатся бесконечным reconnect. Backoff с jitter разносит fleet storm,
но не заменяет caps active operations/bytes/attempts/cleanup. [D03][D13][D14]

Fixed-window «3 в минуту» может пропустить6 на границе окна; token bucket допускает
burst+refill и не тождествен strict rolling bound (M03). В проекте rolling budgets
уже есть — сохранить их смысл. Budget rejection означает local admission result,
не failure удалённого канала. Не возвращать budget после каждого early error:
неудавшийся dial тоже расходует CPU/радио/криптографию.

Сохранять отдельные lanes safety/recovery и optional diagnostics/update/UI history;
добавить предел ожидающих, размер request/result и возможность coalescing без
потери Stop/revoke. «Timeout наблюдателя» не освобождает зависший native owner.
При resource pressure сначала убрать optional/bulk work, а не превратить отсутствие
измерения в quarantine и ещё10 параллельных проверок. Envoy adaptive concurrency —
готовый алгоритмический ориентир для latency/queue feedback; его HTTP minRTT windows
не копируются как доказательство DPI или разрешение direct. [D15]

Сравнивать **выигрыш после цены перехода**. В M08 улучшение35→30ms на горизонте50
действий не окупает500ms переключения;70→30ms окупает при тех же условных входах.
Реальный horizon неизвестен, а старые TCP/UDP sessions могут оборваться. Нужны
hysteresis/minimum dwell/uncertainty и ручной quiet mode; security revoke сильнее
удобства. Recovery от реального отказа не должен ждать декоративного cooldown.

### 13.7. Качество измерения и независимость

Три URL одного origin/CDN/resolver/measurement backend не дают три независимых
голоса. Даже разные VPN transports на одном VPS имеют common-node ceiling: M01
при условных98% node availability даёт97.98775% трём путям, а ошибочная независимая
формула —99.9671491%. Это расчёт с допущениями, не оценка наших VPS. Independence
граф требует provenance и unknown edges; редактируемые веса scoring не вероятности.

Записывать cold/warm DNS/TLS/transport, input size, elapsed stage/bytes/completion,
network/owner/epoch и endpoint dependency; cache hit и keepalive отдельно от cold dial.
Проверять small и bounded bulk **по одному уже установленному соединению**, если
гипотеза касается объёма одной connection; повторная загрузка через новый socket
не проверяет тот же механизм. CDN cache/range/HTTP compression/connection pooling
меняют опыт и фиксируются, чтобы обычный cache miss не объявлялся ТСПУ.

Timeout включать в результат/долю неуспеха; percentile только успешных запросов
может скрыть провалы. Не усреднять p99 разных окон/устройств: нужны counts и
совместимые merged histograms либо отдельные strata (M07). Медленный closed-loop
генератор может перестать посылать новые запросы во время stall и недосчитать
плохую задержку; фиксировать offered rate/пропущенные интервалы/исходный schedule.
Prometheus histogram semantics можно заимствовать без обязательного Prometheus/Grafana
на маленьком VPS. Session IDs/URL query/user app inventory не metrics labels. [D17]

Ноль ошибок в100 независимых Bernoulli опытах ещё допускает≈2.95% failure probability
при односторонней95% границе; в1000 —≈0.299% (M06). Для зависимых ISP/time samples
эти iid-границы неприменимы. Safety доказывается инвариантами и scoped негативными
опытами; finite успешные probes не дают абсолютного «утечек нет».

РФ: использовать матрицу §12.4 и актуальные operator/AS/time strata; отдельные
mobile allowlist, UDP block, IP-prefix loss и volume cutoff. OONI2024 фиксирует
operator-specific reachability anomalies для cloud providers; это основание
измерять **точный** gateway IP, не blacklist каждого немецкого DC навсегда.
2026 USENIX talk о VPN failures — мотиватор независимой проверки, не новое наше
испытание и не сравнительный рейтинг провайдеров. [D24][D25]

### 13.8. Android: батарея и смысл изменения сети

Keepalive, retransmit, health probe, refresh профиля и UI polling — разные работы,
но все могут будить радио.15-second schedule даёт5760 opportunities/day (M11);
это не число фактических wakeups. Бандлировать optional работу, использовать
metered/charging constraints и реальные device измерения. WorkManager не заменяет
VpnService; FCM не требуется для ядра/QR/offline recovery. [D18]

Android SocketKeepalive API29 документирует IPsec NAT-T socket; его нельзя считать
готовым offload произвольного Hysteria/QUIC keepalive. Доступность, интервал и ошибка
hardware support проверяются по API/device. RFC4787 описывает NAT requirements,
не измеренный timeout данного CGNAT.10s library keepalive не универсальный optimum;
его уменьшение/увеличение требует supported API, idle/resume/reconnect/energy опыта. [D19][D20]

Разделить identities: security/owner generation, физический path, resolver context,
стоимость metered/roaming, presentation/quality hints. Более строгая cellular policy
сразу останавливает запрещённые optional bytes; это не обязательно требует убийства
всех рабочих sockets. Изменение маршрута/привязки действительно может требовать
retire. Ослаблять parent/child admission fingerprint без доказанного альтернативного
контракта нельзя. Текущий новый Android fingerprint — WIP/source; исследования
reconnect churn не исправляют его незаметно из этого чата.

При смене сети сначала классифицировать причину/владение/capture, затем применять
нативно поддержанный path update или controlled restart. Отсутствие VALIDATED —
не отсутствие туннеля, а сильный revoke/blocked access не cosmetic hint. Не включать
requestNetwork/вторую SIM/роуминг скрытно ради цифры скорости. Два одновременно
живых native workers и новый exit не становятся seamless handover автоматически.

### 13.9. Windows: барьер, существующие потоки и время

Microsoft best practices советует dynamic WFP sessions для автоматического cleanup,
но именно удаление filters при завершении процесса может противоречить crash-time
strict protection. Persistence, BFE activation и реальный enforcement — разные
свойства. Boot-time и persistent lifetimes документируются отдельно; из них нельзя
вывести непрерывность при runtime BFE failure. Нужны выбранный service/barrier owner,
ограниченные transport exceptions и external observation. [D21]

При отзыве/изменении правил проверять **уже существующие** TCP и односторонние UDP
flows, не только новые соединения. ALE stateful authorization и policy-change
reauthorization имеют свою семантику; недостающие fields при reauthorization не
заменять доверенными values из прошлого. TUN route removal, filter transaction commit
или enum result сами по себе не закрывают эту приёмку. Kernel driver/callout не
проектируется здесь автоматически: сначала supported user-mode возможности. [D22]

Monotonic не означает одинаковую suspend-семантику на любой платформе. Go time docs
предупреждают, что на некоторых ОС monotonic clock останавливается во сне;
Android elapsedRealtime включает deep sleep (§12.6). TTL grant, trust expiry,
measurement freshness и deadline активной работы требуют своих clocks/boot scopes.
После resume нельзя продлить grant, объявить старый proof свежим или сразу породить
все пропущенные periodic jobs. Отдельно проверить запрограммированные timers и
фактическое время callback под CPU pressure. [D23]

### 13.10. Память, маленький VPS и операционная устойчивость

`GOMEMLIMIT` — soft limit памяти, управляемой Go; он не ограничивает весь RSS,
JNI/C allocations, mmap и kernel socket buffers. Слишком низкое значение увеличивает
GC pressure; unlimited pools и число sockets не исправляются одним GOGC. В Android
считать Kotlin+native+Go peak вместе, в Windows — GUI+worker+helpers, на VPS —
core+DNS+служебные процессы.9MiB raw wire превращаются в12MiB base64; три такие копии
уже36MiB без parsed objects (M12), но фактические allocations пока не измерены. [D26]

Лимиты вводить до allocation/fanout: connections/streams/fd/goroutines/threads,
fragment maps, parser depth, image pixels, log/history bytes, distinct cache keys.
Reuse buffer требует clear ownership до последнего consumer; early release ради
latency может испортить ciphertext/профиль. Повторный hash/parse/serialize одного
immutable section можно сокращать только сохранив original-byte/private-proof/CAS
связь. No-backup и bounded size не доказывают power-loss durability или rollback safety.

На Linux VPS различать CPU quota/steal, memory/IO contention, UDP drops и remote
packet loss. PSI показывает время resource stalls; отсутствие PSI/cgroup доступа —
unknown, не «нагрузки нет». CPUWeight/MemoryHigh/MemoryMax/TasksMax/systemd версии —
инструменты будущего controlled resource profile, а не бездумный hard cap: watchdog,
DNS и recovery должны получать ресурсы. Latest systemd docs не доказывают наличие
каждой директивы в Ubuntu24.04. [D27][D28]

Один личный VPS не требует нового distributed control plane. Больше transports
не защищает от неоплаты, disk-full, bad rollout или общего origin. Полезнее сначала
проверенные offline restore/immutable releases/credential rotation, bounded logs,
deadline оплаты с provenance и independent distribution cache. Maintenance/rekey
не начинается на всех gateways одновременно; старый сертификат не оставляется
после явного отзыва ради плавности. После rollback заново действуют source/trust/
path gates; запуск процесса не acknowledgement готовности новой версии.

### 14.1. Уточнение Salamander: дефект выражения и вызываемый метод

Встроенный HY2 outbound sing-box1.13.19 передаёт результат dial в
`bufio.NewUnbindPacketConn`, затем — в `NewSalamanderConn`. У Unbind wrapper
нет `SyscallConn`/`WriteVectorisedPacket`; packet factory проверяет интерфейсы
напрямую и не разворачивает `Upstream`. Поэтому здесь выбирается **обычный**
`SalamanderPacketConn.WriteTo`. Port hopping сохраняет эту цепь для child sockets.
Наличие underlying UDP socket само по себе не включает scatter/gather/GSO/ECN.

Проверены все20 files закреплённого `common/tls`, включая build-tag alternatives.
Встроенные STD/ECH/KTLS configs не реализуют QUIC-specific `qtls.Config`.
uTLS/Reality `STDConfig` явно отвергают такое использование; это не скрытая
альтернативная QUIC-ветка. Этот вывод не означает, что любые TCP-only TLS options
автоматически работают в обычном QUIC STDConfig path.

У inbound raw UDP factory может выбрать vectorised Salamander, но QUIC basicConn
вызывает его `WriteTo`, который передаёт `[salt,payload]` **нижнему** writer.
Собственный `WriteVectorisedPacket` обёртки, арифметика которого проверена M10,
в этой цепи не вызывается. Следовательно, M10 остаётся корректным условным
контрпримером, а воспроизведённого дефекта штатного VPN из него не следует.
Внешний custom caller/изменённое ядро/будущий pin требуют новой проверки.

Оптимизация меняет также ownership: ordinary WriteTo копирует payload, vectorised
WriteTo изменяет его XOR на месте, нижний writer освобождает переданные buffers.
Нужен gate по lifetime/aliasing/error cleanup, а не только исправление индексов.
Scatter/gather одного datagram не тождествен GSO нескольких пакетов.

### 14.2. Готовая QUIC-миграция есть ниже публичного HY2 API

В точном quic-go fork `ccd46a…` есть `Conn.AddPath(Transport)` → `Path.Probe`
→ `Path.Switch`. Комментарий «migration not supported» в обработке preferred_address
не отменяет существующий API. При этом HY2 Client не предоставляет owned Conn/
Transport/path API, а sing-box `InterfaceUpdated` закрывает client с network changed.
Из наличия метода в dependency не следует миграция текущего VPN. [T04]

`Path.Switch` записывает pending path; connection loop применяет его позднее.
Возврат Switch — ещё не receipt применения нового socket и полезной доставки.
В `switchToNewPath` сбрасываются PMTU/RTT/loss state. `MigratedPath` заменяет
установленный CC новым `CubicSender` с `useReno=true`: ранее выбранный HY2 Brutal/
BBR adapter не сохраняется. Новый migration seam обязан явно определить CC policy
после перехода; нельзя обещать прежний алгоритм или скорость по одному Switch.

В HY2 server задан `DisablePathManager=true`: при смене peer address используется
отдельный direct ChangeRemoteAddr path. Нельзя переносить вывод о client migration
CC reset на обычный server port hopping. Это source branch distinction, не оценка
его security/runtime корректности.

RFC9000 различает NAT rebinding и активную миграцию; до handshake confirmation
активный перенос запрещён. Поддержка peer, connection IDs, path validation и reset
path state — отдельные условия. Валидация адреса не доказывает egress/сервис; малая
probe не всегда доказывает minimum MTU при anti-amplification ограничении. [T01]
Новый exit на другом VPS не получает state старого QUIC соединения по совпадению
сертификата. Migration не обещает multipath/bonding или сохранение любых TCP sessions.

Android `Network.bindSocket(fd)` требует unconnected socket. Повторный bind живого
соединения не является готовым способом handover. Нужны supported new-socket/path
API, protect+exact Network bind **до connect**, сохранив fd ownership и policy. [T05]
До такой приёмки нынешний controlled restart остаётся честным fallback внутри
защищённого режима; direct fallback не добавляется.

### 14.3. PMTU: declared capability не равно наблюдаемому свойству сокета

В `wrapConn` значение supportsDF начинается с true. Без доступного SyscallConn
оно остаётся true без вызова setDF в этой функции. На handshake confirmation
MTU discovery запускается по `!DisablePathMTUDiscovery && capabilities.DF`.
Это **не** доказательство отсутствия DF: underlying socket мог быть настроен ранее,
а ОС имеет свои defaults. Но и объявленный DF не доказывает реальную настройку.

У exact packet packer `PackPathProbePacket` добавляет padding до MinInitialPacketSize.
У Salamander добавляется ещё8 bytes; этот wrapper budget учитывается отдельно.
Проверять actual socket flags, wire lengths, outer IP family, PMTU decrease и
последствия смены пути. Не удалять obfs/protect/bind wrapper ради ускорения и не
выдавать PMTU timeout за доказательство DPI. RFC path/MTU semantics остаются
условием, которое проверяется на конкретной сборке и пути. [T01]

### 14.4. UDP очередь ограничена по count, но запись может ждать

Pinned QUIC datagramQueue хранит до32 send frames и128 receive frames. При полном
send queue `Add` блокируется до dequeue либо закрытия общей очереди; контекста
отдельной записи у него нет. `SendDatagram` заранее копирует payload.
HY2 `udpPacketConn.SetWriteDeadline` возвращает `os.ErrInvalid`; read deadline
не ограничивает эту запись. Даже bounded queue не ограничивает число внешних
заблокированных writers и их уже выделенные buffers.

Не оборачивать каждую просроченную запись новой goroutine и повторным SendDatagram.
Сначала trace владельца и фактического завершения, затем bounded admission/bytes/
freshness и поддерживаемая отмена. Нельзя закрыть общую QUIC connection для timeout
одного optional datagram, не определив влияние на другие TCP/UDP users.
Устаревший media datagram лучше отбросить по принятому контракту, чем доставить
после длинной очереди; универсальный срок для произвольного UDP не назначается.
DATAGRAM ACK подтверждает transport processing, не обработку приложения; receive
overflow может сбрасывать payload. Нужны отдельные drop/age/useful-completion facts. [T03]

### 14.5. Таймер ядра, admission и полезное восстановление

HY2 keepalive10s/idle30s из §13 — входные настройки, не жёсткий watchdog SLO.
В exact connection учитываются peer idle timeout и PTO: keepalive interval зависит
от `max(min(configKeepAlive,effectiveIdle/2),1.5×PTO)`, idle deadline — от max(idle,3×PTO).
Keepalive scheduler подавляет повтор по `keepAlivePingSent`; обработка входящего
пакета сбрасывает флаг. Это не ACK receipt прежнего PING и не запрет PTO/path probes.
Планировщик/сон/CPU давление
добавляют задержку. PTO — работа transport recovery, не самостоятельный приговор
«канал заблокирован»; persistent congestion имеет собственные условия. [T02]

Android 3/60 ограничивает replacement admissions, Windows autoretry запускает full
start episode; это не общий cap для DNS races/dials/PTO/probes/channel iteration.
Нужны разные счётчики и один owner внешнего recovery. Смерть child не завершает
зависший parent source/Binder/IO producer: новая работа ждёт actual return.
Конечный child watchdog deadline поэтому не означает конечный service recovery time.

В Windows рассмотренный netwatch пропускает polling при TUN и полагается на
сторожевой probe. Epoch fences отвергают **наблюдённую** смену, но сами не создают
событие о physical transition. Нужна freshness/coverage приёмка, включая no-event
TUN case; это source gap в доказательстве, не воспроизведённый false-connected bug.

Android strict-owner overlay добавляет fresh PackageManager lookups для новых
flows. Они и socket control делят NativeCallbackGate32; порог5s проверяется после
return и не отменяет зависший Binder. При saturation нельзя ускоряться signer-cache/
UID shortcut без сохранения security contract. Проверять setup tails, old/new
flows, Stop/revoke, callback starvation и ICMP/PTB в реальном patched AAR.
Overlay пока не применён/не собран; stock AAR не подтверждает этот путь.

### 14.6. Что переносить и в каком порядке

Переиспользуются exact native QUIC path manager/PMTU/PTO, HY2 factories, текущие
Network leases, retry owners, bounded lanes и scoped observations. Новые transport,
resolver и собственная реализация QUIC не требуются для этих улучшений.

1. TR-01: закрепить method/capability/ownership matrix, включая обычный fallback.
2. TR-05/06: honest freshness и saturation/actual-return recovery contract.
3. TR-04: bounded writers/bytes/age и общий учёт outer-vs-native recovery.
4. TR-02/03: один отдельно выбранный migration/PMTU prototype только после
   API/owner/CC/server gates и разрешения исполнения; controlled restart сохраняется.

Это приоритеты исследований и будущей реализации. Безотказность/превосходство,
прирост Mbps и непрерывный звонок не доказаны чтением исходников.

### 16.1. OP-01 — успешный DNS ответ и свежесть имеют разные значения

PC ProtectedProbe теперь проверяет bounded wire A-answer через HTTPS/SOCKS и
последовательно пробует до3 разрешённых измерителей. Успех относится к одному
DoH exchange, а не к системному DNS, рекурсии до authoritative server сейчас или
общей доступности имён. Query `example.com.` не содержит OPT; отсутствие EDE в
таком ответе не свидетельствует об отсутствии stale/filtering/recovery.

**Новый вывод из стандартов:** HTTP cache age и DNS TTL связаны; `no-cache` не
гарантирует новый authoritative lookup. Serve-stale может законно вернуть старую
запись во время отказа authoritative. EDE может сопровождать даже NOERROR; код
остаётся диагностикой resolver, не доказанным механизмом блокировки. DoH защищает
транзакцию до выбранного resolver, но не делает его утверждения независимой
истиной. EDE EXTRA-TEXT не предназначен для machine classification и может
содержать приватные сведения.

**Решение: adapt существующий typed observation.** Сейчас не добавлять DNSSEC
validator, random per-query name или обязательный EDE. Если нужна именно
проверка cache freshness — отдельный согласованный controlled authoritative
endpoint и бюджет; не приписывать её нынешнему probe. При будущем DNS caching
учитывать Age/TTL; если ответ используется только как observation, отсутствие
полей Age/EDE не объявлять найденной ошибкой кеширования продукта.

**Gate TH-02/RQ-07/08/14, AND-07:** HTTP200+cached/stale DNS, NOERROR+EDE,
unknown/multiple EDE, no OPT, SERVFAIL/negative cache, unavailable authoritative
при живом resolver. Проверять scope/freshness labels и отсутствие ложного
quarantine; не запускать новые authoritative queries по умолчанию.
Первичка: [RFC8484 §5.1](https://www.rfc-editor.org/rfc/rfc8484.html#section-5.1),
[RFC8767](https://www.rfc-editor.org/rfc/rfc8767.html),
[RFC8914 §§2/3/6](https://www.rfc-editor.org/rfc/rfc8914.html).

### 16.2. OP-02 — bootstrap resolver всё ещё отдельный путь

V2-145 перевёл **protected measurement**, но не весь DNS проекта на wire DoH.
В scoped source `corebridge.go` создаёт PreflightResolver для enabled VLESS+WS
hostname до рендера; тот сохраняет UDP стратегии, provider JSON APIs и disk cache
на7 дней. Caller использует IP override, при неудаче продолжает hostname dial.
Это реально найденный call site, но его исполнение/правила WFP здесь не проверены.
Нельзя переносить свойства SOCKS/no-redirect/no-env-proxy protected fetch на этот
`http.Client` с default transport. Фактический proxy/redirect зависит от среды.

В cache entry есть `host/IP/At`; cacheGet проверяет age только сверху и ParseIP.
Следовательно, future At не отвергается самим этим условием; нет явной связи с
network/profile/resolver epoch. Это source gap срока/namespace, а не доказанный
эксплойт или direct leak. Cache TTL7d — локальная retention policy, не DNS RR TTL.
Plain bootstrap lookup может раскрыть gateway hostname; TLS identity сохраняет
другую границу доверия, но не отменяет privacy/availability стоимость lookup.

`publicProbeIPv4 = To4 && IsGlobalUnicast && !IsPrivate` не является полной
IANA globally-reachable policy. Shared100.64/10, documentation и benchmarking
имеют особые назначения; в IANA встречаются и globally-reachable специальные
исключения. Не запрещать всё special-purpose или весь192.0.0/24 одним правилом.
Кроме того, parseable response-address и допустимый dial destination — разные
роли; protected DNS probe не соединяется с каждым возвращённым A.

**Решение: adapt существующий PreflightResolver, не создавать третий resolver.**
Разделить authorized gateway bootstrap, user DNS и measurement. Для bootstrap
требуются owned deadlines/admission, bounded cache read, clock discontinuity/
future timestamp rejection, network/profile/identity provenance, explicit
transport/redirect/proxy policy. IP hint не расширяет подписанные hostname/pin/
destination полномочия. Роль-зависимая address policy получает versioned IANA
snapshot с exact-prefix exception precedence; не обещает actual routability.

**Gate TH-03/RQ-08/09/12/15, COM-07/15, AND-04/05:** poisoned/future/oversized
cache, смена profile/network/host/pins, proxy env/redirect, DNS64/IPv4 literal,
special-purpose samples и stale hint→fresh TLS/owner/protected proof. До измерений
не называть источники независимыми или гарантированно доступными из РФ.
[Go1.26 IP predicate](https://pkg.go.dev/net@go1.26.0#IP.IsGlobalUnicast),
[IANA registry](https://www.iana.org/assignments/iana-ipv4-special-registry/).

### 16.3. OP-03 — portable TUF: конфигурацией diskless режим не получить

Проверены exact go-tuf2.4.2/f5edbde исходники updater/config/trustedmetadata/go.mod,
4 authoritative Git blobs. Утверждения Android ADR-017 подтверждены:

- DisableLocalCache пропускает запись/создание путей, но loadTimestamp/Snapshot/
  Targets всё равно используют loadLocalMetadata→os.ReadFile. Memory Fetcher
  перехватывает download, а не эти чтения; пустой LocalMetadataDir не изоляция.
- GetTrustedMetadataSet возвращает struct value с pointer/map fields, не deep
  owned snapshot и не все original signed bytes. UnsafeSetRefTime назван
  upstream testing helper. Это не отсутствие expiry checks в SDK.
- Lower-level TrustedMetadata имеет **exported instance RefTime**; после New
  его можно установить до update workflow без process-wide clock и Unsafe helper.
  Но этот слой не выполняет сам полный updater workflow/persistence/lookup.
- UpdateTimestamp/UpdateSnapshot могут сохранить signature-verified intermediate
  **до возврата expiry/version error**. Error не означает отсутствие progress.
  Root rotation и rollback-state loading имеют порядок; New(root) self-signature
  check не устанавливает внешнюю authority и не доказывает final-root freshness.

Нынешний PC adapter использует full Updater/private workspace и извлекает
retainedState даже при Refresh error; это существующий source pattern для
progress/application-result разделения. Его временный FS-контракт не превращается
автоматически в memory-only Android API.

| Вариант | Решение и цена |
|---|---|
| Full Updater + memory Fetcher + DisableLocalCache | **Reject как diskless решение:** скрытые local reads остаются |
| Full Updater + явный private workspace | **Reuse PC pattern**, если платформенный owner отдельно принимает FS-контракт; не удовлетворяет текущему запрету ambient/file-I/O автоматически. Нужны CE/no-backup, fixed inventory, ownership, bounded reads/writes/cleanup и exact bytes |
| Pinned TrustedMetadata + узкий portable workflow | **Feasible source seam, conditional adapt.** Криптография остаётся upstream; наш workflow обязан покрыть ВСЕ root/rotation/floors/metadata/target hash/length/delegation-policy/expiry/progress шаги и exact-byte ownership. Это не подпись-only verifier и не выбранный готовый SDK |
| Поддерживаемые upstream Storage/Clock hooks | **Предпочтительный full-updater контракт** для жёсткого memory-only требования; нужен принятый API/patch/version, не предположение о наличии. До него либо отдельно одобренный lower-layer workflow, либо blocker сохраняется |

**Конечный выход исследования:** совместимость требований установлена. В exact
full Updater нет config-only diskless режима; lower-layer даёт instance clock,
но требует отдельной оркестрации. Это конечный architecture decision для AND-04-S4,
а не повод искать случайный compatible SFA HEAD или молча ослабить memory-only.
Рекомендация — согласовать один из двух явных seams до написания adapter:
поддерживаемый full-updater Storage/Clock API либо отдельно reviewed lower-layer
full workflow. Второй AAR, global chdir/clock/logger override, source fork TUF и
UnsafeLocalMode shortcut не выбраны.

**Gate TH-03/AND-04-S4/AND-14:** golden original bytes; expired intermediate
timestamp/snapshot с monotonic retained progress; same-version equivocation;
root/key rotation, missing roles, target length/hash, fixed-start-time и fresh
application commit-time отдельно; no ambient FS/network; one artifact/JNI
provenance. Signature-verified intermediate не разрешает профиль или Connect.
[Pinned SDK](https://github.com/theupdateframework/go-tuf/tree/f5edbde31e5507f46db2069402dc38903fe6d9d4),
[TUF1.0.36 §5](https://theupdateframework.github.io/specification/v1.0.36/#detailed-client-workflow).
Этот анализ не заявляет conformance новой спецификации или готовность SDK.

### 16.4. OP-04 — журнал контроллера не полный аудит VPN

Android SessionJournal уже ограничивает ring128, typed enums, process-local
sequence, parent registration wall/elapsed; дедуплицирует state pairs, сообщает
evictions/exhaustion и не пишет raw config/UID/IP/exception/disk. Это подходящий
existing reuse, а не повод добавлять logging SDK/daemon. Command admission не
равен выполнению команды; state publication не kernel/worker/egress receipt.

**Adapt UI contract:** показывать scope parent/process, границу retained window,
evicted/recordingLimited и отсутствие durable history. Clear не отменяет VPN,
trust floors или уже удержанные snapshots; process restart не доказательство
отсутствия прежней сессии. StateFlow snapshot сохраняет текущую выборку, а не
обязан доставить каждому медленному observer каждое intermediate состояние.
Если потребуется полный forensic audit, это отдельный threat/storage contract,
не расширение retention slider без пересмотра privacy и ресурсов.

**Gate COM-07/12, AND-11/12:** burst>128, slow collector, Clear/rotate/process
death/worker adoption, repeated state, clock jump и held old snapshot; UI не
рисует отсутствующее событие/длительность/полный outage history. Проверять lock
tail/RSS/copies под нагрузкой:128 refs — source cap, не измеренная memory SLO.

### 16.5. OP-05 — privacy до записи и bounded support export

Новые typed observations/journal не означают, что всё приложение перестало
собирать адреса: legacy preflight всё ещё вызывает Logf→App.appendLog с host/IP/
ошибкой. Нужно inventory producers/collectors всех уровней, включая Go/libbox,
HTTP/provider errors, Binder/UI, crash reports и logcat. Здесь прочитан только
исходный поток; реальные пользовательские логи не открывались.

**Adapt allowlist на producer boundary:** typed stage/code/counters/scope/age,
без raw headers/body/URI/token/profile/cert/UID/app inventory. Regex после записи
не удаляет прежнюю копию. Для support export — explicit user action, immutable
review snapshot, видимый состав/объём/time window/dropped count; preview и share
одних bytes. По умолчанию локально, без automatic upload. Нет необходимости
хешировать low-entropy hostname как «анонимный» stable identifier.

Очистка видимой истории, удаление persisted export и cryptographic erasure —
разные операции. Установить честный контракт GC/старых snapshots/выданных URI,
не обещать уничтожение уже отправленного файла. Bounded ring/bytes/queue/format
encoding; logging failure не должен давать direct или останавливать lifecycle.
Версионная schema + synthetic canaries для запретных полей, CR/LF/oversize и
raw exception path входят в будущую разрешённую проверку, не в реальные secrets.

**Gate COM-07/12/13/15, TH-08, AND-08/11/12/14/A-FR-17:** source→UI→export/logcat
inventory, slow storage/share failure/Cancel, old snapshot/Clear и отсутствие
secret fields во всех output sinks. Crash/third-party SDK — отдельный binary
inventory. [OWASP Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html),
[Android log disclosure](https://developer.android.com/privacy-and-security/risks/log-info-disclosure).

### 16.6. OP-06 — first policy SHA и custody нельзя получить из того же пакета

PC V2-144 требует независимо подтверждённые root SHA и cumulative-policy SHA;
это закрывает один cold-enrollment gap. Хеш пакета, полученный тем же путём,
обеспечивает сравнение bytes, но не независимую свежесть. Даже подписанный
baseline не доказывает отсутствие более нового отзыва в мире. Глобально latest
и latest-known-to-custodian имеют разный scope.

**Adapt существующий issuer/transfer UX**, не новый trust protocol: два digest
можно представить одним reviewable public record/QR с явными issuer/purpose/
recipient/scope/as-of/version. Это лишь представление уже обязательных approvals;
не вычислять approval автоматически из inbound bundle. Authority record должен
быть получен по доверенному независимому каналу; QR сам себя не аутентифицирует.
Никакого нового production wire field этим исследованием не вводится.

Custodian receipt хранит exact approved baseline/checkpoint identity, где/когда
проверен и для какой enrollment/recovery операции; publisher backup checksum не
подменяет receipt. Потеря checkpoint/key или uncertain clock → существующий
recovery/blocked, не fresh-install reset старого устройства. Копирование root
без policy и перенос старого private floor должны иметь разные явные outcomes.

**Gate TH-03/07/COM-13, AND-04/13/14:** валидный old package с omitted revocation,
задержанный policy record, same-channel hash substitution, wrong recipient,
ошибка копирования128hex/QR, потеря key/checkpoint и backup restore. UX task:
пользователь понимает, что он подтвердил и откуда взял reference. Тут нет нового
SLO или результата user testing; TUF fixed workflow time не trusted wall clock
и не разрешение позднего application commit.

## 17. Адаптация под неопределённостью: доказательства, причинность и цена решения

а не ещё один список транспортов. Прочитаны current PC V2-146/Android AND-12-S2
snapshots, scoped controller/scoring/health/probe/admission/failover source и
первичные алгоритмы. AD-01…06 — traceability labels уточнений существующих работ.

### 17.1. AD-01 — пригодность определяется набором доказательств, не числом health

Для каждого результата нужен контекст:

`(owner, intent, profile+policy identity, physical path/epoch, required scope,
measurement endpoint/dependency, workload+family, method, start/finish/expiry)`.

Это **целевой evidence contract**, не описание уже существующего полного DTO.
Его следует составить из имеющихся IDs/receipts, не вводить второго session owner.
Значения `unknown/not-supported/not-measured/stale` отличаются от отрицательного
результата. Успех HTTPS/IPv4 не отвечает за IPv6/UDP/голосовую сессию; более новый
узкий тест не сильнее старого широкого только из-за timestamp.

Формально evidence сравнивается по частичному порядку: `e1` может заменить `e2`
только при совместимом контексте, достаточном scope и пригодном сроке. Для required
capabilities `R` нужна совместимая совокупность receipts, а не `max(healthScore)`.
Если используются интервалы пригодности `I_k`, непустое пересечение `∩I_k` и
одинаковые identity/epoch — необходимые условия композиции. Они не доказывают
отсутствие невидимого изменения физической сети; эта неопределённость остаётся.
Нельзя соединять новый DNS receipt с прежними egress/owner фактами другого cutover.

Разделить **допуск к безопасной проверке** и **допуск пользовательского трафика**.
Candidate trial может пройти обычный Start/check только под закрытой защитой;
user-ready появляется после свежего полного gate. Статистическая уверенность,
legacy `live-verified` label или прохождение cooldown этот gate не заменяют.
Freshness detector не продлевает signed expiry/authority/OS permission.

**Gate TH-02/04/RQ-13…15/18, AND-05/07/09:** несовместимые receipts/частичные
families/late publication, физическое изменение между tests, old label+new intent,
timer-only refresh. Для каждого user-facing READY указать actual capability scope
и источник самого слабого обязательного факта; no evidence — не synthetic success.

### 17.2. AD-02 — текущие четыре score-компонента дают меньше информации, чем кажется

По exact `scoring.go` при текущих трёх verdict и обычных входах:

| Verdict | H | F | E | Точный score до сортировки |
|---|---:|---:|---:|---|
| healthy |1|1|1|`0.65 + 0.35·I`|
| no_data |0.5|0|0|`0.15 + 0.35·I`|
| failing |0|0|1|`0.15 + 0.35·I`|

`healthBucket` сортируется **раньше** score. Поэтому внутри каждого current bucket
H/F/E постоянны и C2-порядок определяется I, затем D2/stable tie-break. Это
алгебраическое следствие source, не результат benchmark. Три свидетельства
health/freshness/evidence не независимы: они производны того же verdict.
Настройка их весов сама по себе не добавит информации к текущему C2-ranking.

Ограничение вывода существенно: итоговый выбор не равен одному C2. В failover
сначала фильтруются enabled/legacy live-verified/represented candidates, затем
применяются C2, `orderCandidatesForFailure` и recent-attempt ordering; fresh
switch/protection gates идут отдельно. Нельзя объявить весь controller функцией I
или найденный score-collapse автоматически runtime дефектом.

**Решение: сохранить deterministic baseline**, не подбирать новые «оптимальные»
веса на тех же фактах. Если нужен прирост, добавить действительно новую
source-backed информацию: current workload completion, cost/failure-domain
provenance, measured switch disruption, interval uncertainty. Переход от scalar
independence к dependency graph не делает неизвестные связи независимыми.

**Gate TH-02/04/06/RQ-14/18/20, AND-07/16:** documented candidate-order trace по
всем стадиям, ablation против текущего порядка, разные failure domains/unknown,
неравные sample counts и старые факты. Не заявлять learned probability для score
или улучшение от изменения весов без отдельной matched оценки.

### 17.3. AD-03 — диагностировать нужно и сам измеритель

Lifeguard показывает проблему detector local slowness: здоровый peer может
ошибочно считаться отказавшим. Exact memberlist `awareness.go` реализует
saturating local score и `timeout·(score+1)`; `suspicion.go` дедуплицирует
подтверждения по sender identity и уменьшает soft suspicion timeout с накоплением
подтверждений. Это кластерный протокол, не готовый VPN detector.

**Adapt principle, не cluster engine:** разделить local admission rejection,
local queue/worker starvation, transport setup, resolver/measurement endpoint,
destination service и protection/authority outcome. Таймаут не устанавливает
место проблемы. Новые индикаторы local pressure должны опираться на реальное
admission/wait/actual-return наблюдение, а не новый timer/daemon ради fake CPU score.
Существующие reserved DiagnosticProtected/optional lanes — основа.

При local pressure сокращать optional work и признавать measurement uncertainty.
Можно bounded отложить **soft** suspicion/optional retry; нельзя увеличить trust
expiry, срок пользовательского grant или продолжать READY на протухшем proof.
Если обязательный gate не удаётся обновить, итог определяется protection policy,
а не убеждением «вероятно, завис только детектор».

Envoy различает local-origin и external/transaction errors, а outlier statistics
требуют минимальных host/request volumes. Но его timeout/reset local-origin
означает источник **на стороне proxy**, не доказанную локальную CPU неисправность.
Memberlist unique senders также не означают независимость failure domains.
Нельзя механически превратить3 CDN URLs или3 протокола одного VPS в3 свидетеля.
Envoy panic может выбрать all hosts либо no hosts по policy; поведение,
разрешающее не прошедший safety кандидат, в наш protected controller не переносится.

**Gate TH-02/04/06/RQ-11/12/14/19, AND-02/07/11:** local stall+healthy network,
общий measurement outage, shared resolver/CDN, hard trust revoke при overload,
недостаточный sample volume. Проверять false quarantine вместе с missed faults
и recovery tails: уменьшение ложных тревог ценой бессрочного молчания не победа.
[Lifeguard paper](https://arxiv.org/html/1707.00788v2),
[memberlist pin](https://github.com/hashicorp/memberlist/tree/5cd2c4b0fb09caea5de03aae1adb9c36374ef3e0),
[Envoy outlier](https://www.envoyproxy.io/docs/envoy/v1.38.2/intro/arch_overview/upstream/outlier),
[panic policy](https://www.envoyproxy.io/docs/envoy/v1.38.2/intro/arch_overview/upstream/load_balancing/panic_threshold).

### 17.4. AD-04 — сначала определить измеряемую цель и missing outcomes

Для работы пользователю важнее `P(useful task complete within D | context)`, чем
RTT среди удачных probes. Context включает family/workload/destination/network,
cold/warm состояние и offered load. Deadline D задаётся до сравнения и не меняется
для выигравшего кандидата. Five fast successes out of100 и95 умеренно быстрых
успехов out of100 демонстрируют разницу success-conditioned latency и task success;
это иллюстрация метрик, не измерение продукта.

Хранить разные исходы: planned/admitted/started/completed/failed/timed-out/
user-cancelled/superseded/budget-rejected/not-attempted. Не кодировать последние
четыре как remote-channel failure. Для операционной оценки учитывать end-to-end
время ожидания/восстановления; для причинного анализа отдельно показывать
network stage и local wait. Намеренное исключение aborted samples может создать
survivorship bias. Статистику с timeout нельзя молча трактовать как полный RTT.

История детерминированного winner selection не содержит outcomes невыбранных
каналов; offline оценка иной политики без достаточного coverage неидентифицируема.
Если когда-нибудь понадобятся bandits/off-policy методы, сначала требуется
контракт допустимого exploration и selection probabilities. Из текущего журнала
их не восстановить выдуманным propensity=1. На этапе baseline ML не нужен.

Для будущих paired trials фиксировать workload/deadline/cold-warm/epoch, порядок
A/B и block/ISP/day; не считать100 packets одного outage100 независимыми опытами.
Active probes сами нагружают путь. Envoy отдельно предупреждает, что health-check
traffic искажает minRTT sampling; нельзя оценивать пользовательский cost только
по health probes. Bounded randomized scheduling помогает против синхронизации,
но jitter не гарантирует независимость, репрезентативность или скрытность.

Нельзя ради online сравнения открыть двух lifecycle owners. Если candidate нельзя
проверить изолированно без смены active path, эксперимент проводится в разрешённом
controlled window/лаборатории; quiet mode и safety contract сохраняются.
**Gate TH-02/06/RQ-11/16/18/20, AND-07/11/16:** unequal cancellation/timeout,
непроверенные arms, cold-vs-warm bias, overload от probes, delayed/short/bulk
workload и разные deadline. До paired evidence — descriptive observation,
не причинный вывод «кандидат лучше».
[IPPM methods RFC7799](https://www.rfc-editor.org/rfc/rfc7799.html),
[reactive paths/sampling RFC7312](https://www.rfc-editor.org/rfc/rfc7312.html),
[Envoy concurrency guidance](https://www.envoyproxy.io/docs/envoy/v1.38.2/configuration/http/http_filters/adaptive_concurrency_filter).

### 17.5. AD-05 — повторный просмотр результатов требует отдельной статистики

Fixed-sample95% interval не становится общей95% гарантией, если после каждого
запроса смотреть на него и останавливаться на выгодном результате. Time-uniform
confidence sequences позволяют контролировать ошибку при произвольном stopping,
но тоже требуют названных model/martingale assumptions; произвольная сеть с
меняющейся политикой цензора не становится iid от названия алгоритма.
Первичный результат: [Howard et al., v5](https://arxiv.org/html/1810.08240v5).

**Простой собственный вывод для будущей методики, не выполненный experiment:**
пусть для заранее названных вариантов/strata `i` есть iid bounded outcomes
`X_i,k∈[0,1]` с фиксированным mean `μ_i`; нет selection/censoring bias. Выбрать
`w_i>0, Σw_i≤1` и общий error budget `α∈(0,1)`. Для **каждого sample count n≥1**:

```
δ_i,n = α·w_i / (n·(n+1))
b_i,n = sqrt(log(2/δ_i,n) / (2n))
L_i,n = max(0, mean_i,n − b_i,n)
U_i,n = min(1, mean_i,n + b_i,n)
```

Fixed-n Hoeffding bound ограничивает ошибку на каждом n величиной δ_i,n.
Так как `Σ_n 1/(n(n+1))=1`, union bound даёт:

`P(существуют i,n: μ_i вне [L_i,n,U_i,n]) ≤ Σ_i,n δ_i,n ≤ α`.

Независимость **между событиями просмотра** для union bound не нужна. Но iid/
fixed-mean и корректно собранные observations нужны для использованного
fixed-n bound. Трюк не исправляет biased sampling, коррелированные bursts,
изменение μ, необъявленные новые strata или reset n/α после неудобного результата.
Для более слабых assumptions нужен отдельно выбранный валидный martingale bound,
а не тот же интервал с надписью robust. Это консервативная простая baseline-методика;
modern mixture/empirical-Bernstein boundaries могут быть уже при своих условиях.

**Решение: offline reference/candidate**, не новая production dependency и не
gate безопасности. Author package confseq имеет MIT license; exact README/
LICENSE закреплены, вычислительное ядро и текущие Python/C++ ABI не проверялись.
Перед численным использованием нужны отдельные formula/golden/tail/underflow
и assumption checks. Нельзя заявлять95% uptime/«утечек нет» по этому apparatus.
**Gate TH-02/06/RQ-16/20/FR-012, AND-16:** repeated looks, multiple variants,
partial sampling, drift/change of strata и остановка/перезапуск анализа; явно
указать population/estimand/error budget. Safety proof не p-value.

### 17.6. AD-06 — безопасная адаптация: область допустимого раньше оптимизации

Ввести в целевой contract два различных решения:

1. **Hard safety/lifecycle:** revocation, permission/owner uncertainty, invalid
   authority, protection failure → существующие retire/block/recovery gates.
   Никакой score/confidence/quiet/local-health timeout не покупает обход.
2. **Optional optimization:** только среди допустимых trials, при пригодных
   observations, доступном budget и допустимой цене disruption. Стабильный
   работающий путь не обязан меняться ради маленького неопределённого gain.

Если cost `J` измерен в заранее заданных сопоставимых единицах на задачу,
консервативный proposed switch criterion имеет вид:

`UCB(J_new) + C_switch/H + margin < LCB(J_current)`.

`C_switch` — cost переключения в тех же суммарных единицах; `H` — горизонт задач.
Unknown H/disruption не заполняются удобным числом; сравнение может остаться
inconclusive. Criterion не применяется к срочному safety recovery и не обещает
сохранить существующий TCP/UDP поток. Для повседневных сценариев сначала нужны
измеримые task SLO, не новая универсальная формула utility.

Целевой порядок, собирающий существующие components:

```
event → validate current owner/intent/authority/protection facts
      → hard failure? retain closed barrier; ordinary bounded retirement/recovery
      → classify observation scope + measurement/local-health uncertainty
      → current required proof valid? keep current unless justified optional change
      → eligible trial set → deterministic baseline order + bounded policy budget
      → one owned transition → complete fresh gates → atomic scoped publication
```

Это псевдокод contract, не реализованный ProtectionController/дублирующий actor.
Hysteresis/dwell ограничивают optional churn, но не блокируют Stop/revoke. Все
гейты повторяются после ожиданий/retirement; проигравший/отменённый trial остаётся
ресурсом до actual return. Измерительные consumers не продлевают право публикации.

**Теоретический предел:** можно построить два будущих мира с одинаковыми
наблюдениями до t, где после t ломается соответственно A или B. Causal policy
с одинаковой историей не может заранее выбрать oracle-победителя в обоих.
Следовательно, «всегда самый быстрый/безотказный» не гарантируется алгоритмом
при произвольном неизвестном будущем. Сравнимые требования — safety invariants,
полезное completion/recovery/churn/resource outcomes в объявленном threat/workload
scope и цена ошибок. Это собственный indistinguishable-history аргумент,
не доказательство оптимальности нашей реализации.

**Gate TH-01/02/04/06/08/RQ-11…20, AND-02/07/10/11/16:** alternating path quality,
expensive transitions, quiet+revoke, no eligible candidate, late/blocked returns,
current valid path+inconclusive benefit и genuine outage. Сравнивать baseline и
новую policy по одним scenarios, включая failures/missed faults/false switches;
никакого улучшения скорости до evidence.

## 18. Рецензированный вывод: cache eviction и время жизни заимствованного сообщения

2026-10-26 МСК. **R04-06 принят только как source-факт и условный контрпример**.
[Рецензия руководителя](tasks/THEORY-LAB/reviews/HB01-R04-06.md) содержит exact
inputs, возражения и будущую приёмку. Это не воспроизведённый runtime-сбой,
security severity, измеренная частота или доказанное исправление.

### 18.1. Что проверено

В sing-quic `d83826c306d7c008cafb3fd6d8ee07cbcfd656ed` клиент обрабатывает
DATAGRAM отдельными handlers. Reassembly lookup заканчивается до item.access;
eviction callback этот mutex не берёт. В sing `7c349dacf402256d3a7029746073b05d2ead584a`
удаление expired oldest entry может выполнить callback под cache mutex.
[Client caller](https://github.com/SagerNet/sing-quic/blob/d83826c306d7c008cafb3fd6d8ee07cbcfd656ed/hysteria2/client_packet.go),
[reassembly/pool](https://github.com/SagerNet/sing-quic/blob/d83826c306d7c008cafb3fd6d8ee07cbcfd656ed/hysteria2/packet.go),
[LRU](https://github.com/SagerNet/sing/blob/7c349dacf402256d3a7029746073b05d2ead584a/common/cache/lrucache.go).

Условный trace: borrower A ещё собирает p и индивидуально приостановлен дольше
age; другой handler создаёт q той же живой session и вызывает expiry p.
Callback сбрасывает incoming referenced messages p до окончания A. Их backing
buffer может быть unmanaged: no-op Buffer.Release не отменяет отдельный reset
logical message. Это не утверждение об освобождении памяти ОС или воспроизведённом
повреждении. [Buffer semantics](https://github.com/SagerNet/sing/blob/7c349dacf402256d3a7029746073b05d2ead584a/common/buf/buffer.go).

Нужна индивидуальная scheduling pause, не один глобальный stop-the-world.
Server dispatcher в прочитанной ветке serial, поэтому тот же trace на него
автоматически не переносится. Windows go.mod указывает эти source versions;
наличие соответствующего кода в работающем EXE/whole Android AAR — отдельный gate.

### 18.2. Следствие для ограничений ресурсов

Возраст entry и отсутствие его в cache не доказывают окончание всех использований.
Reclaim/recycle допустим после fencing новых borrowers и actual completion старых,
либо при едином сериализованном owner. Pointer reachability для GC не заменяет
logical lease на переиспользуемый объект.

Лимит видимых entries не является общим memory bound: отдельно учитываются
active, visible, detached, ready и retiring backing storage, без двойного счёта
shared aliases. Admission должен происходить до новых allocations/workers;
таймаут ожидания не возвращает credit за ещё работающего владельца.

Один дополнительный lock в callback нельзя считать готовым исправлением:
cache.mu→item.access и будущий item.access→Delete/cache.mu создадут инверсию.
Варианты для адресного design review — один owner либо detach/borrower accounting
с bounded retired memory и явным lock order. Новый transport/ядро ради этого
не требуется; source adaptation сохраняет лицензионные обязательства upstream.
