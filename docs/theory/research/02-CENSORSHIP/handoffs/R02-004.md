**R02-10.** Renderer Windows создаёт plain VLESS через ShadowTLS3 и validator
освобождает его от собственного TLS, считая ShadowTLS шифрующим звеном.
Actual `sing-shadowtls v0.2.1`, commit `af3279d7446641d5dd2e66cada24ce4597e98d35`,
передаёт post-switch payload с HMAC/framing без шифрования. No-flow VLESS
не добавляет cipher: UUID/destination и plaintext app content остаются читаемыми
наблюдателю client→entry. HTTPS не расшифровывается этим выводом.

Три ключевых raw actual-tag файла совпали с cache по SHA-256. Старый exploratory
pin fcd445d3… не использован как actual evidence. Source chain и protocol intent
согласуются; XOR donor-handshake не является data encryption.

**Предлагаемое применение:** сначала рассмотреть исключение этой композиции
из protected eligibility/default/failover; затем согласовать encrypted replacement
и server/profile migration. Готовые варианты: SS AEAD-2022 через тот же ShadowTLS
(existing core, но нет PFS) либо настоящий verified inner TLS для VLESS (metadata
и camouflage анализировать повторно). Нельзя починить только портом/padding/score.

**Границы:** не доказана активность канала, текущий сервер/профиль не исследован,
live leak не заявлен. Android current graph ShadowTLS отвергает и TLS каждому
принимаемому transport требует; такой же Android bug не утверждается.
Из этой редакции не следует изменение текущего профиля или подтверждение исправления.
