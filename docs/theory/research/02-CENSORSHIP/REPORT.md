# R02-001 — составной fingerprint и независимые контрмеры

**2026-10-25 · READY_FOR_REVIEW.** Приёмка научным руководителем на дату
исходного среза не выполнялась. [Источники/pins](SOURCES.md),
[краткий разбор](handoffs/R02-001.md).

## 1. Вопрос, baseline и новизна

**Вопрос:** какие признаки видны у трёх уже применимых семейств, что меняет
каждая контрмера и где её защитное утверждение перестаёт действовать?

База уже содержит TLS-in-TLS, ограничения padding/mux и Salamander, различие
IP/SNI/UDP filtering, граф отказов, base-rate анализ и E-04. Эти положения
не выдаются за новые. Семейства выбраны по текущему renderer L04:

1. VLESS / WS / TLS / CDN, `/ws`, early data, opt-in h2mux+padding.
2. VLESS / raw TCP / REALITY, Chrome preset, **без flow в текущем рендере**.
3. Hysteria2 / QUIC / Salamander, direct origin, port hopping по descriptor.

Четвёртый descriptor ShadowTLS существует, но не расширяет этот первый срез:
он требует отдельной проверки протокола, хотя использует тот же donor и Chrome
настройку. Его наличие не доказывает независимость от REALITY.

**Новое относительно прочитанной базы:** R02-01 исправляет фактический capability
gap в старом исследовании; R02-02 восстанавливает конкретный wire contract через
слои; R02-03 уточняет условность anti-probing по знанию и стадии допуска.
Последние два — инженерные уточнения и выводы из кода, не открытие нового DPI.

## 2. Модель противника и наблюдения

Рассматривается сетевой наблюдатель, не взломавший устройство/криптографию:

- **O1, access/on-path:** destination IP/порт, TCP/UDP, незашифрованные части
  handshake, размеры/направления/время; видимость может быть односторонней.
- **O2, TLS endpoint/CDN:** дополнительно расшифрованный внешний HTTP/WS.
  Видит VLESS-обёртку, но не получает автоматически plaintext внутреннего HTTPS.
- **O3, активный проверяющий:** возможности O1 плюс свои соединения; результат
  зависит от знания пути, obfs-пароля и разных credentials.
- **O4, противник доступности:** может блокировать целый IP/ASN/carrier/UDP,
  не классифицируя каждый поток как VPN. Допустимый collateral damage неизвестен.

Это модель, не утверждение, что все эти механизмы внедрены каждым оператором РФ.
P07 описывает исторический stateful ТСПУ; P03 — конкретные наблюдения CDN;
P08/P09 — ограниченные полевые сообщения. Ни один источник не устанавливает
универсальную текущую AND-формулу. Классификатор, активная проверка и решение
блокировать — три разные операции.

## 3. Матрица составного fingerprint

| Признак/стадия | WS + TLS + CDN | TCP + REALITY, текущий no-flow | HY2 + Salamander |
|---|---|---|---|
| До application handshake у O1 | TCP к CDN edge; DNS/SNI имени сервиса, если видимы | TCP к origin; SNI донора, а не скрытый destination IP | UDP к origin; внешний пакет обёрнут Salamander, обычный QUIC Initial parser без PSK неприменим |
| ClientHello / стек | Chrome_Auto из pin, затем WS override ALPN=http/1.1; не полный браузер | Chrome_Auto и REALITY-модификация handshake; не тот же wire, что WS | Параметры QUIC/TLS остаются внутри obfs; UDP/размеры/длительность снаружи |
| После внешнего допуска | Шифрованные для O1 bursts; O2 видит HTTP Upgrade, path, headers и early data | За REALITY следует VLESS, затем inner application; flow пустой | QUIC → HTTP/3 auth → proxy streams; внешний obfs не убирает статистику |
| Multiplex/padding | Descriptor включает h2mux+padding; не равен HTTP/2 на CDN-соединении | Только opt-in; не считать свойства Vision включёнными | QUIC streams и auth padding; Salamander сам не делает traffic shaping |
| Что скрыто от O1 | HTTP path/headers/UUID и внутренние данные внутри внешнего TLS | Содержимое proxy payload после handshake; SNI/IP/паттерны остаются | QUIC wire bytes без obfs PSK; QUIC/TLS продолжает обеспечивать собственную криптографическую защиту |
| Что остаётся для составного анализа | IP/ASN/CDN, CH/ALPN, TCP/session reuse, размеры/направления/время | IP/ASN/порт, CH/SNI, bursts/lifetime, множество соединений | IP/ASN/порт, UDP policy, длины datagrams/направления/время, hopping |
| Активная проверка | Контроль website / неправильный path / правильный path + неправильный UUID — разные случаи | Неверный внешний REALITY admission и валидный REALITY + неверный VLESS UUID — разные стадии | Неизвестный/неверный obfs PSK; правильный PSK + неверный HY2 auth; valid auth — три разных случая |
| Общий предел | Carrier целиком может деградировать; вход CDN не заменяет origin/exit | Блок origin/его доступности; работа нового handshake зависит от donor dial U03 | Общий UDP block; доступность origin; смена порта не меняет ASN/VPS |

Это manual source model U01–U04/L04, **не записанный pcap** и не измеренная
точность детектора. Отсутствие ECH в исследованном renderer не заменяет проверку
полного будущего профиля. HTTP/3 без obfs имеет другой wire profile; нельзя
одновременно приписать одному потоку стандартный H3 cover и Salamander scrambling.

## 4. Какие резервы действительно покрывают разные причины

В L04 все три семейства имеют общий origin и ожидаемый exit; REALITY/ShadowTLS
имеют общего donor. L06 уже учитывает provenance/unknowns и не объявляет RankHint
вероятностью независимости. Устаревшую scalar-модель здесь не повторяем как дефект.

| Причина отказа | Кандидат контрмеры | Что остаётся общим / контрпример |
|---|---|---|
| Блок UDP | Проверенный TCP путь | TCP тоже может быть запрещён; неизвестный timeout не доказывает UDP block |
| QUIC Initial/SNI parser | Salamander при доступном UDP | IP/ASN и UDP остаются видимыми; PSK-known наблюдатель отличается от blind |
| Блок direct origin IP со стороны клиента | CDN entry **может** пережить его | Нужны доступный edge и origin со стороны CDN; outage самого origin ломает все |
| Outage/неоплата единственного VPS | Другой работоспособный origin/exit | Новый порт/протокол на том же VPS не помогает; второй VPS того же аккаунта не покрывает account suspension |
| Деградация Cloudflare carrier | Проверенный direct или иной carrier | Иной carrier при том же origin сохраняет origin outage; цена whole-carrier block — не запрет для противника |
| Burst/lifetime detector | Иной проверенный поведенческий профиль | Смена только SNI/CH не обязана менять post-handshake статистику |
| Блок нового handshake donor | Профиль с другим обязательным donor / без donor | Для уже открытого потока зависимость может отличаться; не приписывать outage handshake-домена всем фазам |
| Недоступна доставка профиля | Независимый заранее доверенный recovery route | Транспорт не создаёт новую authority и не снимает expiry; контракт R05/R06 |

Это покрытие **механизмов**, не произведение вероятностей. Другая страна сама
по себе не устанавливает иной ASN/account/publisher/маршрут. Рассуждение о минимальном
наборе резервов должно начинаться с причины отказа и общих обязательных зависимостей.

## 5. R02-01 — Vision поддержан ниже нашего запрета

**Утверждение / source fact.** Тезис «Vision отсутствует в pinned sing-box 1.13.19»
неверен для прочитанного dependency closure. U01 объявляет flow в outbound и users,
передаёт его `vless.NewClient`; U02 принимает `xtls-rprx-vision`, содержит VisionConn
и registry для uTLS под with_utls. Это проверено не по одной современной web-странице,
а по точным pins, совпавшим с локальным module cache.

**Локальное последствие.** L04 не рендерит flow; L05 отвергает любой непустой flow,
объясняя это отсутствием поддержки ядра. L02 и историческая запись V2-031 закрепили
то же неверное основание. В Android L08 поле допускается; L07 ещё не подтверждает
собранный совместимый AAR. Значит, «поддержка ядром», «policy разрешает», «профиль
включает» и «native путь проверен» надо учитывать раздельно.

**Новизна / польза.** Исправляется прежнее отрицательное заключение и становится
виден кандидат без смены движка. Это не рекомендация включить Vision по умолчанию.
Source-only наличие не обещает обход или ускорение; P08 содержит как раз сообщения
о деградации одного класса VLESS+REALITY+Vision в некоторых сетях.

**Reuse и цена.** Уже транзитивный U02, GPL-3.0-or-later; не писать свой Vision.
Опциональный профиль потребует двухстороннего flow contract, совместимых TLS wrappers,
проверки reflect/unsafe зависимости, UDP/XUDP/mux семантики и rollback. `directRead`/
`directWrite` в Vision означают работу с underlying transport connection, а не
разрешение выпускать защищённый пользовательский трафик мимо VPN.

**Контраргумент / falsifier.** В deployed binary могли отсутствовать нужные теги,
мог быть другой core, несовместимый wrapper или сервер без flow. Тогда кандидат
непригоден для того artifact; это не восстанавливает утверждение «кода в pin нет».

**Применение:** TH-05/E-02/03/04/08, AND-01/18. Сначала руководителю исправить
основание в общей теории, разработчикам — отдельный compatibility spike после P0.
Старый запрет не снимать одним изменением строки ошибки.

## 6. R02-02 — Chrome preset не описывает полный wire profile

**Утверждение / source fact + вывод.** В U03 `HelloChrome_Auto` закреплён на
`HelloChrome_133`; U01 по строке chrome выбирает этот preset. Но WS NewClient
при пустом ALPN устанавливает только http/1.1, а TLS wrapper переписывает ALPN
в ClientHello. При отсутствии User-Agent U01 добавляет `Go-http-client/1.1`.
L04 собственный UA не задаёт и включает WS early-data header. Следовательно,
одной строкой chrome нельзя аттестовать браузерный стек или все его признаки.

**Наблюдатель имеет значение.** ALPN ClientHello доступен O1 без ECH; HTTP UA,
path и early data видны O2 после termination внешнего TLS. Нельзя объявлять
заголовок пассивной утечкой через корректный TLS. Сервер назначения внутреннего
HTTPS также не становится автоматически наблюдателем WS-заголовков до CDN.

**Новизна / польза.** В baseline уже сказано «uTLS недостаточно». Здесь найдены
конкретные преобразования между renderer → TLS adapter → WS, определено, кто их
видит, и показано, почему одно имя preset не доказывает разнообразие/сходство.

**Контрпример.** Обычный браузер тоже может делать WebSocket Upgrade через HTTP/1.1;
Go-клиенты бывают легитимными. Эти признаки не доказывают VPN и не дают оценку FPR.
Нельзя «исправить fingerprint» рекламированием h2 для HTTP/1.1 Upgrade или одной
сменой UA. Методы с другой HTTP-семантикой требуют реальной поддержки обоих концов.

**Adapt и цена.** Составить исследовательский паспорт
`observer × phase × core/dep pin × preset/overrides × HTTP behaviour × mux/cover`.
Это checklist для сравнения, не новая authority/schema/оценка в adaptive SDK.
Reuse существующих U01/U03, без клонирования TLS или HTTP stack. Цена — captures,
контрольный corpus и аккуратная актуализация при upgrade, а не гарантированный gain.

**Применение:** TH-05/E-04 и AND-18; Android wire profile выводить из его graph,
сборки и adapters, а не наследовать Windows UA/ALPN как доказанный факт.

## 7. R02-03 — anti-probing условен по знанию и стадии

**Утверждение / source fact + модель.** Неверная credential не определяет один
универсальный отрицательный путь. В U03 провал REALITY admission ведёт к donor
fallback; после успешного внешнего REALITY U02 отдельно проверяет UUID/flow.
В U04 Salamander стоит до QUIC, а HTTP masquerade выполняется внутри QUIC/H3.
Проверяющий без obfs PSK не взаимодействует с тем же HTTP handler, что проверяющий
с правильным PSK и неверным HY2 password. Внутренний HTTP fallback не равен
стандартному HTTP/3 wire cover снаружи Salamander.

**Точная граница из кода.** Для обычного успешного `SalamanderPacketConn.WriteTo`
отправленная длина равна `len(input)+8`: соль плюс XOR того же payload. Там нет
операций fragmentation, length padding, batching или намеренного timing shaping.
Следовательно, этот слой сам не уничтожает длины/направления последовательности;
scheduling/loss/coalescing в других слоях отдельно могут менять наблюдение.
Это не взлом QUIC/TLS и не доказанный классификатор HY2.

**Не переносить доказательство.** P02 измерял TCP-механизм GFW и явно исключал
UDP из его воздействия. Отсюда не следует, что Salamander обнаружен таким же
алгоритмом в РФ. P01 показывает отдельный класс риска, но не доказывает точность
на нашем obfs UDP пути. Разрешены гипотезы, а не готовый диагноз цензору.

**Новизна / польза.** Generic E-04 уже был в плане; дополнение — конкретная
матрица стадий/знания U01–U04 и implementation-level граница преобразования.
Она предотвращает ложные выводы «404 всё замаскировал» и «таймаут значит DPI»,
а также смешение обфускации wire bytes с shaping. Уже известное ограничение
Salamander само по себе не считается новым результатом.

**Контраргумент / falsifier.** Обычный сервис может тоже молчать на мусор;
неверная локальная конфигурация даёт те же симптомы. Наличие различающихся
веток исходника ещё не устанавливает практически различимый remote oracle.
Реальный эффект и цена противника требуют будущего controlled corpus.

**Adapt и цена.** Развить E-04, используя существующие обёртки, без своего crypto
или padding. Дополнительные credential-class cases повышают стоимость стенда;
экспорт должен хранить только labels/результаты, не passwords/UUID/header bytes.
R05 владеет доверительным допуском и custody, R03 — реакцией на неопределённость,
R04 — overhead будущего shaping; здесь формулируется наблюдаемая граница.

## 8. Конечная будущая приёмка — сейчас НЕ запускалась

Только после отдельного разрешения; собственные endpoints, ограниченные объёмы,
никакого массового scanning или probing чужих серверов.

| Case | Положительный контроль | Отрицательный случай / что не следует заключать |
|---|---|---|
| V1, capability | Оба конца с тем же pin/tags и согласованным flow выполняют полезные TCP операции | Unsupported wrapper/flow mismatch должен дать scoped failure без direct; parser PASS не native PASS |
| V2, compatibility | Отдельные no-flow и Vision профили, зафиксированные workload/mux/XUDP semantics | Несогласованный сервер, неправильный UUID, malformed input; default не менять по одному успеху |
| W1, observer | Собственная клиентская запись и TLS endpoint capture позволяют восстановить фактический CH/ALPN/headers | O1 не должен получать HTTP headers из encrypted capture; baseline содержит реальные benign WS/Go clients |
| P1, outer admission | Правильный REALITY admission и UUID | Неверный внешний admission; отдельно правильный внешний + неверный UUID; сравнить response/close/timing с cover |
| P2, HY2 admission | Правильные obfs PSK/auth и полезный ответ | Нет/неверный PSK; отдельно правильный PSK + неверный auth; packet loss и неверная конфигурация — отдельные controls |
| P3, shape | Парные наблюдения обычного Salamander path при фиксированном workload | Сопоставить длины с model +8; не заявлять masking по одному successful handshake |
| F1, причины отказов | Работоспособные подтверждённые TCP и UDP пути | Раздельные UDP block / direct entry block / origin outage / carrier outage; общий VPS не считать независимым резервом |
| C1, сравнение | Held-out дни/сети/benign sessions, зафиксированная цель и цена ошибок | Не подгонять бесконечно fingerprint; малый lab corpus не даёт nationwide FPR/availability |

В каждом случае фиксировать source/build/config revision, оператор/ASN/тип сети,
день и network context, стадию достижения, deadline, полезный исход и unknown.
Ни одна строка таблицы этим исследованием не получила PASS.

## 9. Свежая литература: что пока не заимствуем

[QUICstep, PETS 2026](https://gfw.report/publications/pets26a/en/) — полезный
контрпример универсальности handshake hiding: работа ограничивает модель цензора
и требует доступного QUIC destination. Для доступа к сайтам после миграции
destination видит клиентский адрес; это не наш protected-egress контракт.
Миграция к собственному VPN origin — отдельная архитектура/API-задача, не готовая
возможность текущего HY2. Вывод: reference/defer, не включать direct ради обхода.

[CensorLess, PETS 2026](https://gfw.report/publications/pets26b/en/) — существующее
исследование FaaS carrier; private mode по-прежнему использует VPS. Его результаты
по стоимости не доказывают выгоду при одном пользователе и нашем бюджете.
Artifact/license/provider/trust audit не выполнен; для R02 это кандидат отдельного
исследования, без переноса cloud deployment, crypto или fronting в продукт.

## 10. Предлагаемая вставка руководителю и порядок разработки

**В §5 / рядом с решением REALITY:**

> Уточнение R02-01, 2026-10-25: в sing-box v1.13.19 на pin b5ebaa1f… и
> sing-vmess 3aed1551… присутствует xtls-rprx-vision, включая uTLS adapters.
> Прежнее «Vision отсутствует в ядре» неверно. Текущий Windows renderer сохраняет
> no-flow, а validator запрещает непустой flow; Android allowlist поле принимает,
> native artifact не подтверждён. Reuse-кандидат требует двухстороннего профиля,
> native compatibility и E-02/03/04/08, не default-on и не обещание обхода.

**В §2.4 после uTLS / в E-04:**

> Паспорт маскировки должен учитывать наблюдателя, стадию и knowledge class.
> В текущем WS пути Chrome_Auto означает pinned Chrome133 preset с ALPN override
> http/1.1; HTTP headers и early data видит TLS endpoint, не внешний пассивный
> наблюдатель. REALITY admission и VLESS UUID, а также HY2 obfs PSK и HTTP auth
> проверяются раздельно. Нельзя принять один fallback/timeout за общую
> anti-probing неотличимость. Salamander обычного WriteTo меняет wire bytes и
> добавляет 8 bytes, но сам не делает shaping; TCP-результат GFW2023 не доказывает
> блокировку этого UDP профиля в РФ.

Руководитель решает, принимать ли формулировки; общая теория не перезаписана.

Последовательность предложений существующим владельцам:

1. **TH-05:** исправить capability основание и provenance в документации;
   сохранить историческую запись V2-031 с датированной поправкой.
2. **TH-05 / AND-01/18:** после P0 выбрать ограниченный Vision compatibility
   spike на существующем ядре; валидаторы/renderer/server менять согласованно,
   не путать разрешение поля с готовой реализацией. Разработка здесь не начата.
3. **TH-05/E-04:** реализовать observer/admission матрицу при разрешённом
   тестировании; только затем выбирать поведенческую контрмеру по результату.
4. **TH-07 / R06:** оценить действительно иной origin/account/carrier для
   конкретного отказа. Покупка/развёртывание здесь не выполнялись.

## 11. Предел доказательства и следующий вопрос

Пакет доказывает наличие/ветвление прочитанного source и описывает проверяемые
модели. Он не устанавливает deployed версии сервера, успешный native flow,
current RF detector, безопасность всех ветвей, численный выигрыш или рыночное
превосходство. Прочитанные headers не исполнялись и секреты не извлекались.

Следующий R02-срез после review: объясняет ли **совместное** наблюдение начала
и установившейся сессии больше, чем отдельный ClientHello, и какие доступные
поведенческие контрмеры меняют именно этот механизм при сохранённом protected
egress? Начать с одного принятого пробела, не со смены всех транспортов.
