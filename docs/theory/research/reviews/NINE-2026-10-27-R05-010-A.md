# R05-010-A — рецензия условного пути expired timestamp → returned Progress

27 октября 2026. Отдельная рецензия R05-010-A. Прежние собственные
выводы рецензента о recovery не получают от неё независимого подтверждения.

## Решение и точная область

**ACCEPTED только как source-факты и условный trace для нового timestamp:**
при перечисленных ниже предпосылках rejected по expiry timestamp может
оказаться в `Progress.NextState().Cache["timestamp.json"]`. Текущий consuming
caller с `retain=true` вызывает retention до возврата исходной delivery error.
При этом в рассмотренном вызове **нет нового artifact proof и разрешения
применить обновление**.

**Не принято этой рецензией:** весь пакет A/B/C; обобщение trace на snapshot;
фактический успешный durable write; воспроизведённый lockout, частота/severity,
достижимость проблемного signed input в эксплуатации, дефект криптографии SDK
или обход проверки обновления. Полный normative/OS/adoption audit отсутствует.

Уточнение REPORT §2.5 корректно разделяет pointer, условную попытку записи
и последующее использование. Это исправление scope, не runtime-проверка.

## Условия trace: ничего не создавалось и не подписывалось

1. Есть ранее принятый, корректно сформированный state/root и cache T10;
   root свежий относительно **SDK RefTime**. Новая root rotation отсутствует,
   запрос следующего root завершает цепочку предусмотренным 404 fetcher.
2. Предъявлен **корректно подписанный уполномоченной ролью** новый T1000:
   version 1000>10, snapshot reference S20 не уменьшается, ненулевой Expires
   строго раньше SDK RefTime. Источник такого input и практическая возможность
   его появления **не установлены**. Подделка подписи не предполагается.
3. Strict JSON/role/schema/shape, resource bounds, request, context, source
   state, workspace и все предшествующие prerequisites проходят. Фактические
   OS file operations не проверены; эта предпосылка явно условна.
4. У новых bytes есть единственный соответствующий delivered original;
   отсутствует неоднозначность сериализаций для `boundMetadata`. Нет panic.
   Предшествующие cache entries остаются корректными по shape.
5. Время `now`, переданное проектом, не ниже ClockFloor. Оно не объявляется
   аутентифицированными UTC часами или тождественным внутреннему SDK RefTime.
   Для expiry trace используется именно RefTime, не спорная boundary equality.

Числа T10/T1000/S20 — символические обозначения версий, не данные пользователя
и не исполняемые fixtures.

## Проверенный ход

1. `Updater.loadTimestamp` читает old T10, затем получает new T1000. Подписи,
   тип и rollback/reference проверки `UpdateTimestamp:120–146` предшествуют
   присваиванию `trusted.Timestamp = newTimestamp` на строке 151.
2. `checkFinalTimestamp:163–168` проверяет expiry **после** присваивания.
   При выбранном Expires возвращается ошибка; SDK loadTimestamp возвращает
   её до `persistMetadata:347`. Следовательно, SDK не сохранил новые bytes
   как успешно завершённый timestamp workflow.
3. Проект вызывает `retainedState` после `Refresh()` и **до** проверки
   `refreshErr`: `client.go:150–172`. `GetTrustedMetadataSet` — shallow copy
   структуры с указателями, не журнал завершённых проверок.
4. `boundMetadata` связывает T1000 с действительно доставленными original bytes.
   Этот gate исключает произвольный объект без источника и неоднозначные bytes,
   но не восстанавливает факт успешного final timestamp check.
5. `timestampContinuity` допускает возрастающий version и неуменьшающийся
   snapshot reference; final expiry в этой функции отсутствует.
   `retainedState:51` назначает T1000 в next cache. `State.Validate` и
   `guardMetadataShape` не отбрасывают ненулевой, но прошедший Expires.
6. `PrepareArtifacts:154` создаёт Progress, затем на :171–172 возвращает его
   вместе с refresh error. Ни заполнение proofs на :216–217, ни finalPolicy
   для артефакта не достигаются. `NextState` возвращает clone; `Proof` nil.
7. При `retain=true` и ненулевом progress вызывающий код пытается выполнить
   `retainDeliveryProgress` перед `deliveryErr`-веткой. Проверки source digest,
   anchor/clock, binding, vault ownership и commit fences могут прервать эту
   попытку. Их прохождение и успешный commit на диске **не доказаны**.
8. Независимо от возможности retention исходная delivery error возвращается
   на `update_delivery.go:102–103`. `ApplyUpdate` прекращается на ошибке до
   применения payload. Полученный progress **не разрешает установку артефакта**.

## Контраргументы и почему scope именно такой

**Сильнейшая альтернатива:** lower-level SDK намеренно загружает expired
intermediate timestamp, чтобы можно было сравнить следующего кандидата с его
версией. Это прямо описано в комментарии `UpdateTimestamp:97–102` и не является
само по себе ошибкой библиотеки. Но full workflow §5.4 отвергает **новый**
expired timestamp до его persistence; имя TrustedMetadata не доказывает
завершённость этого workflow шага для любого наблюдаемого указателя.

Возможно отдельное ограничительное правило «сохранять все аутентифицированные
наблюдённые версии ради последующего denial floor». Это иной контракт с ценой
доступности и recovery, а не автоматически принятый TUF predecessor.
Данная рецензия показывает границу, не выбирает новую продуктовую политику.

**Противоположный trace:** invalid signature нового T1000 возвращает ошибку
до assignment; указатель остаётся old T10. Его сохранение как ранее принятого
predecessor допустимо. Запретить всякий progress при любой ошибке — значит
потерять правомерный прогресс, включая ранее принятые стадии. Такой патч здесь
не предлагается и не выполняется.

Потенциальный будущий отказ ниже сохранённой высокой версии остаётся
**условным последствием**: он требует фактической записи и соответствующего
подписанного input. Ни реальная уязвимость, ни её severity, ни частота или
эксплуатационная блокировка пользователя не установлены.
