# R05-001-A/B: допустимый TUF progress после ошибки

Дата независимой сверки: **2026-10-27**. Исходный авторский
[пакет R05-001](../05-TRUST-SAFETY/handoffs/R05-001.md),
[REPORT §§3–4](../05-TRUST-SAFETY/REPORT.md) и существенное ограничение из
[R05-002](../05-TRUST-SAFETY/handoffs/R05-002.md) прочитаны. Авторские файлы
сохраняются; решение ниже не принимает эти пакеты целиком.

## 1. Решение и точная область

| Claim | Решение | Принятая область |
|---|---|---|
| **R05-001-A** | **ACCEPTED: specification + pinned public source** | Внутренняя мутация TrustedMetadata при ошибке не является разрешением сохранять новый offending timestamp/snapshot. Ранее принятая история и допустимый predecessor — другие случаи; root имеет отдельный порядок |
| **R05-001-B** | **ACCEPTED в ограниченной specification/source-model области** | §5.3.11 требует сбросить оба TUF cache — timestamp и snapshot — при указанной ротации ключей timestamp/snapshot. Проверен условный source trace S-only full-key replacement с сохранённым timestamp signer. Текущий дефект Snowden, все варианты ротации и OS recovery не установлены |

Термин «ротация» в проверенном trace означает **полную замену ключей snapshot**
с отзывом прежнего quorum. Обобщения на добавление одного keyID, изменение
threshold, повторное использование key material или цепочку S→S′→S этим
решением не принимаются. R05-002, включая минимальность durable state и выбор
конкретного storage/API, остаётся отдельно **READY_FOR_REVIEW**.

## 3. Почему A подтверждён

В спецификации новый timestamp становится trusted после проверок подписи,
версий и срока (§5.4.2–4), затем сохраняется (§5.4.5). Новый expired timestamp
должен быть отброшен. Для snapshot до сохранения обязательны связь с timestamp,
подпись, версии ссылок и срок (§5.5.2–7).

В pinned lower layer присваивание `trusted.Timestamp = newTimestamp` выполнено
**до** `checkFinalTimestamp`; для snapshot аналогично перед `checkFinalSnapshot`.
Ошибка возвращается после изменения внутреннего объекта. Это намеренно позволяет
загрузить **прежний** cache для rollback protection, даже если его срок истёк
или версия snapshot уже не совпадает с новым timestamp.

Решающая граница — caller. `loadTimestamp/loadSnapshot` отдельно обрабатывают
local cache, а для **нового downloaded** объекта вызывают `persistMetadata`
только после успешного `Update*`. Ошибка expiry нового объекта в эту запись
не проходит. У равноверсионного timestamp отдельный no-change branch, без
сохранения нового тела. `GetTrustedMetadataSet` возвращает копию struct с
указателями/map, а не доказательство завершённого workflow или owned raw bytes.

**Условный контрпример автора подтверждён логически:** прежде принят t10;
подписанный t1000 уже expired к fixed start time. Если сторонний adapter
сохранит его из mutated pointer, он создаст floor1000, которого нормативный
workflow не принимал, и отвергнет последующий обычный t11. Требуются реально
подписанные bytes/достаточный signer; подделка подписи и exploit продукта
этим рассуждением не показаны.

Обратная крайность также неверна: прежний accepted t10 нельзя удалять только
потому, что он теперь expired. И valid t11, уже принятый на своём шаге, не
становится rejected из-за последующей ошибки snapshot, target или приложения.
Исключение — отдельное проверенное основание ротации/reset ниже.

**Root имеет другой порядок.** §§5.3.4–8: dual-threshold, строго N+1, принятие
и запись каждого intermediate root. Срок конечного root проверяется затем
в §5.3.10. Сохранённый root prefix при последующем expiry error поэтому допустим;
это не разрешение нового target. Публичный Go caller повторяет этот порядок.

## 4. Почему B принят только с оговорённой областью

Норма §5.3.11 обеих просмотренных редакций:

> If the timestamp and / or snapshot keys have been rotated, then delete the trusted timestamp and snapshot metadata files.

Условие относится к ключам ролей timestamp/snapshot и стоит **после final-root
freshness check**; оно не зависит от того, хранится ли ключ snapshot онлайн.
Слово «both» в нашем выводе важно: при замене snapshot key недостаточно удалить
только snapshot, потому что версия snapshot хранится также в timestamp.
Одно увеличение root version без такой ротации не даёт этого reset.

**Условный trace на public Go source, без исполнения:**

1. Под R7 ранее принят t5 с `snapshot.version=100`, signer timestamp T.
2. Допустимая root chain даёт fresh R8: snapshot keys S полностью заменены S′,
   timestamp signer T прежний. Root signatures/версии корректны.
3. Publisher выдаёт t6 с `snapshot.version=1`, signed T; новый snapshot1 signed S′.
   Все не относящиеся к reset gates предполагаются успешными.
4. `onlineRefresh` вызывает `loadRoot`, сохраняет R8, затем `loadTimestamp`.
   В просмотренном caller отсутствует отдельная инвалидация T/S cache на этом
   переходе. Старый t5 всё ещё проходит подпись T и загружается.
5. При t6 сравнение `newSnapshotMeta.Version < snapshotMeta.Version` даёт 1<100,
   возвращает `ErrBadVersionNumber` до нового сохранения. Повторная операция
   с R8 и тем же старым cache может повторить отказ.

Норма с выполненным reset допускает перейти к новой metadata-ветке; прочитанный
bare SDK path в этих условиях блокируется раньше. Это **конкретное различие
со spec в объявленных inputs**, не заявление о полном несоответствии библиотеки
и не оценка адаптера Snowden, который может иметь дополнительную логику.

**Сильнейший контрпример к расширению:** прочитанный Python reference case
для snapshot fast-forward recovery меняет **и timestamp, и snapshot keys**.
Если старый timestamp больше не имеет достаточных новых подписей, он не
загрузится, и приведённый t5 barrier не возникнет. Это другой publisher recipe,
не опровержение S-only trace и не доказательство поддержки всех rotations.
Добавление keyID без отзыва старого quorum, dual-signed старый cache и reuse
ключей требуют отдельной проверки. Успешное удаление cache также не гарантирует
невозможность повторно принять старый ещё-valid документ под неизменённым signer.

## 5. Практическое решение и цена

**Уточнить OP-03:** сохраняется допустимый progress конкретного workflow шага,
а не любой intermediate и не всё состояние только после полного успеха.
Одна ошибка не кодирует происхождение объекта. Следующий workflow должен
опираться на согласованную retained history; бесконтрольный повтор того же
mutated Updater противоречит его documented single-Refresh lifetime.

**Reuse** выбранного go-tuf сохраняется. Нужен согласованный boundary для
original bytes, accepted step, root/cache basis и storage result; второй
crypto stack/serializer или универсальный новый journal не требуется по одному
этому выводу. Library `persistMetadata` и последующее чтение файла не являются
самостоятельным доказательством power-loss durability платформы.

TUF reset не обнуляет application epochs, profile/update version floor,
cumulative bans, enrollment/custody или user protection intent. Это отдельные
контракты приложения, не побочный эффект смены доверия metadata-роли.

Цена уточнения: хранение происхождения и проверка переходов/ошибок. Слишком
широкий reset ослабляет antirollback, слишком узкий мешает recovery. Выбор
per-step против per-return persistence и устранение неоднозначных crash cuts
требуют отдельного решения по R05-002. Поля DTO/storage не назначаются рецензией.

## 6. Границы проверки

Проверка выполнена чтением versioned spec и exact public source, включая
error/caller chain и противоположный paired-key case. Криптография, SDK,
тесты, новые fixtures, native crash/power loss и сеть VPN **не запускались**.
Ручной trace не выдаётся за воспроизведение.

Адресат **TH-03 / FR-008/011**, Android — через его владельца. Конечная матрица
future cases помещена в [тематическое дополнение](../../architecture/SAFETY-AND-TRUST.md#tuf-progress-and-reset-2026-10-27).
App/source drift, полная conformance, bound ресурсов/IO и фактическая пригодность
publisher recipe остаются неизвестными. Научное ACCEPTED не меняет product status.
