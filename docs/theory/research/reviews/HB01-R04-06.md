## Ручной контрпример и проверка возражений

Предпосылки: клиентская UDP session остаётся живой; приходят допустимые
фрагменты двух packet IDs p/q этой session; p — oldest entry; разрешена
индивидуальная пауза handler A дольше текущего wall-clock cache-age10s,
при этом другие handlers продолжают исполняться. Bounds на такую паузу
в прочитанном caller не установлены. Это условие модели, не измерение частоты.

1. Последний fragment p принят A: lookup обновил expiry и вернул item;
   A держит item.access, все fragments записаны, но сборка ещё читает их.
2. A приостановлен до завершения чтения. Cache mutex не удерживается A.
3. После expiry handler B получает fragment q и создаёт другое cache entry.
   Oldest p удаляется; callback освобождает messages p без item.access.
4. A продолжает читать те же logical messages после их reset/pool return.
   Таким образом сам item mutex не доказывает lifetime до actual completion.

**Сильные ограничения:** глобальный stop-the-world сам по себе не даёт B
работать; быстрая обработка/другой порядок/отсутствие later fragment могут не
создать trace. referenced=false не сбрасывается release, поэтому вывод относится
к проверенному incoming allocation path, а не любому udpMessage. Память Go
может оставаться достижимой для GC: вывод о нарушении logical ownership,
а не доказанное освобождение physical backing memory в ОС.

Не установлены достижимость конкретной нагрузки из недоверенной стороны,
практический upper bound паузы, конкретный exception, exploitability или влияние
на реальную сессию. Критичность и скорость/RSS/battery не измерялись.

## Принятое архитектурное следствие

Expiry/visible-cache cap не является разрешением reclaim объекта, если есть
borrower. До recycle нужны запрет новых borrowers, detach и доказанное окончание
старых использований; либо единый сериализованный владелец. Detached/ready/
retiring backing storage продолжает учитываться в бюджете, shared aliases нельзя
суммировать как разные allocations. Это требование будущей схемы, не готовый fix.

Просто добавить item.access в callback недостаточно как универсальное решение:
callback идёт под cache.mu; будущий cache.Delete под item.access даст обратный
порядок. Нужны explicit lock order и конечный proof actual retirement.

Следующие адресаты предложения: RQ-03 / TH-06 / COM-12 / AND-11, после P0 и
точного artifact gate. Их статусы/планы и source эта рецензия не меняет.

## Конечная будущая приёмка — NOT_RUN

1. Pause borrower + later expired-ID insertion: один lifetime, recycle только
   после actual completion, корректный terminal outcome.
2. Duplicate/out-of-order/fragment-total change + eviction/close: без двойного
   логического владельца; retained bytes и число workers ограничены до allocation.
3. Новый cache size/janitor/Delete: borrower fencing и согласованный lock order;
   visible-entry cap отдельно от detached/retiring memory и RSS.
4. Раздельные client/server cases и exact native artifact на обеих платформах;
   до/после — useful completion/fault/resource при заранее заданной нагрузке.

scan или исполнения криптографии здесь не было. Общую теорию дополняет только
