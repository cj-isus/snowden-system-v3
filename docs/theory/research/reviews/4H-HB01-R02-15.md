## 2. Стандарт и реализация

RFC8446 §4.1.3 задаёт специальный фиксированный Random для HRR. §4.1.4 требует
supported_versions; соответствие TLS1.3 не означает новый случайный вызов на
каждое соединение. Это свойство стандарта, не дефект TLS1.3.

В reviewed client `streamWrapper.Read` seeding one-shot: `v3_client.go:84`.
Server extracts first frame random через `v3_server.go:74`; HRR не исключён.
Обе стороны используют одинаковую основу. В `client.go:119` и
`service.go:252` задана направленная C-цепочка. Final ServerHello этот seed не
заменяет. Проверка TLS1.3 capabilities в сервере не отбрасывает HRR-константу.
Это source-факт согласованности состояния, а не выполненный handshake.

Ручной вывод: у первого data-предиката одинаковые PSK, seed/direction и payload
дают одинаковый ожидаемый MAC. Криптооперации не выполнялись. Случайные значения
в ранее подписанном ClientHello не дают серверной свежести при повторении этого
же целого input. Проверяющий helper вычисляет соответствие tag, не ведёт здесь
учёт использованных ClientHello. Факт не расширяется на другие версии или внешние gates.

## 3. Проверка сильнейших возражений

| Возражение | Независимая проверка | Ограниченный итог |
|---|---|---|
| Donor TLS Finished делает повтор outer невозможным | Entry code отмечает handshakeFinished после data-HMAC match; собственного donor Finished verification перед этой отметкой в этом path нет | Нельзя переносить весь TLS endpoint proof на отдельный outer admission |
| Закрытие donor всегда отменяет успешный switch | service нормализует recognized closed/cancel/timeout после отметки. Group default собирает ошибки и завершает child context; parent ctx не становится автоматически новым freshness proof | Есть условная source-ветка к handler. Иной error, parent cancellation, timing/order/visibility могут её оборвать; runtime расписание не доказано |
| CachedConn заново проверяет session | Названный Read сначала выдаёт переданный cache; core inbound далее маршрутизирует соединение | Дополнительного универсального freshness gate в этом seam нет; routing/inner acceptance всё ещё неизвестны |
| Strict TLS1.3 решает HRR | HRR — штатное TLS1.3 сообщение, capability helper проверяет negotiated version extension | Одного strict/minimum для исключения принятой seed-проблемы недостаточно |
| Донор/PSK/gates отличаются от модели | Actual deployment не читался | Реальное соединение/эксплуатация не установлены; это обязательный предел |

Следовательно, принимается **условный предикат и source path**, а не universal
successful handler delivery. Во всех предложениях исправления необходимо
сохранять это различие. Для concurrency/IO необходим отдельный разрешённый этап.

## 5. Цена подходов и готовые механизмы

| Подход | Почему рассматривать | Цена / существенный предел |
|---|---|---|
| Отказ HRR в affected outer branch | Устраняет конкретную принятую предпосылку seed-предиката | В рассмотренном API готовый HRR-reject flag не установлен. Нужен отдельный consumer/source design; теряются часть donors/соединений и возможна новая наблюдаемая форма отказа |
| Только выбрать другого донора | Может сократить вероятность HRR в названной среде | Не proof отсутствия HRR на будущих backend/capability изменениях |
| Использовать поддерживаемый verified inner encrypted protocol | Отдельная inner admission может остановить переход к содержимому/target | Both-end identity/profile/server migration и собственные replay/camouflage/PFS условия. Конкретный replacement по этой рецензии не выбран |
| Новый обеим сторонам session binding | Требует явно определить свежий источник, canonical transition и wire agreement | Нельзя поменять seed только на одной стороне или объявить добавленный повторяемый ClientHello достаточным исправлением |
| TLS exporter как готовая магия для donor relay | [RFC8446 §7.5](https://www.rfc-editor.org/rfc/rfc8446.html#section-7.5) даёт TLS endpoint primitive | Рассмотренный entry — relay, не endpoint donor TLS; exporter secret здесь не получен. Это не drop-in исправление текущей композиции |

Scoped notices ShadowTLS/sing/core прочитаны: GPL-3.0-or-later; у core есть
дополнительный запрет использовать имя/создавать впечатление связи без согласия.
Это не полная legal/dependency/binary closure. Public sources сохранены только
для исследования, product reuse/import/dependency update не выполнялись.
Ошибочный session proof не создаёт разрешения на direct fallback или снижение защиты.

## 6. Что ещё остаётся неизвестным

Наличие legitimate HRR transcript, повторяемого первого ответа донора, неизменного
PSK и отсутствие внешнего replay gate — **предпосылки**, не измеренные факты.
Parent lifecycle, routing, inner credentials/cache/key/time, target доступность
и application acknowledgement — следующие независимые условия. Их нельзя
вывести из одинакового MAC-предиката. HTTPS не расшифрован; exactly-once не обещан.

Только future NOT_RUN: HRR/no-HRR и changed key; strict + HRR; alternate relay
errors/cancel/order; cache/route/inner deny; real artifact/native path; effect of
chosen mitigation on compatibility/camouflage. Это список для будущего разрешённого
этапа, не добавленные tests/fixtures и не simulated execution.
