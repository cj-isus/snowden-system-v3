# R05-005 — offline negative knowledge и границы отзыва

2026-10-26. **READY_FOR_REVIEW / NOT ACCEPTED.** Только public primary/reference
и ручной анализ; crypto/OS/provider/network verifier не исполнялся.

## 1. Что уже было известно, что уточняется

THEORY architecture §16.6 уже различает globally latest и latest-known, R05-002
различает purposes/clock intervals. Их новыми находками не считаем. Новый вопрос:
какое конкретно отрицательное свидетельство даёт revocation API/protocol, как
меняется свежесть при profile/scope и где native verifier перестаёт быть pure
explicit-time функцией. Product SDK/real trust state не читались.

Угроза: replay корректного старого статуса, missing/stale cache, неверный issuer/
serial/scope, uncertain clock, потеря новых revocation/floor после recovery.
Отсутствие атаки на transport само по себе не делает старое свидетельство свежим.

## 2. Scope и результат проверки

Предлагаются логические типы, не новые production wire fields:

- `StatusAsOf(scope, subject, issuer, policyRevision, observedAt, evidence)`;
- `Denied(scope, effectiveTime, reason, authorityRevision, evidence)`;
- `Unknown(reason)` — missing/stale/clock/unsupported/IO/wrong scope/authority.

Scope включает соответствующую purpose/domain: OS certificate status, app
signer policy, TUF role/key, profile/epoch, credential/server, recovery permission.
Нельзя переиспользовать OCSP good для разрешения TUF release или профильный
recovery permit для снятия OS signer rejection.

[RFC6960 §2.2/§3.2](https://www.rfc-editor.org/rfc/rfc6960.html#section-2.2):
`good` не доказывает факт выдачи сертификата и не является общей certificate
validity проверкой. Требуются правильный CertID, подпись и полномочия responder,
свежесть thisUpdate и applicable nextUpdate. producedAt — время подписания
ответа, не замена времени известного статуса. Unknown не equivalent good.

Контрпример: валидный ответ good о serial у другого issuer либо recently signed
ответ с древним thisUpdate. Одна проверенная подпись/недавний producedAt ещё не
выполняет нужный status predicate. Это не уязвимость протокола/библиотеки.

## 3. Конечная временная модель

Пусть статус известен на `s`, выбранная policy допускает age≤δ, validity interval
`[s,n)`, а обоснованный текущий clock interval `[L,U]`. Без дополнительных
допусков достаточная проверка во всех возможных текущих временах:

`s ≤ L ∧ U < n ∧ U − s ≤ δ`.

Это собственная формализация worst-case policy, не буквальный алгоритм всех
OCSP implementations. Принятые skew margins/границы nextUpdate задаются отдельно;
их нельзя незаметно умножать каждым wrapper. При unknown upper bound нельзя
вывести конечную максимальную давность из одного wall-clock floor. Старый elapsed
permit не переносится через reboot без принятой continuity модели, как в R05-002.

Удовлетворение δ означает допустимую давность знания, а не линейно согласованное
отсутствие отзыва прямо сейчас. Два мира с одинаковым local evidence и разным
новым внешним отзывом неразличимы offline. Instant global revocation, произвольно
долгая автономность и отсутствие нового trusted input вместе не гарантируются.
Это граница постановки, не основание молча ослабить текущую safety policy.

Сильный counterexample к универсальной проверке «nextUpdate обязателен»:
[RFC6960](https://www.rfc-editor.org/rfc/rfc6960.html#section-4.2.2.1) допускает его
отсутствие; это означает постоянно доступное новое status information.
[Профиль RFC5019 §4](https://www.rfc-editor.org/rfc/rfc5019.html#section-4), напротив,
требует nextUpdate и отказывает при отсутствии. Сначала выбранный profile,
затем условия: optional в ASN.1 не означает разрешение indefinite cache.
RFC5019 допускает pre-produced/cached responses и не требует nonce для каждого
запроса. Отсутствие nonce не объявляется vulnerability; time freshness обязательна.

## 4. CRL: counterevidence против глобального max/вечного union

[RFC5280](https://www.rfc-editor.org/rfc/rfc5280.html#section-5.2.3) задаёт CRL number
для issuer+scope. Delta/base требуют согласованных issuer, scope, key/IDP и
number relationships. Нельзя выбрать global max CRL number между независимыми
issuers или считать отсутствие serial в partial reason scope разрешением.

Статус revoked не универсальный timeless set: §5.3.1 допускает removeFromCRL
в delta после expiry/снятия hold; §5.3.2 отличает invalidityDate от даты обработки
отзыва. Sign-before-published-revocation не доказывает sign-before-compromise.
Долговременную подпись оценивает выбранная policy, не самодельное сравнение
одной даты. Наш отдельный sticky app retirement не снимается автоматически от
PKI hold transition. Точно так же valid app policy не очищает CRL rejection.

Практический вывод — reuse mature provider/валидированный protocol workflow,
не разработка нового CRL merger. Осознанно stricter app ban допустим как
другая policy, но его нельзя называть точным воспроизведением CA semantics.

## 5. Windows: explicit pTime не делает provider герметичным

[CertGetCertificateChain](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-certgetcertificatechain)
различает `CERT_CHAIN_REVOCATION_CHECK_CACHE_ONLY` и
`CERT_CHAIN_CACHE_ONLY_URL_RETRIEVAL`: второе относится также к URL objects для
chain building. Конфигурация одного revocation cache flag не доказывает closure
прочих AIA/CTL/root retrieval paths. WTD flags из R05-004 — другой API boundary.

Документация pTime прямо оставляет trust list/root store/revocation checking
зависимыми от текущего состояния; CRL должна быть current-valid. Следовательно,
native result не portable pure proof только от `(artifact, historicalTime)`.
Contract должен сохранять два факта: проверку portable policy с её явными
inputs и отдельный актуальный OS/provider gate. Не переводить глобальные часы
и не отключать revocation ради воспроизводимого success.

[CERT_TRUST_STATUS](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/ns-wincrypt-cert_trust_status)
различает revoked, unknown и offline/stale. [CertVerifyCertificateChainPolicy](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-certverifycertificatechainpolicy)
возвращает TRUE и при failed policy: проверять ещё `pPolicyStatus.dwError==0`.
Это отличается от `WinVerifyTrust LONG==0`. Вызов завершился и subject принят —
разные результаты. Source продукта на наличие такой ошибки не проверялся;
соответствующего defect claim нет.

## 6. Android, credentials и recovery

APK signing lineage — не публичная CA revocation service и не general OCSP good.
Android current/history identities из R05-004 сохраняются; app signer retirement,
TUF roles и credential revocation имеют отдельные authorities. Новый honest
worker может быть обязан остановить действие после нового принятого запрета,
но механизм не предотвращает first execution злонамеренной замены через
подконтрольный attacker OS signing channel: сохраняется предел R05-004.

Server-side credential revoke и локальная допустимость lease не одно событие.
Offline client не доказывает, что удалённый сервер всё ещё разрешает credential;
server enforcement/error относится к отдельному наблюдению. Проверки VPS тут нет.

Emergency recovery пакет должен иметь независимо доверенное основание для
конкретной purpose, exact artifact/scope и сохраняемую согласованную историю.
Известный deny не снимается старым good/старым root/исторической подписью. При
неизвестной свежести новое действие разрешается только если принятая action policy
действительно допускает такое unknown; default safety не меняется исследованием.
Продолжение ранее adopted bounded grant — отдельное требование, не переименование
нового acceptance в resume. Когда безопасного основания нет, honest blocked и
reviewable recovery action лучше недоказанного «восстановлено»/direct fallback.

## 7. Готовая практика и цена

**Reuse** существующий TUF workflow/платформенные stores и OS provider; не
добавлять custom OCSP/CRL engine. RFC — protocol references (IETF Trust terms),
не лицензия конкретной библиотеки. Windows API implementation не копируется;
ничего не установлено, native support/IO/provider policy требуют будущей приёмки.

**Reference/adapt concept:** [Uptane2.1.0 §5.4](https://uptane.org/docs/2.1.0/standard/uptane-standard)
требует secure/recently attested time; full verification сопоставляет разрешения
Director и Image repositories и сохраняет update state. Это готовая идея
разделения approval, а не источник magical offline freshness. Partial verification
имеет более узкие свойства; один signer на обеих сторонах не даёт независимости.
Весь automotive stack не предлагается внедрять в VPN. Документ exact2.1.0;
лицензия реализации/репозитория не проверена, footer сайта All Rights Reserved:
только ссылка/reference, no source/text wholesale borrowing.

Цена — доставка и хранение актуальных status/chain/policy inputs, ограниченный
допустимый offline интервал, понятный blocked/recovery UX и дополнительная
операционная независимость approval. Bytes/RAM/latency/стоимость людей не
измерены. Назначение произвольного δ числом здесь не сделано.

## 8. Конечные future cases и falsification

Все **NOT_RUN**, fixtures не создавались:

| ID | Case / критерий |
|---|---|
| N1 | Valid OCSP good о неверном issuer/subject → scope rejection |
| N2 | Recent producedAt, old thisUpdate или unknown clock upper bound → не fresh по выбранной δ-policy |
| N3 | Missing nextUpdate → разный outcome согласно явно выбранным RFC6960/5019 profiles, без indefinite default |
| N4 | New same-scope deny, затем replay old good/backup → deny/history не сняты |
| N5 | Delta/base wrong scope/key/reason/number, serial отсутствует в partial CRL → не global good |
| N6 | Hold→removeFromCRL и отдельный sticky application retirement → PKI/app policy различены |
| N7 | Historical pTime и изменённый current OS root/revocation store → результат не объявлен hermetic portable replay |
| N8 | CertVerifyCertificateChainPolicy TRUE, dwError nonzero → rejected policy, не success |
| N9 | Offline cache empty/stale при обязательной current check → unknown/block, без скрытого network/disable flags |
| N10 | Emergency recovery под старым anchor или из чужой purpose, floors выше старого image → reject/approved new path, no reset |

Falsification: новая независимо доверенная информация или реальный secure clock
сужает неразличимые миры — вывод о недоступности freshness тогда может измениться.
Доказанная native enforcement policy может усилить action boundary. Без этого
изменять требования на instant revocation+indefinite offline нельзя. Основной
дальнейший выбор — какие actions требуют какой давности evidence, кто доставляет
её и кто вправе выдать recovery permission. Не новый runtime PASS.
