# R05-004 — от конечного пакета к работающему образу

2026-10-26. **READY_FOR_REVIEW, не ACCEPTED.** Plan-only; исходники и документы
читались, подписи/installer/process/device не запускались. Продолжение ровно
открытой границы R05-003. Новых дефектов product SDK здесь не заявлено.

## 1. Угроза и расположение полномочий

Рассматриваются повреждённый mirror, replay старого корректного выпуска,
подмена файлов между проверкой и применением, частичная установка/утраченный
ответ и ошибочная атрибуция нового процесса. Доверяем ОС/loader/package manager
в выбранной support matrix, существующему проверяющему компоненту и заявленной
модели file/process custody. Kernel/admin compromise, произвольная инъекция
в доверенный процесс и подмена всей независимой истории не решены этим contract.
Даже «локальный атакующий» требует уточнить права: file writer не равен actor,
который может менять память verifier или дублировать его handles.

Раздельные authority: delivery/TUF, OS application signer, provenance builder,
store/installer и emergency recovery. Разные имена ключей не доказывают
независимость: issuer-side gate остаётся частью issuer, если он им управляет.

**Предел расположения проверки:** код, уже полностью контролируемый кандидатом,
не является независимым запретом его первого исполнения. Контрпример: actor
получил допустимый OS signing key/канал, поставил новый APK/EXE и удалил из него
свою TUF self-check. Проверка при старте такого нового кода не гарантирует, что
он не исполнился. Это вывод модели полномочий, не найденный exploit продукта.
Нужен доверенный предшествующий verifier/installer либо внешняя OS/management
policy, контролирующая все входящие в обещание execution channels. Для обычной
consumer установки через сторонний канал такой полной authority у приложения нет.

## 2. Один contract и область доказательства

Для выбранного канала c и intent/generation g разрешение adoption требует:

`ChannelAuthority(c) ∧ FinalArtifactBinding ∧ PlatformAccept(c,OS) ∧ Custody`

`∧ InstalledBinding ∧ ExecutingBinding ∧ CurrentIntent(g) ∧ Readiness(g)`.

Это логические обязательства, не требование создать новый owner/SDK struct.
Они могут обеспечиваться существующими leases, immutable stage и OS transaction.

| Граница | Требуемое основание | Недостаточное свидетельство |
|---|---|---|
| Конечный выпуск | Exact digest/length конечного подписанного artifact или явно утверждённого набора вариантов | Хеш unsigned build/AAB вместо delivered bytes |
| OS signing | Приемлемая проверенная подпись/identity по конкретному OS/API/каналу | Любой CA-trusted signer или найденный в файле cert |
| Staging | Тот же проверенный объект/набор, внешние writers исключены на нужном интервале | Повторное открытие того же имени без continuity |
| Installation | OS outcome согласован с current package identity/version/splits/target | Вызов commit, progress или ранее полученный callback |
| Execution | Trusted loader выбрал соответствующий объект/пару; process incarnation и custody сохранены | Имя процесса, PID, версия из памяти UI или path string |
| Adoption | Новый owner подтвердил требуемую готовность под текущим intent, старый отозван | Успех CreateProcess/наличие окна |

При потере ответа набор возможных installation states сохраняется, как в R05-002.
Заново сопоставить известный session/transaction и фактическую установленную
идентичность; не переименовывать outcome unknown в clean failure или Ready.
Readiness приложения отдельно от доказанного protected VPN egress.

## 3. Windows: PE, подпись и image custody

[Microsoft PE signing](https://learn.microsoft.com/en-us/windows/win32/secbp/understanding-pe-signatures)
прямо различает SIP hash и flat file hash. Authenticode исключает некоторые поля,
включая checksum/certificate structures. Значит, корректная OS подпись не
идентифицирует все bytes конечного EXE. Release digest вычисляется после
финального signing/timestamping; изменение bytes требует нового принятого target
или явно проверенной transformation chain. Самодельная нормализация подписи
для совпадения хеша не предлагается.

[WinVerifyTrust](https://learn.microsoft.com/en-us/windows/win32/api/wintrust/nf-wintrust-winverifytrust):
успех только `LONG == 0`, не HRESULT/SUCCEEDED. Из общей CA trust нельзя вывести,
что это нужный Snowden publisher. Expected identity должна относиться именно
к подписи, прошедшей выбранную policy. Embedded/catalog/multiple-signature
политика должна быть явной; полный enumeration adapter в срезе не проверен.

[WINTRUST_FILE_INFO](https://learn.microsoft.com/en-us/windows/win32/api/wintrust/ns-wintrust-wintrust_file_info)
допускает read handle, но также требует file path. [WINTRUST_DATA](https://learn.microsoft.com/en-us/windows/win32/api/wintrust/ns-wintrust-wintrust_data)
различает revocation flags и `WTD_CACHE_ONLY_URL_RETRIEVAL`: одного
`WTD_REVOKE_NONE` недостаточно для обещания отсутствия network retrieval.
Cache-only ограничивает эту проверку; не подтверждает closure всего приложения
или актуальность неизвестного отзыва. Время/PKI policy не заменяют TUF floors.

[CreateFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)
связывает sharing с уже открытыми handles; delete access включает rename.
Сопоставление VolumeSerialNumber+FileId через [FILE_ID_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info)
различает открытые file objects, но не доказывает неизменность contents.
Нужны права, запрет конфликтующих writes/renames, custody родительского пути,
согласованный handoff и проверенный lifecycle. Не объявляется, что один flag
устраняет reparse/ancestor/handle-transfer races на всех FS.

[CreateProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw)
принимает имя модуля; рекомендуемый explicit full application path устраняет
часть неоднозначности поиска, но не заменяет custody. Возврат происходит до
конца initialization, DLL failure может завершить процесс после успеха API.
[QueryFullProcessImageName](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-queryfullprocessimagenamew)
возвращает path, не digest/mapped-file lease. Хеш bytes уже отображённой памяти
не предлагается как замена: это другой объект относительно исходного PE/loader.

**Closure обещания:** проверка main+helper не доказывает весь исполняемый код.
[DLL search](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-search-order)
включает зависимости, redirection и loaded modules; full path первой DLL не
закрепляет все её dependencies. Выбрать либо узкое обещание main/helper identity
при доверенных OS/runtime dependencies, либо отдельный inventory и OS enforcement
для closure. Референс [DLL security](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-security)
даёт ready search-path primitives; здесь они не внедрены и отсутствующими
у продукта не объявлены.

## 4. Android: final APK set, lineage и наблюдение installation

[APK v2](https://source.android.com/docs/security/features/apksigning/v2) защищает
определённые sections и signed data, не произвольные bytes всего signing block.
Встроенный APK content digest не подменяет flat digest конечного APK.
OS verifier уже содержит anti-stripping/failure guards: после неуспеха имеющейся
v2/v3 проверки нельзя самостоятельно принимать пакет через более слабый fallback.

[v3.1](https://source.android.com/docs/security/features/apksigning/v3-1) задаёт
SDK-dependent rotation: один package может использовать старый signer на старой
ОС и rotated signer на новой. Поэтому expected signer привязывается к OS/range,
lineage и выбранной app policy, а не к одному универсальному leaf fingerprint.

[SigningInfo](https://developer.android.com/reference/android/content/pm/SigningInfo)
и pinned framework PackageManager/SigningInfo различают current signer set и
history. `hasSigningCertificate` означает «был или сейчас подписан» этим cert;
это не утверждение о текущем leaf и не proof отсутствия app-specific revocation.
Мультиподпись — set целиком, не любой совпавший элемент; rotation для него не
поддерживается по этим API. Историческое сходство и текущая authority — разные
predicates. Existing fresh signer probes продукта этим не объявляются ошибкой.

[PackageInstaller.Session](https://developer.android.com/reference/android/content/pm/PackageInstaller.Session)
даёт OS-owned staging, write/fsync/close и sealing при commit. Commit асинхронен,
может требовать user action; все streams должны быть закрыты. Contract выбирает
явный полный package/split set или проверяет inherited set отдельно. Только
base APK не описывает code-bearing splits. Проверка file path до копирования
не связывает автоматически bytes OS session; нужен честный stream/object binding.

`STATUS_SUCCESS` — installation outcome, не VPN readiness. При восстановлении
заново запросить package/signing/version/split observations и открыть новый
process/session generation. [SessionParams](https://developer.android.com/reference/kotlin/android/content/pm/PackageInstaller.SessionParams)
по умолчанию убивает процессы при install, но API34 `setDontKillApp` разрешает
просить сохранение процессов при определённом inherited-split install. Поэтому
installed metadata не универсальный fingerprint уже выполняющегося кода.
User/profile и package incarnation входят в область наблюдения; UID/PID в одиночку
не обозначают вечную installation identity.

Update ownership API34 требует permission, включается при initial install и
по документации заставляет другие installers запрашивать user action. Это не
безусловный запрет другого канала и не независимый cryptographic signer.
Не обещать silent update всем API29+ устройствам.

## 5. Каналы — разные способы исполнить ChannelAuthority

| Канал | Что можно переиспользовать | Обязательный предел |
|---|---|---|
| Windows текущий unpackaged updater | Existing signed target, source/intent, root/image/Job/pair custody и adoption gates | Все native/loader/durability gates ещё требуют evidence; запуск вне updater не контролируется автоматически |
| Windows MSIX | OS package identity/signing/blockmap и conditional runtime integrity | Это смена packaging; service/helper/driver/permissions compatibility не проверена; не вся Store EXE установка является MSIX |
| Android direct signed APK | Final signed APK/set + app delivery policy + OS PackageInstaller/signing continuity | App gate контролирует собственный workflow; сторонняя установка/первый запуск имеют другую authority |
| Google Play/AAB | Play App Signing и package-manager policy | Upload cert отличается от installed app signing cert; AAB bytes не final APK; нужны approved variants/transformer trust либо явно store-owned authority |
| Иной store/managed installer | Явно согласованные signing key/lineage/package и installer policy | Разные ключи могут запретить cross-channel update; один ключ расширяет полномочия взаимного update |

[Play signing](https://developer.android.com/studio/publish/app-signing) и
[bundle FAQ](https://developer.android.com/guide/app-bundle/faq) подтверждают
различие upload/app key и возможность distribution APK из Play. Нельзя проверять
установленный пакет по upload fingerprint. Если требование «каждый байт до любого
исполнения одобрен нашим TUF» обязательное, обычный store-managed channel требует
дополнительного доверенного gate/заранее утверждённых final variants; startup
self-check одна этот пробел не закрывает. Это архитектурный выбор, не disable
platform verification.

[MSIX signing](https://learn.microsoft.com/en-us/windows/msix/package/signing-package-overview)
указывает runtime integrity для non-Store пакетов при соответствующем manifest
и Windows2004+. Не переносить гарантию на любой EXE. [MSIX update policy](https://learn.microsoft.com/en-us/windows/msix/app-package-updates)
блокирует downgrade по умолчанию, но имеет разрешённые override channels;
OS version monotonicity не заменяет собственную security floor. Аналогично
[Android versionCode](https://developer.android.com/studio/publish/versioning)
защищает относительно текущей installed version, не независимой вечной истории.

## 6. Recovery и применение к текущему source

Installation rollback и trust rollback разделяются. После сохранённого нового
trust progress нельзя восстанавливать старый trust cut вместе с файлами.
Если старый binary ниже уже обязательной security floor, простое восстановление
bytes не делает его разрешённым. Возможные стратегии — current-authorized
recovery artifact, отдельно утверждённое bounded exception либо forward-fix
release с новым допустимым OS version/security policy. Повышенный versionCode
сам по себе не доказывает устранение старой уязвимости. Чистка floors/aliases
и обход OS signing не предлагаются; невозможность безопасного offline recovery
фиксируется typed blocked, не скрывается direct fallback.

Windows update_image.go прямо оставляет pair installation unavailable до native
acceptance. update_pair.go уже удерживает writer root при retirement payloads,
получает prospective image acceptance до освобождения root и удерживает original
process/Job/image до OS exit. update_accepted_image.go имеет startup quarantine,
проверку accepted version/helper и installed-pair lease; receipt отсутствует
при initial install и явно не считается release-integrity proof. Это source
факты, не выполненные native гарантии. SDK/backend implementation не читались.

Android AND-14 planned; minSdk29 по плану. AND-06 identity-policy probes и package
churn существуют как отдельная source область; новый installer этим исследованием
не реализован. Не дублировать profile trust gate в APK signer/OS version logic.

## 7. Ready reuse / defaults / цена

**Reuse OS APIs** в собственных исходных platform boundaries, без нового
самописного ASN.1/ZIP/PE/signature verifier. OS implementation не копируется;
runtime/SDK terms и actual binary/build support остаются platform gate.
**Reference/adapt apksig** для host release verification: android-16.0.0_r2,
commit `61f88cbe6f81b4536d1ef124daf3caa4ad014afd`, Apache2. API caller chain
`ApkVerifier.verify()`150→private verify183→containsErrors606→setVerified611.
Положительное основание только `Result.isVerified()`, не отсутствие exception
или первый cert. Builder null/SDK range и anti-stripping guards уже есть.
Default min из APK manifest, max Integer.MAX_VALUE не является доказательством
поддержки всех будущих Android. Для device-specific signer выбирать SDK range
и lineage semantics явно. Current docs v3.2/Android17 не приписаны старому pin.

README позиционирует apksig вне Android device; Java1.8 declaration не доказывает
встраиваемость в APK. Captured generic build.gradle включает cloud signing deps;
не брать весь host toolchain в клиент. Android.bp и CLI caller не загрузились:
нет полного proof transitive IO/size/license closure. Рассмотрены только
успешно захваченные verifier/API sources. Масса/RAM/latency не измерены.

MSIX — **conditional/reference**, не бесплатная смена формата; существующие
pair/native resource полномочия требуют отдельного spike. Новые зависимости,
certificate purchase/trust-store changes и packaging migrations не выполнены.

## 8. Контрпримеры и конечная будущая приёмка

Все нижеследующие cases **NOT_RUN**, fixtures не созданы:

1. Подписать/timestamp после release hash → flat target mismatch; принять только
   final approved bytes. Допустимое PE signature не отменяет mismatch.
2. Валидный CA signer другого publisher или неприемлемый current APK signer
   при подходящей history → reject выбранного app policy, без обвинения OS API.
3. Подмена installed name/ancestor между verify и launch → custody refusal;
   same path/hash report от недоверенного child не заменяет trusted binding.
4. Корректный held image, новый чужой процесс с повторным PID → не adopted;
   сохраняется process incarnation/owner fence.
5. Android v3.1 один пакет на API29 и33+ → разные допустимые current identities
   согласно проверенной policy; неподдержанный OS range → unknown/refuse.
6. Валидный base + чужой/устаревший inherited split → reject whole-set binding.
7. PackageInstaller commit→pending user action→cancel/reboot/lost reply → typed
   pending/unknown с reconciliation, без Ready/floor reset.
8. Install callback успех, но процесс старый при допустимом split path либо
   readiness не достигнута → installed не равно adopted.
9. Play upload cert/AAB digest подставлены вместо delivered signing identity/
   APK set → mismatch/неприменимое ожидание; нужен выбранный channel contract.
10. Cache-only Windows без свежего revocation data → honest unknown по policy,
    не assertion «отзывов нет» и не скрытый online lookup.
11. Bad candidate rollback восстановил старые files ниже raised floor → blocked
    или отдельно разрешённый recovery path; trust progress не откатывается.
12. Pair image правильна, сторонний writable DLL/DCL вне declared closure →
    не выводить whole-process integrity; проверить выбранную narrower promise.

Strongest counterevidence: existing Windows custody уже реализована в source;
OS signing/installer already solve substantial parts; native OS build/FS/managed
policy может укрепить contract. Это снимает диагноз missing guard, но не
подменяет ещё отсутствующую native/device evidence. Самостоятельный opposing
pass — artifacts/opposing-review.md. Научное решение принадлежит руководителю.
