# R05-007 — bootstrap и миграция effective repository policy

2026-10-26. **READY_FOR_REVIEW**, claims R05-007-A/B; не ACCEPTED.
Source/specification и логическая модель. Crypto/tests/fixtures/native не
исполнялись; production SDK и реальные состояния не читались.

## 1. Новый вопрос относительно R05-006

TAP4 готово определяет поиск по mapping, но adopter выбирает саму mapping.
Нужно независимо определить право менять ordered selectors/roots/thresholds,
а затем сохранить его через offline/legacy/mirror и cache migrations.
R05-006 already covers guards, custom exclusion и basic IO. Здесь добавлены
конкретный alias/cache trace, transition contract и точная Hashes.Equal semantics.

### Authority map

| Объект/действие | Источник полномочия | Чего недостаточно |
|---|---|---|
| Initial policy/root enrollment | Независимо подтверждённый baseline через доверенный existing installer/custodian/канал | Hash/QR из того же inbound package |
| Publish content | Enrolled TUF content role в разрешённом scope | Право content signer менять mapping/порог |
| Change effective mapping | Governance, разрешённая уже принятой policy; отдельные условия ослабления/переноса authority | Подпись только ключами, указанными новым кандидатом |
| Rotate repository root | Непрерывность старый→новый root по TUF, правильный scope и current cut | Совпавшее имя repository или self-signed latest root |
| Select mirror/route | Допустимая transport choice для уже принятой authority | Право URL/ASN назначать новые trusted roots |
| Recovery | Отдельное принятое recovery полномочие и purpose; см. будущий срез | Обычный retry, confirm boolean или очищенный cache |

Разные keys/repo names не доказывают operational independence. Контрпример:
два различных корректных keypair лежат у одного скомпрометированного custodian;
он получает threshold2 и может одобрить weakening. Это не duplicate-key bypass:
SDK signature/repo uniqueness guards сохраняются. Honest approver должен проверять
содержание transition, а не автоматически подписывать issuer output.

## 2. Бounded policy identity и bootstrap

Логические элементы принятого cut: policy identity/version, governance baseline,
client capability/schema, repo lineage→trusted state, effective selector semantics,
application purpose/floors, текущий intent/revision. Это информационные различия,
не требование добавить новые wire fields, fifth fixed target или отдельный store.

Кандидат mapping должен быть exact artifact, проверенным действующей authority.
Практический reuse — существующий signed target/approved-policy seam; JSON
NewConfig сам input не аутентифицирует. Предлагаемая связь: текущая policy
разрешает переход от **своего exact identity** к exact candidate bytes и его
capabilities/scope. Правило авторизации берётся из current baseline, не из
новой mapping. При первом enrollment baseline поступает независимо.

Signing existing TUF target и root threshold reuse достаточно как криптографические
примитивы; новый signature protocol не нужен. Но если один content signer также
может заменить все governance anchors, это прежняя authority, не новая защита.
Известная политика, запрещающая ослабление ниже требуемой assurance, не снимается
одним ростом version или новым числом подписей.

Byte identity необходима для prepare/commit связывания; её недостаточно без
зафиксированной semantics. Unknown critical schema/selector/capability → отказ
или explicit unsupported, не молчаливое игнорирование. Равная version и разные
bytes → конфликт, не выбор лексикографически большего hash. Signed targets
нельзя переупаковывать/нормализовать после проверки для получения нужного digest.

## 3. Конкретный alias/cache контрпример

В pinned multirepo initTUFClients формирует metadataDir из LocalMetadataDir и
repoName, затем создаёт updater с supplied bootstrap root. Пусть под именем A
накоплен current root/cache/floors. Новая допустимая по синтаксису mapping
переименовывает ту же authority в B и передаёт прежний bootstrap root; новый
путь B может не содержать истории A. Рост map version и прежний threshold
не переносят историю автоматически.

Это conditional wrapper trace, не exploit нашего SDK. Если platform store уже
выдаёт B сохранённый cut стабильной lineage либо отдельный app floor отвергает
старый target, соответствующее плохое action блокируется. Но native directory
rename сам этого не доказывает. Repo-name traversal guard уже есть и иной вопрос.

Следствие: stable enrolled repo lineage имеет независимую от display name/URL/
cache directory identity. Rename/remove/re-add не означает новую clean enrollment.
Нужны сохранённый cut/retirement record либо эквивалентная гарантия протокола.
Нельзя просто потребовать current-root bytes всегда равными initial-root SHA:
это заблокирует нормальную root rotation. Initial authority identity, current
trusted root и mutable alias — разные сущности.

Ресурсная граница retirement history тоже нужна. При исчерпании нельзя молча
забывать floor; bounded refusal/отдельный approved checkpoint/recovery — явный
вариант. Минимальное число persisted fields без chosen storage protocol здесь
не заявлено; сохраняется conditional argument R05-002.

## 4. Transition state machine — модель, не новый implementation API

| Состояние/шаг | Условия/эффект |
|---|---|
| Current P | Одна согласованная принятая policy и current per-lineage cuts |
| Prepare N from P | Проверить exact predecessor P, current governance, bytes/schema/capability, bounds и effective whole mapping; не активировать N |
| Prepare repository migration | Сопоставить stable lineages, сохранить все applicable floors/caches; новые authorities требуют отдельного enrollment основания |
| Candidate target under transition | При выбранной joint-mode policy проверить P AND N на одном exact artifact/app purpose и нужных current cuts; relabel старого receipt запрещён |
| Commit N | Повторить current source/intent/time/capability checks; durable coherent state согласно platform contract; будущие admissions bound к N |
| Retire P / old owners | Старые prepared decisions не становятся решениями N; старое permission отозвано по принятому lifecycle contract |
| Unknown commit/crash | Сохранять возможные cuts, применять только общий безопасный Gate либо blocked/reconcile; не old-policy fallback ради доступности |
| Same-version fork / wrong predecessor | Не объединять автоматически; нужен новый разрешённый transition/conflict-resolution от текущего cut |

Joint-mode — условный безопасный migration вариант, не обязательная вечная dual
validation: его operational/key/time availability предпосылки надо выбрать.
Численно больший threshold сам по себе не доказывает strengthening при смене
custodians/paths/terminating rules/custom grants. Для fixed bounded target set
можно проверить effective decisions; general language inclusion произвольных
selectors здесь не обещается. Semantic lowering должно быть versioned/approved,
а не следствием OS-specific filepath трактовки.

Свойства при указанных предпосылках: новый mapping не сам себе authority;
известный policy/repo history не уменьшается вне отдельно разрешённых reset
семантик; подготовленный target принят только при тех source/policy identities,
которые реально действуют в момент admission. Историческая подпись не current
authority; valid artifact не installed/executing/adopted.

Local fork detection не даёт global single history. Два изолированных клиента
могут видеть разные допустимые branches; без нового общего witness/authority
input это не исправляется deterministic hash winner. Новый consensus/log здесь
не предлагается. Mirrors могут withholding/lag; coherent per-repo TUF snapshot
не атомарное cross-repo publication.

## 5. Offline / legacy capability matrix

| Client capability | Новый mapping | Безопасное действие / предел |
|---|---|---|
| C0: не понимает обязательный map gate | Может игнорировать TAP4 | Existing trusted upgrade path/внешняя installer policy; не называть client gate enforced |
| C1: парсит TAP4, нет нужной app/custom/semantic capability | Library target agreement недостаточно | Refuse unsupported critical policy или явно отдельный legacy channel contract |
| C2: понимает schema/governance/floors и stable lineage | Может подготовить transition | Current authority+coherent cut+final checks; unknown остаётся typed |
| C3: знает migration/joint mode | Может проверить обе policy на одном artifact | Только при доступных required proofs/current clocks; offline не снимает ни одну сторону |
| Offline capable, chain цела | Возможен catch-up | Сохранённые intermediate roots/policy transitions, bounds, final current validity |
| Offline с пропущенным root/policy link либо expired/unknown prerequisites | Safe automatic catch-up не доказан | Restricted recovery; не jump к self-signed latest и не floor reset |

TUF root rotation reuse — old+new threshold и последовательность N+1. Existing
go-tuf default MaxRootRotations256 ограничивает одну loadRoot попытку, не обещает
catch-up произвольного числа roots за один вызов. Повторные принятые progress
возможны только через настоящий workflow/storage contract; guards не отключать.
Один подписанный min-client field не заставляет C0 читать новый field. Capability
указывает semantics реально работающего verifier/канала, не user-agent строку.

## 6. R05-007-B: точное agreement в Hashes.Equal

Закрыт прежний source gap R05-006: в raw pinned metadata.go:852 Hashes.Equal
возвращает true, если есть общий algorithm и все общие значения совпали.
Он не требует одинакового набора algorithm keys. TargetFiles.Equal488 добавляет
Length; custom исключён. Это compatibility relation, не полная equivalence.

Ручной symbolic trace (одинаковая длина L и один честный файл F):

| Repo | Утверждённые hashes |
|---|---|
| A | sha256=a |
| B | sha256=a, sha512=b |
| C | sha512=b |

A~B и B~C, но A!~C: relation нетранзитивно. При threshold3 порядок B,A,C даёт
одну representative group с3 именами; порядок A,B,C — группу A/B и отдельную C,
без threshold3. Это source/model liveness пример, не исполненный тест.
Группа сравнивается с representative, не со всеми подписанными constraints.

Strongest counterevidence: DownloadTarget→TargetFiles.VerifyLengthHashes проверяет
скачанные bytes; verifyHashes880 проверяет все заявленные sha256/sha512 и отвергает
unknown algorithm. Конструирование несовместимого hash bridge само по себе не
доказывает arbitrary payload acceptance. При корректных byte verifications это
может привести к отказу/разному availability, не к установленному exploit.
Прежние duplicate/conflict guards сохраняются.

Для строгого application agreement: выбрать уже обязательную artifact identity
(например approved manifest SHA256+length), потребовать её явного совпадения у
всех counted approvers, сохранить их полные signed constraints и проверить
actual bytes against каждого нужного target descriptor готовым VerifyLengthHashes.
Не отбрасывать противоречивые extra hashes молча: тогда нельзя утверждать,
что этот approver разрешил bytes. Критические custom facts либо внутри exact
manifest, либо имеют отдельную approved app agreement policy.

Это narrow adapt existing API, не patch стандартной crypto/hash функции и не
назначение обязательной новой product схемы. Цена: больше retained descriptors,
validation/resource bounds и явный rollout compatibility. Никакой экономии RAM
или скорости без замеров.

## 8. Future acceptance — все NOT_RUN

1. Trusted current governance→exact next map→valid capability/current cut→new
   candidate: positive transition; separately test startup/adoption later.
2. New map подписан только своими newly declared keys → reject circular bootstrap.
3. Content signer пытается снизить t/расширить selectors → reject вне governance;
   two distinct keys у одного actor не доказывают independent authorization.
4. New map version выше, но same repository переименован/cache empty → history
   сохраняется по stable lineage или blocked, не clean enrollment.
5. Remove/re-add alias после retired state/history cap → no silent floor loss.
6. Same-version different bytes / wrong predecessor / stale prepared source →
   conflict/refuse, не deterministic winner/relabelled receipt.
7. Strong rule не достиг threshold, earlier/fallback rule слабее → effective
   mapping review обнаруживает неприемлемое расширение authority.
8. C0/C1 получает mandatory schema/min-client field → честный unsupported/legacy
   channel, не «защита включена» на основании опубликованного поля.
9. Offline root chain сохранена в пределах cap→progress/final fresh checks;
   missing link/too many/expired final→bounded retry/recovery без bypass.
10. Approval target соответствует P, current policy уже N либо unknown commit →
    current-source fence/reconcile, без stale accept.
11. A/B/C common-hash trace в двух порядках и разный custom → различить target
    compatibility и exact application agreement; cases не запускались.
12. Malicious inconsistent extra hash → all-required-descriptor byte validation
    отвергает несогласованную approval; no claim о cryptographic break.
13. Windows/Android selector escaping/version различается → semantic guard либо
    restricted approved grammar, не reinterpret signed bytes.

Opposing review отдельно в artifacts. Следующий конкретный срез — восстановление
trust authority при loss/compromise и native credential/store recovery, не
повтор general global-latest невозможности. Acceptance руководителя отдельно.
