# R05-008 — native backup/recovery примитивы: что они доказывают и не доказывают

26 октября 2026. Область R05-001…007 сохраняется. Native действия,
реальные states и SDK не читались и не исполнялись. Факты основаны на
документации, спецификациях и Snowden source.

## 1. Матрица примитивов

| Примитив | Даёт | Не даёт | Recovery-следствие |
|---|---|---|---|
| Windows DPAPI user-scope (CryptProtectData) | Конфиденциальность и привязка к цепочке учётной записи (SID+пароль) | Переносимость: blob не расшифровывается после смены учётки/админского password-reset; экспорт master key вне домена невозможен | Vault после переустановки/нового пользователя **не восстанавливается** ⇒ единственный честный путь — fresh enrollment с явным согласием; floors не «сбрасываются», а переустанавливаются новой сессией доверия |
| Доменный бэкап master keys (AD: ms-PKI-DPAPIMasterKeys; MS-BKRP) | Серверной стороне — восстановление master key через домен | Применимость к автономному consumer Snowden (домена нет) | Граница теории: доменный путь существует, но не является доступной предпосылкой |
| Android Keystore/KeyMint (hardware-backed) | Неэкспортируемость ключа, attestation, invalidation-флаги | Перенос ключа бэкапом: ключ физически не покидает TEE/StrongBox; restore ⇒ новый ключ, старый invalid | «Восстановление» ключа невозможно по построению; восстанавливаться могут только данные ПОД ключом, и их расшифровка требует старого ключа ⇒ резервные копии зашифрованных ключом данных на новом устройстве бесполезны без отдельной re-wrap схемы |
| Android Backup (Auto Backup/D2D) | Перенос app-data по правилам | Перенос keystore-ключей (исключено ОС); Snowden сейчас `allowBackup=false` (manifest:4) — перенос исключён целиком | Если будущий consumer включит backup — правила обязаны исключать trust-состояние, либо restore обязан проходить floor-проверку |
| BiometricPrompt+CryptoObject / setUserAuthenticationRequired | Authentичность присутствия пользователя в момент операции (confirmation подписан keystore-ключом) | Authority на смену доверия; freshness вне момента подтверждения | Это примитив подтверждения согласия, не восстановления полномочий |

## 2. R05-18 — разделение authenticity / freshness / authority на restore-пути

Формализация для recovery без тихого обнуления floors (продолжение R05-002):

1. **Authenticity** блока доверия даётся подписью в TUF-слое (метаданные, R05-006),
   не native-примитивом: DPAPI/Keystore подтверждают привязку к устройству/учётке,
   но не авторство issuer'а.
2. **Freshness** решения не переносима бэкапом: восстановленная копия состояний —
   это срез прошлого. D2D/auto-restore заменяет локальное состояние старыми bytes:
   без внешнего anchoring (server floors, R05-002) восстановление **молча
   откатывает floors** — контрпример к «backup = безопасное восстановление».
   Монотонный floor обязан жить вне восстанавливаемого набора или восходить к
   подписанной позиции, недоступной для отката локальным restore.
3. **Authority** на переход доверия — threshold/миграционная политика (R05-006/007);
   ни DPAPI, ни Keystore, ни BiometricPrompt её не предоставляют: подтверждение
   присутствия ≠ полномочие сменить карту доверия.

**Вывод (R05-18):** native-примитивы образуют слой *custody+presence*, а не слой
*authority*. Любой recovery-план, в котором restore бэкапа сам восстанавливает
trust-состояние, либо (а) неявно предполагает домен/внешний anchor, либо
(б) является тихим floor-reset — что прямо запрещено контрактом R05-002.
Честная минимальная схема: restore восстанавливает только не-key material
(настройки, не-ключевые данные); ключи/floors переустанавливаются fresh consent
(BiometricPrompt/DPAPI-NG presence) + подписанная серверная floor-позиция.

## 3. Отображение на Snowden (read-only dated inputs)

- Windows: vault = DPAPI (windows/app.go, delivery_state.go, sysutil vaultDir).
  После смены устройства/учётки blob невосстановим — совместимо со схемой:
  recovery через повторный import/энроллмент, не через резервную копию blob.
- Android: ключ Keystore AES (`KeyGenParameterSpec`,
  `setUserAuthenticationRequired(false)` — ProfileStoreCrypto.kt:31),
  `allowBackup=false`. Ключ не переносим; данные под ключом на новом устройстве
  требуют re-wrap; отсутствие биометрической привязки означает, что presence-
  confirmation для критичных операций сейчас отсутствует — кандидат на будущий
  seam, не дефект доверия сам по себе.

## 4. Контрпример и цена

Restore-план «скопируем vault.v1.json + keystore-blob в облако» ломается трижды:
DPAPI-блоб не расшифруется на новой учётке; keystore-ключ не экспортируется;
floors откатываются. Рабочая альтернатива дороже: out-of-band recovery secret
(фраза/файл, зашифрованный независимо от устройства) + подписанные floors на
сервере + presence-подтверждение при переустановке. Цена: UX-шаг энроллмента и
хранение recovery-secret; выгода: отсутствие тихих откатов доверия.
