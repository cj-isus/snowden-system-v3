# R05-008 — native backup/recovery примитивы: что они доказывают и не доказывают

Первоначальный срез — **26 октября 2026**; авторский статус — **READY_FOR_REVIEW**.
Ниже согласованы ранняя формулировка, уже сохранённые документы и
[разбор применения к проекту](../../../planning/knowledge-application/sections/TRUST.md#k5).
Это редакторское ограничение вывода, а не принятие пакета целиком.

**Краткий вывод.** Защита ключа, подтверждение пользователя, полномочие на
операцию и непрерывность истории — разные свойства. Резервная копия файлов
сама по себе не гарантирует безопасное восстановление доверия. Однако из
этого не следует единственная обязательная схема с сервером или биометрией.

**Применимость.** Проектирование восстановления после потери ключа, устройства,
учётной записи или состояния. Сначала нужно назвать, что потеряно, что
пережило отказ и какие истории должен различать принимающий решение клиент.

**Ограничения.** Не проверены реальные DPAPI/Keystore-вызовы, устройство,
перенос D2D, backup rules итогового приложения и долговечность хранилищ.
Сохранённые документы не доказывают эти свойства текущего бинарника.

## 1. Матрица примитивов

| Примитив | Что даёт в своём контексте | Чего не следует обещать | Следствие для восстановления |
|---|---|---|---|
| Windows DPAPI user-scope (`CryptProtectData`) | Защиту данных в контексте выбранной учётной записи/машины и параметров вызова | Обычное изменение пароля, административный сброс, новая учётная запись, переустановка и доменное восстановление — разные сценарии. Нельзя объявлять любую смену пароля безусловной потерей данных | Отдельно определить доступность прежнего контекста, recovery-agent/backup-key и способ повторного получения данных. DPAPI не сообщает актуальные полномочия издателя |
| Доменное восстановление DPAPI (`MS-BKRP`) | Пример отдельного пути восстановления с дополнительными участниками и ключами | Наличие такой схемы не означает, что она доступна на автономном ПК Snowden | Указывать необходимые роли и сохраняемые материалы; не добавлять домен как скрытую предпосылку |
| Android Keystore/KeyMint | Неэкспортируемость материала через заявленный API и выбранные условия использования ключа | Нельзя автоматически приписывать каждому ключу TEE/StrongBox, аттестацию, поддержку требуемого флага или возможность расшифровки на другом устройстве | Шифртекст без доступного ключа не равен пустому профилю. Перенос данных требует отдельной схемы ключей/повторного зачисления, если она предусмотрена |
| Android Auto Backup/D2D | Перенос разрешённых данных по правилам ОС и приложения | `allowBackup=false` не является универсальным доказательством запрета D2D на всех target31+ OEM. Правила облачного копирования и переноса нужно различать | Исключить чувствительное состояние по принятому контракту или обрабатывать восстановленную историю с явной проверкой. Итоговые manifest/rules и поведение устройства здесь не проверены |
| `BiometricPrompt` + `CryptoObject` | Аутентификацию пользователя для выбранной операции/ключа при поддерживаемой политике | Успешный prompt не является подписью показанного смысла действия, аттестацией всех ключей или полномочием сбросить историю | Использовать только там, где действительно требуется ручная операция; не делать условием каждого фонового reconnect |
| Protected Confirmation | Отдельный механизм подтверждения конкретных данных при соответствующей поддержке | Его свойства не следуют из обычной биометрической аутентификации. Подписанный скрытый `extraData` не означает, что пользователь видел его смысл | Отдельный [разбор R05-009](handoffs/R05-009.md) связывает отображённый текст, точные данные, текущий запрос и полномочия |

В уже сохранённой документации Auto Backup прямо отмечено исключение:
для части производителей на Android 12+ `allowBackup=false` отключает облачное
копирование, но не D2D. Ранний вывод «перенос исключён целиком» поэтому снят.
Для DPAPI сохранённый пример Microsoft также различает административный сброс
и смену пароля пользователем и допускает отдельный recovery-agent/backup-key.

## 2. R05-18 — разделение authenticity / freshness / authority на restore-пути

1. **Подлинность источника.** Проверенная подпись связывает данные с выбранным
   издателем в рамках цепочки доверия. DPAPI/Keystore защищают локальное владение
   материалом, но не назначают издателя и не заменяют проверку подписи.
2. **Непрерывность истории.** Если атакующий может откатить весь доступный набор
   checkpoint к прежним корректным байтам, клиент без пережившего отказ
   независимого основания не различит «нового события не было» и «событие было,
   но вся память о нём откатилась». Подпись старой копии эту неоднозначность
   не устраняет. Это условие модели, не утверждение, что каждый restore всегда
   откатывает floors.
3. **Актуальность.** Переживший историю anchor ещё не сообщает о недоставленном
   новом отзыве. Честное offline-обещание ограничено названными данными,
   временем и политикой, а не знанием самого нового глобального состояния.
4. **Полномочие на действие.** Согласие человека — отдельный вход. Оно не
   разрешает само по себе обнулить принятый floor, вернуть отозванный ключ
   или принять новую карту доверия.

Основное доказательство непрерывности и варианты допустимых носителей —
[тематическая глава](../../architecture/TRUST-CONTINUITY-AND-AGREEMENT.md).
[R05-010 B/C](handoffs/R05-010.md) сохраняет более поздние условия: отдельная
custody-копия, пережившая запись, аппаратный регистр, доверенный внешний канал
или серверный anchor дают разные гарантии. Они не сводятся к одному серверному API
и не приняты этим редактированием целиком.

## 3. Отображение на Snowden (read-only dated inputs)

Срез 26 октября описывал Windows DPAPI vault и Android AES/GCM store с
`setUserAuthenticationRequired(false)`, `allowBackup=false`. Это описание
прочитанных тогда исходников, не проверка установленного приложения сегодня.
Применённый security level AES здесь неизвестен; отсутствие запроса StrongBox
не доказывает software-only реализацию.

В [разборе применения K5](../../../planning/knowledge-application/sections/TRUST.md#k5)
уже отмечено, что store различает отсутствие ключа, незавершённое зачисление
и неопределённую транзакцию. Существующий Windows recovery-permit относится
к восстановлению envelope при сохранном checkpoint, а не ко всей потерянной
истории. Эти границы нужно сохранять, не создавать новый alias на ошибке чтения
и не превращать тайм-аут в разрешение удалить историю.

## 4. Контрпример и цена

Копия шифртекста может оказаться бесполезной на другом устройстве без ключа.
Копия целого прошлого trust-state может скрыть более позднюю принятую историю.
Это два разных отказа; устранение одного не доказывает устранение другого.

Возможные решения используют уже существующие custody/store/recovery границы.
Если выбран независимый recovery-secret, это дополнительное хранение и UX.
Если выбран сервер, это отдельная зависимость доступности и доверия; старый
подписанный ответ не становится актуальным от нового consent. Аппаратный или
внешний anchor имеет собственные требования поддержки и эксплуатации.
Ни один вариант не объявляется единственно правильным до выбора модели отказа.

Практический маршрут — [план ПК](../../../planning/knowledge-application/PC-PLAN.md)
и [план Android](../../../planning/knowledge-application/ANDROID-PLAN.md):
доверие/хранение/восстановление прежде дополнительных prompts и сервисов.
Лицензии платформенных API не заменяют проверку выбранных библиотек и артефактов;
измеренных затрат CPU/RAM/энергии или обещанного RTO здесь нет.

## 5. NOT_RUN

Native DPAPI/Keystore/BiometricPrompt-вызовы, реальный restore/D2D, проверка
итоговых backup rules, power-loss/долговечность и выбранная out-of-band схема
не выполнялись. Это будущие границы приёмки, не новые поручения на исследование.
[Источники Z](SOURCES.md#sources-r05-008) сохраняют точные ссылки и ограничения
сохранённых представлений; runtime и отдельное научное принятие остаются открытыми.
