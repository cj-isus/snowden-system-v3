## Главный новый вывод и сильнейший контраргумент

Для automatic recovery мало сохранять latest root и неатрибутированный cache:
нужна информация, различающая **старый floor с незавершённым reset** и тот же
record, **принятый уже после reset**. Она может быть данными context/frontier,
durable log либо гарантией atomic протокола, исключающего неоднозначную историю.
Вечный BLOCKED обходится без полезного state, поэтому «минимум» определён
относительно обязательных положительных recovery веток, а не safety одной.

**Сильнейший контраргумент принят:** pinned Python reference test source для
snapshot recovery использует совместную ротацию T/S. Ограниченный publisher
recipe может исключить S-only ветку и сократить требуемое дополнительное state.
Нужно подтвердить invalid old quorum/cache under new authority, отсутствие
достаточных новых подписей в старых cached records и key-material reuse.
Нельзя назвать recipe поддержкой всех lawful переходов или считать такой
контракт уже проверенным в нашем publisher/SDK.

## Дополнительные результаты

- Unknown commit описан множеством возможных cuts; действие должно проходить
  **полный** Gate в каждом из них, а не выбираться по score/confidence. После
  потери ответа возможен committed D без adopt; rollback следующего A не должен
  отменять уже подтверждённый P.
- Pure single-return verifier, hard crash до возврата и per-root durable
  persistence нельзя обещать одновременно. Для последнего нужен явный
  step/barrier seam либо approved иной storage contract; crypto не переписывается.
- Purpose до вычисления minimum deadline: TUF import, preparation freshness и
  runtime authority различаются. Новая трактовка не разрешает клиенту продлить
  уже выданный short grant. Clock floor без upper-time assumption не даёт UTC freshness.
- Existing platform stores — первый reuse. bbolt1.5.0 MIT — pinned reference/
  условный кандидат; SQLite — reference режимов transactions, без выбранного
  binary/driver pin. Никакая зависимость не добавлена и migration не предложена.

1. **TH-03 / AND-04-S4b T05…11:** требуем все lawful переходы выбранной spec или

2. **Trust/platform contract:** per-step persistence или per-return progress?
   Должен быть достижимый API/caller barrier, не формулировка без носителя.
3. **Clock/renderer:** какие authority bounds применимы к каждому purpose и
   какие storage/clock adversaries входят в обязательную гарантию?
4. **Windows/Android:** после решения адресно mapping cut в существующий
   journal/encrypted CAS; затем отдельно разрешённые T1…T11 и K0…K7 cases.
   Этот пакет не закрывает TH/FR/AND product gates и не меняет чужие планы.
5. **R03:** hard admissibility перед score; неизвестность store/clock не budget
   для unsafe action. **R06:** сохранить UI различие stored/uncertain/admitted,
   custodian/prepared recovery вместо кнопки очистки floor. Общение через руководителя.
