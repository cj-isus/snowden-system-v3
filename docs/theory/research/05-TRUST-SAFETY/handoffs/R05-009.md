# R05-009 — Key Attestation, операция и подтверждение

**27 октября 2026 · READY_FOR_REVIEW**, не ACCEPTED и не продуктовый PASS.
[Полный анализ](../REPORT-009.md) · [Источники, reading scopes и pins](../SOURCES-009.md).

## Краткий итог

Key Attestation, авторизация конкретной key operation и Protected Confirmation
доказывают **разные predicates**. Текущий checkpoint AES Snowden не является
аттестованной парой ключей и намеренно не требует per-use authentication.
Для дополнительной assurance критического manual действия нужен отдельный
policy-selected signing workflow; ни его подпись, ни fresh consent не заменяют
current authority, replay gate или свежесть статуса отзыва.

## Адресное предложение вместо продуктовой реализации

Android owner/TH-03/TH-08 — адресаты, **не закрываемые здесь requirements**.

1. Сохранить current storage-key policy для unattended recovery.
2. Если выбран critical manual scenario с strong consent, отдельно определить
   required authentication/confirmation/security-domain support и signing-key
   policy; metadata/presence не выдавать за новый root-authority grant.
3. Explicit unsupported/as-of/unknown/error сохранить в UI/логическом contract;
   обычный dialog не получает label protected confirmation автоматически.
4. Готовую библиотеку рассматривать как source-pinned candidate с named caller,
   а не готовый proof end-to-end или незаметную новую зависимость Android.

Для общей architecture главы предлагается короткая вставка в REPORT §8,
но главы/индексы/чужие STATE этим автором **не изменены**.
