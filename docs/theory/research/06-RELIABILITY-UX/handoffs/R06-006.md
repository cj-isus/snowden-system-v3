# R06-006 — рабочий authenticated proxy при strict VPN и важной сессии

Дата: **2026-10-26**. Статус: **READY_FOR_REVIEW**, не ACCEPTED/product PASS.
[REPORT §25…30](../REPORT.md), [SOURCES §7](../SOURCES.md).

## Новое сверх общего corporate/LAN/captive-portal caveat

1. Browser/PAC/SSO availability, proxy authentication, VPN consent/authority,
   protected egress и app outcome раздельны. Transport-owner bootstrap→P для E
   не равен user direct grant. Exact temporal prerequisites/cuts дают action
   barrier при unsupported scheme/permissions/CONNECT/bootstrap cycle.
2. Actual Windows Snapshot→engine start→local SOCKS mutation→probe/Restore
   не реализует upstream corporate auth. Static S0→S1→external S2→Restore S0
   показывает lost-update conflict; PAC delete failure игнорируется. Не live
   incident/частота и не общий security scan; нужен owner/conflict/readback contract.
3. HTTP building block — TCP CONNECT/Basic, не NTLM/Negotiate/PAC drop-in.
   Outer UDP и inner datagrams не смешиваются. Android proxy fingerprint и
   Builder.setHttpProxy recommendation не transport proxy connector.

## Польза и границы UX

До optional вмешательства в живую call/RDP session — совместимость/authority;
далее конкретное доступное действие: supported proxy auth, IT либо другая
разрешённая сеть. Не спрашивать password, если challenge/scheme не установлены.
Один смысловой status/action/cancel, keyboard/assistive access; background auth
не ворует focus. Это usability hypotheses, не user-tested design.
Quiet intent не подавляет hard revoke/expiry/Stop; proxy200 не protected egress,
не миграция всех flows и не remote transaction acknowledgement.
