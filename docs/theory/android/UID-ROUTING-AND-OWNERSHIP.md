# Android VPN: перехват приложений, lockdown и текущий владелец

[Оглавление](../README.md) · [Термины](../GLOSSARY.md) · [Android и UX](PLATFORM-AND-UX.md)

## Краткий вывод

Набор приложений, чей трафик захватывает VPN, и набор приложений, которым
запрещён выход вне VPN, задаются разными механизмами. Доступ самого VPN-приложения
не представляет автоматически обычное приложение. Разрешение семейства адресов,
декларация физической сети и фактическая привязка сокета также различаются.

**Когда применять.** При проектировании правил по приложениям, IPv6, always-on,
смены сети и согласия пользователя. Предмет проверки включает пользователя
Android, UID, исключения, семейство адресов, поколение TUN и реальный сокет.

**Граница знания.** DR27-14 от 28 октября 2026 года относится к API
Android16/API36 и исходникам `android-16.0.0_r1`: frameworks/base
`99b01a65cc4c104933788b3143285ab6bae65827`, Connectivity
`627eb3c63e7c7cb3cb9f8ea319e4bb1676079c3a`, netd
`68859d33e9bfe9ddb1afdc282905c63339c1928d`.
Это не общая проверка OEM-прошивок, текущих исправлений безопасности
или артефакта Snowden. [Сохранённая рецензия](../research/reviews/2026-10-28-DEEP-REVIEW.md).

<a id="1-кого-перехватывает-vpn-и-кому-запрещён-non-vpn--разные-множества"></a>
## 1. Перехват и запрет обхода относятся к разным наборам UID

В закреплённом [Vpn.java](https://android.googlesource.com/platform/frameworks/base/+/99b01a65cc4c104933788b3143285ab6bae65827/services/core/java/com/android/server/connectivity/Vpn.java?format=HTML)
цепочка `agentConnect→createUserAndRestrictedProfilesRanges` строит набор UID
для перехвата. `setVpnForcedLocked` строит набор lockdown, исключая пакет
владельца VPN и административный список исключений. Поэтому включение
собственного пакета в перехват TUN ещё не делает его подходящим представителем
обычного UID при проверке запрета обхода.

Привязка пакета разрешается в UID конкретного пользователя Android.
Пакеты с общим UID не разделяются одним правилом по пакету; рассматриваемый
снимок учитывает и UID SDK sandbox. Наследование диапазонов restricted profiles
не равно наследованию управляемого рабочего профиля: проверяются другой тип
профиля и отношение с родителем. У restricted user есть отдельный запрет
на собственный VPN.

`DevicePolicyManager.setAlwaysOnVpnPackage(...,lockdownAllowlist)` требует
полномочий владельца устройства или профиля. Его список исключений не является
списком `VpnService.Builder`: он может разрешать работу без VPN при его
недоступности, а подключённый VPN ещё должен включить эти приложения в перехват.
Исключение в Builder само по себе не отменяет lockdown. В AOSP `allowBypass`
учитывается вместе с `!mLockdown`.
[DPM API](https://developer.android.google.cn/reference/android/app/admin/DevicePolicyManager?hl=en).

**Контрпример.** TUN отсутствует, lockdown сохранён. UID владельца VPN имеет
разрешённый начальный прямой доступ, а обычный UID блокируется. Успех проверки
из VPN-приложения не подтверждает защиту другого UID. Прямой доступ владельца
также сам по себе не устанавливает утечку обычного приложения.

<a id="2-разрешить-family-не-значит-направить-её-через-tun"></a>
## 2. Разрешённое семейство адресов не задаёт маршрут через TUN

`makeLinkProperties` начинает с `allowIPv4/allowIPv6`, затем разрешает
семейство при наличии соответствующего адреса, unicast-маршрута **или адреса
DNS-сервера**. Для неразрешённого семейства добавляется маршрут по умолчанию
`RTN_UNREACHABLE`.

| Конфигурация | Какой вывод допустим |
|---|---|
| Только IPv4 в TUN, без каких-либо IPv6-входов | IPv6 может оставаться заблокированным |
| Добавлен один IPv6 DNS-сервер | Семейство IPv6 разрешено; маршрут `::/0` через TUN этим не создан |
| Семейство разрешено, но маршрута перехвата нет | Возможен переход к другим маршрутам, если действующая политика его не запрещает |
| Lockdown действует для обычного UID | Соответствующий путь вне VPN должен блокироваться; это ещё не работающий IPv6 через VPN |
| Использован `excludeRoute` API33 | Применяется `RTN_THROW`, а не отклоняющий маршрут |

[Builder API](https://developer.android.google.cn/reference/android/net/VpnService.Builder?hl=en)
и `makeLinkProperties` описывают разные механизмы. Результат проверки IPv4
не переносится на IPv6, другого пользователя, профиль или класс исключений.

<a id="3-underlying-declaration-bind-и-protect-выполняют-разные-действия"></a>
## 3. Объявление физической сети, bind и protect не взаимозаменяемы

По публичному API `setUnderlyingNetworks` сообщает системе:

| Значение | Смысл декларации |
|---|---|
| `null` | Используется системная сеть по умолчанию без собственного списка |
| Пустой массив | VPN не имеет нижележащего соединения |
| Список N1,N2 | Используются перечисленные сети в порядке предпочтения |

Setter проверяет установленного владельца, копирует массив и передаёт его
`NetworkAgent`; последующая доставка асинхронна. Возвращённое `true`
не подтверждает миграцию сокета, внешний выход или закрытие старых потоков.
Пустой массив также не является подтверждением блокировки трафика
или завершения владения ресурсами.
[VpnService API](https://developer.android.google.cn/reference/android/net/VpnService?hl=en),
[NetworkAgent](https://android.googlesource.com/platform/packages/modules/Connectivity/+/627eb3c63e7c7cb3cb9f8ea319e4bb1676079c3a/framework/src/android/net/NetworkAgent.java?format=HTML).

В netd `PROTECT_FROM_VPN` проверяет право UID и меняет метку конкретного сокета.
Эта операция не задаёт список разрешённых шлюзов и срок исключения.
`denyProtect` запрещает последующие такие действия, но сама функция не закрывает
все уже существующие транспортные сокеты. Ограничение «только шлюз и начальные
запросы до дедлайна» остаётся обязанностью владельцев операций в приложении.
[FwmarkServer](https://android.googlesource.com/platform/system/netd/+/68859d33e9bfe9ddb1afdc282905c63339c1928d/server/FwmarkServer.cpp?format=HTML),
[NetworkController](https://android.googlesource.com/platform/system/netd/+/68859d33e9bfe9ddb1afdc282905c63339c1928d/server/NetworkController.cpp?format=HTML).

Контрпример: сокет явно привязан к Wi-Fi, а приложение объявило `[cellular]`.
Декларация не перепривязывает сокет и не подтверждает прекращение его работы.
Область DNS-запроса дополнительно определяется цепочкой реального соединения;
см. [разбор прокси и NAT64](../observability/PROXY-DNS-NAT64.md).

<a id="4-prepare-не-read-only-permission-getter"></a>
## 4. prepare() может менять владельца VPN

В AOSP ранее одобренное приложение через `Vpn.prepare` может вызвать
`prepareInternal` и сменить текущего обычного владельца VPN без нового диалога.
Другой always-on VPN обрабатывается отдельной запрещающей ветвью.
Поэтому фоновая «проверка разрешения» этим вызовом способна изменить жизненный цикл.

При `establish()` заново проверяются UID владельца и согласие AppOp.
Утрата полномочия даёт `null`; неверное объявление сервиса или `BIND_VPN_SERVICE`
связано с отдельной `SecurityException`. Прежний `RESULT_OK` не резервирует
право на будущий `establish`.

`prepareInternal` сначала отключает интерфейс и агент, затем отправляет
отзыв через односторонний Binder. `onRevoke` поэтому не является началом
блокировки и не подтверждает завершение рабочих процессов или закрытие
принадлежащих приложению файловых дескрипторов.

При смене TUN API допускает ещё действительный старый дескриптор, хотя новый
исходящий трафик уже направляется в новый интерфейс.
`updateLinkPropertiesInPlaceIfPossible` может сохранить `NetworkAgent`;
стабильный `netId` не заменяет поколение TUN. Эти различия основаны на
`prepare`, `prepareInternal` и `establish` в указанном выше Vpn.java.

<a id="5-предмет-proof-и-будущая-приёмка"></a>
## 5. Применение и границы приёмки

Минимальная модель области проверки:

`user/profile · UID/capture/exemption class · inner/outer family · route scope · TUN generation · socket protect/bind · network epoch · время`.

Она задаёт смысл результата, а не требование записывать реальные UID
и список приложений в диагностику. Для интерфейса достаточно разрешённых
типизированных фактов и явно неизвестных свойств.

**Что переиспользовать.** Платформенные механизмы владения, сетевых эпох,
привязки сокетов и проверки результата `protect`. Второй владелец VPN
не требуется самим разбором. Цена — отдельная проверка представителей UID,
семейств адресов, переходов и административных исключений; её нельзя заменить
одним успешным запросом самого VPN-приложения.

**Связь с разработкой.** [План Android](../../planning/knowledge-application/ANDROID-PLAN.md):
ANDR-03/04/05 — первый путь, смена сети, согласие и правила приложений;
ANDR-02/09 — точный артефакт и проверка платформы. В
[плане ПК](../../planning/knowledge-application/PC-PLAN.md) разделение настройки
и фактического применения относится к PC-01/05, но требует собственного
доказательства для WFP. Android-результат его не заменяет.

**Будущая приёмка (`NOT_RUN`).** Отказ и выдача согласия; отзыв между
`prepare` и `establish`; ранее одобренное приложение против обычного
или always-on владельца; владелец, обычный и административно исключённый UID
при lockdown без TUN; только IPv4 против IPv4 с IPv6 DNS без IPv6-маршрута;
personal/work/restricted profiles; общий UID и sandbox; новый TUN при старом
дескрипторе и `netId`; привязка Wi-Fi при декларации cellular или пустого массива;
фактическое освобождение ресурсов после отзыва. Сведения об устройстве,
OEM и текущем APK получают отдельно от анализа API и исходников.
