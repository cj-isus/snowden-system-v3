# Обвязка Snowden System

## Проектный вход

Основной стек остаётся Go/Wails/Vue. Установлен core из локального комплекта
project-harness; модели, permissions, MCP и конфиги приложения не менялись.
Корневой package.json задаёт границу Node resolver и короткие команды проверок;
runtime UI зависимости остаются в windows/frontend. Инструменты harness требуют
Node >=22.13. Исполняемая матрица и запуск тестов: [TESTING.md](TESTING.md).

```powershell
node scripts/harness/project.mjs map
node scripts/harness/project.mjs doctor
node scripts/harness/project.mjs next
node scripts/harness/project.mjs check --scope harness
```

Последняя команда только показывает план. По запросу проверки добавить `--run`.
Scope `frontend`/`backend` вызывает задачи **готового Task**, а не самописный
исполнитель shell pipelines. Нативные команды заданы один раз в Taskfile.yml.
По умолчанию задачи и runner не устанавливают зависимости, не ходят на VPS
и не запускают административные проверки.

### Готовые инструменты, локальная установка

Версии/источники/SHA256 архивов — `.harness/tools.lock.json`. Обновление только
осознанным изменением lock после чтения release notes. Windows amd64 bootstrap:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/harness/bootstrap-tools.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/harness/bootstrap-tools.ps1 -Apply -GoTools
.tools/task/task.exe --list
.tools/task/task.exe --dry backend:check
```

Если текущий Go proxy недоступен, `-OfficialGoProxy` выбирает
`https://proxy.golang.org` **только на время установки**, сохраняя старое значение.
Если release asset недоступен, `-SourceGitleaks` явно выбирает pinned source
fallback из lock. Такой binary проверяется `go version -m`, а не хешем
официального zip: не выдавать source build за release asset.

Первый вызов показывает план; второй явно скачивает pinned Task/Gitleaks и
собирает pinned govulncheck через Go. Архивы сверяются с SHA256, извлекается
только ожидаемый executable и license. Go tool ставится в `.tools/go`, не в
глобальный GOBIN; `windows/go.mod` не меняется. Поддержка иных OS/arch требует
выбора официальных assets/checksums, а не запуска Windows binary.
`.tools/installed.json` — локальная квитанция хешей, не самостоятельный trust root.
Без полного завершения bootstrap doctor честно покажет missing tools.

Taskfile не содержит dynamic `sh` variables/remote includes/dotenv, поэтому его
`--dry` не имеет их побочных эффектов. Обычный вызов Task без задачи показывает
следующий срез. Git hooks не устанавливаются. Установка бинарника не означает
успешную проверку исходников или отсутствие уязвимостей.

### Проверка и evidence

`project.mjs check --scope harness --run` делает только syntax/static diagnostics.
Frontend/backend проверки запускаются отдельно, когда запрошены. Runner пишет
exit status, время, команды и bounded source fingerprint в ignored
`.artifacts/harness/last-<scope>.json`; raw output/секреты не сохраняются и не
эхоятся. При провале для диагностики адресно выполнить безопасную упавшую команду.
Это не сертификат security: fingerprint не охватывает всю ОС, внешние настройки
и сеть. Native проверки не используют checksum-cache для автоматического PASS.

Две отдельные security задачи:

- `Task security:staged` → Gitleaks только по staged text diff, полное redaction,
  без raw report и проверок credentials у провайдера. Пустой index — blocked,
  не PASS. Binary-файлы и нестейдженные provisioning/env/vault не сканируются.
  Явный config расширяет default rules без общего allowlist; это не гарантия
  обнаружения всех UUID/паролей произвольного формата.
- `Task security:vuln` → govulncheck по production tags. Это **явная online**
  проверка базы Go vulnerabilities, не запрос к VPS и не OS leak-test. До её
  фактического выполнения результата CVE-аудита нет.

`Task` здесь означает `.tools/task/task.exe`. Тесты/сборки приложения не были
перезапущены из-за редактирования правил. V2-094 — историческое приложение;
V2-095 — установка и static acceptance обвязки.

### Правила продолжения

- PLAN — backlog/решения; STATE — один короткий заменяемый снимок; MAP — навигация.
- Спецификация текущего сложного среза — `docs/tasks/<ID>.md`, статус только PLAN.
- LESSONS искать по теме. SESSION-STATE/memory/archive не читать автоматически.
- Один активный срез, одно доказуемое закрытие. Сначала P0/lifecycle, затем
  профили/диагностика/поставка; UI не скрывает отсутствие backend или данных.
- Бюджеты контекста проверяет doctor через .harness/project.json. Лимит строк —
  ограничение объёма правил, не измеренная экономия токенов.
- Общие scripts/skills/managed AGENTS block не переписаны. HARNESS.md адаптирован
  под проект; при обновлении из исходного комплекта ожидаем ручной merge этого
  файла. Не исправлять installer manifest, чтобы скрыть конфликт.

## Переносимые процедуры исходного комплекта

Этот документ загружай при подключении среды, длинной задаче или её оценке. Для обычной правки достаточно AGENTS, карты и поиска по теме.

## Установка и запуск

В **исходном demo**, не в этом VPN-проекте: `npm ci`, затем `npm run check`.
Здесь используются проектные команды выше. Общий `doctor.mjs` проверяет только
основу; `project.mjs doctor` дополняет его реальными Go/Vue/Task источниками.

Перенос из исходного каталога harness, без изменения package.json целевого проекта:

```powershell
node scripts/setup.mjs "D:/path/to/project"
node scripts/setup.mjs "D:/path/to/project" --apply
```

Первый вызов показывает план. `--apply` разрешает запись. Существующие файлы и пользовательские правила сохраняются; собственный блок AGENTS ограничен маркерами. Конфликт с изменённым managed-файлом останавливает запись всего плана. Изменяемые STATE/LESSONS сохраняются. Установщик не удаляет файлы старого профиля при смене профиля.

`--profile visual` добавляет визуальные навыки, capture/compare и роли. `--codex` добавляет дефолт `gpt-6.1-sol/medium` только при отсутствии конфликта с конфигом проекта. Разрешения, MCP и глобальный config установщик не меняет. Подключение к существующему проекту не заменяет его инструкции и архитектуру.

После установки из **целевого** проекта:

```powershell
node scripts/harness/project.mjs map
node scripts/harness/project.mjs doctor
```

Core требует только Node для инструментов harness; приложение продолжает использовать свой стек. В visual-профиле добавь `playwright`, `pngjs`, `pixelmatch` существующим менеджером зависимостей проекта и установи Chromium (`npx playwright install chromium` для npm). `doctor.mjs --visual` покажет недостающие зависимости. PNG-референс и baseline подключаются к реальной задаче; пустой scaffold не означает принятый дизайн.

## Контекст и продолжение

| Что требуется | Где хранится | Когда читать |
| --- | --- | --- |
| Постоянные соглашения | AGENTS.md | Автоматически, кратко |
| Где искать код и команды | docs/MAP.md, manifests, CI | Незнакомая часть/смена структуры |
| Исправленная ошибка, предпочтение | docs/LESSONS.md | Поиск по теме |
| Текущее состояние длинной задачи | docs/STATE.md | Возобновление и перед передачей |
| Причина архитектурного решения | Существующий ADR/DECISIONS | Изменение затронутого решения |
| Условная процедура | SKILL.md и его references | Только при подходящей задаче |

Сохраняй в STATE критерии приёмки и проверяемые факты: файл, команду, результат, нерешённое и следующий шаг. Перед продолжением сверь их с текущим кодом. Для короткой задачи отдельный план/журнал не нужен. Контекст переполнен или задача завершена → обнови STATE; при необходимости начинай следующий чат с конкретной новой задачей и ссылкой на состояние. Автоматическую compaction не отключай и не подменяй стенограммой в файле.

Предпочитай явное владение файлами при разрешённой параллельной записи. В этом
проекте субагенты используются по явному запросу. Модель наследуется от родителя;
в оценку включаются все агенты и повторы. Возвращать причины и ссылки, не raw logs.

## Модель и усилие

Модель и effort сохраняются из текущих настроек пользователя. `--codex` при этой
установке не применялся. Выбирать иной режим имеет смысл только для конкретного
сравнения качества/затрат, а не объявлять один default оптимальным без замеров.

Проектный config применяется к доверенным проектам, настройки UI/CLI и управляемые политики могут иметь больший приоритет. В custom agents не задаём отдельный sandbox: они наследуют разрешения родителя. Источники: [configuration](https://learn.chatgpt.com/docs/config-file/config-basic), [subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents), [AGENTS](https://learn.chatgpt.com/docs/agent-configuration/agents-md). Проверено по документации 2026-10-18.

## Как оценить полезность на токен

Для этого проекта набор сравнения: активный RunProbe/cancellation, metrics session,
roundtrip transport schema, Vue blocked/unavailable state и возобновление OFF-задачи.
Сравнивать один и тот же исходный срез, модель и acceptance; не брать удачный
новый запуск против заведомо провального старого. SQL-задачи ниже — только пример
переносимого комплекта, здесь БД нет. До реальных данных вывод об экономии отсутствует.

Оптимизируй стоимость принятой задачи при неизменном качестве. Уменьшение AGENTS или числа вызовов само по себе этого не доказывает. Сначала снижай повторные поиски, дубли компонентов, бессмысленные итерации и перепроверки; затем сравнивай усилие модели.

Выбери реальные задачи: расширение существующего компонента; поиск дубля; UI по референсу; ошибка потока данных; SQL-запрос; миграция; возобновление после нового чата; изменение backend/CLI. Для каждого случая фиксируй начальное состояние, запрос, критерии и проверки. SQL проверяй в тестовой БД с фактическим инструментарием проекта. Без БД отмечай проверку непроведённой.

Сравни исходную и новую среду на одинаковых начальных состояниях, модели и запросах; несколько повторов на задачу. Отдельно фиксируй обучающий набор для настройки и отложенные задачи для проверки, чтобы не подгонять правила под примеры. Оценщик смотрит результат и проверки до знания варианта. Сначала проверяй acceptance/регрессии, затем затраты.

Одна строка данных в массиве JSON:

```json
{"task":"reuse-component","variant":"candidate","accepted":true,"inputTokens":12000,"outputTokens":2100,"cachedInputTokens":8000,"seconds":95,"rework":0}
```

Это **пример формата**, не результат замера. Объедини строки запусков в `evals/runs/comparison.json` и выполни `node scripts/harness/eval.mjs evals/runs/comparison.json`. Включай в расход всех субагентов, неудачные попытки и исправления. Cached input уже часть input, reasoning обычно часть output; не суммируй их повторно. Нет достоверного usage → пропусти поле, отчёт покажет неполные данные. Токены разных моделей не равны по цене; для денег используй фактический billing, тариф и cache usage, без выдуманной цены токена.

Отчёт показывает acceptance rate, суммарные токены **всех** попыток на принятую задачу, время и переделки. Он описательный: не доказывает статистическую значимость и не проверяет равенство условий эксперимента. Ввод проверяет числа; выполнение задачи и честность acceptance подтверждаются артефактами/проверками отдельно.

## Развитие среды

Новое правило добавляй после конкретного сбоя или явного предпочтения. Повторно подтверждённое общее правило переноси из уроков в AGENTS; специализированное — в соответствующий skill. Исполнимые проверки предпочтительнее новых абзацев. Не добавляй MCP/плагины заранее: подключай инструмент, когда он решает реальную задачу и доступен в целевой среде.
