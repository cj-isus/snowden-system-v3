Два плана от 4 ноября учитывают части последнего планирования, текущие платформенные
снимки и ограничения новых сведений о VPS/CDN. Они задают следующий порядок работ;
статусы требований остаются в реестрах владельцев. Неполные предложения не считаются
готовой реализацией или проверенным поведением.

[Общий план KA-1](PLAN.md) сохраняется как основание минимальных контрактов и
межплатформенной последовательности. Ниже — аналитические срезы 28–29 октября: обоснования и источники
решений. Описания «текущего кода» в них относятся к названному source-срезу;
новые изменения проверяются по плану платформы и реестру владельца.
Новые исследования остановлены.

## Что должна дать сводка

Для каждого знания: источник и предпосылки → существующая реализация/пункт плана → обоснованное решение → конкретное изменение → владелец/зависимость → будущая приёмка. Уже написанный код не считается runtime проверенным; идея может быть отложена или отвергнута.

## Правила применения плана

1. Для уникальных знаний, включая архивные и поздние, указывать обоснованное решение: применить, адаптировать, отложить, отвергнуть либо оставить открытым. Число просмотренных строк само по себе не доказывает полноту анализа.
2. Сопоставлять предложения с названным срезом исходников и существующими требованиями. Изменения после этого среза проверять у владельца; дата документа не доказывает актуальность всего рабочего дерева.
3. Сначала safety/lifecycle/trust и честный UX, затем bounded performance/адаптация, затем дополнительные transports/features с доказанной пользой.
4. Разделять задачи по реальным владельцам компонентов. Согласовывать минимальные интерфейсы, позволяющие независимо развивать ПК и Android; новые зависимые потоки не создавать без необходимости.
5. Эксплуатация рассчитана на один купленный VPS с явной единой точкой отказа. БД, control-plane и кластер требуют доказанной потребности. Серверные действия и развёртывание требуют отдельного разрешения владельца; чтение этой сводки его не предоставляет.
6. Передавать задачи соответствующим существующим владельцам с конкретными входами и выходами этапа. Нативная, устройственная и полевая приёмка остаются отдельными границами проверки.
