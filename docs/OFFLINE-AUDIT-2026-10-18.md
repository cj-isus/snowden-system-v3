# Строгий офлайн-аудит Snowden System — 2026-10-18

## 1. Вердикт и границы

**Уточнение 2026-10-20 (V2-097):** ниже сохранены исходные находки аудита.
Выполнен первый локальный срез OFF-01/02/03: intent/StopReason, strict WFP
без auto-expiry, ранний helper, probe deadlock/panic/cancel, applied metrics
и structural switch. AUD-018 исправлен. Команды, ограничения и текущие
статусы — [evidence](evidence/2026-10-20-adaptive-lifecycle.md) и PLAN §5.1.
Это не полное закрытие 23 находок и не доказанная production safety WFP.

**Проект нельзя считать завершённой, доказанно безотказной VPN-системой.** В нём уже есть полезное ядро: embedded sing-box, строгая проверка конфигурации, проверка egress перед running, откат переключения, WFP, DPAPI, подписанные профили и учёт здоровья каналов. Однако между этими частями остаются ошибки, затрагивающие защиту, восстановление и достоверность состояния. Добавление транспортов и настройка весов классификатора сейчас менее приоритетны, чем исправление этих ошибок.

Найдено **23 замечания: 2 P0, 17 P1, 4 P2**. Здесь P0 — блокер выпуска с заявленными гарантиями защиты/аварийного восстановления; P1 — обязательное исправление надёжности или существенного контракта; P2 — следующий этап качества. Приоритет — оценка аудита, а не свидетельство эксплуатации уязвимости.

Исследованы `docs/AGENTS.md`, master plan, теория обхода, предыдущий аудит алгоритма, конфигурации/деплой, Go lifecycle/core/render/probe/WFP/metadata/vault/update, адаптивный слой и лаборатория, Vue API/навигация/mock/опросы и упаковка. Архивные планы использовались как контекст; действующий план — только `docs/PLAN.md`.

**Ограничения:** по сообщению владельца VPS не оплачен. SSH, VPS, Cloudflare API, боевые каналы, административные WFP/TUN-тесты и изменение системной сети не выполнялись. Секретные файлы и пользовательский vault не читались. Удалённая доступность, реальная скорость, отсутствие сетевых утечек на устройстве и состояние сервера этим аудитом не установлены. Исторические live-результаты сентября не аннулируются, но не доказывают работоспособность 18 октября.

В отчёте используются три вида основания: **воспроизведено локально**, **установлено по исходникам**, **пробел доказательств/риск**. Последнее не означает найденную фактическую утечку.

## 2. Что система представляет собой сейчас

```text
Vue / Wails / tray
         ↓
App + глобальный runtime_
  ├─ start/stop/switch + Manager + embedded sing-box
  ├─ watchdog / netwatch / autoretry / background probes
  ├─ ChannelHealth / классификатор / scoring / quarantine
  ├─ WFP + helper того же GUI EXE
  └─ render + DPAPI vault + metadata + updater
         ↓
WS/CDN | HY2 | REALITY | ShadowTLS
         ↓
один origin / один хостер-ASN / общий платёжный отказ
```

В `windows/backend/render/descriptors.json` все четыре профиля имеют один origin и один ASN. ShadowTLS имеет статус configured. Три других несут исторический live-verified сентября. Это несколько транспортных вариантов одного инфраструктурного узла. При отключении VPS за неуплату транспортная диверсификация не создаёт резервного сервера. Модель `fdmodel.go` уже содержит ограничение independence для общего origin+ASN — это правильная защита от завышения оценки.

SOCKS — отдельный режим с ограниченной областью покрытия: приложения могут игнорировать системный proxy. Его нельзя приравнивать к защите всего устройства TUN+WFP.

### Воспроизведённые контрпримеры

1. В `runtime_` временно заданы непустые manager и `ClientConfig`, создан новый `App`, `probeCore()` запущен в горутине. За 500 мс он не возвращается, хотя до любого сетевого вызова ещё не дошёл. Ветка берёт `a.mu`, затем вызывает `pushState()`, который берёт тот же mutex. Вывод теста: `active probe self-deadlocks before any network call`.

## 4. Дефекты и необходимые исправления

### AUD-001 — P0: автоматический аварийный stop открывает обычный direct

**Основание: исходники.** `windows/corebridge.go:516` (`blockUnsafePath`) вызывает общий `stopCore`; `corebridge.go:774` останавливает manager, затем снимает WFP через `disarmKillSwitch`. Manager восстанавливает предыдущий proxy. После удаления TUN/фильтров внешние приложения снова могут выходить по обычному маршруту. То же семейство cleanup используется при неудачных стартах и повторных попытках.

Узкий запрет `direct` внутри protected selector действительно реализован. Он не обеспечивает системную блокировку после автоматической ошибки. Фраза «error/BLOCKED, никогда direct» сейчас шире поведения ОС.

**Исправление:** отдельное состояние желаемой защиты `DesiredProtection`, независимое от состояния engine. Ввести причины остановки: пользовательская, ошибка, утечка, обновление, завершение. При автоматической ошибке strict-политика сохраняет защитный барьер между попытками и при отсутствии каналов. Только явное отключение пользователем либо отдельно выбранная политика восстановления допускают его снятие. Закрытие UI само по себе не должно незаметно менять выбранный режим защиты.

**Приёмка:** внешний непопадающий под AppID процесс не проходит напрямую при probe failure, all-failed, паузе retry, switch rollback failure и ошибке renew. Явное пользовательское отключение восстанавливает сеть. Проверить IPv4/IPv6, TCP/UDP/DNS, новые и уже открытые соединения на изолированной Windows-среде.

### AUD-002 — P0: dead-man helper конфликтует с SingleInstance GUI

**Основание: исходники приложения и используемой зависимости.** `windows/killswitch_windows.go:199` запускает тот же EXE с `--killswitch-expire`. Обработка флага находится в `App.startup`, `windows/app.go:168`. До неё `windows/main.go:74` включает Wails SingleInstanceLock с тем же UniqueId. В Wails v2.13.0 `internal/frontend/desktop/windows/frontend.go` вызывает SetupSingleInstance раньше OnStartup; `single_instance.go:37–68` при существующем окне передаёт сообщение и завершает второй процесс.

Следовательно, при обычном работающем GUI дочерний helper уходит раньше выполнения cleanup-таймера. `cmd.Start()` и запись PID не подтверждают, что helper готов и продолжает жить. После crash persistent WFP может остаться без обещанного ограниченного по времени восстановления. Процессный crash именно производственного EXE текущим аудитом не запускался; вывод получен из порядка исполнения. Старые tests с `Engine.Stop` этого пути не проверяют.

**Исправление:** служебный режим обрабатывать в самом начале `main`, до Wails, updater и SingleInstance; либо отдельный минимальный служебный бинарник. Нужны handshake готовности, контроль живости, generation ID, атомарное состояние lease и проверка личности процесса перед его завершением. Нельзя считать успешным lease по одному `cmd.Start`. Передача новому helper и cleanup старого должны исключать гонку проверки владельца с последующим удалением новых фильтров.

**Продуктовое противоречие:** «автоматически снять блок через 90 секунд после crash» и «сохранять strict fail-closed после crash» несовместимы. Нужен явно определённый контракт. Предлагается strict по умолчанию, служебное восстановление защиты и явный аварийный инструмент отключения. Если нужен auto-unblock, он должен быть отдельно выбранной и честно названной политикой.

**Приёмка:** subprocess-тест собранного EXE при живом GUI, проверка helper ready/PID/generation, принудительное завершение GUI, наблюдение политики после срока lease, перезапуск и очистка. Без выхода к VPS это возможно в Windows VM, но не выполнено здесь.

### AUD-003 — P1: ручная проверка пути навсегда блокирует App

**Воспроизведено локально.** `windows/corebridge.go:810–821` вызывает `a.pushState()` внутри удержанного `a.mu`; `windows/app.go:857` захватывает тот же нерекурсивный mutex. Зависает probe, затем все операции, которым нужен App mutex. Существующий `TestAppBindingMethodsDoNotSelfDeadlock` в `hardening_test.go` эту активную ветку probe не проверяет.

**Исправление/приёмка:** публикация через корректный locked-вариант или неизменяемый snapshot после освобождения mutex; постоянный regression-тест активного RunProbe и конкурентных GetState/Stop. После устранения deadlock отдельно определить обработку результата leak у ручного probe, чтобы она соответствовала автоматическому safety outcome.

### AUD-004 — P1: panic переключения ошибочно возвращает успех

**Воспроизведено локально.** `windows/backend/core/manager.go:313`, defer в `SwitchChannel`: recover ставит StateError, останавливает engine и восстанавливает proxy, но не устанавливает возвращаемую ошибку. Функция имеет безымянный return `error`; после recover вызывающий получает `nil`. `windows/failover.go` трактует nil как успех и публикует running.

**Исправление/приёмка:** единообразное завершение операции с явным ненулевым error для panic; тесты panic в new/rollback probe и сверка результата, Manager, engine, UI и proxy. Не подменять проверку просто перехватом panic без ошибки.

### AUD-005 — P1: Stop не отменяет незавершённый Start

**Основание: исходники.** `startCore` использует `context.Background`, в том числе для `manager.Start`, и неотменяемый `time.Sleep(20s)` (`windows/corebridge.go:304`). `stopCore:742` ждёт startBusy только 5 секунд, после чего продолжает работу с текущим manager. Более поздняя стартующая горутина всё ещё может опубликовать новый engine/proxy/running. Старый тест проверяет лишь старт, завершившийся через 300 мс.

Дополнительно `windows/backend/core/engine.go:57–91`: `Start` создаёт собственный Background-контекст до `box.Start`; `Stop` вызывает `box.Close` под mutex и отменяет runtime-контекст только после Close. Таймаут Manager не делает эти вызовы автоматически прерываемыми. Гарантия bounded lifecycle требует проверки, а не только наличия `WithTimeout` снаружи.

**Исправление:** один владелец lifecycle-команд, отменяемый контекст операции, номер поколения, cancel-aware ожидания. Завершение старого поколения не меняет новое состояние. При невозможности надёжно ограничить зависший embedded engine рассмотреть отдельный процесс/службу ядра с ограниченным протоколом управления.

**Приёмка:** Stop/quit во время resolve, render, Start, probe, failover и retry; после принятия Stop ни один старый worker не включает engine/proxy. Проверить зависающие Start/Close через injection, закрытие окна, смену режима и update.

### AUD-006 — P1: сборщик метрик и ядро получают разные сессии

**Основание: исходники.** `windows/corebridge.go:182` создаёт и сохраняет `runtime_.metrics`; строка 187 создаёт вторую сессию и добавляет вторую `WithClashAPI`. Последняя опция задаёт ядру другие controller/secret. `GetMetrics` опрашивает первую сессию. При обычном успешном создании обеих сессий метрики недоступны; это детерминированное несоответствие, а не отсутствие трафика.

В `windows/metrics.go:80–88` отладочная ветка `SNOWDEN_CLASH_PORT` дополнительно теряет listener без `Close`, занимая выбранный порт. Это отдельный дефект этой ветки.

**Исправление/приёмка:** одна сессия на реально созданный engine; сохранить её только при успешном commit старта; закрывать резервирующий listener. Локальный e2e render→engine→authenticated `/connections` должен подтвердить одинаковые порт/ключ и ненулевые счётчики на loopback-трафике. Проверить неуспешный и бесшовный switch.

### AUD-007 — P1: подготовка кандидата меняет состояние живого engine

**Основание: исходники.** `renderAndPrepare:102` усекает `engine.log` и заменяет глобальные метрики ещё до валидации/применения кандидата. В `windows/failover.go:180–246` seamless switch меняет лишь selector живого engine, но затем целиком заменяет `runtime_.cc` новым рендером. Изменения DNS, descriptors, controller, маршрутов и других полей этого рендера при seamless не применяются. При отказе подготовки побочные изменения уже произошли.

**Исправление/приёмка:** чистый prepare без публикации, отдельно commit конфигурации и engine session. При switch разрешать seamless только для существующего неизменившегося набора outbounds и параметров; structural diff требует Reload. Снимок applied config должен описывать работающий engine. Логи ротировать на создание engine, не на рендер кандидата.

### AUD-008 — P1: общие endpoints проверки сами могут выключить рабочие каналы

**Основание: исходники.** Все встроенные каналы зависят от одной self-hosted `/ip` цели и api.ipify; DNS-шаг привязан к `1.1.1.1/dns-query`, внешний TUN-probe — к Cloudflare trace. Требование успеха каждого шага связывает доступность туннеля с доступностью этих сервисов. Отказ одного endpoint может погасить транспорт, который продолжает передавать пользовательские данные. Будущий второй VPS также не должен наследовать проверку на первом, отключённом сервере.

**Исправление:** явные независимые группы источников, отдельный результат endpoint unavailable и transport unavailable, ограничения задержки, проверенные альтернативы. Нельзя просто объявить таймаут security PASS. Сохранить обязательную аутентичность egress-доказательства, но уметь получать её через альтернативные доверенные источники. Диагностика транспорта и проверка security имеют разные правила деградации.

**Приёмка:** отдельное отключение каждого echo/DNS endpoint при исправном локальном transport; доказать отсутствие ложного all-channel outage и отсутствие ложного protected PASS при нехватке доказательств. Для ambiguous evidence — явный restricted/unverified статус согласно выбранной политике.

### AUD-009 — P1: probe доказывает меньше, чем написано в гарантиях

**Основание: исходники и граница метода.** `backend/core/probe.go:122,252,267` проверяет HTTPS через SOCKS и собственный HTTP DoH. Реальный render использует другой DNS-путь (`tls://8.8.8.8`), а Windows DNS Client/UDP/AAAA/маршруты отдельного процесса этой проверкой не покрыты. Два URL валидируются по количеству, но не по независимости host/provider. Совпадение direct и tunnel IP в SOCKS не доказывает обход туннеля: возможен уже работающий внешний TUN с тем же exit. Разные IP также не доказывают отсутствие иных утечек.

**Исправление:** выделить transport liveness, engine DNS, системный DNS, routing и leak evidence в разные типизированные результаты. В TUN обязательный внешний non-exempt проверяющий процесс, в том числе DNS/IPv6/UDP. Использовать нормализованные IP, не текстовое равенство произвольной формы адреса. Наличие исключений LAN/bootstrap/split должно быть частью политики и объяснения UI.

**Приёмка:** отрицательные сценарии Windows DNS вне tunnel, IPv6 bypass, UDP bypass, другой VPN, неверный expected egress, разные egress по доменным правилам. Прямой bootstrap адреса VPN допустим только как документированное ограниченное исключение, не как DNS пользовательских доменов.

### AUD-010 — P1: подписанный профиль не переносит возможности встроенного

**Основание: исходники.** `windows/backend/metadata/metadata.go:60` описывает лишь часть ChannelDescriptor. В `backend/render/render.go:272–322` даже имеющиеся в metadata `UUIDRef`, `RealityPublicKeyRef`, `RealityShortIDRef` не копируются в итоговый дескриптор. REALITY из такого envelope не пройдёт соответствующую проверку refs. Не передаются также mux, ShadowTLS ref, probe/diagnostic endpoints, failure domains, HY2 port hopping и другие поддержанные встроенным форматом поля.

Это мешает исправлению инфраструктуры через подписанный профиль и создаёт разные контракты для встроенной и доставленной конфигурации. B2 нельзя считать готовым для полного набора текущих каналов.

**Исправление/приёмка:** единая версионированная transport schema, полный конвертер и migration. Для каждого поддержанного транспорта: встроенный descriptor → sign → decode/verify → apply → render → строгий parser ядра; существенные поля должны совпасть. Отдельно revocation/expiry/downgrade/неполный профиль.

### AUD-011 — P1: credential ref на деле означает kind

**Основание: исходники.** `windows/corebridge.go:33` ищет секрет условием `m.Kind == ref` и возвращает первую запись. HY2 в рендере использует общие `hy2-password`/`hy2-obfs-password`. Это не адресуемое хранилище секретов независимых экземпляров канала. Два HY2-сервера с разными паролями нельзя выразить тем же надёжным способом, что произвольные профили.

**Исправление/приёмка:** стабильные SecretID/namespace профиля, kind только как тип валидации, явные ссылки всех transport credentials. Миграция текущих слотов без потери значений; тест двух однотипных каналов с различными synthetic secrets, roundtrip export/import и rollback миграции.

### AUD-012 — P1: цепочка обновления имеет race после проверки payload

**Основание: исходники/риск при изменяемом каталоге update.** `windows/updateapp.go:165–202` проверяет исходный payload, освобождает App mutex и затем заново открывает файл в `copyFile`. Проверки хеша staged-файла перед rename нет. Повторная проверка в Apply закрывает окно между Check и Apply, но не окно между VerifyPayload и Copy. Параллельные Apply также не сериализованы на всю транзакцию. Stop error лишь логируется, после чего подмена продолжается.

Ключи доставки профилей и ключи подписи исполняемого обновления используют одну таблицу доверия. Компрометация уполномоченного издателя профилей тем самым распространяется и на код. Это свойство модели доверия, а не доказательство удалённого взлома; local attacker с теми же правами уже имеет широкие возможности в пользовательском каталоге. Elevation GUI делает такую границу особенно важной.

**Исправление/приёмка:** отдельная сериализованная update-транзакция; создать staging с контролируемым доступом, проверить подпись/размер/хеш именно staged bytes и устанавливать именно их; раздельные code/profile signing roles; корректное экранирование путей перезапуска и аварийный откат. Тест подмены source между verify/copy, concurrent Apply, disk full, Stop failure, launch failure и путей с апострофом.

### AUD-013 — P1: штатный deploy не воспроизводит сервер и небезопасен для восстановления

**Основание: исходники.** `configs/README.md` честно указывает: `server-combined.json` — только baseline, без действовавших REALITY/ShadowTLS/mux/WARP и с другим WS-port. Однако `configs/deploy-vps.sh:82` записывает его прямо поверх рабочего config, а проверяет только после записи. Backup/atomic commit/rollback отсутствуют. Некорректный файл остаётся на диске даже без немедленного рестарта.

`SSH_OPTS` использует `-p` и для ssh, и для scp. У scp порт задаётся `-P`, а `-p` означает сохранение атрибутов. Это дополнительно ломает заявленный способ передачи параметров.

**Исправление/приёмка:** полное декларативное описание сервера и версий, secrets только по ссылке; отдельные argv ssh/scp; staging на сервере → validate → backup → atomic replace → управляемое применение → health → rollback. Подготовить всё офлайн и проверить на локальном Linux-стенде. Боевой deploy только после возвращения оплаченного VPS и отдельного разрешения.

### AUD-014 — P1: разные ветки switch failure завершают восстановление по-разному

**Основание: исходники.** В `windows/failover.go:220` default-ошибка `SwitchChannel` записывает error и возвращается. В этой ветке нет общего safety finalizer/планирования retry, хотя Manager мог уже остановить engine и восстановить proxy. Global runtime при этом сохраняет непустые manager/cc; наблюдатель в `corebridge.go` определяет наличие сессии по этим указателям. Автоматический путь может восстановиться на последующем тике, но ручной switch не получает того же немедленного гарантированного завершения операции.

**Исправление/приёмка:** один типизированный SwitchOutcome: committed / rolled_back_verified / stopped_protected / failed. Единый обработчик барьера, session state, active tag и retry. Все entrypoints — кнопка, tray, watchdog, netwatch — должны иметь одинаковые переходы. Не проверять running наличием manager pointer.

### AUD-015 — P1: WFP verifier не проверяет существенные условия permit

**Основание: исходники; пробел доказательств, не установленный bypass.** `windows/wfp_killswitch_windows.go:227` сверяет ID, provider, sublayer, layer, action и persistent, но не conditions/weight и не фактический LUID/AppID. Для expected specs используются `verify-placeholder` и LUID=1. Неверный permit с тем же ID будет признан допустимым. Правила находятся на ALE_AUTH_CONNECTv4/v6; более широкий исторический план connect/receive/NDP не подтверждается фактическим составом.

AppID-exemption разрешает прямой выход всему GUI/embedded engine процессу, не только transport dial. Это увеличивает доверенную поверхность Wails и привилегированного процесса. Проверка внешним curl на старте полезна, но не заменяет проверку всей политики и её изменений.

**Исправление/приёмка:** сравнивать canonical policy целиком с текущим реальным LUID/AppID, включая веса/условия/неожиданные owned rules; доказать достаточность выбранных WFP layers для точной модели угроз. Снизить привилегированную поверхность отдельной службой с ACL и авторизованным IPC. Тесты corruption условий, adapter recreation, suspend/resume/reboot, existing flows, IPv6, UDP/DNS. Чужие административные WFP policies требуют отдельной модели совместимости.

Не следует «чинить» это произвольным переключением флага hard/soft. Arbitration WFP зависит от sublayer, weight, action rights. Исторический комментарий о soft block не является доказательством корректности или некорректности firewall; нужна проверка effective policy.

### AUD-016 — P2: классификатор — эвристика, confidence не является вероятностью

**Основание: исходники/методология.** `windows/failclass.go` выводит причины из строк HTTP/SOCKS/TLS ошибок и порта. RST не доказывает injection; таймаут — блокировку порта; TLS error — allowlist. Нет оплаченного VPS — достаточное известное инфраструктурное объяснение текущего отказа, его нельзя переименовывать в DPI.

`lab_test.go` и таблицы полезны как regression suite, но 20/21 на малом составленном наборе не доказывают качество в реальных сетях или калибровку confidence. Присваивание 0.85 не даёт 85% вероятности правильного диагноза.

**Исправление/приёмка:** наблюдаемая форма отдельно от гипотезы причины, confidence пометить экспертным; типизированные error codes вместо парсинга локализованных строк. Независимый holdout с инфраструктурными сбоями, истёкшими сертификатами, endpoint outage и congestion. Измерять abstention/false positives/ошибочные переключения; safety-реакция должна опираться на доказательство нарушения, не на предполагаемую цензуру.

### AUD-017 — P2: диагностический общий budget не ограничивает всю операцию

**Основание: исходники.** `windows/diagprobe.go:88–146` проверяет wall-clock deadline только перед ступенью; не создаёт общий deadline для всех запросов. Одна ступень содержит до двух последовательных запросов по 8 секунд и может существенно превысить оставшийся budget. Пояснение budget exhaustion затем перезаписывается итоговым summarize. Короткий egress probe ≤256 байт при этом закономерно не видит volume freeze.

**Исправление/приёмка:** общий `context.WithTimeout`, остаточный бюджет каждого шага, typed incomplete outcome и явная отметка непроверенных ступеней. Volume-test запускать ограниченно по требованию/подтверждённой деградации, а не на каждом фоновом тике. Локальный сервер с задержкой на каждом шаге должен укладываться в общий deadline с небольшим измеренным overhead.

### AUD-018 — P1: текущая сборка UI зависит от постороннего файла диска

**Воспроизведено локально.** `npm run build` прошёл vue-tsc и упал в Vite CSS/PostCSS loader на `D:/package.json`, начинающемся `EF-BB-BF`. Это файл окружения вне проекта; `windows/frontend/package.json` BOM не имеет. Не следует массово перекодировать файлы репозитория или считать ошибку дефектом Vue-компонентов. Чужой `D:/package.json` в этом аудите не менялся.

**Исправление/приёмка:** ограничить discovery PostCSS конфигурацией проекта; задать воспроизводимую среду Node/package manager; выполнить чистую frontend/Wails/installer сборку в независимом каталоге. Учитывать package lock. Упаковщик должен прогонять тесты с production tags, а не только обычные, и явно различать полный installer PASS от «NSIS не найден, выход 0».

### AUD-019 — P1: evidence и выпуск не привязаны к проверяемой ревизии

**Основание: текущая рабочая копия и документация.** Git не имеет коммитов, все каталоги untracked; связь актуальных исходников, старых EXE и сентябрьского evidence здесь не восстанавливается по commit ID. Это не утверждение об отсутствии резервных копий или другого remote-репозитория — они не исследовались.

Master plan одновременно содержит старое live в шапке, незакрытый failover и широкое «full fault matrix» после одного класса Engine.Stop-тестов. Crash GUI/helper, питание/reboot, DNS/IPv6/UDP и cancel-races из этой записи не следуют. Ссылка `scripts/rotate-channel-secrets.sh` в §7 не найдена в текущем дереве; отзыв исторически скомпрометированного CF-токена не доказан этим аудитом.

**Исправление/приёмка:** baseline commit после проверки состава и исключения секретов, artifact manifest (revision, toolchain, tags, dependency versions, SHA256), раздельные unit/integration/OS/live evidence. Автоматизированный release gate, backup/restore, отдельные code signing роли, история ротации без секретных значений. Старые записи журнала сохранять, текущие ограничения добавлять датированным уточнением.

### AUD-020 — P2: preview/mock и навигация требуют отдельной UX-приёмки

**Основание: исходники, визуальный аудит окна не выполнялся.** `frontend/src/api/mock.ts:365` включает mock при `?mock=1` и отсутствии `window.go`, но не проверяет `import.meta.env.DEV`, вопреки комментарию «только dev». В нормальном Wails с уже существующим `window.go` mock запрещён, плашка в App есть — это положительная защита. Открытый браузерный `?mock=1` не является доказательством работы VPN.

Смысл меню/подразделов в `App.vue` и `ContextTabs.vue` уже разделён. Дальнейшее исправление должно сохранить эту иерархию. Массивы sectionForView/groups/searchEntries дублируют навигационную модель. При ширине ≤620px `.tab-copy` скрывается полностью, а отдельного aria-label у кнопки нет. Это проблема доступности при таком viewport, хотя окно Wails сейчас ограничено MinWidth=940. У polling composables нет общей защиты от наложения долгих запросов и устаревших ответов.

**Исправление/приёмка:** mock только в dev-артефакте; единый navigation registry; доступные имена, focus и клавиатура; session generation и in-flight guard опросов. Проверить 940×600, 1180×780, 1366×768 и scaling 125/150/200%; пустые/ошибка/заблокировано/нет VPS/нет метрик. Убрать дублирование карточек там, где достаточно строк/таблицы. Оценка красоты требует отдельного просмотра, а не одного компилятора.

### AUD-021 — P2: повторяющиеся проверки создают лишние HTTP-пулы

**Основание: исходники/ресурсный риск.** `backend/core/probe.go:122,252` на каждом Run создаёт новые transports для direct и tunnel без `CloseIdleConnections` и без явного `IdleConnTimeout`. Аналогичный шаблон есть в volume diagnostic. Закрытие response body не закрывает все keep-alive соединения; одноразовые pools не переиспользуются следующим probe. В длительной сессии это создаёт лишние соединения/горутины и нагрузку. Масштаб роста в текущем приложении не измерялся.

**Исправление/приёмка:** владение transport на уровне session с reuse и закрытием при teardown либо гарантированный cleanup одноразовых clients; ограничить idle lifetime/concurrency. Провести многоцикловой локальный soak с учётом handles, goroutines, памяти и соединений. Оптимизацию частоты PowerShell/UI/background probes делать после корректной телеметрии и измерений.

### AUD-022 — P1: импорт профиля не является атомарной транзакцией

**Основание: исходники.** `windows/onboarding.go:183` сначала сохраняет merged trusted keys, потом проверяет подпись/семантику envelope. При отказе envelope доверенные ключи уже изменены. После этого envelope и version floor записываются до последовательного импорта секретов. Ошибка на одном секрете оставляет частично обновлённый профиль и уже поднятую версию; автоматического rollback нет. Preview не выполняет полную проверку подписи/применимости дескрипторов. Подтверждение человеком действительно есть, но не делает частичную запись корректной.

**Исправление/приёмка:** единый validate/preview план всего импорта в памяти, затем staged generation ключей/конфига/секретов с атомарным переключением указателя или журналируемым rollback. Проверить состояние диска после ошибочной подписи, несовместимого descriptor, неверного секрета, нехватки места и обрыва на каждой записи; при отказе исходный профиль и version floor сохраняются. Эта задача входит в OFF-04.

### AUD-023 — P1: KDF входного бандла допускает чрезмерные затраты до аутентификации

**Основание: исходники; ресурсная атака не запускалась.** `windows/backend/onboarding/onboarding.go:186–202` ограничивает N снизу и сверху, но не ограничивает сверху R/P и совокупную стоимость scrypt. Уже разрешённые N=2^21 и R=8 требуют около 2 GiB рабочей памяти для основной таблицы. Размер входной transport-строки 256 KiB не ограничивает объём KDF. Вычисление выполняется до GCM-проверки пароля/подлинности, в том числе в Preview; импорт недоверенной строки может истощить память/CPU GUI, в котором живёт и engine. Внешняя эксплуатация без доставки строки пользователю здесь не утверждается.

**Исправление/приёмка:** фиксированные допустимые KDF-профили версии формата либо строгие границы вычисленной memory/work cost, число параллельных операций, изолированное выполнение и ограниченный размер всех декодированных полей. Неподдерживаемые дорогие профили отвергаются до вызова scrypt. Unit-тестирует решение admission policy без реального выделения гигабайтов. Эта задача входит в OFF-04/06.

## 5. Сопоставление с теорией владельца

| Принцип теории | Оценка реализации | Что менять |
|---|---|---|
| Несколько независимых путей важнее «лучшего протокола» | Разные транспорты есть, инфраструктурной независимости нет | Разделять transport diversity и origin/ASN/payment/CDN/credential/control-plane зависимости |
| При отсутствии подтверждённого пути не выпускать защищённый трафик | Selector ограничен; системный cleanup нарушает строгую интерпретацию | AUD-001/002/015, явная политика защиты при crash/error |
| Не путать открытый порт с работающим VPN | Protected probe — правильная основа | Разделить liveness/security/endpoint health и расширить фактические проверки |
| Freeze после объёма не виден в коротком handshake | Diagnostic range-ступени уже есть | Общий deadline, независимый контроль, не выдавать короткий probe за доказательство отсутствия freeze |
| Различать наблюдение и объяснение | Ошибки типизируются, но названия reset_injected/whitelist и confidence сильнее evidence | AUD-016; uncertainty и отказ от диагноза допустимы |
| Mux может и помогать, и ухудшать | Встроенный WS mux=true, REALITY без глобального mux — разумная осторожность | Переносить профиль без потери mux, доказывать совместимость обоих концов; A/B, не глобальная догадка |
| Bootstrap не должен зависеть от ещё не созданного tunnel | Preflight и отдельный bootstrap есть | Явно ограничить разрешённые direct control-plane исключения, проверить реальный DNS-путь ОС |
| Egress репутация отдельно от transport | Теория верно разделяет | Профиль проверки должен учитывать policy-based egress; 403 сайта не означает смерть VPN |
| Allowlist/shutdown — границы продукта | «BLOCKED» допустим | Не утверждать универсальную невозможность для любой частичной allowlist; фиксировать достижимые разрешённые пути и собственную модель угроз |

Тезисы о «неотличимости» WS/CDN или REALITY от обычного трафика следует заменить на ограниченные свойства конкретной модели наблюдателя. Отсутствие обнаружения в одном опыте не доказывает неразличимость. High-port, ECH, obfs, mux и смена TLS fingerprint — гипотезы/профили для измерений, не универсальные гарантии. Юридические положения справочника этим техническим аудитом не проверялись.

**Максимум не выжат ни теоретически, ни инженерно.** Для заявленной цели важнее устранить системные противоречия, измерить стоимость проверок и обеспечить действительно независимый путь. Обещать абсолютную безотказность или «самый быстрый VPN» без сравнимого benchmark невозможно. Неоплата единственного сервера показывает конкретный общий failure domain, а не недостаток количества протоколов.

## 6. План переделок и порядок работ

Канонические задачи, владельцы, зависимости и статусы добавлены в `PLAN.md`, §5.1, ID **OFF-01…OFF-09**, журнал **V2-094**. Этот отчёт — доказательная база, а не второй независимый roadmap.

### Целевая организация

1. **ProtectionController** владеет желаемой политикой и WFP-барьером. Engine может быть stopped, когда защита остаётся blocked. Причины stop типизированы.
2. **SessionController** последовательно принимает команды, отменяет операции и публикует immutable applied snapshot с generation ID. Watchdog/netwatch/tray/UI отправляют команды ему, не меняют engine разными путями.
3. **EngineSession** владеет реальной конфигурацией, selector, metrics transport, логом и lifecycle engine. Prepare не имеет побочных эффектов. Семантически новый config требует apply/reload.
4. **ProbeService** отделяет security evidence от transport/endpoint health; endpoint policy версионируется и переносится вместе с профилем. Диагностические проверки имеют общий budget.
5. **ProfileStore / SecretStore / UpdateService** используют единый тип transport, стабильные SecretID и раздельные роли доверия. Обновление — транзакция verified staged bytes.
6. В перспективе — минимальная привилегированная Windows-служба для engine/WFP, обычный GUI и авторизованный IPC. Выделение службы делать после фиксации contracts и regression tests, а не одновременно переписывать всё без проверяемой основы.

### Последовательность

**Сначала OFF-01/02:** контракты safety, regression, deadlock/panic, helper и cancel/Stop. Затем **OFF-03/04:** применённая сессия, metrics, outcomes и полноценные профили. Далее **OFF-05/06:** реальные доказательства пути, updater, resource lifetime. Параллельные независимые задачи по окружению/документации допустимы, но product acceptance зависит от критического пути. **OFF-07** восстанавливает воспроизводимую сборку и release evidence. **OFF-08** доводит UX. **OFF-09** — полностью подготовленный сервер и live-приёмка после оплаты; закупка второго VPS не блокирует офлайн-исправления.

### Что можно проверить без платного VPS

| Стенд | Набор проверок |
|---|---|
| Go unit/property/fuzz | Конвертация каждого транспорта, refs, stale generation, panic/error, state transitions, подписи, staged update |
| Loopback интеграция | Реальный sing-box, selector/rollback, fake proxy, metrics, независимые mock endpoints, latency/reset/EOF/freeze/endpoint outage |
| Linux VM/контейнер на локальной машине | Полный server render/check, staged deploy, rollback, synthetic credentials, конфигурационная совместимость |
| Изолированная Windows VM с snapshot и admin | Production EXE helper, реальные WFP/TUN/внешний процесс/DNS/IPv6/UDP, Stop/crash/reboot/adapter change, восстановление после отказа |
| UI с локальным backend/fixtures | Все реальные состояния, доступность, DPI/scaling, отсутствие mock в release |

Не запускать disruptive firewall-тесты на рабочем компьютере пользователя как часть обычного `go test`. Служебные настройки должны восстанавливаться даже после неуспешного теста.

### Критерии готовности

- Для всех P0/P1 есть regression/acceptance evidence; тест возвращает ошибку при инъекции дефекта, а не только PASS на happy path.
- После команды Stop старые операции не запускают новую сессию; pending/blocked отражаются честно и имеют ограниченный отклик UI. Целевые времена утверждаются по локальному baseline, а не объявляются достигнутыми заранее.
- В strict-режиме ни один проверенный аварийный переход не выпускает защищённый трафик напрямую. Автоматический auto-unblock, если он вообще поддерживается, явно отделён как иная политика.
- Чистая frontend/tagged Go/Wails/installer сборка привязана к ревизии; пользовательский EXE и manifest относятся к тем же исходникам. Отсутствующий NSIS не считается полным успешным release.
- Для скорости измеряются throughput, RTT/TTFB p50/p95, time-to-protected, recovery time, packet loss, CPU/RAM/handles, контрольный маршрут и стоимость включённых проверок. Все варианты сравниваются на одном стенде и временном окне, отдельно TCP/UDP и один/много потоков. Массовое включение mux/Brutal/TFO без результата A/B не является оптимизацией.
- После возвращения VPS — повторная живая проверка с актуальной датой по нескольким сетям; второй ASN считается независимым только после доказанного end-to-end пути и проверки общих control-plane зависимостей.

## 7. Справочные первоисточники

- Локальные исходники pinned Wails v2.13.0: `internal/frontend/desktop/windows/{frontend.go,single_instance.go}` — порядок SingleInstance и OnStartup.
- [Microsoft: Filter Arbitration](https://learn.microsoft.com/en-us/windows/win32/fwp/filter-arbitration) — порядок WFP и права действий. Не выводить свойства effective policy из одного названия hard/soft.
- [Go net/http Transport](https://pkg.go.dev/net/http#Transport) и [CloseIdleConnections](https://pkg.go.dev/net/http#Transport.CloseIdleConnections) — жизненный цикл HTTP-пулов.
- [sing-box TUN](https://sing-box.sagernet.org/configuration/inbound/tun/) — документация для сопоставления с pinned кодом. Текущий сайт upstream не подменяет совместимость реально закреплённой версии.

## 8. Итог

Оплата VPS вернёт возможность полевой проверки, но сама не исправит перечисленные ошибки клиента. Наиболее результативная ближайшая работа полностью офлайн: строгая политика защиты, helper/process lifecycle, отмена операций, единая engine session и полный профиль. Продуктовая реализация в рамках этого аудита не менялась; следующий этап — выполнять OFF-01…OFF-09 с отдельными доказательствами каждого закрытия.
