## 1. Модель цензуры: слои атаки

Современная блокировка — многослойная. Каждый слой требует своего обхода:

```text
L0  закон/платформа     — удаление контента, давление на магазины/CDN/платежи
L1  DNS                 — подмена, NXDOMAIN, block page, фильтр DoH/DoT
L2  IP/маршрутизация    — чёрные списки IP, подсети, ASN, датацентров
L3  HTTP/TLS/SNI        — фильтр Host/SNI, forged RST, ECH-блокировки
L4  DPI/поведение       — fingerprint протоколов, тайминги, размеры пакетов
L5  throttling          — намеренное замедление вместо ошибки
L6  allowlist/интранет  — разрешён только национальный набор сервисов
L7  физический shutdown — BGP withdrawal, глушилки, отключение энергий
```

Ключевые следствия:

- смена DNS не помогает при блокировке на L2/L3/L4;
- обычный VPN (известный IP, известный протокол) уязвим на L2/L4;
- ECH скрывает SNI, но не IP назначения и не факт подключения к провайдеру [документировано, RFC 9849];
- Tor/VPN бесполезны при L6/L7 без независимого физического пути;
- «подключено» ≠ «защищённый трафик реально прошёл через туннель» [доказано нами — см. случай route.final=block];

## 2. Слой за слоем: механизмы и контрмеры

### 2.1. DNS (L1)

Механизмы: подмена A-записи, NXDOMAIN, redirect на block page, фильтрация DoH/DoT-endpoint'ов.

Контрмеры (по возрастанию надёжности):
1. DoH/DoT к независимому резолверу — скрывает запрос, но endpoint виден и может быть заблокирован.
2. DNS внутри туннеля (dns.detour: proxy) — доминирующая практика; запрос уходит резолверу через защищённый канал.
3. Встроенный резолвер клиента, bootstrap по IP.

Подводные камни:
- DoH через `https://1.1.1.1/dns-query` с `detour: direct` в окружении с фильтрацией L1 — прямая утечка и точка отказа [доказано нами: bootstrap домена сервера шёл через direct и периодически срывался];
- правило `{"outbound": "any"}` в dns.rules перенаправляет ВСЕ DNS-запросы (включая резолвинг адреса самого VPN-сервера) на указанный сервер; если этот сервер доступен только через туннель — рекурсивная зависимость и вечный цикл/таймаут [доказано нами];

### 2.2. IP/ASN/CDN (L2)

Механизмы: блок IP, подсети, ASN, хостеров; collateral damage от блокировки CDN.

Контрмеры: другой origin/CDN, другой ASN, фронтинг через популярные CDN (Cloudflare в РФ частично деградирует, но TCP 443 к CF edge остаётся достижимым из большинства сетей — [полевое наблюдение, требует постоянной перепроверки]).

Важно: IP VPS, торчащий прямо (наш HY2), — постоянный L2-риск. TCP-путь через CF скрывает origin за edge-IP.

### 2.3. HTTP/TLS/SNI (L3)

Механизмы: фильтр по SNI в ClientHello, по Host в HTTP; forged RST; timeout после ClientHello; поддельные сертификаты (MITM).

Контрмеры:
- TLS 1.3 + ECH (RFC 9849) — скрывает SNI; поддержка CDN/сервера обязательна;
- домен-фронтинг — мёртв для крупных CDN [документировано];
- WebSocket-туннель через легитимный домен за CDN — traffic выглядит как обычный HTTPS+WSS к сайту [используется нами];
- REALITY — кража TLS-отпечатка реального сайта; сложнее для цензора, но fingerprintable [документировано XTLS].

Анти-паттерн: отключение проверки сертификата. Наше правило: `insecure` запрещён; для self-signed HY2 — пиннинг сертификата в конфиг клиента [реализовано].

### 2.4. DPI/протокольный fingerprint (L4)

Механизмы: классификация по handshake/таймингам/размерам; active probing (цензор сам подключается к подозрительному серверу).

Контрмеры:
- uTLS (имитация ClientHello браузера) — усложняет пассивный fingerprint; upstream сам помечает как не-undetectable [документировано];
- обфускация транспортного слоя: salamander (HY2), obfs4, WebTunnel;
- WebSocket через CDN: трафик неотличим от обычного сайта на edge, но VLESS-протокол внутри WS распознаётся активным пробером, знающим путь [гипотеза с высоким правдоподобием];
- анти-active-probing: сервер должен отвечать на неавторизованные подключения как обычный веб-сервер (404/редирект), а не как VPN [направление развития].

Важно про WS early-data: sing-box передаёт первую порцию VLESS через заголовок `Sec-WebSocket-Protocol` в base64url. Значение заголовка — произвольная base64-строка, НЕ литерал «VLESS». Это опровергает популярное заблуждение о «специальном заголовке VLESS» [доказано нами серверными логами].

#### 2.4a. Поведенческая заморозка: детект по AND-сигналам (2026, полевые данные)

С начала 2026 TSPU в ряде регионов перешла от сигнатур к ПОВЕДЕНЧЕСКОМУ анализу:
решение о деградации принимается при одновременном совпадении нескольких
сигналов (логическое AND), а не по одному байтовому паттерну [полевое
наблюдение сообщества, Habr 1047442/990236 — реконструкция чёрного ящика,
числа читать как рабочие гипотезы]. Сигналы из обсуждений:

1. **AS/подсеть назначения**: зарубежные DC (Hetzner/DO/OVH) и ряд RU-облаков
   проходят «поведенческую проверку» чаще; крупные CDN (Cloudflare/Akamai/Google)
   целиком в список не входят — иначе легла бы половина легального рунета
   [анализ]. Это согласуется с нашей хроникой: CDN-ветка канала A деградирует
   волнами (V2-026/039/040), а HY2/QUIC — в другие окна.
2. **TLS-fingerprint клиента (JA3/JA4)**: uTLS-имитация браузера остаётся
   необходимой, но недостаточной. Важно: после начала заморозки СМЕНА
   fingerprint не лечит и по полевым данным может продлевать штраф-окно —
   заранее запасать альтернативные fingerprint-профили бессмысленно; полезнее
   менять транспорт (порт/путь/протокол).
3. **Тайминги/объём**: известны наблюдения «заморозка после первых ~15–20 КБ»
   (net4people #490) и «долгоживущее TCP-соединение = подозрительное» — ровно
   наш класс V2-026 (freeze после 16 КБ) и подтверждённая живучесть
   коротких запросов.

Практические следствия для нас:
- **Порт имеет значение**: в февральской волне VLESS+REALITY на 443 рубился,
  тот же конфиг на высоком порту (47000+) продолжал работать в заметной доле
  случаев [полевое наблюдение]. Наш REALITY на 8443 — уже «не 443»; при
  деградации 8443 следующий шаг — перенос на высокий порт (нфtables-redirect
  как у HY2-hopping, без правки клиента).
- **Multiplex на REALITY НЕ включаем** (opt-in в рендере и так консервативный):
  mux размазывает много потоков по одному TCP-соединению — увеличивает
  «долгоживущие соединения с большим объёмом», что попадает в поведенческий
  профиль заморозки. Держать прямые короткоживущие соединения.
- **Разнородность = выживание**: TCP+REALITY (прямой), QUIC+obfs (прямой),
  WS+CDN — три разных сигнатурных профиля. Побеждает не «лучший протокол»,
  а независимость отказов [полевое наблюдение — «швейцарский нож» выживает].
- **Мобильные сети**: в волнах февраля–июня LTE-операторы работали, когда
  проводные деградировали [полевое наблюдение] — при диагностике фиксировать
  оператора/тип сети (у нас это есть: NetworkFacts.connectionType/ISP).
- **Выборочный SYN-блэкхол не-443 портов (своя дата-точка, 2026-09-14,
  V2-051)**: в сети владельца зафиксирован эпизод, когда TCP SYN ко ВСЕМ
  не-443 портам VPS (8443/8445/закрытый 12345) молча терялись — "CONNECTED"
  локально (отдает middlebox), но на сервере 0 пакетов (tcpdump; методология
  подтверждена тем же фильтром на живом 443-хендшейке); 443 и SSH при этом
  живы, nft-счётчик правила 8445 = 0 с момента создания. Важно: канал
  «порт выше 443 живёт» НЕ абсолютен — фильтр может включаться на дни
  (8443/REALITY был достижим 2026-09-12 из той же сети и чёрный 2026-09-14)
  и, судя по закрытому 12345, распространяется на весь диапазон, а не только
  на известные порты. Экспериментально: реальный протокол на нестандартном
  порту может оказаться недостижимым целиком — держать 443-вариант канала
  (CDN/WS) и UDP-канал как альтернативные пути, high-port — третий эшелон.

### 2.5. QUIC/UDP (L1.5)

Механизмы: полный запрет UDP/443; разбор QUIC Initial (ключи известны) с извлечением SNI [исследование, USENIX Security 2025 — GFW].

Следствие: HY2/QUIC-пути деградируют первыми. Наша практика: в сети с фильтрацией UDP HY2 просто не подключается («no recent network activity»), а TCP/VLESS-WS продолжает работать [доказано нами 2026-09-08]. Держать оба: TCP-канал базовый, UDP-канал бонусом.

### 2.6. Throttling (L5)

Труднее доказать и труднее обойти. Признаки: работает, но медленно; различия между протоколами на одном маршруте. Контрмера: другой транспорт/маршрут; измерение через baseline (OONI-подход), не «на глаз».

### 2.7. Allowlist и shutdown (L6/L7)

Программного обхода нет. Нужен другой физический путь (роуминг, спутник, другой оператор). Наш продукт честно сообщает BLOCKED — и это правильное поведение, описанное в fail-closed контракте.

## 3. Архитектурные принципы защищённого клиента (выводы из практики)

1. **Fail-closed** — при отсутствии подтверждённого защищённого пути трафик не выпускается. Никакого «а вдруг напрямую получится».
2. **Доказательство, а не индикация**: protected probe = DNS через туннель + 2 HTTPS-цели + ожидаемый egress + negative direct-leak test. HTTP 101/открытый порт/успешный handshake — НЕ доказательство [доказано нами: сервер с route.final=block принимал VLESS-сессии и блокировал весь трафик, при этом клиент выглядел «подключённым»].
3. **Один владелец lifecycle**: обёртка владеет контекстом движка. Операционный таймаут операции (Start/Reload) не должен быть контекстом движка — иначе движок умирает сразу после старта [доказано нами: P0-дефект Manager].
4. **Секреты только по ссылке**: конфиги в git — с плейсхолдерами; рендер в runtime — локально; секреты никогда не в чат/лог/diff.
5. **Сертификат pinned, не disabled**: self-signed сервер = пиннинг PEM в клиенте, `insecure` запрещён.
6. **Два канала = разные классы отказа**: TCP/CDN (VLESS+WS+TLS) и UDP/direct (HY2) не должны падать одновременно от одной причины.
7. **Валидация конфига до запуска**: references, selector без direct, отсутствие плейсхолдеров, strict JSON.
8. **Клиентская фича транспорта = контракт ОБОИХ концов**: при включении транспортной оптимизации на клиенте (mux, padding, новые поля) серверный inbound обязан уметь её терминировать ТЕМ ЖЕ изменением — иначе получаем невидимую снаружи деградацию: CDN жив, TLS жив, auth проходит, а данные рвутся (EOF) [доказано нами 2026-09-12: клиентский h2mux+padding по умолчанию против сервера без multiplex → probe «3 of 4 failed: EOF» при полностью рабочем пути]. Отсюда же: default-on транспортных фич небезопасен при гетерогенной серверной ферме — включать фичу стоит вместе с сервером или через дескриптор (per-канал), а не глобальным дефолтом.
9. **Провал probe ≠ утечка ≠ недоступность канала**: три состояния требуют разных реакций. Мерцание (сеть дрогнула) — трафик физически не идёт мимо туннеля, останавливать его «для безопасности» нечего: быстрое подтверждение серией репроб и продолжение. Реальная утечка (direct = tunnel в SOCKS) — fail-closed. Деградация канала (подтверждённая серия) — автопереключение. Одно состояние «probe failed» для всех трёх случаев превращает любое сетевое чихание в полный останов VPN [доказано нами: инцидент V2-026 — CGNAT-мерцание роняло VPN целиком на первом же тике].
10. **Bootstrap не должен быть единственным и экзотичным**: резолв имени туннельного сервера ДО старта движка — мультистратегичный (plain UDP флот + DoH по IP-литералу + кэш последнего хорошего), в коде приложения, а не в конфиге ядра: политика владеет кодом, а не hopes. DoT/853 — популярная тихая точка отказа в фильтрующих сетях [вывод из THEORY §2.1; реализация preflight в V2-037].
11. **TCP-сессии должны переживать простаивание**: REALITY-сессии без mux простаивают дольше WS; системные TCP keep-alive (Linux 2ч+) не удерживают NAT/стейт-записи — сессия мертва при возврате трафика. Держать keep-alive 60/20с на dial (сервер + клиент) и TFO для быстрых ресоединений [инженерная практика; V2-045]. Конфигурация «валидная ≠ живая»: sing-box check пропускает семантически мёртвые блоки (REALITY без server_name = пустой список принятых SNI = все клиенты «invalid connection») — сверять по логам хендшейков, не по check [доказано нами 2026-09-12: REALITY-инбаунд без server_name принимал TCP, отвечал как донор, но все аутентичные клиенты отвергал].
12. **Multiplex — инструмент с двойным дном**: mux экономит хендшейки и маскирует объём, но создаёт долгоживущие соединения с большим объёмом — именно поведенческий профиль, под который ТСПУ точит заморозку (§2.4a). Для каналов, живущих под поведенческим анализом, — короткоживущие прямые соединения без mux; mux включать только там, где сервер явно демультиплексирует И поведенческий детект не активен.

## 4. Реестр ложных блокеров (анти-знание)

Эти «блокеры» были найдены в старом плане/аудите и опровергнуты live-проверкой. Фиксируем, чтобы не повторить:

| Ложный блокер | Откуда | Правда |
|---|---|---|
| «nginx возвращает 400 на Sec-WebSocket-Protocol: VLESS» | SERVER-2026-09-01-1 | nginx отдаёт 101; 400 отдаёт сам sing-box на невалидный base64 subprotocol. Литерал «VLESS» не используется реальным клиентом [доказано] |
| «нужен скрипт vps-diagnose-and-fix-nginx-ws.sh» | тот же | Скрипт решал несуществующую проблему; сервер ни разу не был причиной 400 [доказано] |
| «CF token IP-restricted = мягкий блокир» | phase-0 evidence | Реального чтения через API не требовалось: всё проверяется DNS/TLS/SSH. Токен вообще не нужен для текущего MVP [доказано] |
| «нужен второй домен для независимого failure domain» | PLAN §5.2 | Верно, но это не блокер разработки клиента; каналы живут на одном VPS и это документированный компромисс |
| «WS 400 — ожидаемо, реальный клиент пройдёт» | PHASE-8A journal | Дважды неверно: и 400 не от nginx, и «пройдёт» оказалось ложью, пока не починили серверный route.final [доказано] |
| «сертификат legacy-zone не соответствует → Full (Strict) недоступен» | RELEASE-2026-08-28-1 | Починено и не имеет отношения к клиентскому пути |

| «клиентский mux можно включить глобальным дефолтом, сервер не трогая» | V2-037 live | EOF на всех соединениях при живом CDN+TLS+auth: sing-box-сервер без multiplex-блока рвёт mux-стримы; чинится сервером (multiplex enabled+padding) или per-канальным дескриптором [доказано] |
| «probe «3 of 4 failed: EOF» при живом сервере = дефект клиента/сервера (V2-039)» | live-сессия 2026-09-12 | Сервер ни при чём: nginx/sing-box/config чисты (SSH-проверка по runbook), /ip отвечает, non-mux curl прошёл бы — но A/B live-тест mux on/off показал ОДИНАКОВЫЙ висящий запрос без ответа, серверные логи видят dial и open stream без ошибок. Это деградация return-пути клиент↔CF (класс V2-026), совпавшая по времени. Урок: «EOF на probe» ≠ «транспорт сломан»; прежде чинить — A/B один параметр + серверные логи [доказано] |

Мета-вывод: почти все длинные блокеры проекта были **серверными конфигурационными ошибками**, которые могли быть найдены за один SSH-сеанс с чтением серверных логов. Урок: живая диагностика > гипотезы из документации.

## 5. Открытые вопросы и направления (бэклог теории)

- REALITY/XHTTP как канал B: **исследовано 2026-09-11** (docs/B1-REALITY-RESEARCH.md, PLAN V2-031): ядро умеет REALITY (клиент под with_utls), XHTTP — нет (форки client-only); выбран VLESS+TCP+REALITY без Vision. Осталось открытым: live-поведение REALITY в целевых РФ-сетях после деплоя VPS-B [требует полевой проверки];
- ECH через Cloudflare для VLESS+WS: скрывает SNI от локального DPI [проверить поддержку CF];
- XHTTP вместо WS: **изучено 2026-09-11**: в pinned upstream-ядре отсутствует (SagerNet/sing-box#3076 открыт), есть только в форках (sing-box-lx — client transport, сервер = Xray). Смена ядра отклонена (V2-031); переоценить, если XHTTP попадёт в upstream;
- anti-probing: поведение VLESS-инбаунда на неавторизованный WS-запрос (сейчас: 400 от sing-box = палево; нужно: ответ как у обычного сайта) [гипотеза, проверить]. Для канала B закрывается дизайном REALITY (неавторизованный TLS уезжает прозрачным прокси на донора — RESEARCH §5); для канала A остаётся открытым (COMPETITOR-FEATURES F5);
- национальный DNS: поведение клиента в сети, где домены удаляются из резолверов [исследование];
- IPv6-утечки в TUN-режиме [проверить];
- семантика `dns.rules.outbound: any` vs `"outbound": ["proxy"]` в sing-box 1.13 [документировано частично, протестировать];
- IP-репутация датацентра ≠ отказ канала: Cloudflare-fronted сервисы (chatgpt.com — проверено live 2026-09-12) отдают 403 JS-challenge на egress датацентровского VPS, причём С САМОГО сервера (не зависит от клиента/транспорта/маршрута). Туннель при этом полностью жив (probe pass, другие сайты 200). Это граница продукта: egress-IP принадлежит ASN хостера, и репутацию чинит только другой egress (B1) — не код клиента [доказано]. Развитие (V2-041, тот же день): даже с одним VPS egress можно заменить БЕЗ второго сервера — серверный sing-box endpoint wireguard на Cloudflare WARP + route rule по домену; проверено live: chatgpt.com/cdn-cgi/trace через туннель = warp=on, ip=104.28.219.140 вместо 203.0.113.10. Остаточная граница: интерактивный Cf-Mitigated: challenge curl/не-браузерный клиент не решает по определению — WARP убирает IP-фактор, финальный JS-челлендж проходит браузер. Egress = отдельное измерение от транспорта: канал жив, но IP «грязный» — это два независимых сбоя с независимыми фиксами.

## 6. Как проверять новые факты (метод)

1. Воспроизводимый тест на живой системе (curl/openssl/ssh/log), а не чтение документации.
2. Разделять «вижу ответ edge/CDN» от «вижу ответ origin» (по cf-ray, Server-заголовку, логам сервера).
3. Сравнивать поведение через туннель и напрямую (egress-маркеры).
4. Хеши секретов вместо чтения значений при сверке конфигураций.
5. Каждый вывод в этот файл — с датой и уровнем достоверности.
