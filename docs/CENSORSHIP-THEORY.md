## 0. Инженерная поправка 2026-10-19

Нормативные требования перенесены в PLAN FR-009…012. Ниже сохраняется
исследовательская история; прежние формулировки «неотличим», «гарантирует»,
«не блокируется» нельзя читать как универсальное доказательство. В этой
сессии измерений текущих блокировок на сетях владельца не проводилось.

- [исследование] Шифрование/случайный payload не обеспечивают нераспознаваемость:
  USENIX Security 2023 описывает пассивные эвристики для fully encrypted traffic.
  Это измерения конкретной системы и периода, а не доказательство одинакового
  поведения нынешних российских сетей. [Исследование и открытые данные](https://gfw.report/publications/usenixsecurity23/en/).
- [документировано] OONI отделяет аномалию от подтверждённой блокировки:
  нестабильная сеть и отказ сайта могут давать ложные срабатывания. Поэтому
  единичный timeout/reset у нас означает наблюдение, не установленный диагноз.
  [Методика интерпретации OONI](https://ooni.org/support/interpreting-ooni-data/).
- [инженерный вывод] WS/CDN, REALITY, ShadowTLS и HY2 — кандидаты для разных
  условий. TLS/QUIC, порт и fingerprint не дают универсального выигрыша.
  Один origin/ASN/egress или общий DNS остаётся общей точкой отказа.
- [граница измерения] Малый HTTPS echo подтверждает только проверенный запрос;
  freeze, долгие потоки, IPv6/UDP/OS DNS требуют других проверок. Различие
  direct/protected IP не является полным доказательством OS fail-closed.
- [решение проекта] Strict WFP не должен сам открывать direct после crash,
  истечения таймера, автоматической ошибки или повторного запуска GUI.
  Снять барьер может явный Disconnect после остановки engine. Persistent
  filters и транзакции — разные свойства: при переустановке политики нельзя
  удалять старые блоки до готовности новых. [WFP transaction API](https://learn.microsoft.com/en-us/windows/win32/api/fwpmu/nf-fwpmu-fwpmtransactionbegin0).

До оплаты VPS можно доказать локальные lifecycle/data contracts и проверить
синтетические сбои. Реальную скорость и устойчивость к текущей фильтрации
без живого пути измерить нельзя. Критерии сравнения — PLAN FR-012.

**Поправка V2-109, 2026-10-21.** Авторские разделы и история сохранены, но
исправлены причинные и абсолютные выводы: AND-классификатор ТСПУ не установлен;
CDN entry ≠ egress; chunked/Range ≠ новые TCP-соединения; 400 ≠ доказательство
VPN; QUIC CID ≠ обход IP-блока; allowlist ≠ физический shutdown. Сопоставление
с кодом — §7.4, новые основания — §11. Внешние исследования просмотрены;
сеть владельца, серверы и транспортная работоспособность сейчас не измерялись.

## 1. Модель цензуры: слои атаки

Это наша классификация воздействия, **не уровни OSI**. Механизмы могут
сочетаться; одна контрмера иногда затрагивает несколько классов:

```text
L0  закон/платформа     — удаление контента, давление на магазины/CDN/платежи
L1  DNS                 — подмена, NXDOMAIN, block page, фильтр DoH/DoT
L2  IP/маршрутизация    — чёрные списки IP, подсети, ASN, датацентров
L3  HTTP/TLS/SNI        — фильтр Host/SNI, forged RST, ECH-блокировки
L4  DPI/поведение       — fingerprint протоколов, тайминги, размеры пакетов
L5  throttling          — намеренное замедление вместо ошибки
L6  allowlist/интранет  — разрешён только национальный набор сервисов
L7  физический shutdown — BGP withdrawal, глушилки, отключение энергий
```

Ключевые следствия:

- смена DNS не помогает при блокировке на L2/L3/L4;
- обычный VPN (известный IP, известный протокол) уязвим на L2/L4;
- ECH скрывает SNI, но не IP назначения и не факт подключения к провайдеру [документировано, RFC 9849];
- при L6 важны реальные разрешённые пути и возможность использовать их как
  транспорт; при L7 без какого-либо внешнего пути передавать новые данные нельзя (§2.7);
- «подключено» ≠ «защищённый трафик реально прошёл через туннель» [доказано нами — см. случай route.final=block];

## 2. Слой за слоем: механизмы и контрмеры

### 2.1. DNS (L1)

Механизмы: подмена A-записи, NXDOMAIN, redirect на block page, фильтрация DoH/DoT-endpoint'ов.

Варианты (универсального порядка надёжности нет):
1. DoH/DoT к независимому резолверу — скрывает запрос, но endpoint виден и может быть заблокирован.
2. DNS внутри туннеля (dns.detour: proxy) — доминирующая практика; запрос уходит резолверу через защищённый канал.
3. Встроенный резолвер клиента, bootstrap по IP.

Подводные камни:
- direct DoH к IP-литералу шифрует DNS-содержимое до резолвера, но выдаёт
  его адрес и зависит от внешнего пути. Это не plaintext DNS-утечка само по себе;
  для пользовательских имён может нарушать protected-route policy. Bootstrap
  имени самого туннеля — отдельное минимальное исключение, без общего direct fallback;
- правило `{"outbound": "any"}` в dns.rules перенаправляет ВСЕ DNS-запросы (включая резолвинг адреса самого VPN-сервера) на указанный сервер; если этот сервер доступен только через туннель — рекурсивная зависимость и вечный цикл/таймаут [доказано нами];

### 2.2. IP/ASN/CDN (L2)

Механизмы: блок IP, подсети, ASN, хостеров; collateral damage от блокировки CDN.

Контрмеры-кандидаты: другой origin/ASN, доступный CDN reverse proxy. Доли
«большинство сетей» у проекта не измерены; достижимость edge не доказывает
прохождение больших потоков. [Cloudflare описал ограничения в РФ в июне 2025](https://blog.cloudflare.com/russian-internet-users-are-unable-to-access-the-open-internet).

Важно: у прямого HY2 клиент соединяется с IP VPS. При CDN-входе наблюдатель
на участке клиент→edge видит edge-IP; origin может раскрываться через другие
каналы, DNS-историю или ошибки конфигурации. Обычный reverse proxy своего
домена и domain fronting с различными SNI/Host — разные конструкции.

### 2.3. HTTP/TLS/SNI (L3)

Механизмы: фильтр по SNI в ClientHello, по Host в HTTP; forged RST; timeout после ClientHello; поддельные сертификаты (MITM).

Контрмеры:
- TLS 1.3 + ECH (RFC 9849) — скрывает SNI; поддержка CDN/сервера обязательна;
- домен-фронтинг: Google/AWS отключили в апреле 2018, Azure (meek-azure)
  продолжал работать; в 2021–2022 Azure анонсировал запрет, но 2023-09-25
  уточнил исключение Azure Front Door: несовпадение разрешается для доменов
  **одной Azure subscription**, а не произвольного чужого front domain.
  Это не готовый публичный meek-резерв. [Microsoft, политика 2023–2024](https://learn.microsoft.com/en-gb/answers/questions/1461527/take-action-to-stop-domain-fronting-on-your-applic);
- WebSocket-туннель через легитимный домен за CDN — traffic выглядит как обычный HTTPS+WSS к сайту [используется нами];
- REALITY — аутентифицированный транспорт с TLS-маскировкой и обработкой
  неавторизованного трафика через handshake target. Это не «кража сертификата»
  и не гарантия нераспознаваемости; реализация, донор и конфигурация обоих концов
  существенны. [Upstream REALITY](https://github.com/XTLS/REALITY).

Анти-паттерн: отключение проверки сертификата. Наше правило: `insecure` запрещён; для self-signed HY2 — пиннинг сертификата в конфиг клиента [реализовано].

### 2.4. DPI/протокольный fingerprint (L4)

Механизмы: классификация по handshake/таймингам/размерам; active probing (цензор сам подключается к подозрительному серверу).

Контрмеры:
- uTLS (имитация ClientHello браузера) — усложняет пассивный fingerprint; upstream сам помечает как не-undetectable [документировано];
- обфускация транспортного слоя: salamander (HY2), obfs4, WebTunnel;
- WebSocket через CDN скрывает содержимое от внешнего пассивного наблюдателя
  при корректном TLS, но оставляет размеры/время/длительность. CDN завершает
  TLS и видит HTTP/WS; знание WS-пути само по себе не даёт VLESS-credentials;
- анти-active-probing: сервер должен отвечать на неавторизованные подключения как обычный веб-сервер (404/редирект), а не как VPN [направление развития];
- TLS-in-TLS-фингерпринт вложенных рукопожатий — протокол-агностичный детект
  прокси-трафика (USENIX Security 2024, Xue/Kallitsis/Houmansadr/Ensafi):
  padding и mux не устраняют все признаки; split-streams — отдельная
  проверяемая гипотеза, не доказанная этой работой защита (§2.11);

Важно про WS early-data: в нашем рендере выбран `Sec-WebSocket-Protocol`,
данные кодируются base64url, это не литерал «VLESS». Заголовок виден TLS-endpoint,
но не читается пассивно сквозь TLS. Это режим конфигурации, а не обязательное
поведение всякого sing-box WS-клиента (render.go / pinned transport/v2raywebsocket).

#### 2.4a. Поведенческая заморозка: гипотеза AND-сигналов и полевые данные

Обсуждения 2026 года (Habr 1047442/990236) предлагают модель совокупности
сигналов. Это реконструкция чёрного ящика, **не установленное правило AND и
не доказательство замены сигнатур поведенческим анализом во всех ТСПУ**.
Сигналы-кандидаты для контролируемого эксперимента:

1. **AS/подсеть назначения**: зарубежные DC (Hetzner/DO/OVH) и ряд RU-облаков
   проходят «поведенческую проверку» чаще; крупные CDN (Cloudflare/Akamai/Google)
   могут иметь другую политику. Высокая цена collateral damage не запрещает
   цензору деградировать CDN целиком. В нашей хронике CDN-ветка A деградировала
   волнами (V2-026/039/040), а HY2/QUIC — в другие окна.
2. **TLS-fingerprint клиента (JA3/JA4)**: один из возможных признаков.
   uTLS не необходим для всех транспортов и не достаточен для маскировки.
   Сообщения о продлении «штраф-окна» после смены fingerprint — гипотеза;
   нельзя запрещать альтернативы без A/B или менять их бесконечно автоматически.
3. **Тайминги/объём**: известны наблюдения «заморозка после первых ~15–20 КБ»
   (net4people #490) и «долгоживущее TCP-соединение = подозрительное» — ровно
   наш класс V2-026 (freeze после 16 КБ) и подтверждённая живучесть
   коротких запросов.

Практические следствия для нас:
- **Порт имеет значение**: в февральской волне VLESS+REALITY на 443 рубился,
  тот же конфиг на высоком порту (47000+) продолжал работать в заметной доле
  случаев [историческое полевое сообщение, не текущая доля]. Порт 8443 также
  может блокироваться; новый порт требует согласованного descriptor/client/server.
  Один серверный redirect не меняет адрес назначения пакетов клиента у цензора.
- **Multiplex на REALITY — opt-in**, согласованный с сервером. Общая длинная
  TCP-сессия может ухудшать объёмный лимит, но уменьшать число новых TLS-сессий.
  Направление эффекта определяет эксперимент (§2.10 п.8), не имя транспорта.
- **Разнородность как кандидат резерва**: TCP+REALITY, QUIC+obfs, WS+CDN
  имеют разные wire profiles; общая инфраструктура всё ещё может отказать
  одновременно. Выигрыш устойчивости проверяется, не следует из трёх названий.
- **Мобильные сети**: в отдельных сообщениях LTE-операторы работали, когда
  проводные деградировали [полевое наблюдение] — при диагностике фиксировать
  оператора/тип сети (у нас это есть: NetworkFacts.connectionType/ISP).
- **Выборочный SYN-блэкхол не-443 портов (своя дата-точка, 2026-09-14,
  V2-051)**: в сети владельца описан эпизод недостижимости трёх проверенных
  портов VPS (8443/8445/закрытый 12345). Локальное "CONNECTED" не подтверждало
  серверный handshake; на сервере 0 пакетов в capture (методология
  подтверждена тем же фильтром на живом 443-хендшейке); 443 и SSH при этом
  живы, nft-счётчик правила 8445 = 0 с момента создания. Важно: канал
  «порт выше 443 живёт» НЕ абсолютен — фильтр может включаться на дни
  (8443/REALITY был достижим 2026-09-12 из той же сети и чёрный 2026-09-14)
  и затронул проверенный закрытый 12345. Это не скан всего диапазона и не
  доказательство источника drop или поддельного SYN-ACK. Текущий rank портов
  нельзя вывести из одной сентябрьской точки; 443/UDP/high-port — кандидаты,
  каждый требует свежей проверки, без универсального «третьего эшелона».

### 2.5. QUIC/UDP (L1.5)

Механизмы: запрет UDP целиком/по порту, разбор QUIC Initial с извлечением SNI
при отсутствии ECH. Initial secrets выводятся из публичных параметров — это
не расшифровка последующих application data. [RFC 9001 §5.2](https://www.rfc-editor.org/rfc/rfc9001.html#section-5.2).
[Zohaib et al., USENIX 2025](https://gfw.report/publications/usenixsecurity25/en/)
измерили такой механизм в Китае; перенос на нынешнюю РФ требует измерения.

При реальном запрете UDP QUIC не подключится. Но одиночный QUIC timeout не
доказывает такой запрет: в нашей истории диагноз 2026-09-08 был пересмотрен
после live-прохождения HY2 2026-09-09 (PLAN §2.1). TCP и UDP — взаимные
кандидаты резерва; их текущий приоритет зависит от проверенного пути.

### 2.6. Throttling (L5)

Труднее доказать и труднее обойти. Признаки: работает, но медленно; различия между протоколами на одном маршруте. Контрмера: другой транспорт/маршрут; измерение через baseline (OONI-подход), не «на глаз».

### 2.7. Allowlist и shutdown (L6/L7)

Нужно различать три случая [инженерный вывод]:

1. **Исключения из throttling по SNI/Host**: часть имён получает другой режим;
   это ещё не строгий IP allowlist. Ошибка классификации middlebox может
   оставлять путь; проверять в стенде, не обещать программную невозможность.
2. **Строгий allowlist**: наш внешний endpoint недостижим. Путь возможен лишь
   если среди разрешённых сервисов есть реально доступный и пригодный relay
   с контролируемой нами/согласованной серверной стороной. Нельзя произвольно
   превратить чужой разрешённый сайт в VPN простым SNI/Host.
3. **Нет внешнего канала вообще**: программой отсутствующую связь не создать;
   требуется другой оператор/роуминг/физическая среда с рабочей связностью.

Нет проверенного разрешённого пути → BLOCKED при сохранённой защите.
Надпись «подозрение на allowlist» не заменяет диагноз всей сети.

### 2.8. ТСПУ: что известно о самой машине

ТСПУ — распределённая инфраструктура сетевого вмешательства. Ниже разделены
академические измерения, исторические заявления и неподтверждённые сведения;
состав устройств и охват каждого нынешнего оператора этим документом не установлены.

**Правовая хроника [сохранённые ссылки редакции 2026-09-16]:**
Следующие правовые номера, санкции и утверждения об обязанностях не прошли
повторную сверку с действующей редакцией официальных актов в V2-109. Это
исследовательские заметки, не основание юридических/UI-решений; вторичные
публикации не становятся первичными из-за метки «документировано».
- Федеральный закон 90-ФЗ от 01.05.2019 («суверенный Рунет») ввёл в 126-ФЗ «О связи»
  ст. 65.1–65.2, а в 149-ФЗ «Об информации» — ст. 15.9. Практическое заблуждение:
  «ТСПУ прописаны в 149-ФЗ» — на самом деле обязанность оператора пропускать трафик
  через ТСПУ — это п. 5.2 ст. 46 закона «О связи» (126-ФЗ), а ст. 15.9 149-ФЗ — про
  централизованное управление сетями через НЦУС/ЦМУ ССОП. Указывать нужно оба закона.
- Оператор обязан разместить ТСПУ у себя, обеспечить электропитание и доступ ГРЧЦ
  (оператор системы), но НЕ имеет доступа к софту/правилам «чёрного ящика»
  [документировано: Роскомсвобода, Ъ]. Оператор юридически отвечает за непропуск
  трафика через ТСПУ (штрафы 500 тыс — 5 млн руб с 2023 г. [документировано, КоАП]).
- С 1 января 2023 — ужесточение ответственности операторов; с 30 ноября 2024
  операторы обязаны согласовывать с РКН запуск/вывод из эксплуатации сетей
  и не препятствовать ТСПУ [документировано].
- Август 2024: поправки о сборе операторами данных об оборудовании
  абонентов (IP, MAC, регион, номер ТСПУ); декабрь 2024 — проект приказа РКН о
  формате передачи. Цель — корреляция «пользователь ↔ ТСПУ ↔ класс трафика»
  [документировано, Meduza 2024-12-21].
- Октябрь 2024: проект приказа РКН — порядок применения ТСПУ по решениям
  генпрокуратуры и её заместителей без суда [документировано: anti-malware.ru,
  secuteck; порядок действий цензора остаётся засекреченным].

**Deployment [исторические заявления ведомств/публикаций, не наш аудит]:**
- К августу 2023 РКН отчитался: 100% узлов связи оборудованы ТСПУ (мобильные,
  ШПД, трансграничные) [Интерфакс 2023-10-24].
- Заявление об импортозамещении (РГ 2024-06-03) не доказывает состав всего парка.
  ГРЧЦ как участник эксплуатации/управления нельзя автоматически называть
  производителем всех аппаратных и программных компонентов.
- ТСПУ ставятся на границе сети оператора: inline либо mirror/SPAN [исследование,
  Habr 992232]. Inline-инстанс может дропать, помечать и инжектить пакеты; mirror —
  наблюдает; отдельный инжектор на том же комплексе всё ещё способен отправлять
  пакеты. Схему конкретного оператора из этих вариантов не выводим.

**Архитектура из академического исследования [исследование: Xue, Mixon-Baca,
ValdikSS, Ablove, Kujath, Crandall, Ensafi — "TSPU: Russia's Decentralized
Censorship System", IMC 2022, dl.acm.org/doi/10.1145/3517745.3561461]:**
- ТСПУ — это ДЕЦЕНТРАЛИЗОВАННАЯ система: тысячи инстансов близко к абоненту,
  с централизованным управлением правилами (не «один большой фаервол» в центре).
- Инстансы in-path (в разрыв) и stateful (помнят соединение) с уникальным для
  каждого инстанса состоянием — отсюда «разные сети режут по-разному».
- Авторы выделяют SNI/IP/QUIC-триггеры и шесть поведений, включая drop и
  модификацию пакетов. Ранее здесь ошибочно смешивались триггеры, fingerprint
  и способы вмешательства; точная таксономия — §5.2 статьи, не наша новая шестёрка.
- Активное пробирование в РФ — отдельная гипотеза из dev.to/shinomontaz 2026-02;
  IMC'22 не доказывает её и не атрибутирует случайные сканы цензору.
- В выборке исследования 70% обнаруженных endpoints были не далее двух хопов
  от middlebox. Это не «все ТСПУ всегда в 1–2 хопах» и не замер задержки вмешательства.

**Что это означает практически [вывод]:**
- Один и тот же сервер может быть жив в МТС и мёртв в Мегафоне одновременно.
  Диагностика обязана фиксировать оператора/регион (NetworkFacts), иначе
  «работает/не работает» не интерпретируемо.
- Блокировка может проявиться только на части соединений (stateful
  per-соединение) — важна серия повторов, не один probe.
- Централизованное управление совместимо с несинхронным применением и
  локальным состоянием; нельзя предполагать единую текущую политику всех сетей.

### 2.9. Как операторы мешают VPN: каталог методов с фактчекингом

Уровни воздействия ТСПУ на VPN-трафик — от грубого к тонкому. Для каждого —
источник и уровень достоверности.

**A. Блокировка по IP/подсети [документировано]:** чёрные списки IP известных
VPN-провайдеров. Смена IP может помочь, пока не повторена блокировка и не
затронута новая подсеть; реестр не обязан исчерпывать фактические фильтры.

**B. Протокольная блокировка [документировано — хронология волн, Amnezia
(habr.com/ru/companies/amnezia/articles/861198)]:**
- 2021-09 — первые блокировки VPN-сервисов (VyprVPN, Opera VPN).
- 2023 — протокольные волны: OpenVPN, IKEv2/IPsec; 2023-08 — массовая волна
  OpenVPN+WireGuard; 2023-09 — WireGuard у ~20% пользователей не восстановился.
- 2024-08 (волна вокруг 1 августа) — широкая блокировка WireGuard во многих
  регионах; прошла почти незаметно на фоне замедления YouTube.
- 2024-10-15 — блокировка Shadowsocks на мобильном интернете.
- 2025-12-04 (РБК) — донастройка ТСПУ: целевая блокировка SOCKS5, VLESS, L2TP.
  РКН подтвердил только «развитие систем безопасности» [РБК]. Эксперты: VLESS
  стали выявлять по косвенным признакам, т.к. раньше он оставлял «минимум
  технических следов» [The Moscow Times, 2026-02-17].
- 2026 — продолжение: выборочные деградации по регионам и операторам.

**C. Функциональное подавление [наблюдаемый класс]:** соединение может
установиться, а передача данных — остановиться. Cloudflare описывает resets
и timeouts своих путей в июне 2025; этот источник не доказывает DNS-подмену
во всяком таком случае. Поэтому «подключено» ≠ «работает».

**D. Объёмная остановка [измерения поставщика + полевое сообщение]:**
- [Cloudflare, 2025-06-26](https://blog.cloudflare.com/russian-internet-users-are-unable-to-access-the-open-internet)
  описал ограничения с 9 июня на пути из РФ к своим сервисам: около первых
  16 КБ, разные TCP/TLS и QUIC варианты, resets и timeouts. Это данные о его
  сети в тот период, не универсальный порог российского интернета.
- [net4people #490, 2025-06-27](https://github.com/net4people/bbs/issues/490)
  описывает остановку после примерно 15–20 КБ server→client **на TCP-соединение**
  для некоторых зарубежных сетей. Новые соединения помогали в сообщённых
  опытах; HTTP-запросы внутри прежнего соединения — нет. Пакетные лимиты,
  исключения SSH/RDP и отдельные ASN — варианты сообщений, не один доказанный
  общий алгоритм. Нельзя объединять их с Cloudflare в закон «25 пакетов = 16КБ».

**E. TLS connection-based policing (TCP+TLS на 443) [полевое наблюдение]:**
net4people/bbs#546 (2025-11-14+): MTS/MGTS, JustLan, LanInterCom, Ростелеком
(Ижевск). Симптоматика: соединение рвётся как только идёт реальный трафик через
туннель (VLESS+Reality+vision); чем больше трафика, тем быстрее разрыв;
curl/браузер на тот же endpoint работает; через ~60 секунд можно переподключиться.
Гипотеза автора — влияние числа активных TLS-соединений; причина не установлена.
Mitigation по данным #546: убрать flow (vision), включить mux; смена порта с 443.
Позже (22.11) mux/XHTTP перестали помогать у части пользователей.

**F. Белые списки (L6 в нашей модели) [документировано]:**
- Эксперименты с «белым списком» мобильного интернета (2025, несколько регионов).
- 2026-03: Москва, 10 дней теста — доступ только к списку Минцифры; часть
  районов осталась без связи [Новая газета 2026-03-14].
- Эти публикации описывают разные режимы ограничений; техническая граница
  определяется доступными relay и реальным enforcement, см. §2.7.

**G. Полное отключение интернета (L7) [документировано]:**
- 2025-07 — 2099 шатдаунов мобильного интернета за месяц (проект «На связи»);
  с мая 2025 хотя бы раз отключали в каждом из 83 регионов [Novaya Europe 2026-03-26].
  Причина — БПЛА; механика — по регионам и по операторам, на часы.
- 2025-08: сообщения об ограничениях звонков WhatsApp/Telegram [Хабр/РБК].
  SIP-сигнатуры этих приложений первичным измерением здесь не подтверждены;
  общий факт ограничения звонков не раскрывает их протокол или механизм фильтра.
- В шатдауне программного обхода нет — только альтернативный физический путь.

**H. Активное пробирование [класс атак; атрибуция РФ не доказана здесь]:**
проверяются ответы, тайминги, replay и некорректные входы сервера. В GFW
такой класс измерен [Wu et al.](https://gfw.report/publications/usenixsecurity23/en/).
REALITY и web fallback — меры против части проб; ответ 404/400 сам по себе
не удостоверяет ни маскировку, ни VPN. Проверять отличимость от контрольного сайта.

**I. Сигнатурное вмешательство (IMC'22):** SNI/IP/QUIC-триггеры;
не подменять их универсальной гипотезой фильтра по QUIC CID (§2.8).
Механика помех смешанная: инстансы ТСПУ stateful, решения по соединениям
асинхронны.

**J. Сбор и корреляция данных [документировано]:** РКН собирает с операторов
IP/MAC/регион абонента + номер ТСПУ, через который идёт трафик (август–декабрь
2024). Плюс отчёт ГРЧЦ за 2023: «более 100 сигнатур для ограничения доступа...
в т.ч. VPN-сервисам, с эффективностью >95%» [документировано, отчёт ГРЧЦ].
Плюс ML-классификация зашифрованного трафика (VAS Experts, ResNet, 2023).

**Что из этого НЕ работает (фактчекинг анти-знания):**
- Правовые тезисы предыдущей редакции смешивали использование инструмента,
  рекламу и поиск материалов, административную и уголовную ответственность.
  Старые суммы/номера отозваны как непроверенная правовая справка. Техническая
  модель не устанавливает законность конкретного действия; юридические тексты
  продукта требуют отдельной актуализации по официальным актам.
- «Смена порта решает» — НЕ абсолют: эпизоды V2-051 (2026-09-14) показывают,
  что фильтр может закрывать и не-443 порты; выборочно и временно.
- «ECH гарантирует доступность» — неверно: ECH под Cloudflare (public_name
  cloudflare-ech.com) заблокирован с 2024-11-05 по сигнатуре «SNI cloudflare-ech.com
  + ECH extension» [net4people/bbs#417, ЦМУ ССОП официально рекомендовал
  отказаться от Cloudflare 2024-11-07]. Cloudflare при этом временно отключил ECH
  (community.cloudflare.com). ECH с другим public_name (defo.ie, tls-ech.dev)
  работал в описанном опыте. Это историческая сигнатура, не текущий тест всех
  CDN. ECH решает задачу приватности части ClientHello, не гарантирует путь.
- «Фрагментация всегда спасает» и «фрагментация всегда бесполезна» — оба
  утверждения чрезмерны. TLS records, TCP segmentation, IP fragmentation и
  рассинхронизация парсеров — разные методы. Их эффект зависит от middlebox;
  обычная нарезка payload не обходит счётчик суммарных байтов соединения.

**Контрмеры, которые подтверждаются данными [направление для нас]:**
1. Многоканальность с РАЗНЫМИ классами отказа (TCP+CDN / UDP+QUIC / high-port) —
   предохранитель от точечных донастроек ТСПУ (2025-12 показала: за один день
   легли SOCKS5+VLESS+L2TP у части операторов).
2. Проверять срок жизни/объём carrier-соединения как параметр (§2.4a),
   учитывая стоимость handshake и невозможность просто переоткрыть произвольный
   пользовательский TCP-поток с середины без поддерживающего это транспорта.
3. Различать **entry ASN**, видимый провайдеру клиента, и **egress ASN**, видимый
   целевому сайту. CDN reverse proxy меняет первый, дополнительный exit — второй.
4. Fail-closed + честная диагностика: различать "заморозку" (таймаут без RST),
   "RST", "DNS-саботаж" и "белый список" — разные реакции клиента (таймаут-логика
   vs мгновенный fail vs отсутствие пути). Словарь причин — в диагностике.
5. Регион/оператор как первоклассный факт телеметрии — ТСПУ распределённые,
   поведение зависит от них; без этого тега любая статистика блокировок шум.

### 2.10. Контрмеры: как противостоять каждой механике ТСПУ

Свод кандидатов по документации и полевым данным: для каждой механики из §2.9 —
возможные меры, не гарантии. Сверено с нашими правилами (PLAN V2-031 —
ядро не меняем; V2-037 — mux не глобальный дефолт; §2.3 этого файла —
insecure запрещён; серверные правки — только по явному разрешению владельца).

**Матрица «механика → контрмера»:**

| Механика (§2.9) | Контрмера | Статус/источник |
|---|---|---|
| A. IP/подсеть блок | CDN-фронт (edge IP не наш); смена ASN | [документировано] практика |
| B. Протокольная блокировка | иной wire profile: HTTPS/REALITY/QUIC-obfs; число профилей не равно независимости | дизайн upstream, проверка §10 |
| C. «Портит, не рвёт» | fail-closed + классификация отказа (см. ниже) | [доказано нами] |
| D. Объёмная остановка | проверять новые carrier-соединения/иной путь; HTTP chunks не сбрасывают TCP-счётчик, QUIC также может ограничиваться | исторические §2.9-D, эксперимент E-02 |
| E. TLS-policing на 443 (#546) | mux/XHTTP (меньше одновременных TLS), перенос порта, другой класс транспорта | [полевое] #546 |
| F. Белые списки | определить enforcement/доступный relay; нет validated пути → BLOCKED | §2.7; Cheburcheck описывает иной режим исключений |
| G. Шатдаун | fail-closed, честный BLOCKED, авто-reprobe по факту возвращения сети (V2-053/054 уже сделано) | [доказано нами] |
| H. Активное пробирование | аутентификация до отличимого поведения, web fallback, replay/error/timing matrix | дизайн, эксперимент E-04 |
| I. SNI/IP/QUIC-сигнатуры | согласованный TLS/obfs-профиль; CID migration не меняет заблокированный destination IP | §2.3/2.5, pinned compatibility |
| J. Сбор/корреляция | минимизация метаданных и доверительных сторон; VPN не предоставляет анонимность сам по себе | threat model §7 |

**Транспортный уровень — конкретика по документации sing-box (pinned ядро):**

1. **TLS-пиннинг лучше, чем мы думали**: sing-box 1.13+ умеет
   `tls.certificate_public_key_sha256` — пиннинг ПО ПУБЛИЧНОМУ КЛЮЧУ
   (список base64 SHA-256). Продление сертификата с тем же SPKI может сохранить
   пин; **ротация ключа меняет пин**. Нужны signed current/next, overlap,
   revocation, rollback policy и привязка к ChannelID; `insecure` запрещён.
   [документировано: sing-box.sagernet.org/configuration/shared/tls]
2. **REALITY**: сервер должен иметь `handshake.server` на реальный TLS 1.3 + h2
   донора и заполненный `server_name` (наш дефект 2026-09-12, §3.11: пустой список
   принятых SNI отвергал всех клиентов). «Steal oneself» (донор = свой сайт на той же
   машине) — вариант сократить зависимость от чужого донора, но не доказательство
   неотличимости. Нужна проверка клиента и неавторизованных входов.
   [документировано: XTLS/Xray-core docs; sing-box reality fields]
3. **uTLS — ограниченная имитация**: текущая upstream-документация помечает uTLS
   «Not Recommended» — uTLS копирует структуру ClientHello, но браузеры
   (BoringSSL/NSS) поведенчески другие, детект возможен; рекомендуемая альтернатива
   — NaiveProxy/браузерный dialer [документировано: sing-box TLS docs]. Для нас:
   существующий pinned путь сохраняется, NaiveProxy рассматривается отдельно.
   Рекомендация upstream не заменяет сравнительный замер (§9.3).
4. **TLS-фрагментация (`fragment`/`record_fragment`, 1.12+)**: upstream
   предупреждает об ограниченности простой нарезки и цене задержки. Это не
   эксперимент, исключающий все методы рассинхронизации на всех ТСПУ. Низкий
   приоритет до доказанного дефекта parser enforcement, не глобальный default.
5. **TLS `spoof` (sing-box 1.14)**: инжект фейкового ClientHello с белым SNI
   перед настоящим (wrong-sequence/checksum/ack/md5/timestamp — сервер отбрасывает,
   middlebox видит легитимный SNI). Требует CAP_NET_RAW/Windows-администратора
   (WinDivert). Кандидат на «режим проверки белых списков», но режим ТСПУ
   «всё, кроме списка» не обходит [документировано: sing-box TLS docs, 1.14].
6. **HY2/QUIC**: пример **нативного Hysteria2**, не JSON нашего sing-box:
   port hopping через диапазон — сервер: `listen: :20000-50000`
   (сам настраивает nftables-redirect); клиент sing-box (since 1.12.0):
   `server_ports: ["2080:3000"]` + `hop_interval` [документировано:
   sing-box hysteria2 outbound docs, v2.hysteria.network Full Server Config].
   Контрмера к точечному портовому дропу; `obfs.salamander` — когда режут
   QUIC-сигнатуры (превращает пакеты в случайные байты, НО несовместим с
   «валидным HTTP/3» — включать осознанно, per-канал); `sniGuard: strict` —
   сервер принимает только свой SNI. Поддержку аналогичной политики в конкретной
   server implementation проверять отдельно, названия YAML/JSON не взаимозаменяемы.
7. **TCP Brutal**: конгест-контроль «шлём с заданной скоростью, игнорируя потери»
   — v2 не требует поддержки протоколом (правило `brutalctl add <dst> <rate>`);
   критично НЕ делать его дефолтным конгест-контролем (без правила = 1 Mbps);
   проверяется отдельно при loss, с лимитом скорости и измерением задержки
   соседнего трафика; не создаёт пропускную способность [документировано:
   github.com/apernet/tcp-brutal README].
8. **Multiplex — per-канальная политика, НЕ дефолт** (наш принцип §3.12):
   - при лимите байтов на carrier mux может ухудшить ситуацию;
   - при ограничении количества TLS-сессий может помочь. Сообщения #546
     неоднородны. Гипотеза механизма определяет эксперимент, не автоприменение
     mux по одному timeout. Параметры должны поддерживаться обоими концами.
9. **XHTTP-идея (референс, у нас в ядре — splithttp-кандидат, V2-047)**: split
   up/down в разные соединения (можно разного транспорта/адреса/даже провайдера),
   TLS 1.2 + настоящий nginx на 443 перед ядром — серверный fingerprint
   подлинный, и Vision не нужен [документировано: Habr 990208, xray-examples].
   **В pinned sing-box 1.13.19 нет ни splithttp, ни xhttp**: проверен switch
   option/v2ray_transport.go. Предыдущая строка об upstream splithttp была
   ошибочна. [Xray design discussion #4113](https://github.com/XTLS/Xray-core/discussions/4113)
   — источник идеи, не готовая совместимость с нашим движком.

**Поведенческий уровень:**

10. **Idle, keep-alive и ротация — разные свойства**: TCP keep-alive проверяет
    простой и может поддерживать NAT-state, но не ограничивает срок жизни или
    накопленные байты. Значения 60/20с — наш исторический профиль, не универсальный
    оптимум. TFO — эксперимент с middlebox/fingerprint/replay-ограничениями,
    а не обязательное ускорение. Не обрывать действующие потоки ради ротации.
11. **Серверная разбивка контента**: chunked transfer и HTTP Range полезны
    для собственной HTTP-диагностики/докачки, но при reuse одного TCP-соединения
    счётчик байтов не обнуляют. VPN не может произвольно переписать Range внутри
    end-to-end HTTPS; миграция байтового потока требует поддержки обоих концов.
12. **Мультистратегичный DNS bootstrap** (V2-037 реализовано): plain UDP флот +
    DoH по IP-литералу + кэш последнего хорошего. Никогда не 853-only
    [§2.1, документировано].

**Маршрут/egress:**

13. **Egress-репутация — отдельное измерение** (V2-041): CDN-fronted вход
    обычно оставляет выходом VPS. Дополнительный WARP/server outbound может
    менять exit, но добавляет зависимость/доверие и не гарантирует снятие challenge.
14. **Первый хоп внутри РФ** [гипотеза]: меняет маршрут клиент→entry и точку
    международного выхода, но добавляет наблюдателя/стоимость/общий отказ.
    IMC'22 не устанавливает, что весь внутристрановой трафик не фильтруется.
    Нужны отдельные измерения обеих частей; в MVP не входит.
15. **Разные сети = разные failure domains** (LTE vs wired, §2.4a): при
    деградации одного класса сетей — переключение канала, а не ожидание.

**Диагностика и реакция (совместимо с fail-closed):**

16. **Классификация отказа по наблюдаемому поведению** — словарь причин для
    controller — **исторические имена, не доказанные причины**:
    - `ResetInjected`: наблюдается reset; без wire/capture нельзя отличить
      серверный сброс от инжекции, тем более доказать SNI-блок;
    - `SilentFreeze`: EOF/timeout в малом probe не доказывает объёмный freeze;
      нужны bytes/time/completion на ограниченной объёмной проверке;
    - `TlsPolicing443`: сравнение браузера и туннеля даёт гипотезу, не диагноз;
    - `PortBlackholed`: отсутствие ответа — также routing/firewall/server fault;
    - `DnsSubverted`: отличать ошибку DNS-пути от подтверждённой подмены;
    - `WhitelistMode`: гипотеза политики требует набора контрольных направлений;
      нельзя отнимать рабочий validated путь по одной TLS-ошибке;
    - `DirectLeakConfirmed`: отдельный структурный safety outcome, а не regex
      или просто совпавший публичный IP; реакция немедленная, без debounce.
    Реальный словарь failclass.go включает другие коды (`dns_path_failure`,
    `protected_channel_unavailable`, `unknown`); первая версия списка не API.
    Target, route, network epoch и форма ошибки обязательны для интерпретации.
17. **Методика Cheburcheck как референс, не production security probe**:
    [страница whitelist](https://cheburcheck.ru/kb/whitelist) прямо отделяет
    доменные исключения из замедления от мобильного allowlist. Её SNI-тест
    использует отключённую проверку сертификата; переносить его в protected
    probe запрещено. `--resolve` меняет DNS→IP, не отдельно SNI; URL задаёт
    имя, а смена URL одновременно меняет другие HTTP/TLS-параметры. Для
    причинного A/B нужен собственный endpoint с известными виртуальными
    хостами и валидным доверием, контроль Host/ALPN/reuse. Один Range-ответ
    доказывает лишь завершение этого запроса. Программная/правовая безопасность
    внешнего измерения из наличия команды не следует.

**Анти-знание (не повторять):**

- «любая TLS-фрагментация спасёт от ТСПУ» — нет универсального результата;
- «uTLS = невидимость» — upstream Not Recommended; поведенческий детект жив;
- «ECH решит SNI» — сигнатурно заблокирован на CF с 2024-11 (§2.9 анти-знание);
- «RFC-стандарт = доступен» — ECH стандартизован лишь в марте 2026 (RFC 9849),
  а deployment упирается в политику каждого CDN — стандарт ≠ поддержка ≠ доступность;
- «Brutal-дефолт ускорит» — без правила = 1 Mbps, дефолтом быть не должен;
- «смена порта — абсолют» — V2-051: фильтр может закрыть весь не-443 диапазон.

**Правовые тексты продукта — отдельная проверка:** прежний вывод о запрете
конкретных слов в UI и смешение видов ответственности не обоснованы этой
технической теорией. Не вводить такое продуктовое правило без сверки
действующих официальных норм; юридическая актуализация здесь не выполнена.

### 2.11. Дополнение из стороннего AI-обзора (GPT-5): что принято, что опровергнуто

Нам прислан большой обзор «методов обхода для РФ» (автор — LLM). По правилу §6
каждое значимое утверждение пропущено через фактчекинг; здесь — итог интеграции.

**Принято (подтверждено первоисточниками):**

1. **TLS-in-TLS-детект вложенных рукопожатий** — реальное исследование:
   «Fingerprinting Obfuscated Proxy Traffic with Encapsulated TLS Handshakes»
   (Xue, Kallitsis, Houmansadr, Ensafi, USENIX Security 2024). Протокол-
   агностичное обнаружение прокси по паттернам вложенных TLS-хендшейков.
   Следствие для нас: канал A (VLESS+WS+TLS: внешний TLS к CF + внутренние
   TLS-сессии абонентов) в принципе ложится под такой детект. Контрмеры:
   работа показывает ограничения random padding и mux: признаки burst/roundtrips
   могут оставаться. Split-streams/XHTTP надо испытывать отдельно; статья не
   доказывает их нераспознаваемость. [USENIX, paper](https://www.usenix.org/conference/usenixsecurity24/presentation/xue-fingerprinting).
2. **Эвристики против полностью зашифрованного трафика** — «How the GFW Detects
   and Blocks Fully Encrypted Traffic» (Wu et al., USENIX Security 2023):
   цензор не определяет «зашифрованность» точно, а применяет грубые эвристики
   с исключениями для «похожего на известные сервисы» трафика. Прямо перекликается
   с общей идеей сочетания признаков, но не подтверждает российскую AND-модель.
3. **Бюджет донастройки**: РКН обновлял систему замедления/блокировок
   на ~60 млрд руб. (2025–2027) [документировано: Forbes 2024-09-10] —
   ожидать продолжения волн донастройки ТСПУ (уже видим: 2024-12, 2025-12).
4. **Домен-фронтинг** — история уточнена (см. §2.3): «мёртв с 2018» — неточно;
   Azure Front Door изменил исключение в 2023 (§2.3). Собственный Azure
   reverse proxy — кандидат после проверки договора/WS/стоимости; произвольный
   domain fronting не следует из этого исключения.
5. **Класс стегано/медиа-транспортов** (Stegozoa, CovertCast, DeltaShaper —
   разные cover media, не одна скорость) и **traffic morphing/padding/FEC** —
   исследовательские направления. FEC исправляет часть потерь за лишние байты,
   сам по себе не маскирует протокол и не исправляет shutdown. Для MVP не берём.
6. **Рейтинг Tor-мостов в РФ не установлен**: исходное Snowflake > meek >
   obfs4 не имеет сопоставимой выборки. [Tor в январе 2026](https://forum.torproject.org/t/tor-project-user-support-report-for-january-2026/21221)
   описывает неоднородные блокировки и проблемы доставки мостов. Публичный
   список и доступность distribution plane столь же важны, как транспорт.

**Опровергнуто/скорректировано (анти-знание):**

1. **«VLESS не отвечает неавторизованному подключению»** — слишком широко:
   400 на некорректный WS наблюдался в нашей истории, но ошибочный HTTP-запрос
   может получить 400 и у обычного сайта. Вопрос — воспроизводимая отличимость
   серии ответов/таймингов от cover, а не сам код; REALITY также требует проверки.
2. **«Trojan выдаёт себя ответом на неверный запрос»** — по дизайну наоборот:
   Trojan при неуспешной аутентификации отдаёт настроенную веб-страницу
   (анти-probing by design) [документировано Trojan-GFW]. Риск пробирования
   существует при неправильной настройке, но это не свойство протокола.
3. **«Проценты детекции» (OpenVPN 100%, SS ~95%, Trojan ~90%, VMess ~80%,
   VLESS <5%)** — источник в обзоре не верифицируется ([42] без выходных
   данных). Ни порядок рейтинга, ни эти ЧИСЛА
   считать фактами или рабочими вероятностями нельзя: [неверифицируемо, не использовать].
4. **«SSH-туннель как постоянный резерв»** — под 16КБ-механикой SSH — исключение
   (#490 upd2), но считать его постоянным резервом нельзя: исключение может закрыть
   в любой день (см. судьбу не-443 портов, V2-051) [вывод].
5. **«ML/RL-агент выбирает транспорт»** — направление осмысленное, но у нас
   уже есть детерминированный AdaptiveController с классификатором причин
   (§2.10 п.16); по AGENTS §2.3 сначала зрелые аналоги, RL — не MVP. ML
   можно рассматривать только после валидации телеметрии/ground truth и
   выигрыша на отложенных сетях; не автономный агент без safety shield (§8).
6. **«TLS 1.3+ECH скрывает SNI»** — верно для внутреннего ClientHello в модели
   RFC 9849, но из этого не следует доступность или сокрытие IP. Исторический
   CF ECH-блок — пример ограничения deployment, не опровержение криптографии.

**Итог интеграции:** ценность обзора — в систематике классов (стегано, morphing,
мультихоп, RL) и двух свежих исследованиях (USENIX 2023/2024); слабость —
непроверяемые проценты и игнорирование наших live-фактов (sing-box 400,
ECH-блокировка, 16КБ-механика не упомянута вовсе). Правило сохраняем: теории
в этот файл попадают только после сверки с первоисточником или живым тестом.

## 3. Архитектурные принципы защищённого клиента (выводы из практики)

1. **Fail-closed** — при отсутствии подтверждённого защищённого пути трафик не выпускается. Никакого «а вдруг напрямую получится».
2. **Доказательство, а не индикация**: protected probe = DNS через туннель + 2 HTTPS-цели + ожидаемый egress + negative direct-leak test. HTTP 101/открытый порт/успешный handshake — НЕ доказательство [доказано нами: сервер с route.final=block принимал VLESS-сессии и блокировал весь трафик, при этом клиент выглядел «подключённым»].
3. **Один владелец lifecycle**: обёртка владеет контекстом движка. Операционный таймаут операции (Start/Reload) не должен быть контекстом движка — иначе движок умирает сразу после старта [доказано нами: P0-дефект Manager].
4. **Секреты только по ссылке**: конфиги в git — с плейсхолдерами; рендер в runtime — локально; секреты никогда не в чат/лог/diff.
5. **Сертификат pinned, не disabled**: self-signed сервер = пиннинг PEM в клиенте, `insecure` запрещён.
6. **Два протокола не означают два независимых пути**: TCP/CDN и UDP/direct
   различаются частью причин отказа, но один VPS/аккаунт/exit/publisher может
   отключить оба. Нужна карта общих зависимостей (§7.3).
7. **Валидация конфига до запуска**: references, selector без direct, отсутствие плейсхолдеров, strict JSON.
8. **Клиентская фича транспорта = контракт ОБОИХ концов**: при включении транспортной оптимизации на клиенте (mux, padding, новые поля) серверный inbound обязан уметь её терминировать ТЕМ ЖЕ изменением — иначе получаем невидимую снаружи деградацию: CDN жив, TLS жив, auth проходит, а данные рвутся (EOF) [доказано нами 2026-09-12: клиентский h2mux+padding по умолчанию против сервера без multiplex → probe «3 of 4 failed: EOF» при полностью рабочем пути]. Отсюда же: default-on транспортных фич небезопасен при гетерогенной серверной ферме — включать фичу стоит вместе с сервером или через дескриптор (per-канал), а не глобальным дефолтом.
9. **Провал probe ≠ утечка ≠ недоступность канала**: одиночный liveness failure
   допускает bounded reprobe при сохранённом барьере. Наличие барьера подтверждать
   отдельно, из timeout его не вывести. Совпавший direct/tunnel IP бывает при
   общем NAT/exit; различный IP тоже не доказывает отсутствие всех OS-утечек.
   Подтверждённый safety outcome — немедленный fail-closed; неопределённость
   нельзя превращать в security PASS. Исторический V2-026 показывает цену
   ложных остановок, но его атрибуция именно CGNAT не установлена здесь.
10. **Bootstrap не должен быть единственным и экзотичным**: резолв имени туннельного сервера ДО старта движка — мультистратегичный (plain UDP флот + DoH по IP-литералу + кэш последнего хорошего), в коде приложения, а не в конфиге ядра: политика владеет кодом, а не hopes. DoT/853 — популярная тихая точка отказа в фильтрующих сетях [вывод из THEORY §2.1; реализация preflight в V2-037].
11. **Idle требует проверки и восстановления**: keep-alive, app heartbeat,
   срок жизни carrier и NAT — разные параметры (§2.10 п.10). Исторические
   60/20с/TFO не универсальный default. Parser/check не доказывает семантику:
   в инциденте 2026-09-12 REALITY без принятого server_name отвергал аутентичных
   клиентов, хотя TCP/донор отвечали. Это evidence конкретной конфигурации.
12. **Multiplex имеет разнонаправленные эффекты**: меньше хендшейков, общие
   очереди/потери и больший объём carrier. Не «маскирует объём» автоматически.
   Выбирать согласованный профиль по E-02/E-03 и workload, не по догадке о DPI.

## 4. Реестр ложных блокеров (анти-знание)

Эти «блокеры» были найдены в старом плане/аудите и опровергнуты live-проверкой. Фиксируем, чтобы не повторить:

| Ложный блокер | Откуда | Правда |
|---|---|---|
| «nginx возвращает 400 на Sec-WebSocket-Protocol: VLESS» | SERVER-2026-09-01-1 | nginx отдаёт 101; 400 отдаёт сам sing-box на невалидный base64 subprotocol. Литерал «VLESS» не используется реальным клиентом [доказано] |
| «нужен скрипт vps-diagnose-and-fix-nginx-ws.sh» | тот же | Скрипт решал несуществующую проблему; сервер ни разу не был причиной 400 [доказано] |
| «CF token IP-restricted = мягкий блокир» | phase-0 evidence | Реального чтения через API не требовалось: всё проверяется DNS/TLS/SSH. Токен вообще не нужен для текущего MVP [доказано] |
| «нужен второй домен для независимого failure domain» | PLAN §5 Phase B (B1) | Верно, но это не блокер разработки клиента; каналы живут на одном VPS и это документированный компромисс |
| «WS 400 — ожидаемо, реальный клиент пройдёт» | PHASE-8A journal | Дважды неверно: и 400 не от nginx, и «пройдёт» оказалось ложью, пока не починили серверный route.final [доказано] |
| «сертификат legacy-zone не соответствует → Full (Strict) недоступен» | RELEASE-2026-08-28-1 | Починено и не имеет отношения к клиентскому пути |

| «клиентский mux можно включить глобальным дефолтом, сервер не трогая» | V2-037 live | EOF на всех соединениях при живом CDN+TLS+auth: sing-box-сервер без multiplex-блока рвёт mux-стримы; чинится сервером (multiplex enabled+padding) или per-канальным дескриптором [доказано] |
| «probe EOF однозначно означает дефект клиента/сервера (V2-039)» | сессия 2026-09-12 | Mux on/off дали одинаковое зависание, сервер видел dial/open stream. Это не локализует неисправность только в клиент↔CF и не исключает серверный egress/CDN/цель. Старое «сервер ни при чём» и контрфактическое «curl прошёл бы» отозваны. Нужны независимые контрольные запросы и captures обоих концов. |

Мета-вывод: история содержит реальные серверные ошибки, но доля «почти все»
не посчитана. Проверка обоих концов ускоряет локализацию; clean logs и живой
/ip не исключают остальные причины. Текущий офлайн-режим сохраняется.

## 5. Открытые вопросы и направления (исследовательские заметки)

Статусы исполнения принадлежат PLAN §5.1/§5.3. Ниже — история вопросов и
уточнения, не параллельная очередь разработки.

- REALITY/XHTTP как канал B: **исследовано 2026-09-11** (docs/B1-REALITY-RESEARCH.md, PLAN V2-031): ядро умеет REALITY (клиент под with_utls), XHTTP — нет (форки client-only); выбран VLESS+TCP+REALITY без Vision. Осталось открытым: live-поведение REALITY в целевых РФ-сетях после деплоя VPS-B [требует полевой проверки];
- ECH через Cloudflare для VLESS+WS: **частично закрыто 2026-09-16**: ECH на CF
  (public_name cloudflare-ech.com) блокировался в описанных сетях с 2024-11-05
  (§2.9, #417) — рассчитывать только на ECH через CF
  как на защиту нельзя; ECH с собственным public_name на своём домене — открытый
  вариант [гипотеза, требует серверного эксперимента];
- XHTTP вместо WS: **изучено 2026-09-11**: в pinned upstream-ядре отсутствует (SagerNet/sing-box#3076 открыт), есть только в форках (sing-box-lx — client transport, сервер = Xray). Смена ядра отклонена (V2-031); переоценить, если XHTTP попадёт в upstream;
- anti-probing: сравнить всю матрицу WS/REALITY ответов с cover-сайтом;
  исторический 400 не доказательство VPN, дизайн REALITY не закрывает E-04;
- национальный DNS: поведение клиента в сети, где домены удаляются из резолверов [исследование];
- классификатор причин срыва (§2.10 п.16): словарь ResetInjected / SilentFreeze /
  TlsPolicing443 / PortBlackholed / DnsSubverted / WhitelistMode /
  DirectLeakConfirmed — **v2 интегрирован 2026-09-23** (windows/failclass.go,
  PLAN V2-087): детерминированный, поверх probe-отчёта; leak и allowlist дают

- failure domains / независимость каналов (§2.10 п.18): **модель v1 реализована
  2026-09-16** (windows/backend/render/fdmodel.go, PLAN V2-059; PLAN §5 Phase B):

- первый хоп внутри РФ (§2.10 п.14): RU-VPS как транзит — серверный эксперимент
  (нужен второй VPS в РФ-датацентре) [гипотеза, вне MVP];
- альтернативный CDN-фронт (Azure Front Door, §2.11): аварийный путь, если
  CF-ветка канала A деградирует целиком; проверить WS-проксирование и стоимость

- семантика `dns.rules.outbound: any` vs `"outbound": ["proxy"]` в sing-box 1.13 [документировано частично, протестировать];

  реализация, rate и политика сайта также существенны. Дополнительный exit
  проверять по целевой задаче; вход через CDN не подменяет выход VPS.

## 6. Как проверять новые факты (метод)

1. **Паспорт утверждения:** формулировка, источник/версия/дата, страна/ASN,
   измерение или дизайн, альтернативное объяснение, что его опровергнет.
   Документация доказывает контракт, source — конкретную реализацию,
   unit — конечный набор случаев, live — только проверенный путь/период.
2. **Сначала вопрос, затем проверка:** не запускать live из наличия команды
   в документе. Офлайн — fixtures/анализ; стенд — отдельная изоляция;
   сеть владельца/сервер — после соответствующего запроса и доступной инфраструктуры.
3. **Локализация:** client→edge→origin→exit→target и обратное направление.
   cf-ray/Server — подсказки, не криптографическое доказательство origin;
   нужны nonce/идентификатор запроса и сопоставимые серверные данные.
4. **Причинность:** paired A/B, один фактор, чередование порядка, одинаковая
   полезная нагрузка; отмечать IP-family, DNS/reuse/cache, server load, время.
   Действие может менять и сеть: блокировка/TTL/остаточное состояние создают carryover.
5. **Приватность:** синтетические payload; публичные key fingerprints/config
   identity, не значения секретов и не хеши слабых паролей. Raw captures могут
   содержать адреса/имена/credentials — локальное ограниченное хранение и redaction.
6. **Вывод:** observation отдельно от inferred mechanism; явные unknown,
   failed/skipped runs, sample size и границы применимости. Возраст evidence
   снижает его пригодность, но не превращает наблюдение в ложь. План экспериментов — §10.

## 7. Строгая модель: что именно мы оптимизируем

### 7.1. Противник, доверие и предел обещаний

[Инженерная модель, не описание секретной реализации ТСПУ.]

| Участник | Что видит/может менять | Чего выбранная защита не обещает |
|---|---|---|
| Локальный ISP / middlebox | IP, порты, размеры/время/направления, открытый ClientHello, drop/reset/rate/reorder, DNS | TLS скрывает содержимое, но не скрывает существование соединения |
| Активный пробер | Создаёт свои сессии, повторяет записи, исследует ошибки/время ответа | Не знает ключ по умолчанию, но может получить публично распространяемый профиль |
| CDN / TLS frontend | Клиентский IP, HTTP/WS после терминации внешнего TLS | Внешний TLS не скрывает эти данные от CDN; внутренний HTTPS защищает свой payload |
| VPN entry/exit и хостер | Метаданные потоков; exit видит target IP/DNS и plaintext протоколы | VPN не заменяет end-to-end TLS и не устраняет корреляцию времени/объёма |
| Publisher / update mirror | Профили, endpoints, распространение версий; mirror может задержать/подменить bytes | Подпись не делает endpoint доступным; компрометация signing key — отдельная угроза |
| Локальный процесс / администратор | Файлы, IPC, права, ОС; возможности зависят от привилегий | Защита сети не доказывает безопасность скомпрометированного хоста |

Не складывать эти роли в одного всеведущего противника без явного сценария.
Модель пассивного ISP и модель CDN с TLS-ключом дают разные наблюдения.
Не применять скрытые настройки downgrade, `insecure` или direct fallback
ради «доступности»: они меняют задачу безопасности, а не решают её.

«Теоретический максимум» — условная граница для заданной сети, противника,
бюджета и допустимого доверия. Нельзя одновременно гарантировать неотличимость,
нулевой overhead, нулевое время восстановления и работу при отсутствии пути.
Цензор может принять высокую цену collateral damage; популярность CDN не veto.

### 7.2. Поверхность наблюдения и экономическая модель

Полезна последовательная модель: дешёвый IP/ASN/порт-фильтр → разбор
handshake → агрегаты потока → дорогая проверка/проба. Это **возможный pipeline**,
а не установленный порядок в РФ. Цель транспорта — уменьшить различимость
в выбранной модели и повысить цену блокировки; цель клиента — сохранить
доступный проверенный путь с ограниченной ценой адаптации.

Четыре независимых вопроса:

1. **Обнаружение:** отличим ли wire image от контрольных легитимных потоков?
2. **Перечисление:** можно ли получить наши endpoints/профили через distribution?
3. **Подавление:** готов ли цензор блокировать эти endpoints/класс целиком?
4. **Восстановление:** можно ли безопасно доставить новый профиль после блокировки?

Хорошая маскировка не исправляет публично перечисляемую единственную IP-точку;
новые IP не исправляют сломанный control plane. Размер/тайминг/серии burst
остаются даже у криптографически корректного протокола [S02][S03].

**Базовая частота важнее красивого accuracy.** Для доли VPN `π`, true-positive
rate `t` и false-positive rate `f` точность положительного решения:

```text
PPV = t·π / (t·π + f·(1−π))
```

Синтетический пример: π=0.001, t=0.99, f=0.01 → PPV≈9%, а не 99%.
Это арифметика условной модели, не замер цензора. Для оценки детектора нужны
base rate, benign corpus, PR/ROC и цена ошибок; «18/18 lab cases» не калибрует
вероятность в живой сети. Проверять на других днях/ASN/нагрузках, не только
на примерах, по которым написаны правила.

### 7.3. Независимость — граф, а не число протоколов

```text
клиент → access ISP → bootstrap/resolver → entry/CDN → origin → exit → target
                                   ↘ profile publisher / trust / time / payment
```

Каждый путь имеет зависимости: физическая сеть, IP-family, prefix/ASN,
carrier, origin/process/host, exit, TLS donor, DNS, publisher/key, учётная запись
и оплата. Отдельные домены на том же аккаунте CDN не устраняют блок аккаунта;
разные VPS в одной подсети не защищают от prefix-block. Один и тот же target
для всех probes создаёт ложный общий отказ даже у здоровых каналов.

Точные соотношения для двух отказов A/B:

```text
P(оба недоступны) = P(A) · P(B | A)
P(хотя бы один работает) = 1 − P(A ∩ B)
```

Подстановка `P(B|A)=P(B)` разрешена только при обоснованной независимости.
Например, два транспорта с одним выключенным origin не дают резерв, сколько
бы строк ни было в selector. Для исследования строить fault tree и минимальные
наборы общих отказов; не выдавать penalty score за вероятность.

Для неизвестных полей хранить **coverage/provenance**, а не только score:
подписанное утверждение владельца, статическая деривация, датированное измерение.
Unknown не означает ни «совпадает», ни «различается». Выбор кандидата при unknown
возможен, заявление о доказанной независимости — нет. Подмена CDN entry на другой
не обязательно меняет origin/exit/publisher; это проверяется отдельно.

### 7.5. Control plane, ключи и автономность

Нужны отдельно доступность профилей, подлинность, свежесть, совместимость и
восстановление доверия. Два mirror с одним key/аккаунтом не дают две независимые
границы доверия. Подписанный вредоносный профиль после кражи publisher key остаётся
подписанным; простая Ed25519-проверка не решает компрометацию издателя.

[TUF 1.0.37, 2026-10-08][S20] — зрелый референс разделения ролей/thresholds,
rollback/freeze/mix-and-match защиты и ротации root. Это не утверждение, что
наш envelope уже реализует TUF. Адаптировать требования и regression scenarios,
решение о библиотеке/миграции принимать отдельно в OFF-06.

До выдачи профиля: ChannelID→SecretID→pin/capabilities, min/max client/core
version, auth и signed validity. Rotation: current+next, overlap, отзыв, crash
между stage/commit, clock jump и восстановление из backup. Пин должен приходить
по доверенному пути; TOFU в атакуемой bootstrap-сети не равен установленному доверию.

Автономность не означает бесконечно принимать expired/revoked профиль. Нужны
явная политика last-known-good **в пределах доверия/сроков**, отдельное поведение
ошибочных часов и восстановление из заранее доверенного offline package.
Expiry при недоступном publisher может снизить availability — trade-off
документировать, не скрывать автоматическим отключением проверки.

## 8. Адаптация при неполных и меняющихся данных

### 8.1. Состояние и наблюдения

Скрытое состояние включает перегрузку, отказ сервера, политику сети, остаточный
блок, неисправность target и клиента. Наблюдение одно и то же (timeout) может
порождаться каждым из них. Следовательно, controller решает задачу частичной
наблюдаемости; на первом этапе достаточно детерминированных правил с `unknown`.
POMDP/bandit/RL — возможные модели исследования, не необходимость внедрения ML.

Минимальное observation: mono time + wall time, network epoch, channel/config
identity, attempt/generation, target и фактический route/IP-family, stage
DNS/dial/TLS/auth/data, bytes up/down, deadline/completion/error form,
provenance и ограничения. Не писать browsing history, payload или credentials.
Структурное событие сильнее regex; отсутствие capture не заполнять «SNI-block».

Раздельные оси: **Safety**, TransportHealth, EgressHealth, EndpointHealth и
InfrastructureHealth. HTTP challenge обычно даёт сведения о site policy,
certificate error — о trust/config/time; ни одно не следует автоматически
лечить перебором портов. Пример альтернативных причин — OONI [S05].

### 8.2. Правило решения и защитные инварианты

```text
validated candidates + свежие наблюдения + budget + protection intent
→ stay / bounded reprobe / diagnose / switch / recover / blocked
→ один Manager, generation/epoch check → apply → fresh protected gate → publish
```

Safety — жёсткое ограничение, а не штраф в utility. После него сравнивать
доступность, p95 recovery/TTFB, goodput и цену. Профиль с меньшим RTT, но без
удостоверенного protected пути не выигрывает score.

- Подтверждённая утечка или недостоверный барьер → safe error немедленно.
- Один liveness timeout → ограниченное подтверждение, не новый «диагноз DPI».
- Только endpoint outage → другой независимый измеритель; не гонять все транспорты.
- Общий origin недоступен → приоритет другого origin, а не всех его протоколов.
- Все пути непроверены/недоступны → BLOCKED и bounded retry без снятия защиты.
- Пользовательский Disconnect отличается от ошибки, crash и закрытия GUI.

Смена транспорта обычно не мигрирует существующий пользовательский TCP-поток.
«Seamless» разрешено писать только для фактически сохранённых потоков;
reconnect новых потоков и verified rollback — отдельные результаты.

### 8.3. Колебания, бюджет и обучение

Cooldown, hysteresis, min dwell и backoff с jitter ограничивают колебания,
но их величины должны измеряться. Reset на новом epoch не должен стирать
protection intent. Старые observations не могут commit после смены сети/сессии.
Репутацию канала ослаблять с возрастом, различать срок действия профиля и TTL
наблюдения; не сбрасывать безопасность из-за устаревшей статистики.

Один общий budget: максимальные concurrent probes, bytes/окно, attempts,
CPU/time, server rate, батарея/стоимость сети; maintenance probes проходят тот
же limiter. Отмена UI не означает, что запущенная работа перестала потреблять
ресурсы. Неподчиняющийся engine Start/Close требует process boundary, не ещё
одного goroutine timeout. Стенд должен проверять boundedness и накопление работы.

Исследование нового кандидата — только из валидного доверенного набора, без
protected user payload до gate. Не сканировать порты/домены массово и не
переобучаться на собственных probes. Сначала replay фиксированного fault schedule,
затем shadow recommendations, canary и rollback. ML допускается при выигрыше
на отложенных сетях/днях и стоимости ошибок, с fallback к объяснимой политике.

## 9. Скорость: физические ограничения и полезные оптимизации

### 9.1. Модель затрат

[Инженерные приближения, не предсказание конкретного результата.]

```text
goodput = полезные завершённые bytes / wall time
goodput ≤ min(access, entry path, relay CPU, relay↔exit, exit↔target, target)
BDP = bottleneck bytes/s × RTT seconds
carrier throughput ≲ in-flight window / RTT  (если именно окно ограничивает)
recovery = обнаружение + очередь/cooldown + prepare/apply + fresh gate
```

Не складывать latency всех стадий вслепую: соединения/резолв могут переиспользоваться,
часть работы параллельна. Отдельно cold start, warm reuse, time-to-first-byte,
полное завершение и latency под нагрузкой. Speedtest с одним длинным скачиванием
не описывает интерактивный browsing и не включает цену отказавших попыток.

Короткие carriers уменьшают накопление байтов, но добавляют RTT, crypto/CPU,
NAT/port state и риск rate limit. При условном лимите `B` байт/carrier и полном
времени цикла `T` последовательный поток ограничен `B/T`; параллелизм может
помочь лишь до общей ёмкости, лимитов и новой сигнатуры. Не предлагать
«новый TCP каждые 16 КБ» без transport reassembly и проверки end-to-end семантики.

### 9.2. Где искать выигрыш

| Мера | Возможный эффект | Цена / обязательный контроль |
|---|---|---|
| Меньше лишних reload/probe/повторов | recovery и CPU без смены протокола | не пропускать fresh gate, cancellation/epoch atomicity |
| Mux / bounded pool | меньше handshakes | TCP-level head-of-line, общий failure blast radius, очереди и bytes/carrier |
| QUIC streams | потери одного stream не требуют упорядоченной доставки другого | общий congestion controller/path; UDP block/MTU/NAT; не обещает отсутствие задержек [S12] |
| Надёжный внешний byte stream для TUN | совместимость TCP-пути | outer loss задерживает внутренние потоки и может вызывать повторные retransmission; отличать packet-over-TCP от split proxy |
| MTU/PMTUD и размеры буферов | устранение blackhole/оконного bottleneck | family/encapsulation overhead, oversized buffers → latency/RAM; E-05 |
| Congestion control / bandwidth caps | лучшее использование loss-path | rate выше доступного вызывает очереди/потери, измерять соседний поток; Brutal не default [S13] |
| Padding / timing shaping | меньше выбранных статистических признаков | bytes/CPU/latency и новые fingerprints, абляция и benign corpus [S03] |
| FEC / дублирование | latency при части случайных потерь | больше wire bytes, не лечит полный drop; не дублировать неидемпотентные запросы |
| Keep-alive / resumption / TFO / 0-RTT | idle recovery/handshake в некоторых условиях | расход сети, replay/idempotency, несовместимость middlebox; не replay control-plane Apply [S06] |

QUIC connection migration [S23] может сохранять сессию при смене адреса/пути, если
это поддерживают оба конца; не означает миграцию в другой независимый VPN exit
и не преодолевает заблокированный destination IP. Для SOCKS отдельно выяснять
поддержку UDP у приложения и прокси; для TUN — ОС-маршрут/DNS/IPv6, не браузерный mock.

### 9.3. Что разумно заимствовать и когда

Это shortlist для оценки, **ничего автоматически не устанавливается**.
Latest docs содержат возможности вне нашего pin; фиксировать tag/commit,
лицензию зависимостей, wire compatibility и rollback до любой интеграции.

| Источник | Что брать | Ограничение / решение |
|---|---|---|
| NaiveProxy [S14][S15] | Реальный Chromium network stack, padding negotiation, управление carrier lifetime; release v147.0.7727.49-3 добавляет realistic preambles | Это prerelease reference, не выбранная поставка. Принципы → отдельный compatibility spike: pin, packaging, child process/kill-switch, server capability. Root BSD-style license не отменяет third-party notices |
| Xray XHTTP [S16] | Разделение up/down, ограничение reuse, разные пути и HTTP transport modes | Не включён в sing-box 1.13.19; не менять ядро/встраивать sidecar до TH-04 и ADR с измерением. Дизайн upstream не даёт универсальной устойчивости |
| Hysteria2 [S11] | Согласование rate, QUIC/TCP+UDP proxy, HTTP/3 cover либо obfs как разные профили | Salamander скрывает QUIC wire image ценой несовместимости с обычным H3; не обходит общий UDP-block. Новые Gecko/Realm/Mimic в current docs не приняты нашим pin |
| Tor WebTunnel/Snowflake [S17] | Разделение транспорта, distribution и проверки свежести мостов | Не рейтинг и не готовый high-speed VPN backend; runtime/dependencies/trust/нагрузка оцениваются отдельно |
| UPGen, USENIX 2025 [S18] | Диверсификация семейств протоколов как research alternative к единой FEP-сигнатуре | Результат авторов на своём threat model; не доказательство работы в РФ и не production-приоритет |
| TUF [S20] | Роли доверия и threat-driven update regression matrix | Применять к OFF-06 после инвентаризации envelope; не заявлять TUF compliance по сходству |
| Toxiproxy [S21] / iperf3 [S22] | Готовые TCP fault injections / эталонные controlled throughput measurements | MIT / BSD-3-Clause. Toxiproxy не эмулирует UDP/DPI/WFP; iperf3 не доказывает обход, Windows официально не поддерживается |

Важное новое направление из практики NaiveProxy: обновлять не только ClientHello,
но и поведение соединения. Preambles/shaping также имеют расход и могут создавать
новую сигнатуру; польза проверяется, а не принимается из маркетингового README.
Большую генеративную traffic-shaping систему или собственную криптографию до
этих сравнений не разрабатывать.

## 10. Программа экспериментов и критерии знания

Это спецификация будущих проверок. **В V2-109 они не запускались.**
Реализация и статус — PLAN §5.3; живые измерения требуют доступной
инфраструктуры и соответствующего запроса, публикация OONI не включается автоматически.

### 10.1. Минимальный паспорт опыта

- Гипотеза и конкурирующие объяснения, контролируемый фактор и прогноз.
- Client/core/server/tool versions, config identity, capability set, topology,
  network epoch/ISP/family, время и ограничения capture. Не секреты.
- Workload, random seed/порядок A/B, fault schedule, warmup/cache/reuse,
  time/bytes/concurrency budget, abort policy и исключения.
- Метрики до запуска, точность/размер выборки по значимому эффекту и вариативности;
  нет универсального «трёх успешных запросов достаточно».
- Raw synthetic observations, failures/cancellations/timeouts, способ агрегации,
  доверительный интервал, полный знаменатель попыток и воспроизводимая команда.

### 10.2. Матрица опытов

| ID / вопрос | Контроль и вмешательство | Измерение / критерий | Уровень, граница |
|---|---|---|---|
| E-01 Safety/lifecycle | Connect/Stop/error/crash/reboot/update; IPv4/IPv6/UDP/OS DNS; старый helper, зависший Start/Close | Не возникает разрешённый protected direct; intent и generation сохраняются; ошибка cleanup видима, время/ресурсы ограничены | Pure models → process tests → отдельная Windows VM. Unit не доказывает WFP |
| E-02 Freeze по объёму или времени? | Собственный endpoint, payload 1/8/16/32/64/256 KiB и выше по budget; разные pacing/reuse/новые carriers, направление, mux on/off | Completion и распределения bytes/time до остановки. | E-03 Лимит сессий / mux | Один exit/нагрузка, concurrency 1/2/4/8, фиксированный aggregate rate; reuse и mux как отдельные факторы | Handshakes/sec, queues, p95 TTFB, goodput, resets и живучесть существующих потоков | Стенд; фразы «mux помогает» без workload недостаточно |
| E-04 Active probing / TLS-in-TLS | Свой сервер и cover, корректный/неверный auth, replay, malformed/truncated input, разные паузы и веб-нагрузки | Ответы/время/размеры и benign-corpus confusion matrix с base-rate анализом; correct client проходит | Lab capture. | E-05 Loss/MTU/idle/семантика | Loss/burst/reorder/RTT/rate, MTU blackhole, family, sleep/wake/network change; один параметр за раз | Goodput, latency соседнего потока, завершение TCP, реальный UDP/DNS и reconnect; CPU/RSS/handles | Изолированный Linux network lab + Windows VM. Не менять сеть рабочего хоста |
| E-06 Измеритель или путь? | Падает только echo/DNS/target, TLS expired, challenge, общий egress, clock jump; healthy alternative targets | Safety не PASS по недостатку данных; endpoint outage не роняет все каналы; classifier abstains; budgets соблюдены | Fixtures + local servers. Нет принудительного «whitelist» из x509/443/timeout |
| E-07 Независимость и distribution | Отключить общий origin/ASN/carrier/resolver/publisher, испортить signed update/pin, version rollback; unknown FD | Выбран работоспособный другой dependency path либо BLOCKED; no silent trust fallback; fresh provenance | Модели/стенд; реальный второй origin/ASN — только после OFF-09 |

Toxiproxy полезен для TCP latency/reset/timeout/ограничения bytes [S21], но
`limit_data` **закрывает** соединение — это не точная модель silent drop после
порога. Для silence/UDP/packet loss нужен другой известный fault mechanism
в изолированном стенде. Сначала проверить, что инъекция действительно сработала;
успешный тест с неработавшим fault injector не считается прохождением сценария.

### 10.3. Статистика и stop criteria

Сравнивать внутри блоков ISP×epoch×day×family×workload, чередовать A/B и
сохранять неуспешные серии. Повторения на одном middlebox могут зависеть от
общего состояния: считать их независимыми Bernoulli trials без основания нельзя.
Timeout — цензурированное наблюдение длительности, а не нулевая скорость;
throughput только завершённых быстрых сессий создаёт survivorship bias.

Для uptime/failover учитывать длительность outages и полезные завершённые
операции. Percentile по маленькому n неустойчив; показывать n/распределение,
paired differences и интервалы (например block bootstrap по независимым сессиям/
сетевым окнам). Для нуля failures в n **независимых одинаково распределённых**
испытаниях приближённая верхняя 95% граница failure rate — 3/n; без предпосылок
это правило неприменимо и в любом случае не доказательство абсолютной безопасности.

Перед опытом выбрать primary metric, практически значимый effect и допуски
остальных метрик на baseline. Принять кандидат, если эффект устойчив в
отложенных блоках, safety не нарушена, resource/latency budgets выдержаны.
Остановить опыт при leak, trust failure, потере контроля нагрузки или saturation
стенда; такой run сохраняется как failure/invalid с причиной. Если эффекта нет,
не подбирать ещё десятки fingerprint до случайного PASS — пересмотреть гипотезу.
