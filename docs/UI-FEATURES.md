# UI-фичи snowden.system — что показывать пользователю (бриф для дизайна)

> Дата: 2026-09-11. Назначение: единый список фич и данных, которые полезно
> иметь пользователю VPN-клиента. Описано **ЧТО**, не **КАК**: форма, вёрстка,
> компоненты и визуальный язык — за дизайнером. Источники фактов: PLAN.md §4.1,
> AGENTS §3.6, журнал V2-0xx. Группировка ниже — смысловая, не макет.
>
> Обязательные правила честности (ограничения для любого макета):
> 1. UI показывает только фактические состояния (stopped/starting/running/
>    stopping/error/reloading/blocked) и статусы каналов из данных. Никаких
>    «connected»-синонимов, фейковых серверов/стран/трафика.
> 2. Отсутствие данных = явный «нет данных», ноль не заменяет отсутствие измерения.
> 3. Секреты — только метаданные (fingerprint, статус, счётчик раскрытий);
>    значение — по явному действию, не логируется.
> 4. Пояснения на русском: факт/правило, не гипотеза («probe не пройден»,
>    а не «DPI тебя заблокировал»).

---

## 1. Главный экран (суть продукта в один взгляд)

Что пользователю нужно видеть прежде всего:

1. **Текущее состояние защиты** — одна главная сущность: включена ли защищённая
   передача трафика прямо сейчас. Состояния: stopped / starting / running /
   stopping / error / reloading (переключение канала идёт) / blocked (все
   каналы исчерпаны). Каждое — с человеческим объяснением на русском.
2. **Главная кнопка действия** — подключить / отключить; в состояниях
   starting/stopping/reloading — неактивна с объяснением «подождите».
3. **Через какой канал идёт трафик** — имя канала (из дескриптора, не хардкод):
   транспорт (например VLESS+WS / QUIC / REALITY), сервер-имя, порт. Если
   канал неизвестен или данные недоступны — честно «нет данных».
4. **Жив ли защищённый путь** — результат последней автоматической проверки
   (probe): когда прошла, сколько проверок из скольких succeeded, чем
   подтверждён egress. Не путать с «интернет есть»: это проверка защищённого
   пути через туннель.
5. **Режим маршрутизации** — системный прокси или TUN-адаптер (уровень всей
   системы). Пользователь должен понимать, что «включён VPN» ≠ «весь
   системный трафик завёрнут» (SOCKS покрывает только то, что умеет прокси).
6. **Причина блокировки**, если blocked — на русском: «все каналы исчерпаны
   (failover)», что это значит и что делать (повторить подключение, когда
   сеть восстановится).

Полезно рядом (второстепенное, но ожидаемое):

7. Сетевой контекст: имя/тип активной сети, если доступно — многие отказы
   «канал жив, но return-путь деградировал» привязаны к смене сети.
8. Время последней успешной проверки и время последнего события смены
   состояния.
9. Индикатор того, что приложение — единственный экземпляр (второй запуск
   фокусирует существующее окно) — это не фича для показа, а поведение;
   в UI достаточно не иметь дублирующих опасных действий.

---

## 2. Каналы (выбор пути)

Пользователь выбирает, через какой канал идти. Полезно иметь:

1. **Список всех каналов из дескрипторов** — для каждого:
   - идентификатор и человекочитаемое имя;
   - транспорт/протокол (VLESS+WS через CDN, HY2/QUIC, VLESS+REALITY и т.п.);
   - сервер (имя/IP из дескриптора) и порт;
   - **статус валидации** — ключевая честная метка: live-verified /
     configured / planned / degraded / blocked / retired. Пользователь должен
     видеть, что «configured» — это «ещё не доказан на этой машине»;
   - признак активного (текущего) канала;
   - признак того, входит ли канал в текущий селектор.
2. **Действие «переключиться на канал»** — с честной семантикой: переключение
   проходит через переподключение и обязательную проверку; во время
   переключения состояние «reloading», действия заблокированы.
3. **Правила, которые UI обязан объяснить (подсказки):**
   - автоматическое переключение при деградации выбирает только доказанные
     каналы (live-verified); configured-канал — только вручную;
   - HY2 (UDP-канал) зависит от того, пропускает ли сеть UDP — в сетях с
     UDP-фильтром он не поможет;
   - канал с пометкой configured при переключении обязан пройти проверку —
     если проверка не пройдёт, соединение будет закрыто (fail-closed).
4. **Понимание «почему каналов мало»** — если канал один: честная подсказка,
   что автопереключению «не с чего происходить», второй канал появится после
   добавления сервера.

---

## 3. Автоматическая защита (failover и сторож)

Фича уже работает в ядре; пользователю полезно понимать её состояние:

1. **Индикатор «сторож активен»** — что защищённый путь проверяется
   периодически (без цифр «сколько раз», без пугающих тиков в лицо).
2. **История переключений каналов** — когда и на какой канал произошёл
   автопереход, по какой причине (деградация защищённого пути). Пустая
   история — тоже валидное состояние («переключений не было»).
3. **Состояние failover-инцидента**: серия провалов, лимит попыток,
   cooldown — но в человеческих терминах («происходит проверка альтернативы,
   попытка 1 из 2»), без внутренних имён состояний.
4. **Событие «все каналы исчерпаны» → blocked** — с объяснением: туннель
   остановлен сознательно, чтобы трафик не пошёл мимо защиты (fail-closed).

---

## 4. Диагностика (ручная проверка)

1. **Кнопка «Проверить сейчас»** — ручной запуск protected probe.
2. **Разбитый по шагам отчёт** (обязательный контракт probe):
   - DNS через туннель;
   - HTTPS-цель 1 и цель 2;
   - ожидаемый egress vs наблюдаемый egress (IP-адреса — это не секрет);
   - проверка отсутствия утечки напрямую (direct-leak), с учётом режима
     (SOCKS: адреса должны различаться; TUN: совпадать).
   Каждый шаг: success/fail/нет данных + человекочитаемое описание.
3. **Категория отказа при провале** — на русском, фактами: «DNS не отвечает
   через туннель», «TLS-рукопожатие не завершилось», «сервер недостижим»,
   «egress не совпал с ожидаемым». Запрещено диагностировать «это точно DPI».
4. **Кнопки самопомощи**:
   - «Починить системный прокси» (лечит зависший мёртвый прокси после
     аварийного завершения) — с объяснением, когда это нужно;
   - статус самопочинки при старте («зависший прокси устранён» — если был).

---

## 5. Тесты окружения (страница «Проверки»)

Набор живых тестов, которые уже реализованы в ядре; UI показывает их список,
последний результат и детали по шагам:

1. Доступность UDP в текущей сети (важно для HY2) — с честным выводом
   «UDP фильтруется — QUIC-каналы в этой сети работать не будут».
2. Достижимость HY2-сервера (UDP до origin:порта из дескриптора).
3. Наличие всех секретов каналов в хранилище (без значений).
4. Права администратора (нужно для TUN) — с объяснением, что TUN включается
   через запрос повышения прав (UAC).
5. Подключённость ядра (core-wired) — «ядро готово к запуску».
6. Общее правило: результат теста — это факт на момент прогона, не постоянное
   состояние; UI должен отделять «последний результат» от «текущего состояния».

---

## 6. Секреты (хранилище)

1. **Список слотов секрета** по видам: UUID VLESS, пароль HY2, obfs-пароль,
   SSH-ключ VPS, CF API-токен, pin-сертификат канала, произвольный custom.
2. **Метаданные вместо значений**:
   - SHA256-fingerprint (короткий, для сверки «тот же ли секрет на сервере»);
   - статус последней проверки (verify ok / fail / не проверялся);
   - дата последней проверки;
   - счётчик раскрытий значения (reveal-аудит).
3. **Действия по каждому секрету:**
   - добавить/заменить значение (из файла или вставкой);
   - удалить;
   - «Проверить» — живая проверка по виду секрета (сверка хешей с сервером
     по SSH для канальных секретов, реальный вход для SSH-ключа, verify для
     CF-токена, честный skip для custom) с пошаговым отчётом;
   - «Показать» — раскрытие значения по явному действию (с фиксацией в аудите);
   - «Тест» — проверить, что значение принято бэкендом (формат, длина).
4. **Правила, которые UI обязан доносить:**
   - значения не попадают в логи, диагностику и скриншоты состояний;
   - после замены секрета на сервере нужно обновить его и здесь;
   - сверка с сервером — по хешу, поэтому UI может показывать «совпадает/
     не совпадает» без раскрытия значения.
5. **Состояние хранилища**: где лежит (путь AppData), что переживает
   переустановку приложения; предупреждение при отсутствии слота, нужного
   активному каналу.

---

## 7. Журнал (логи)

1. **Хвост журнала в реальном времени** — уровни info/warn/error, время;
   фильтр по уровню; копирование выделенного.
2. **Кнопка «Открыть папку логов»** — файл app.log живёт в AppData.
3. **Гигиена содержимого**: в логах нет секретов; если пользователь видит
   странное — можно копировать целиком, это безопасно (UI не должен
   показывать значения секретов и в логе).
4. **Разделение «журнал приложения» и «журнал ядра»**, если оба доступны;
   из логов sing-box извлекается путь каждого соединения (inbound→outbound) —
   полезно на уровне диагностики, не на главном экране.

---

## 8. NetGuard (самопочинка системы)

Страница честного наблюдения за служебными задачами Windows:

1. **Статус задач NetGuard** (SYSTEM и user): состояние из машинных статусов
   (ready/running/disabled/no-access/not-found) — с человеческим переводом.
   Важно: no-access ≠ «не найдена» — задача есть, но скрыта правами; UI
   обязан показать «частично наблюдаема», а не предлагать удалить.
2. **Состояние системного прокси**: включён/выключен, адрес:порт, жив ли
   слушатель на порту (это и есть «стухший прокси»).
3. **Политика DNS/DoH на адаптерах** — установлена ли зашифрованная пара DNS.
4. **События из журнала NetGuard** — последние HEALED/PROBLEM.
5. **Кнопка «Починить сейчас»** — тот же консервативный код, что и автопочинка.
6. **Раздел «что это такое»** — короткое объяснение на русском: зачем это
   (после падения VPN системный прокси/DNS могли остаться сломанными),
   что трогается, а что никогда (чужие VPN, PAC, внешние прокси).

---

## 9. Режим TUN (весь системный трафик)

1. **Переключатель SOCKS ↔ TUN** с честным объяснением последствий:
   - TUN требует администратора — будет запрос UAC и перезапуск приложения;
   - после переключения приложение перезапускается и, если VPN был запущен,
     подключится само;
   - в TUN-режиме системный прокси не используется (маршрутизацию делает
     адаптер) — это не «прокси сломался».
2. **Индикатор текущего режима** (сохраняется между запусками).
3. **Состояние адаптера** (snowden0 создан/подключён) — если данные доступны;
   недоступно → «нет данных», не ошибка.

---

## 10. Метаданные доставки профилей (envelope, B2)

Скрытая для новичка, но полезная продвинутому владельцу страница:

1. **Состояние подписанного envelope**: установлен/нет, версия, key_id,
   срок действия, кто подписал (fingerprint ключа).
2. **Статус доверенных ключей**: сколько, когда добавлены (значения ключей —
   не секреты, но и не нужны в полный рост).
3. **Каналы из envelope** — те же карточки, что и встроенные, с явной меткой
   источника («встроенный набор» / «из подписанного обновления»).
4. **Явные состояния отказа** (если envelope повреждён/просрочен/отвергнут):
   причина на русском и что это значит — встроенный набор продолжает
   действовать; fail-closed, а не тихий откат.
5. **Revocations** — какие каналы отозваны подписанным обновлением.

---

## 11. Системные события и устойчивость (сквозные фичи)

Не отдельные экраны, но факты, которые обязаны быть наблюдаемы в UI:

1. **Self-heal при старте** — если прошлый процесс погиб с включённым
   системным прокси, приложение чинит его до старта ядра; событие видно в
   журнале и уместно как баннер «устранены последствия аварийного завершения».
2. **Единственный экземпляр** — второй запуск фокусирует существующее окно;
   UI не должен пугать «уже запущено» ошибкой.
3. **Закрытие окна = контролируемое отключение** — при закрытии окно может
   задержаться на секунды (остановка туннеля, restore прокси); полезна
   ненавязчивая индикация «завершение…», чтобы пользователь не убивал процесс.
4. **Смена сети** — если сеть сменилась (Wi-Fi→LTE), сторож поймает деградацию
   сам; UI полезно показать событие «сеть изменилась» рядом с историей probe.
5. **Уведомления системы (toast)** — на события самопочинки и деградации
   (уже есть для NetGuard HEALED); уместно и для failover-переключений.
6. **Crash-диагностика** — путь к crash-логу в AppData при аномальном
   завершении; на экране ошибки — предложение «открыть папку логов».

---

## 12. Справка и границы (честность продукта)

Полезно иметь экран/раздел «О защите» — статичный текст, объясняющий:

1. Что продукт делает: защищённый трафик только через проверенные каналы,
   при отсутствии рабочего канала — блокировка, никогда «просто прямой».
2. Что продукт НЕ обещает: работу при полном shutdown/allowlist режима;
   работу в сетях с фильтрацией UDP для QUIC-каналов; вечную работоспособность
   одного сервера.
3. Почему иногда «VPN выключился сам» — fail-closed: лучше честная остановка,
   чем молчаливая утечка трафика мимо защиты.
4. Что такое статусы каналов и почему «configured» — не «готов».
5. Сведения о сборке: версия приложения, версия ядра (pinned sing-box),
   режим сборки (теги) — без внутренних деталей, позволяющих навредить.

---

## Приоритеты (что важнее в макете)

- **P0** (без этого экран неполон): §1 главный экран, §2 каналы, §4
  диагностика, §6 секреты, §7 журнал.
- **P1** (отличает продукт): §3 failover-состояния, §5 проверки окружения,
  §8 NetGuard, §9 TUN.
- **P2** (для владельца/продвинутого): §10 envelope, §12 справка, детали §11.

## Что дизайнеру НЕ делать (запреты контракта)

- Не рисовать «страны»/флаги/список городов — каналы приходят из данных,
  их состав конечен и не содержит географической фасады.
- Не показывать график трафика «для красоты» — источника достоверных
  метрик нет; счётчик интерфейса ≠ трафик VPN (AGENTS §3.4). Если захочется
  скорости/трафика — сначала отдельный контракт на источник данных.
- Не превращать статусы в синонимы «connected» — палитра состояний задана
  (§1), blocked и error визуально не прячутся за зелёным.
- Не маскировать пустые данные нулями — явные «нет данных».
- Не показывать секреты в списках/поиске/экспорте — только по явному
  «Показать».
