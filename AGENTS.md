# Snowden System — проектные правила

Эта часть уточняет общий harness ниже. Требования пользователя имеют приоритет.

## Начало и продолжение

- Для новой задачи: `docs/MAP.md` → точечный `rg` → нужные исходники.
- Для «продолжи»: `docs/STATE.md` → указанный OFF-пункт `docs/PLAN.md` → код.
  Не перечитывай весь журнал, архив, теорию и старые session snapshots каждый раз.
- Единственный реестр требований, решений и статусов — `docs/PLAN.md`.
  STATE — заменяемый снимок; MAP — указатель; LESSONS — подтверждённые уроки.
  `docs/SESSION-STATE.md` и `docs/memory/` — исторические снимки, не точка старта.
- Дополнительные правила подхватываются по пути: `windows/AGENTS.md`,
  `windows/frontend/AGENTS.md`, `configs/AGENTS.md`. Справочник: `docs/AGENTS.md`.

## Границы работы

- Сейчас VPS не оплачен по сообщению владельца. Работа по умолчанию офлайн.
  SSH/Cloudflare/deploy, изменение proxy/DNS/WFP/TUN и live-тесты требуют
  соответствующего явного запроса; статический doctor ничего этого не запускает.
- Не читать значения `*.env`, `secrets/`, реальный vault, runtime-config или
  пользовательские логи без необходимости задачи. Не выводить секреты нигде.
- Не делать commit/push/reset/rebase, не стирать чужие изменения, не обновлять
  зависимости массово. Исходное дерево untracked — `git diff` не показывает всё.
- Тесты добавлять/запускать по запросу пользователя на тестирование/проверку.
  Команды и критерии в плане сами по себе не разрешают live или admin-тест.
- Субагенты — по явному запросу; мелкий поиск и зависимые изменения выполнять
  самостоятельно. Учитывать их расход при замерах, если они используются.

## Качество и стоимость результата

- Один активный проверяемый срез. P0 safety/lifecycle раньше новых транспортов,
  ML и декоративной переделки. Следующий срез выбирается из PLAN §5.1.
- Перед созданием сущности найти существующие API/компоненты/потребителей;
  сохранять Vue/Wails/Go package boundaries, не навязывать чужую схему каталогов.
- Различать контракт и текущий дефект: FR-009…011 пока planned. Не описывать
  целевую ProtectionController/службу как уже реализованный код.
- Безопасный трафик не получает direct fallback. Автоматическая ошибка и ручное
  отключение различаются; правила защиты — PLAN §3, аудит AUD-001/002.
- Статусы implemented/local/live не взаимозаменяемы. PASS только с командой,
  областью, результатом и актуальными входами; build не доказывает VPN-путь.
- Контекст подгружать по задаче; длинные логи фильтровать. После одинаковой
  ошибки менять гипотезу. Свежий результат переиспользовать только при неизменных
  входах, команде, тегах и среде; отсутствие замера не заполнять нулём.
- Перед завершением обновить STATE и конкретный PLAN-пункт; журнал §6 только
  дополнять. Финал: результат, доказательство, остаток. Экономия токенов пока
  не измерена; цель — меньше повторов при сохранённой приёмке.

# Рабочие соглашения

- В незнакомой части сначала прочитай `docs/MAP.md`, затем точечный `rg` и нужные файлы. Если карта устарела: `node scripts/harness/map.mjs --out docs/MAP.md`. Карта — указатель, а не полный индекс.
- Перед созданием компонента, утилиты или стиля найди существующий аналог, его варианты и публичный API, включая stories. Сначала расширяй/композируй подходящее. Новый компонент обоснуй отсутствием пригодного аналога; не дублируй похожую реализацию.
- Выясни фактическую структуру проекта и дели код на осмысленные компоненты в его соглашениях. `hooks/data/share/shared/lib` — примеры, не шаблон обязательных папок. Не навязывай архитектуру и не дроби код ради количества файлов. Подробности — skill `repo-recon`; frontend/SQL — `frontend-postgres`.
- Перед задачей ищи уроки по теме в `docs/LESSONS.md`. Исправленная ошибка или поправка пользователя → краткая запись с причиной и рабочим решением. Не сохраняй догадки и статус как уроки.
- Команды и зависимости проверяй по manifest/lockfile проекта и CI. Наличие команды в документации не означает, что она работает. Диагностика: `node scripts/harness/doctor.mjs`.
- Для короткой задачи работай прямо в коде. Для работы через несколько сессий веди `docs/STATE.md`: цель, критерии приёмки, решения, проверенные результаты, следующий шаг. При возобновлении проверь записи по текущим файлам.
- Долговременное архитектурное решение с причинами сохраняй в существующем ADR/DECISIONS. Память опыта, состояние задачи и архитектурные решения храни отдельно.
- Делегируй независимое исследование или проверку субагенту, когда выигрыш в качестве/времени оправдывает его контекст. Мелкий поиск и зависимые шаги выполняй сам. Дай агенту узкий вопрос, минимум контекста и ожидаемый результат; для записи назначь файлы, предупреди о других исполнителях. Возвращай summary с доказательствами, не сырые логи.
- Подгружай только релевантные skills и разделы документации. Не дампь репозиторий, lockfile или длинные логи. Не повторяй исследование, если есть свежий проверяемый результат.
- Проверяй изменённое поведение и обязательные проверки проекта. После успеха повторяй их только при новых изменениях или сомнениях. После повторного одинакового сбоя меняй гипотезу, а не воспроизводи попытку.
- Завершай по критериям приёмки: что изменено, чем проверено, что осталось. Не заявляй успех или экономию токенов без измерений. Длинные процедуры и методика оценки — `docs/HARNESS.md`, читать по необходимости.
- Держи этот файл ≤200 строк. Переноси сюда только подтверждённые общие уроки; процедуры оставляй в skills. Машинные правила проверяй инструментами.
